# 영상 무손실 보관

이 문서는 카메라 영상의 녹화와 후처리 과정에서 추가적인 화질 손실을 줄이는 방법을 설명한다. 원본 녹화 단계에서는 수신한 RGB 픽셀값 또는 JPEG 압축 데이터를 보존하고, 학습용 파생 영상을 만들 때 불필요한 색 변환과 반복적인 손실 압축을 최소화한다.

이 문서에서 '무손실 보관'은 레코더가 수신한 데이터에 추가 손실을 발생시키지 않는 것을 뜻한다. Isaac 의 RGB 입력은 픽셀값을 보존하며, 펑션베이의 JPEG 입력은 재인코딩 없이 압축 데이터를 보존한다. JPEG 생성 과정에서 이미 손실된 정보는 복원하지 않는다. RGBA · BGRA 입력의 알파 채널은 보존하지 않는다(§2.1).

## 1. 개요

### 1.1 원칙

녹화 단계에서는 수신한 데이터를 보존하고, 손실을 일으키는 처리는 학습용 파생 영상을 만들 때로 미룬다. 이유는 다음과 같다.

1. 손실 압축으로 제거된 정보는 설정을 변경하거나 재인코딩해도 복원할 수 없다.
2. 손실 압축을 반복하면 화질 손실이 누적된다. 손실 녹화본을 디코딩해 가공하고 다시 손실 인코딩하면 두 번의 압축 손실이 쌓인다.
3. 가공 방식(배경 보정 · 렌즈 왜곡 보정 등)은 나중에 바뀔 수 있다. 원본이 보존되어 있으면 언제든 원래 데이터에서 다시 만들 수 있다.

### 1.2 손실이 생기는 단계

| 단계 | 손실 | 비고 |
|---|---|---|
| 디코딩 | 재압축에 따른 손실을 추가하지 않는다 | 다만 디코더 구현과 색 변환 방식에 따라 출력 픽셀값이 달라질 수 있다(§4) |
| 손실 인코딩 (H.264 CRF · 비트레이트) | 있음 | 인코딩할 때마다 양자화가 다시 일어난다 |
| 색공간 변환 (RGB ↔ YUV 4:2:0) | 있음 | 색 해상도가 1/4 로 줄고 반올림 오차가 생긴다. 변환 방식에 따라 오차 크기가 다르다(§5.2) |
| 기하 변환 (크기 변경 · 회전 · 왜곡 보정) | 있음 | 픽셀을 다시 샘플링하며 보간으로 흐려진다 |

그래서 녹화는 색공간 변환과 손실 인코딩을 피하고, 파생 영상은 디코딩 → 가공 → 인코딩을 한 번에 처리한다.

## 2. 입력 형식별 녹화 방식

수집에 쓰는 두 백엔드는 카메라의 출력 형식이 다르다. 레코더는 입력 형식(`input_format`)에 따라 녹화 방식을 선택한다.

### 2.1 Isaac — RGB 픽셀 보존

Isaac 은 무압축 `rgb8`(`sensor_msgs/Image`)을 발행한다. 녹화 단계가 원본 픽셀값을 보존할 수 있는 유일한 단계다.

```
rgb8 raw (stdin) → ffmpeg -c:v libx264rgb -qp 0 -pix_fmt rgb24
```

- `libx264rgb` 는 RGB 를 YUV 로 바꾸지 않고 인코딩한다. `-qp 0` 은 x264 의 무손실 모드다. 녹화본을 디코딩하면 Isaac 이 보낸 픽셀값과 비트 단위로 같다(§7.1).
- 입력 픽셀 포맷별 출력은 다음과 같다. 알파 채널은 버리고 RGB 값은 보존한다.

| `pixel_format` | 코덱 | 출력 `-pix_fmt` |
|---|---|---|
| `rgb8` | `libx264rgb` | `rgb24` |
| `bgr8` | `libx264rgb` | `bgr24` |
| `rgba8` · `bgra8` | `libx264rgb` | `bgr0` |
| `mono8` | `libx264` | `gray` |

- 무손실 압축이라 용량은 영상 내용에 따라 크게 달라진다. 측정 예시는 §7.2 에 있다. 무압축 대역폭은 640×480×3×10 fps = 9.2 MB/s 이다.
- 무손실 모드에서 `preset` 은 화질이 아니라 용량과 인코딩 속도만 바꾼다.

### 2.2 펑션베이 — JPEG 스트림 복사

펑션베이는 시뮬레이터가 JPEG(`sensor_msgs/CompressedImage`)으로 압축해 보낸다. 압축 전 픽셀값은 얻을 수 없으므로, 수신한 JPEG 데이터를 재인코딩 없이 보존한다.

```
JPEG 바이트 (stdin) → ffmpeg -f mjpeg -i - -c:v copy
```

- `-c:v copy` 는 디코딩도 인코딩도 하지 않고 JPEG 데이터를 컨테이너 패킷으로 옮긴다. 녹화본의 패킷은 시뮬레이터가 보낸 JPEG 데이터와 같다(§7.1).
- 타임스탬프 보정 노드(`fb_camera_restamp`)는 `header.stamp` 만 바꾸고 JPEG 데이터는 변경하지 않는다. 따라서 시뮬레이터부터 녹화본까지 JPEG 데이터가 보존된다.
- 모든 프레임이 독립 JPEG 이라 무작위 접근이 빠르고 GOP 를 정할 필요가 없다.
- 화질의 상한은 시뮬레이터의 JPEG 품질이 정한다. 더 좋은 원본이 필요하면 벤더에 JPEG 품질 상향이나 무압축 출력을 요청해야 하며, 그만큼 대역폭이 늘어난다.
- 용량은 시뮬레이터 JPEG 의 크기와 같다. 측정 예시는 §7.2 에 있다.

### 2.3 비교

| | Isaac | 펑션베이 |
|---|---|---|
| 입력 형식 | raw `rgb8` | JPEG |
| 녹화 방식 | `libx264rgb -qp 0` | `-c:v copy` |
| 메타데이터 `codec` | `libx264rgb` | `mjpeg` |
| 녹화 단계의 추가 손실 | 없음 | 없음 (JPEG 생성 과정의 손실은 이미 들어 있다) |
| 측정 예시: 손실 녹화 대비 용량 (§7.2) | 약 2.5배 — 기존 손실 녹화본을 재인코딩한 결과 | 약 0.6배 — 펑션베이 JPEG 크기 기준 |

## 3. 설정과 메타데이터

### 3.1 무손실 녹화 설정

무손실 녹화는 `robot_control/config/image_pipeline.yaml` 의 `image_recorder.lossless` 로 정하며 기본값은 `true` 다. 백엔드와 무관하게 같은 키를 쓰고, 레코더가 입력 형식에 맞는 녹화 방식을 선택한다.

| 위치 | 이름 | 기본값 |
|---|---|---|
| `image_pipeline.yaml` | `image_recorder.lossless` | `true` |
| `rdfp_collect.launch.py` 인자 | `image_recorder_lossless` | YAML 값 |
| `rdfp_image_recorder` 파라미터 | `lossless` | `false` (launch 가 YAML 값을 넘긴다) |
| `FFMpegMp4Recorder` 생성자 | `lossless` | `False` |

손실 녹화로 바꾸려면 `image_recorder_lossless:=false` 를 넘기거나 YAML 값을 바꾼다. 녹화 방식은 녹화 후 되돌릴 수 없으므로 수집 회차 중간에 바꾸지 않는다.

```bash
ros2 launch rdfp rdfp_collect.launch.py backend:=panda_isaac                                  # 무손실 (기본)
ros2 launch rdfp rdfp_collect.launch.py backend:=panda_isaac image_recorder_lossless:=false   # 손실 H.264
```

### 3.2 무손실 녹화에서 쓰이지 않는 설정

| 설정 | raw (Isaac) | JPEG (펑션베이) |
|---|---|---|
| `bitrate` | 쓰지 않는다 | 쓰지 않는다 |
| `encoder_mode` · `preferred_hw_codec` | 쓰지 않는다 — 하드웨어 인코더의 사용 가능 여부를 검사하지 않는다. `gpu` 를 주면 경고만 남긴다 | 쓰지 않는다 |
| `preset` | 쓴다 (용량 · 속도만 바뀐다) | 쓰지 않는다 |
| `gop_size` | 쓴다 (`0` 이면 `fps * 2`) | 쓰지 않는다 |

현재 무손실 녹화 구현은 픽셀 또는 압축 데이터의 보존을 검증한 소프트웨어 인코딩과 스트림 복사 경로만 사용한다. 하드웨어 인코더를 이용한 무손실 녹화는 지원하지 않는다.

### 3.3 메타데이터를 통한 녹화 방식 확인

에피소드마다 생기는 `<prefix>_<start_ts>_metadata.json` 의 `lossless` 와 `codec` 으로 녹화 방식을 확인한다.

| `lossless` | `input_format` | `codec` |
|---|---|---|
| `true` | `rawvideo` | `libx264rgb` (흑백은 `libx264`) |
| `true` | `mjpeg` | `mjpeg` |
| `false` | 둘 다 | `libx264` 또는 하드웨어 인코더 이름 |

`lossless` 키가 없는 메타데이터는 이 기능 이전의 손실 녹화본이다.

## 4. 호환성과 제약

| 사용 프로그램 | 디코더 | `libx264rgb` | `mjpeg` |
|---|---|---|---|
| 적재 (`recorder_registry`) | 사용하지 않는다 (sidecar 기준) | 영향 없음 | 영향 없음 |
| export · `rdfp-train` · GUI 미리보기 | PyAV `to_ndarray('rgb24')` | 비트 단위 일치 확인 | 디코딩 확인 |
| 재생 (`Mp4ImageReplayer`) | OpenCV `VideoCapture` | 비트 단위 일치 확인 (BGR) | 디코딩 확인 |
| 브라우저 · 하드웨어 디코더 | — | 재생하지 못할 수 있다 (`High 4:4:4 Predictive` 프로파일) | 재생 호환성은 별도 확인이 필요하다 |

- 손실 녹화본과 무손실 녹화본이 한 데이터셋에 섞여도 된다. 사용 프로그램은 컨테이너의 코덱 정보로 디코딩한다.
- JPEG 은 디코더에 따라 출력 픽셀값이 다르다. 같은 JPEG 을 PyAV(ffmpeg mjpeg 디코더)와 `cv2.imdecode`(libjpeg-turbo)로 디코딩하면 최대 31 단계까지 차이가 났다(주로 색 경계의 업샘플링 차이). 학습 전처리와 추론 노드는 같은 디코더를 쓴다(§5.6).
- JPEG 은 full range(`yuvj420p`)이고 H.264 손실 녹화는 limited range 다. RGB 로 디코딩하면 디코더가 범위를 처리하지만, YUV 평면을 직접 다루는 코드는 범위를 구분해야 한다.

## 5. 파생 영상 생성 지침

배경 보정, 렌즈 왜곡 보정처럼 모든 프레임을 변환해 새 영상을 만들 때의 지침이다.

### 5.1 한 번의 디코딩과 인코딩

프레임마다 디코딩 → 모든 변환 → 인코딩을 한 번에 처리한다. 변환마다 영상을 따로 만들면 인코딩 손실과 보간 손실이 단계 수만큼 쌓인다.

```
녹화본 디코딩 → (BGR 변환) → 배경 보정 → 왜곡 보정(remap 1회) → (YUV 변환) → 인코딩
```

### 5.2 색 변환

H.264 손실 녹화본(`yuv420p`)을 OpenCV 로 가공할 때는 YUV ↔ BGR 변환 방식이 결과에 큰 영향을 줄 수 있다. 기존 녹화본 한 개로 색 변환 경로를 비교한 시험에서는 PyAV 기본 변환 경로의 왕복 오차가 비교 대상인 CRF 18 재인코딩 오차보다 크게 나타났고, OpenCV 변환 경로의 왕복 오차는 그보다 훨씬 작았다(§7.3).

해당 OpenCV 변환은 BT.601 limited range 를 기준으로 한다. 기존 레코더 녹화본처럼 입력의 색 변환 기준과 범위가 이에 부합하는지 확인한 뒤 다음 경로를 적용한다.

1. 디코딩한 프레임에서 YUV 평면을 `frame.to_ndarray(format='yuv420p')` 로 꺼낸다.
2. `cv2.cvtColor(..., cv2.COLOR_YUV2BGR_I420)` 로 BGR 로 바꿔 가공한다.
3. `cv2.cvtColor(..., cv2.COLOR_BGR2YUV_I420)` 로 되돌린 뒤 `VideoFrame.from_ndarray(..., format='yuv420p')` 로 인코더에 넣는다.

위 조건의 녹화본에서는 PyAV 의 `to_ndarray(format='bgr24')` 와 `VideoFrame.from_ndarray(...).reformat('yuv420p')` 를 쓰는 기본 경로 대신 이 경로를 쓴다. 다른 색공간 · 범위의 입력이라면 두 경로의 왕복 오차를 그 입력으로 다시 확인한다.

RGB 무손실 녹화본을 RGB 로 처리하고 다시 RGB 무손실로 저장하는 경로에서는 RGB ↔ YUV 변환을 피할 수 있다. JPEG 보관본의 디코더 차이는 별도로 고려해야 한다(§4).

### 5.3 기하 변환

- 렌즈 왜곡 보정은 `cv2.initUndistortRectifyMap` 으로 맵을 한 번 만들고 프레임마다 `cv2.remap` 을 한 번만 적용한다. 보간은 `INTER_CUBIC` 또는 `INTER_LANCZOS4` 를 쓴다.
- 해상도는 녹화본과 같게 유지한다. `cv2.getOptimalNewCameraMatrix` 의 `alpha` 가 0 이면 검은 테두리 없이 잘라 확대하므로 조금 흐려지고, 1 이면 모든 픽셀을 남기는 대신 테두리가 검게 된다.
- 배경 마스크를 원본 좌표에서 얻는다면(시뮬레이터 세그멘테이션 등) 배경을 먼저 합성하고 왜곡 보정을 마지막에 한 번 적용한다. 보간이 한 번만 일어나게 하려는 것이다.
- Isaac 카메라는 왜곡 모델을 따로 설정하지 않으면 이상적인 핀홀 모델로 렌더링한다. `isaac_scene.json` 에는 왜곡 계수가 없으므로, 보정 전에 체커보드나 직선 모서리로 실제 왜곡이 있는지 확인한다. 왜곡이 없으면 보정은 보간 손실만 더한다.

### 5.4 출력 인코딩

| 출력 | 설정 | 특징 |
|---|---|---|
| RGB 무손실 | `libx264rgb -qp 0` | 가공 결과의 픽셀값을 보존한다. 파일 크기는 영상 내용과 인코딩 설정에 따라 달라진다 |
| YUV 무손실 | `libx264 -qp 0 -pix_fmt yuv420p` | YUV 로 변환한 뒤에는 손실이 없다 |
| 고화질 손실 | `libx264 -crf 12 -pix_fmt yuv420p` | 브라우저 재생용 후보로 사용할 수 있으며, 대상 브라우저에서 재생 여부를 확인한다 |

각 설정의 용량과 화질 측정 예시는 §7.4 에 있다. 출력 색 태그는 실제 색 표현과 변환 설정에 맞게 지정한다. 색 변환 행렬(`-colorspace`), 색 원색(`-color_primaries`), 전달 특성(`-color_trc`), 값의 범위(`-color_range`)는 각각 별도의 속성이므로 하나씩 확인한다. 기존 녹화본은 색 태그가 비어 있어 사용 프로그램이 기본값으로 추정하며, 원색과 전달 특성은 아직 확인하지 않았다.

### 5.5 프레임 수와 메타데이터 관리

- 프레임 수와 순서를 바꾸지 않는다. `image_frames.frame_index` 가 mp4 의 프레임 번호이고 sidecar 줄 수가 `nframe` 과 같아야 하므로, 한 장만 밀려도 레이블과 영상이 어긋난다. PyAV 로 쓸 때는 원본 프레임의 `pts` 와 `time_base` 를 옮기고, ffmpeg 명령으로 쓸 때는 `-vsync passthrough` 를 붙인다(시스템 ffmpeg 4.4 에는 `-fps_mode` 가 없다). 처리 후 `ffprobe -count_frames` 로 원본과 프레임 수가 같은지 확인한다.
- 원본은 지우지 않는다. 파생 영상은 별도 디렉터리에 같은 파일 이름으로 만든다. DB 의 `image_streams` 는 원본 경로를 그대로 가리킨다.
- 프레임 수와 순서를 유지한 경우 타임스탬프 sidecar(`.jsonl`)를 함께 보관한다.
- 원본 메타데이터(`_metadata.json`)는 출처 기록으로 보존하고, 파생 영상의 코덱 · 해상도 · 손실 압축 여부와 변환 파라미터(카메라 행렬 · 왜곡 계수 · `alpha` · 새 카메라 행렬 · 배경 처리 방식)는 별도로 기록한다. 원본 메타데이터를 파생 영상의 속성으로 그대로 사용하지 않는다 — 예를 들어 무손실 원본을 CRF 12 로 변환한 파생 영상에 원본 메타데이터를 복사하면 `lossless: true` 로 잘못 기록된다.

### 5.6 추론과의 일관성

학습 영상에 적용한 변환은 추론 때 실시간 카메라 이미지에도 똑같이 적용해야 한다. 학습 영상만 보정하면 모델이 학습하지 않은 분포의 입력을 받게 되어, 실행 오류가 발생하지 않더라도 추론 성능이 저하될 수 있다. 변환은 학습 전처리와 추론 노드가 함께 쓰는 하나의 함수로 만들고, 펑션베이처럼 JPEG 을 디코딩하는 경우 디코더도 같게 맞춘다.

파생 영상을 만들지 않는 방법도 있다. 학습할 때 디코딩한 프레임에 바로 변환을 적용하면 재인코딩이 없고, 파라미터를 바꿔도 데이터를 다시 만들 필요가 없다. 640×480 에서 `cv2.remap` 은 1 ms 안팎이다.

## 6. 기존 손실 녹화본

`lossless: false` 의 손실 녹화는 다음과 같다.

| 입력 | 처리 |
|---|---|
| raw | ffmpeg 기본 변환으로 `yuv420p` → `libx264 -b:v 4M -g <gop>` |
| JPEG | ffmpeg 이 JPEG 을 디코딩 → `libx264 -b:v 4M -g <gop>` |

위 표는 소프트웨어 인코더(`libx264`)를 사용하는 경우다. 두 입력 형식 모두 `encoder_mode: auto` 이면 하드웨어 인코더가 선택될 수 있다.

- `gop_size: 0` 은 레코더 기본값 `fps * 2` 다(10 fps 면 20). ffmpeg 기본값(250)이 아니다.
- 2026-09-20 에 모은 Isaac 녹화본 65개(`/data/rdfp/recordings`, 2.6~10.2 MB, 합계 519.5 MB)는 모두 이 방식이다 — `libx264` · `yuv420p` · 4 Mbps · 키프레임 간격 20 · 색 태그 없음. 이 녹화본을 가공할 때는 §5.2 의 색 변환 지침을 따른다.
- 인코딩 방식에 따른 용량과 무작위 접근 성능 측정은 [저장_형식.md 부록 B](../learning/저장_형식.md#부록-b-영상-인코딩-및-디코더-성능-측정-2026-09-19)에 있다. 그 측정은 손실 녹화 설정을 고르기 위한 것이다.

## 7. 검증 범위와 측정 결과

이 장의 수치는 특정 영상과 설정에서 측정한 결과다. 영상 내용과 인코딩 설정이 다르면 값도 달라지므로, 일반적인 보장으로 읽지 않는다.

### 7.1 기능 검증

| 시험 | 조건 | 결과 |
|---|---|---|
| 단위 시험 `test_lossless.py` | raw `rgb8` · `bgr8` 노이즈 프레임을 무손실 녹화한 뒤 PyAV 로 디코딩 | 비트 단위 일치 |
| 단위 시험 `test_lossless.py` | JPEG 8장을 `-c:v copy` 로 녹화한 뒤 패킷 비교 | 수신한 데이터와 동일, OpenCV 로 같은 프레임 수 |
| launch 기동 | `rdfp_collect backend:=panda_isaac` | `lossless=True`, `selected_codec=libx264rgb` |
| launch 기동 | `rdfp_collect backend:=panda_functionbay` | `lossless=True`, `selected_codec=mjpeg` |
| ROS 경로 전체 | 모의 카메라 발행기(64×48 `rgb8` 노이즈)로 에피소드 1개 녹화 | 30/30 프레임 · sidecar 30줄 · 비트 단위 일치. 같은 조건의 손실 녹화는 평균 절대 오차 45.5 (노이즈 프레임이라 압축에 가장 불리한 조건) |
| ROS 경로 전체 | 모의 카메라 발행기(640×480 JPEG)로 에피소드 1개 녹화 | 30/30 패킷이 보낸 JPEG 데이터와 동일 |
| OpenCV 디코딩 | `libx264rgb` 녹화본 | BGR 로 비트 단위 일치 |

### 7.2 용량 측정

| 대상 | 조건 | 결과 |
|---|---|---|
| Isaac (RGB 무손실) | 기존 손실 녹화본 하나(22.9 s, 229프레임, 10.21 MB)를 디코딩해 `libx264rgb -qp 0` 으로 재인코딩 | 25.73 MB (약 2.5배). 이미 손실 압축을 거친 영상에서 측정한 결과이므로, 실제 Isaac 원본은 더 클 수 있다 |
| 펑션베이 (JPEG 스트림 복사) | 펑션베이 JPEG 실측 프레임당 약 26.8 KB, 10 fps | 약 0.27 MB/s. 비교 대상인 H.264 4 Mbps 손실 녹화는 약 0.45 MB/s 였다 |

### 7.3 색 변환 경로 비교

기존 H.264 녹화본 한 개(229프레임)를 각 경로로 색 변환 왕복한 뒤 무손실 인코딩하고, 원본과 YUV 기준 PSNR 로 비교했다.

| 프레임 처리 경로 | PSNR |
|---|---|
| YUV 그대로 통과 | ∞ (완전 일치) |
| OpenCV `COLOR_YUV2BGR_I420` ↔ `COLOR_BGR2YUV_I420` | 93.1 dB |
| ffmpeg 정밀 플래그 (`accurate_rnd+full_chroma_int`) | 76.5 dB |
| PyAV 기본 `to_ndarray('bgr24')` → `VideoFrame.from_ndarray(...).reformat('yuv420p')` | 45.7 dB |
| (비교) 색 변환 없이 x264 `-crf 18` 재인코딩만 | 51.9 dB |

같은 녹화본의 첫 프레임을 OpenCV 경로와 PyAV 기본 경로로 각각 BGR 로 변환하면 차이는 평균 1.15, 최대 3 단계였다.

### 7.4 출력 인코딩 비교

7.3 과 같은 녹화본(10.21 MB)을 색 변환 없이 디코딩 → 인코딩만 해서 원본과 비교했다.

| 설정 | 용량 | PSNR | SSIM |
|---|---|---|---|
| `libx264 -qp 0` (YUV 무손실) | 8.35 MB | ∞ | 1.000 |
| FFV1 (무손실, mkv) | 10.55 MB | ∞ | 1.000 |
| `libx264 -crf 12` | 2.67 MB | 55.1 dB | 0.9982 |
| `libx264 -crf 16` | 1.09 MB | 52.8 dB | 0.9974 |
| `libx264 -crf 18` | 0.77 MB | 51.9 dB | 0.9971 |
| `libx264 -crf 23` | 0.38 MB | 49.4 dB | 0.9963 |

이 시험에서는 YUV 무손실 재인코딩 결과가 기존 손실 녹화본보다 작았다. 기존 녹화본은 목표 비트레이트를 4 Mbps 로 설정했으며, 파일 크기는 영상 내용과 인코딩 설정에 따라 달라진다.

### 7.5 미검증 항목

- 실제 Isaac · 펑션베이 시뮬레이터로는 아직 녹화하지 않았다. Isaac 원본의 실제 용량은 시뮬레이터로 녹화해 확인해야 한다.
- 640×480 raw 프레임을 ROS 경로로 보내는 시험은 시험용 발행기에서 전송 중 프레임이 유실되어(손실 · 무손실 모두) 64×48 로 대신했다. 레코더가 아니라 시험 환경의 문제였다.
