## 0. rosbag 저장 구조 — 운영 규칙

수집이 만드는 rosbag 의 **디렉터리 · 분할 · 재실행 규칙**이다. `scripts/record_rosbag.sh`(진입점은 `scripts/rosbag.sh record`)가 이
규칙대로 기록하고 §6 의 split 탐색이 이 구조를 전제한다. (옛 「rosbag2 운영 방안」 보고서에서 **구현된 부분만** 옮겼다 —
systemd 연계 · SQLite 인덱스 · retention 자동화는 구현하지 않았고 원문은
[../archive/rosbag2_operation_report.md](../archive/rosbag2_operation_report.md) 에 있다.)

루트는 환경변수 `RDFP_ROSBAG_DIR` (`.rdfprc` 기본 `/data/rdfp/rosbag`) 이고, 적재 설정의 `rosbag_dir` 이 같은 곳을 가리켜야 한다.
⚠️ **적재가 끝난 세션 디렉터리는 이 루트 밖으로 뺀다** — sim 시계가 되감기는 백엔드에서는 회차 간에 에피소드 키가 겹친다(§10.3).

### 0.1 권장 디렉터리 구조

상위 디렉터리는 날짜별로 구성하고, 그 아래에 실행 시각 기준 세션 디렉터리를 둔다.

```text
$RDFP_ROSBAG_DIR/   (기본 /data/rdfp/rosbag/)
├── 2026-04-11/
│   ├── session_2026-04-11_09-00-03/
│   │   ├── metadata.yaml
│   │   ├── session_2026-04-11_09-00-03_0.mcap
│   │   ├── session_2026-04-11_09-00-03_1.mcap
│   │   └── ...
│   └── session_2026-04-11_14-22-10/
│       ├── metadata.yaml
│       ├── session_2026-04-11_14-22-10_0.mcap
│       └── ...
├── 2026-04-12/
│   └── session_2026-04-12_00-05-41/
```

#### 0.1.1 split 파일명 규칙

rosbag2 가 생성하는 split 파일의 이름은 **`-o` 옵션으로 지정한 경로의 basename** 을 접두로 쓰고, 뒤에 split 인덱스(`_0`, `_1`, …)와
확장자(`.mcap`)가 붙는다. 예를 들어 `-o $RDFP_ROSBAG_DIR/2026-04-11/session_2026-04-11_09-00-03` 으로 기록하면 다음이 생긴다.

```text
session_2026-04-11_09-00-03_0.mcap
session_2026-04-11_09-00-03_1.mcap
...
```

즉 **세션 디렉터리명과 bag basename 이 같다** — 세션 디렉터리만 보아도 내부 split 을 식별할 수 있게 하려는 전제다. 탐색
(`rdfp.rosbag.catalog`)은 날짜 폴더 `YYYY-MM-DD` 와 세션 폴더 `session_YYYY-MM-DD_HH-MM-SS` 형식만 찾는다.

#### 0.1.2 구조의 장점

* 날짜 기준 보관/백업/삭제가 쉽다
* 프로세스 재시작 시에도 세션 단위로 기록이 분리된다
* 날짜 필터(`session_filter.dates`)로 후보 세션을 디렉터리 단계에서 좁힐 수 있다

---

### 0.2 파일 분할 기준

세션 내부 파일은 **시간 기준**으로 split 한다 — `record_rosbag.sh` 가 `-d <SPLIT_DURATION_SEC>` (기본 3600 초,
`--split-duration` 으로 바꾼다)를 넘긴다.

**크기 상한(`--max-bag-size`)은 걸지 않는다.** 옛 운영 방안은 영상 토픽 때문에 크기 상한을 안전망으로 권했지만, 지금은 영상을
rosbag 에 담지 않으므로(§9) 1 시간 split 도 상태 토픽 위주로 작다. 영상을 다시 bag 에 담게 되면 크기 상한을 함께 검토한다 —
그때의 권장값은 압축 영상 2~5 GB, raw 1080p 1~2 GB 였다(옵션 값은 바이트 정수만 받는다).

split 길이는 **적재의 메모리 요구량**도 정한다 — 리더가 split 하나를 통째로 메모리에 올려 정렬하기 때문이다(§6.2).

### 0.3 중간 종료 · 재실행

#### 0.3.1 기본 방침

`rosbag2` 가 종료된 뒤 다시 실행될 경우, **기존 bag 에 이어쓰기하지 않는다.**

#### 0.3.2 운영 규칙

재실행 시에는 항상 새로운 세션 디렉터리를 만든다. 같은 초에 다시 시작해 이름이 겹치면 다음 초까지 기다려 새 이름을 만든다.

```text
2026-04-11/session_2026-04-11_09-00-03/
2026-04-11/session_2026-04-11_14-22-10/
2026-04-11/session_2026-04-11_18-05-44/
```

#### 0.3.3 이유

* bag 무결성 유지
* 세션 간 경계 명확
* 장애 발생 시 영향 범위 축소
* 조회 시 세션별 필터링 용이

녹화가 SIGKILL 로 끝나면 `metadata.yaml` 이 남지 않아 그 세션은 적재에서 **조용히 빠진다**(§6.1) —
`ros2 bag reindex -s mcap <세션 디렉터리>` 로 되살린다.

## 1. 개요

### 1.1 목적

로봇이 동작하면서 발생하는 데이터는 rosbag2 (MCAP) 로 일단 기록된다. 이 rosbag 은 최종 저장소가 아니라 **정제 전 중간 저장소**이며
저장 용량 확보 등의 이유로 언제든 지울 수 있다. 후처리기는 rosbag 이 유효한 동안 오프라인으로 실행되어, 지정한 범위의 메시지를
**에피소드 단위로 분할**해 PostgreSQL 에 적재한다.

영상은 **rosbag 에 담지 않는 것이 현행이다.** 세션 레코더(`rdfp_image_recorder`)가 에피소드마다 mp4 · sidecar · metadata 를 따로
남기고, 적재는 그것을 **같은 에피소드 행에 등록만** 한다(§9.1). rosbag 에 이미지 토픽이 있을 때 mp4 로 인코딩하는 옛 경로도
남아 있다(§9.2).

### 1.2 실행 형태

- **CLI 배치 프로그램**이다. ROS 2 노드가 아니라 일반 Python 프로세스로 실행되며 노드를 스핀하지 않는다.
- 메시지 역직렬화는 `mcap_ros2` 가 bag 에 내장된 IDL 스키마로 동적으로 한다 — `rclpy` · `rdfp_msgs` 를 import 할 필요가 없다.
  다만 bag 이미지 인코딩 모듈이 `sensor_msgs` 를 import 하므로 **`import` 는 ROS 를 소싱한 셸에서 돈다**(§14).
- 명령은 독립 실행파일로 나뉜다(§3.3).

### 1.3 입력·출력

| 구분 | 대상 |
|---|---|
| 입력 (메시지) | `<rosbag_dir>` 하위의 MCAP rosbag ([§0.1](#01-권장-디렉터리-구조) 구조) |
| 입력 (영상) | `<recordings_dir>` 하위의 레코더 출력 — `*_metadata.json` · mp4 · `.jsonl` sidecar |
| 출력 (DB) | 테이블 14개 (§5.2) — 에피소드(`sessions`), 메시지 타입별 시계열, 영상 메타(`image_streams` · `image_frames`) |
| 출력 (파일) | bag 에 이미지 토픽이 있을 때만 `<output_mp4_dir>/episode_XXXXXXXX/<토픽>.mp4`, 그리고 실행 로그 `<output_mp4_dir>/_logs/postproc_run.jsonl` |

### 1.4 전제

- Ubuntu 22.04, ROS 2 Humble.
- `/session` 토픽(`rdfp_msgs/msg/SessionCommand`)이 bag 에 있다 — 없으면 에피소드를 자를 수 없어 실패한다.
- 메시지의 `header.stamp` 가 에피소드와 **같은 시계**로 찍혀 있다. 이 전제가 깨진 메시지(stamp 0, 다른 시계)는 오류 없이
  어느 에피소드에도 들어가지 않는다(§8.1) — 적재가 이것을 검증하지는 않는다.
- 오프라인 실행이므로 실시간 제약은 없다.

### 1.5 기술 스택

| 영역 | 선택 |
|---|---|
| 언어 | Python 3.10+ |
| MCAP 리더 | `mcap`, `mcap-ros2-support` |
| 메시지 역직렬화 | `mcap_ros2` 가 MCAP 내장 IDL 스키마로 동적 역직렬화 |
| DB 드라이버 | `psycopg` (v3) — `executemany` 배치 삽입 |
| 설정 | `pydantic` (v2) + `PyYAML` |
| CLI | `argparse` (표준 라이브러리) |
| 영상 (bag 경로) | `rdfp.recorder.FFMpegMp4Recorder` 재사용 (ffmpeg subprocess) · 색공간 변환은 `cv_bridge` |
| 테스트 | `pytest` — 대부분 모의 객체, 실 DB · ffmpeg 는 있을 때만 (§15) |

pip 의존성(`mcap` · `mcap-ros2-support` · `pydantic>=2` · `psycopg[binary]>=3`)이 `package.xml` 에 없는 이유: apt 의
`python3-pydantic` 은 v1, `python3-psycopg2` 는 v2 라 요구사항과 맞지 않고, `mcap` 계열은 apt 에 없다. 설치 명령은
[운영 가이드 §2.2](데이터셋_적재_운영_가이드.md#22-python-의존성).

## 2. 용어

운영 관점의 용어(bag 세션 · split · DB `sessions` 가 에피소드라는 점 등)는 [운영 가이드 §1.2](데이터셋_적재_운영_가이드.md#12-용어)
에 있다. 여기서는 에피소드 감지의 정밀한 정의를 둔다.

| 용어 | 정의 |
|---|---|
| 세션 메시지 | `/session` 토픽(`rdfp_msgs/msg/SessionCommand`)의 각 메시지 |
| start_msg | `state == 'IN_EPISODE'` 이면서 **직전 세션 메시지가 `IN_EPISODE` 가 아닌** 메시지 |
| start_ts | `start_msg.header.stamp` (에피소드 시작 시각) — 에피소드 키 |
| stop_msg | `state == 'IN_SESSION'` 이면서 **직전 세션 메시지의 `state == 'IN_EPISODE'`** 인 메시지 |
| stop_ts | `stop_msg.header.stamp` (에피소드 종료 시각) |
| 에피소드 구간 | `[start_ts, stop_ts)` — **반열림 구간** |
| episode_id | `sessions.id` (`BIGSERIAL`). 에피소드의 자연키는 `(start_sec, start_nanosec)` 이고 id 는 대리키다 |

`IDLE → IN_SESSION` 전이의 `IN_SESSION` 메시지는 **stop_msg 가 아니다**. 성패(`outcome`)와 `metadata` 는 **stop_msg 에** 실려 온다.

## 3. 시스템 구성

### 3.1 데이터 흐름

운영 관점의 그림은 [운영 가이드 §1.1](데이터셋_적재_운영_가이드.md#11-데이터-흐름) 에 있다. 아래는 그 안의 단계다.

```text
[<rosbag_dir> 의 MCAP splits]
   │  (1) catalog.discover_splits — metadata.yaml 이 있는 세션만, 날짜 폴더 · 토픽으로 선행 필터
   ▼
[선정된 split 목록]
   │  (2) /session 만 읽어 상태 머신 → episodes[]                       (§7)
   │  (3) 에피소드 필터 (task_label · min_duration · start_ns_in)        (§4.2)
   │  (4) 토픽 분류 — writer 테이블 / bag 이미지 / 무시                    (§5.1)
   │  (5) 스키마 사전 검증 · topics 등록부 upsert                         (§5.3)
   ▼
[에피소드마다 한 트랜잭션]                                               (§8.3)
   │  (6) split 을 header.stamp 로 정렬 · 머지 → 메시지에 에피소드 할당     (§6 · §8.1)
   │  (7) 타입별 writer → 시계열 테이블 / bag 이미지 → FrameRouter → mp4  (§5.6 · §9.2)
   │  (8) 커밋 직전: recordings_dir 의 레코더 mp4 를 episode_key 로 등록   (§9.1)
   ▼
[PostgreSQL]  +  [<output_mp4_dir>/episode_XXXXXXXX/*.mp4 (bag 이미지가 있을 때만)]  +  [_logs/postproc_run.jsonl]
   │  (9) delete_splits_after_import — 실패 · 필터 제외가 없을 때만 split 삭제  (§10.4)
```

**실행 모드**: `parallelism=1`(기본)이면 (6)~(8) 을 단일 프로세스에서 스트리밍으로 돌린다. `parallelism>1` 이면 (5) 까지를 부모가
한 번 하고 에피소드를 워커 프로세스에 나눈다([§3.4](#34-병렬-처리-모드)).

### 3.2 패키지 구성

후처리기는 `rdfp` 패키지의 `rdfp/dataset/`(적재 · 조회 · export) 와 `rdfp/rosbag/`(bag 카탈로그 · `rosbag` CLI) 에 있다.
아래는 2026-10-18 의 실제 트리다 (`tests/` 생략).

```text
src/rdfp/rdfp/dataset/
├── cli_common.py                # 공통 argparse (--config · --log-level) · 기본 설정 경로
├── config.py                    # pydantic v2 DatasetConfig + YAML 로드 (경로 필드 환경변수 치환, topics_file 병합)
├── types.py · episode_key.py    # 공용 타입 · 에피소드 키 (start_sec, start_nanosec)
├── import_cmd.py                # `import` — 적재 전 과정을 인라인으로 (run_import 없음)
├── export_cmd.py                # `export` — 학습 샘플 트리 (E7)
├── stats_cmd.py · list_cmd.py · init_db_cmd.py · replay_cmd.py · replay_gui_cmd.py
├── ingest/
│   ├── pipeline.py              # 직렬 경로 (_run_ingestion) · 병렬 분기 (_run_parallel) · 필터 · 분류 · split 삭제
│   ├── episode_worker.py        # 병렬 모드의 에피소드 워커 (에피소드 = 트랜잭션)
│   ├── episode/detector.py · dispatcher.py · from_bag.py   # /session → 에피소드 창, 메시지 할당
│   ├── media/recorder_registry.py                          # 레코더 mp4 · sidecar 등록 (§9.1, episode_key 로)
│   ├── media/frame_router.py · ffmpeg_sink.py · mp4_image_recorder.py   # bag 이미지 → mp4 (§9.2)
│   ├── run_log.py · exceptions.py
├── db/
│   ├── registry.py              # msg_type → TypeBinding(table, writer, reader)
│   ├── connection.py · initialize.py · schema_check.py · topics.py · config.py (DbConfig · resolve_dsn)
│   ├── writers/                 # 테이블별 INSERT (session_command · joint_state · motion_* · gripper_* · scene_objects · image_* …)
│   ├── readers/                 # 테이블별 SELECT (재생 · export 가 쓴다)
│   ├── topic_message_replayer.py · mp4_image_replayer.py · message_reader.py · image_message_reader.py · _image_helpers.py
├── export/                      # E1~E7 — frame_clock · observation · motion_label · command_label · dataset_meta · writer
└── sql/schema.sql · drop.sql    # 스키마 정본 (§5.2)

src/rdfp/rdfp/rosbag/            # catalog · mcap_reader · merged_stream · episode_ops · cli (`rosbag` 명령)
```

### 3.3 CLI — 독립 명령

옛 `dataset <subcommand>` 단일 CLI 는 **독립 최상위 명령**으로 갈라졌다 — `setup.py` 의 `console_scripts` 에 `rosbag` · `import` ·
`replay` · `stats` · `export` · `list` · `init-db` · `replay_gui` 가 각각 등록된다. 명령별 옵션과 쓰임은
[운영 가이드 §1 · §4](데이터셋_적재_운영_가이드.md#1-개요) 가 정본이다.

갈라 놓은 이유는 **ROS 의존의 경계**다. `import` 는 bag 이미지 인코딩 경로 때문에 ROS 소싱이 필요하지만 `init-db` · `stats` ·
`list` · `rosbag` 조회 · `export` 는 필요 없다. 한 진입점에 묶으면 가벼운 명령까지 무거운 import 를 끌고 온다. 그래서 `import_cmd`
도 무거운 의존을 **함수 안에서 늦게** import 한다. 새 기능은 `dataset <sub>` 서브커맨드가 아니라 형제 `*_cmd.py` 로 더한다.

`rosbag export` 는 자체 적재 경로를 두지 않는다 — 고른 에피소드의 키를 `start_ns_in` 으로, 고른 bag 루트를 `rosbag_dir` 로 실어
`import_cmd.cmd_import` 를 그대로 부른다. 적재 경로가 하나라 설정 · 필터 · 실패 처리가 두 명령에서 같다.

### 3.4 병렬 처리 모드

설정의 `parallelism` 이 2 이상이면 `multiprocessing.Pool`(spawn 컨텍스트)로 에피소드를 병렬 처리한다.

- 선행 단계(split 탐색 · 에피소드 감지 · 필터 · 토픽 분류 · 스키마 검증 · `topics` upsert)는 부모가 한 번 한다. `topics` 를
  여기서 커밋해 두어야 워커의 FK 값이 보인다.
- 각 워커는 `episode_worker.process_episode()` 로 **자기 에피소드만** 맡는다. 자기 DB 커넥션 · `FrameRouter` · `RecorderRegistrar`
  를 새로 열고, `mcap_reader` 의 `header.stamp` 범위 필터로 그 에피소드 구간만 남긴다 — 다만 **split 은 처음부터 다시 읽는다**(§13).
- 워커 인자는 pickle 경계를 넘도록 plain data(`DatasetConfig`, `Episode`, split 경로 `list[str]`, 토픽 매핑)로 제한한다. writer
  클래스는 넘기지 않고 워커가 타입 이름으로 다시 찾는다.
- **실패는 예외가 아니라 결과값이다.** 워커는 예외를 잡아 `episode_failed` 를 실행 로그에 남기고 `status='failed'` 를 돌려준다.
  부모는 그것을 요약의 `failed` 에 세고, 하나라도 있으면 요약을 출력한 뒤 **종료 코드 1** 로 끝나며 split 을 지우지 않는다.
  (2026-10-18 까지는 집계가 `failed` 를 버려 0 으로 끝났다.)

`parallelism=1` 은 `pipeline._run_ingestion` 의 스트리밍 경로이고, 첫 실패에서 예외로 멈춘다(앞서 커밋된 에피소드는 남는다).

## 4. 범위 지정

적재할 범위는 **네 단계**에서 좁혀진다. 설정 필드 작성법은 [운영 가이드 §7](데이터셋_적재_운영_가이드.md#7-설정-파일-필드),
설정 모델의 정본은 `rdfp/dataset/config.py` 다 — 이 문서에 YAML · 모델 코드를 복사하지 않는다(필드가 바뀔 때 어긋났다).

### 4.1 기본 지정 방식 — 단계별로 무엇이 걸리나

| 단계 | 거는 것 | 어디서 | 단위 |
|---|---|---|---|
| ① split 탐색 | `session_filter.dates` | `catalog.discover_splits` | 날짜 폴더 |
| ② split 탐색 | 토픽 목록 (`topics_file` ∪ `topics`, `/session` 자동 포함) | `discover_splits` → 리더 | 그 토픽이 **하나라도** 있는 split 만 남고, 읽을 때도 그 토픽만 읽는다 |
| ③ 에피소드 필터 | `episode_filter` (task_label 포함/제외 · 최소 길이 · `start_ns_in`) | `pipeline._apply_episode_filters` | 에피소드 |
| ④ 토픽 분류 | 메시지 타입 | `pipeline._determine_topic_classification` | writer 가 없는 타입은 경고 후 무시 |

**시간 범위 필터는 `import` 에 없다.** rosbag 은 적재 전 임시 버퍼이고, 에피소드는 `/session` 으로 자동 분절된다. 시각으로 고르는
것은 `rosbag export --since/--until` 이 에피소드 키 목록으로 바꿔 ③ 의 `start_ns_in` 으로 넘긴다.

**토픽 목록은 합집합이다.** `topics_file` 의 항목 뒤에 `topics` 를 붙이고 중복을 지운다 — 좁히는 수단이 아니다. 둘 다 비면 bag 의
모든 토픽이고, `/session` 은 누락돼도 자동으로 앞에 붙는다(없으면 에피소드를 자를 수 없다).

### 4.2 부가 필터

| 필터 | 설명 |
|---|---|
| **task_label include / exclude** | 에피소드 시작 시점의 `task_label` 기준 (§7.3) |
| **min_duration_sec** | `stop_ts - start_ts < min_duration_sec` 인 에피소드는 건너뛴다 |
| **start_ns_in** | 에피소드 키로 못박는다. `rosbag export` 가 넘긴 값은 설정의 값을 **대신한다**(교집합이 아니다) |

조합은 **AND** 로 동작한다. ⚠️ 필터로 빠진 에피소드가 있으면 `delete_splits_after_import` 가 split 을 지우지 않는다(§10.4).

### 4.3 설정 파일 (`dataset_config.yaml`)

설정 파일은 하나다 — 적재 · 조회 · bag CLI 가 같은 `DatasetConfig` 를 읽는다(옛 `rosbag_config.yaml` 은 없다). 출하본은
[config/dataset_config.yaml](../../config/dataset_config.yaml), 수집 래퍼는 데이터 루트에 같은 스키마의 `dataset.yaml` 을 쓴다.

### 4.4 설정 모델의 설계 원칙

- **경로 필드에만 환경변수를 치환한다** — `rosbag_dir` · `output_mp4_dir` · `recordings_dir` · `topics_file` 에 `${VAR}` ·
  `${VAR:-기본값}` · `~` 를 푼다. 다른 문자열에 무차별로 걸면 값에 `$` 가 든 필드가 깨진다.
- **`topics_file` 상대 경로는 그 YAML 의 디렉터리 기준이다** — 녹화 스크립트와 같은 목록 파일을 공유하려는 것이다. 대가로 YAML 을
  복사하면 깨진다.
- **읽는 데 필요한 것은 `rosbag_dir` 하나다**(스키마 필수). `output_mp4_dir` 은 선택으로 두고 `import` 가 에피소드가 있을 때만
  요구한다 — `stats` · `list` 같은 명령이 같은 파일을 읽어야 하기 때문이다.
- **모르는 키는 무시된다** — pydantic 기본값(`extra='ignore'`)이다. 의도한 설계라기보다 남아 있는 한계이고, 오타가 조용히 기본값으로
  돈다(§14).
- **영상 루트는 두 개다** — `DatasetConfig.mp4_roots()` 가 `recordings_dir` → `output_mp4_dir` 순서로 돌려주고 재생이 그것을 쓴다(§9.3).

### 4.5 인증 정보

DSN 은 **설정 파일에 평문으로 기록하지 않는다.** `db.dsn_env` 에 환경변수 **이름**을 두고, 값은 `db/config.py` 의 `resolve_dsn`
이 실행 시점에 그 환경변수에서 읽는다. 그래서 설정 파일을 공유 · 커밋해도 자격 증명이 새지 않는다.

### 4.6 환경변수

환경변수 목록과 `.rdfprc` 의 관계는 [운영 가이드 §6](데이터셋_적재_운영_가이드.md#6-환경변수) 이 정본이다. 실행 로그 경로와
배치 버퍼 크기(1000)는 코드 상수이고 환경변수로 바꿀 수 없다.

### 5.1 토픽 ↔ 테이블 매핑

`db/registry.py` 의 `MESSAGE_TYPE_REGISTRY` 가 **메시지 타입**으로 writer · reader · 테이블을 고른다 (2026-10-18 기준).

| `rdfp_msgs/SessionCommand` | `/session` | `sessions` (에피소드 = `IN_EPISODE → IN_SESSION` 전이). registry 밖 — `SessionWriter` 가 별도 API 로 다룬다 |
| `sensor_msgs/JointState` | `/joint_states` · `/target_joint_cmds` | `joint_states` — **관측과 명령이 같은 테이블, `topic_id` 로 갈린다**. `joint_names TEXT[]` (2026-09-18) |

| `rdfp_msgs/GripperCommand` | `/gripper_cmds` | `gripper_cmds` (`goal` 심볼) |
| `rdfp_msgs/GripperState` | `/gripper_states` | `gripper_states` |

⚠️ **bag 이미지와 레코더 등록을 함께 켜면 `import` 가 죽는다** — 두 경로가 같은 `(episode_id, topic_id)` 로 `image_streams` 를 넣어
UNIQUE 위반이다. 그래서 공용 녹화 목록 `config/recording_topics.list` 에 카메라 토픽이 없다. `CompressedImage` 는 registry 에도
이미지 타입에도 없어 bag 에 담아도 적재되지 않는다(펑션베이 카메라가 이것이다).

### 5.2 스키마

**정본은 `src/rdfp/rdfp/dataset/sql/schema.sql` 이다** (`init-db` 가 그대로 적용한다; `drop.sql` 이 짝). 이 문서에 SQL 을 복사하지
않는다 — 2026-09-18 의 `joint_names` · `motion_*` 추가처럼 스키마가 바뀔 때 두 곳이 어긋났다. 테이블 14개:

| 테이블 | 무엇 | 비고 |
|---|---|---|
| `sessions` | 에피소드 한 건 — `(start_sec, start_nanosec)` **UNIQUE**, `id BIGSERIAL`, `task_label` · `success` · `metadata jsonb` | `success` 는 `stop_episode` 의 `outcome` (NULL = 판정 없음) |
| `topics` | 토픽 이름(UNIQUE) · 타입 등록부 — 모든 시계열 행이 `topic_id` 로 가리킨다 | 영상 토픽은 bag 에 없을 수 있어 `RecorderRegistrar` 가 upsert |
| `joint_states` | 관측 `/joint_states` 와 명령 `/target_joint_cmds` — `topic_id` 로 갈림, `joint_names TEXT[]` | 이름이 빈 행은 export 가 거부 |
| `motion_trajectories` | R1 실행 궤적 — 연산마다 한 행, 경유점 jsonb, `stamp` = t₀ | `duration_sec` GENERATED |
| `motion_events` | R2 연산 이벤트 — 결과 · 끝난 시각 · `truncated_at_sec` | `failed` 만 짝 궤적이 없다 (불변식) |
| `gripper_cmds` · `gripper_states` | 심볼 명령 · 연속 상태(`width` · `stalled` · `at_goal`) | |
| `scene_objects` | `/scene/objects` 스냅샷 (물체 배열 jsonb) | 관측 컬럼에는 넣지 않는다 — [scene_objects_observation_decision](../learning/scene_objects_observation_decision.md) |
| `pose_stampeds` · `twist_stampeds` · `joint_jogs` · `target_joint_states` | `/ee_pose` · servo 입력 둘 · 구형 목표 | |
| `image_streams` | 에피소드 × 카메라 토픽의 mp4 한 벌 — `(episode_id, topic_id)` **UNIQUE**, `mp4_path` 는 **그 영상을 만든 쪽의 출력 루트 기준 상대 경로** | 어느 루트인지는 적지 않는다 (§9.3) |
| `image_frames` | 프레임별 stamp — `(episode_id, topic_id, frame_index)` **UNIQUE** | 레코더 sidecar 또는 `FrameRouter` |

공통 규칙: 시각은 `stamp_sec` · `stamp_nanosec` + GENERATED `stamp_ts`; 자식 테이블은 `episode_id … ON DELETE CASCADE`
(그래서 `on_existing_episode: replace` 가 에피소드째 지우고 다시 넣는다).

**스키마 이전(migration)은 하지 않는다.** `CREATE TABLE IF NOT EXISTS` 라 이미 있는 테이블에 새 컬럼이 붙지 않고, 예외로
`sessions.success` · `sessions.metadata` 만 `ALTER TABLE … ADD COLUMN IF NOT EXISTS` 로 더한다. 그 밖의 컬럼이 늘면 옛 DB 는 §5.3
검증에서 멈추고 `init-db --drop` 으로 재생성해야 한다(적재된 데이터는 bag 에서 다시 넣는다).

### 5.3 스키마 사전 검증

적재를 시작하기 전에 `schema_check.ensure_schema` 가 다음을 보고, 하나라도 어긋나면 **즉시 실패**한다.

1. 필요한 테이블이 있는가 — `sessions` · `topics` + 이번 bag 의 토픽이 쓰는 테이블(+ bag 에 이미지 토픽이 있으면 `image_*`).
2. 각 테이블에 필수 컬럼(`REQUIRED_COLUMNS`)이 있는가 — 옛 DB 가 여기서 걸린다(`table '…' is missing columns: […]`).
3. 자식 테이블의 `episode_id` 가 `sessions(id)` 를, `topic_id` 가 `topics(id)` 를 FK 로 가리키는가.

조회는 `information_schema.columns` · `table_constraints` · `key_column_usage` · `constraint_column_usage` 다.
⚠️ 레코더 등록만 쓰는 실행(bag 에 이미지 없음)에서는 `image_*` 가 검증 대상에 안 들어간다 — 없으면 첫 등록 때 에피소드 실패로 드러난다.
`init-db` 로 만든 DB 에는 늘 있으므로 실제로 문제가 된 적은 없다.

### 5.4 이유: `session_path` 컬럼 제외

rosbag 은 정제 후 삭제될 수 있는 **중간 저장소**이므로, DB 레코드에 원본 세션 디렉터리 경로를 남기지 않는다. 재실행 멱등성은
`sessions.UNIQUE(start_sec, start_nanosec)` 로 확보한다 (에피소드 시작 시각은 ns 정밀도의 `header.stamp` 이므로 **한 회차 안에서는**
실질적으로 충돌하지 않는다). ⚠️ **회차가 다르면 충돌할 수 있다** — §10.3.

### 5.5 Registry 설계

`registry.py` 는 메시지 타입 문자열 → `TypeBinding(table, writer_cls, reader_cls)` 를 한 곳에서 선언한다. 적재(writer)와
복원(reader — 재생 · export)이 같은 엔트리로 묶여, 새 타입은 **한 줄 + writer/reader 클래스**로 붙는다. 행 변환은 각 writer 의
`row_values()` 가 갖는다.

- `SessionCommand` 는 registry 에 없다 — `SessionWriter` 가 `insert_episode` · `find_existing` · `delete_by_id` 로 에피소드 행 자체를
  다룬다.
- 이미지 타입(`IMAGE_MESSAGE_TYPES` = `sensor_msgs/msg/Image` 하나)은 registry 가 아니라 `FrameRouter` 로 간다.
- 토픽 분류(`_determine_topic_classification`)는 writer **클래스가 아니라 타입 이름**을 넘긴다 — 병렬 워커로 pickle 해 보낼 수 있게
  하려는 것이고, 워커가 `resolve_message_type()` 으로 다시 찾는다.
- 같은 타입을 토픽에 따라 다른 테이블로 보내는 장치(옛 `TOPIC_OVERRIDE`)는 없다. 관측과 명령의 `JointState` 는 같은 테이블에
  `topic_id` 로 가른다.

### 5.6 Writer 인터페이스

`db/writers/base.py` 의 `WriterBase` 가 에피소드 경계에서 flush 되는 배치 INSERT 의 공통 베이스다 —
`__init__(conn, batch_size=1000, table=None, topic_id=None)` · `append(episode_id, msg)` · `flush()` ·
`consume_inserted_count()` · `drop_pending()` · `row_values(episode_id, msg)`(서브클래스 구현).

- 커밋 직전 순서: 모든 writer `flush()` → bag mp4 finalize → 레코더 등록 → `conn.commit()` → `consume_inserted_count()` 로 요약 집계.
- 롤백 순서: writer `drop_pending()` → `FrameRouter.abort_episode()` → `conn.rollback()`.
- `table` 인자는 클래스 속성을 건드리지 않고 인스턴스 단위로 테이블명을 바인딩한다.
- **영상 두 경로(`FrameRouter` · `RecorderRegistrar`)는 `WriterBase` 가 아니다** — 같은 모양의 `consume_inserted_count()` 를 따로
  가지며, 파이프라인이 둘을 요약에 **따로 더한다**. 빼먹으면 DB 에는 행이 있는데 요약이 0 으로 보고한다(실제로 그랬다).

## 6. rosbag 읽기 전략

### 6.1 Split 후보 선정

`catalog.discover_splits(rosbag_dir, dates=…, topics=…)` 가 `<rosbag_dir>` 하위를 날짜 폴더 → 세션 디렉터리 순으로 순회하며 각 세션의
`metadata.yaml` 을 파싱한다.

- **`metadata.yaml` 이 없는 세션**(녹화 중 또는 비정상 종료)**은 제외된다** — 오류가 아니라 0 건이 된다(§0.3.3).
- `dates` 는 날짜 폴더 단계에서, `topics` 는 metadata 의 토픽 목록으로 거른다(그 토픽이 하나라도 있는 split 만).
- `rosbag_dir` 이 없으면 `FileNotFoundError` 로 실패한다.
- 결과는 stamp 오름차순 split 목록이다.

(옛 설계의 SQLite 인덱스 `catalog_index_path` 는 구현에서 빠졌다 — metadata.yaml 스캔뿐이다.)

### 6.2 Split 내부 읽기

`mcap_reader.iter_split_messages(path, topics=…, time_range_ns=…)`:

- `mcap_ros2.read_ros2_messages` 로 토픽 필터를 걸어 읽고, **split 하나를 통째로 메모리에 올려 `(header.stamp, 토픽)` 으로 안정
  정렬**한 뒤 내보낸다. 정렬 기준은 반드시 `header.stamp` 다 — bag 의 `log_time`(수신 시각)과 다를 수 있다.
- `header.stamp` 가 없는 메시지는 정렬할 수 없어 **건너뛴다**(DEBUG 로그만).
- `time_range_ns` 는 `[start, end)` 를 `header.stamp` 로 거른다. `mcap_ros2` 의 시간 인자는 `log_time` 기준이라 쓰지 않는다.
- 역직렬화는 MCAP 에 내장된 IDL 스키마로 하므로 소스 메시지 패키지를 설치할 필요가 없다.

### 6.3 여러 Split 스트리밍 머지

- `merged_stream.merge_split_streams` 가 `heapq.merge` 로 split 별 iterator 를 `(stamp, 토픽)` 키로 합친다 — 같은 키면 split
  순서가 tie-breaker 다.
- 각 split 이 정렬돼 있으므로 머지 결과도 전역 정렬이다. 그래서 **적재가 보는 스트림에서는 같은 토픽의 stamp 역행이 나올 수
  없다**(§12).

## 7. 에피소드 감지

### 7.1 알고리즘

`episode/detector.py` 가 세션 메시지만 stamp 오름차순으로 훑으며 직전 `state` 를 유지한다.

```
prev_state = None
current_start = None
current_task  = None
episodes = []

for msg in session_messages_in_stamp_order:
    state, stamp = msg.state, to_ns(msg.header.stamp)

    if state == 'IN_EPISODE' and prev_state != 'IN_EPISODE':      # start_msg
        current_start = stamp
        current_task  = msg.task_label or None

    elif state == 'IN_SESSION' and prev_state == 'IN_EPISODE':    # stop_msg
        if current_start is not None and stamp > current_start:
            episodes.append(Episode(current_start, stamp, current_task,
                                    success=outcome(msg), metadata=metadata(msg)))
        current_start = current_task = None

    # 그 외 전이 (IDLE → IN_SESSION, IDLE 유지, IN_EPISODE → IDLE) 는 무시

    prev_state = state
```

`detector` 는 순수 함수라 bag 없이 시험한다(`tests/ingest/episode/test_detector.py`). `rosbag list-episodes` 도 같은 함수
(`episode/from_bag.episodes_from_splits`)를 써서, 목록과 적재가 에피소드를 다르게 자르는 일이 없다.

### 7.2 경계 포함 규칙

- 구간은 **`[start_ts, stop_ts)`** 반열림으로 처리한다.
- `stop_ts` 와 같은 stamp 의 메시지는 그 에피소드에 **포함하지 않는다**.

### 7.3 `task_label` 고정

에피소드 시작 시점의 `task_label` 을 그 에피소드의 `task_label` 로 고정한다. 노드 규약([session_control_guide](session_control_guide.md))
상 `IN_EPISODE` 중에는 바뀌지 않으므로 중간 재샘플링은 하지 않는다. 빈 문자열(`""`)이면 `NULL` 이다. 빈 라벨로 시작한
에피소드는 bag 안의 메시지가 이미 비어 있어 재적재로도 못 고친다.

### 7.4 비정상 상황 처리

| 케이스 | 처리 |
|---|---|
| 찾은 split 어디에도 `/session` 이 없음 | **즉시 실패** (`no /session messages found within rosbag_dir`) |
| 마지막 세션 메시지가 `IN_EPISODE` 로 끝남 (종료 경계 없음) | 경고 `unfinished episode discarded` 후 그 에피소드 **폐기** |
| stop_msg 의 stamp 가 시작 이하 | 경고 후 그 에피소드 폐기 |
| 시작 없이 stop_msg | 경고 후 무시 |
| `IN_EPISODE → IDLE` (중간 `IN_SESSION` 없이) | **종료로 보지 않는다** — 그 에피소드는 버려지고, 다음 시작이 오면 **경고 없이** 덮어쓴다. 현재 `session_control_node` 는 이 전이를 만들지 않는다(`stop_session` 은 `IN_SESSION` 을 먼저 낸다) |
| 같은 `(start_sec, start_nanosec)` 가 이미 DB 에 있음 | `on_existing_episode` 를 따른다 (§10.1) |

## 8. 메시지 → 에피소드 할당

### 8.1 정책

에피소드 리스트(stamp 오름차순)와 메시지 스트림을 동시에 훑는 **sweep-line** 방식으로 할당한다(`episode/dispatcher.py`).

```python
def assign_episodes(msg_stream, episodes):
    i = 0
    for stamp_ns, topic, msg in msg_stream:
        while i < len(episodes) and stamp_ns >= episodes[i].stop_ns:
            i += 1                       # 이 메시지보다 먼저 끝난 에피소드는 지나간다
        if i >= len(episodes):
            break
        if episodes[i].start_ns <= stamp_ns < episodes[i].stop_ns:
            yield episodes[i], topic, msg
```

시간 복잡도 O(N + E), 메모리 O(E). **구간 밖 메시지는 오류 없이 버려진다** — `header.stamp` 가 0 이거나 에피소드와 다른 시계인
메시지가 여기서 조용히 빠진다(§1.4). rosbag 에는 남아 있으므로 "녹화는 됐는데 DB 에만 없다"로 나타난다.

### 8.2 배치 삽입 · 에피소드 이벤트

- 토픽별 writer 는 내부 버퍼(기본 1000 건)를 두고 `executemany` 로 flush 한다.
- dispatcher 는 에피소드마다 `enter` / `exit` 이벤트를 내고, 메시지가 하나도 없는 에피소드에도 낸다. writer 는 `exit` 에서
  flush 하고, `FrameRouter` 는 `enter` 에서 에피소드 디렉터리를 준비하고 `exit` 에서 mp4 를 닫는다.

### 8.3 트랜잭션 경계

**에피소드 하나가 트랜잭션 하나다.**

1. `sessions` 에 에피소드 행 INSERT → `RETURNING id` 로 `episode_id` 확보 (`skip` 정책이면 여기서 건너뛴다).
2. 시계열 테이블에 메시지 INSERT (배치).
3. bag 이미지가 있으면 mp4 finalize + `image_streams` · `image_frames` INSERT.
4. **레코더 mp4 등록** — `recordings_dir` 의 그 에피소드 녹화를 `image_streams` · `image_frames` 에 INSERT (§9.1).
5. COMMIT.

어느 단계에서 실패해도 그 에피소드의 DB 행을 롤백하고, bag 경로가 만든 mp4 와 에피소드 디렉터리를 지운다(`abort_episode`). mp4 는
최종 경로에 바로 쓰고 실패 시 지운다 — 임시 파일 + rename 으로 원자적으로 공개하지는 않는다. **레코더 파일은 어느 경우에도
건드리지 않는다**(등록 행만 롤백된다).

## 9. 영상

영상이 DB 에 들어오는 길은 둘이다. **한 에피소드 · 카메라에는 하나만 쓴다** — 둘로 넣으면 `image_streams` UNIQUE 위반이다(§5.1).

### 9.1 레코더 mp4 등록 (현행 경로)

영상은 rosbag 에 담지 않고, `rdfp_image_recorder` 가 에피소드마다 다음을 남긴다(2026-09-18 형식).

| 파일 | 내용 |
|---|---|
| `<prefix>_metadata.json` | `episode_key`(`/session` IN_EPISODE 의 `header.stamp`) · 토픽 · 코덱 · 픽셀 형식 · fps · 해상도 · `nframe` · mp4 · sidecar 이름 |
| mp4 | 에피소드 구간의 영상 (CFR) |
| `.jsonl` sidecar | 줄마다 `{"frame_index": N, "stamp": {"sec", "nanosec"}}` — **mp4 의 N번째 프레임 = sidecar 의 N번째 줄** |

`ingest/media/recorder_registry.py` 의 `RecorderRegistrar` 가 이것을 에피소드에 붙인다.

- **열쇠는 `episode_key` 다 — 파일 이름이 아니다.** 파일 이름의 시각은 벽시계(`datetime.now()`)이고 `episode_key` 는 스택 시계라
  `use_sim_time` 스택에서는 둘이 무관하다.
- `recordings_dir` 아래를 **재귀로** 훑어 `*_metadata.json` 을 에피소드 키별로 색인한다(카메라가 여럿이면 목록이 여럿). 루트가 없으면
  빈 색인이다 — **오류가 아니다**(영상 없는 에피소드도 유효하다). 그래서 `recordings_dir` 을 잘못 적으면 영상만 조용히 빠진다.
- `episode_key` 가 없는 metadata(2026-09-18 이전 형식)는 건너뛴다 — 억지로 붙이면 엉뚱한 에피소드에 영상이 달린다.
- **자기 모순은 조용히 넘기지 않는다** (`RecordingError` → 그 에피소드 롤백): mp4 · sidecar 가 없음, sidecar 의 깨진 줄,
  sidecar 줄 수 ≠ `nframe`. 넘기면 프레임 인덱스가 밀린 채 적재되고, 학습에서 영상과 레이블의 위상이 조용히 어긋난다.
- 토픽은 bag 에 없을 수 있으므로 `topics` 를 여기서 upsert 한다(타입을 못 읽으면 `sensor_msgs/msg/Image`).
- `mp4_path` 는 **`recordings_dir` 기준 상대 경로**로 넣는다(루트 밖 파일이면 절대 경로). 데이터 루트를 옮겨도 루트만 바꾸면 된다.
- 에피소드 행을 만든 **그 커넥션**으로, 커밋 **직전에** 부른다 — 메시지 적재가 롤백되면 등록도 함께 되돌아간다.

**등록을 레코더에 맡기지 않는 이유**: 레코더가 DB 에 직접 쓰면 수집이 DB 가용성에 묶인다. rosbag 을 두는 취지(녹화를 DB 에서 떼어
놓는다)에 맞춰, 레코더는 파일만 남기고 DB 는 적재가 만진다.

### 9.2 bag 이미지 인코딩 (`FrameRouter` 경로)

rosbag 에 `sensor_msgs/msg/Image` 토픽이 있을 때만 돈다 — 현행 녹화 목록에는 없으므로 보통 쉰다.

출력 구조:

```text
<output_mp4_dir>/
└── episode_XXXXXXXX/              # sessions.id 를 8자리로
    ├── <토픽_sanitized>.mp4        # '/' → '_', 앞쪽 '_' 제거 (예: /camera/image_raw → camera_image_raw)
    └── ...
```

- **파일은 mp4 하나다.** 글로벌 메타(mp4 경로 · 코덱 · fps · frame_id · 해상도 · 프레임 수)는 `image_streams` 에, 프레임별 stamp 는
  `image_frames` 에 넣는다 — 옛 설계의 `metadata.json` · `frames.jsonl` 파일은 만들지 않는다. `mp4_path` 는 `output_mp4_dir` 기준
  상대 경로다.
- **입력**: `sensor_msgs/msg/Image` 의 8-bit raw(`bgr8` · `rgb8` · `bgra8` · `rgba8` · `mono8`)만. 그 밖의 인코딩(`16UC1` · `32FC1` …)은
  `UnsupportedImageError` 로 **fail-fast** — 그 에피소드가 실패한다. `CompressedImage` 는 여기까지 오지 않고 분류 단계에서 무시된다(§5.1).
- **CFR-passthrough**: 수신 프레임을 순서대로, 드롭 · 중복 없이 인코더에 넘기고 컨테이너는 `mp4.nominal_fps`(기본 30)로 CFR
  선언한다. 원본 stamp 에 맞추는 리타이밍은 하지 않는다 — **정확한 프레임 시각은 `image_frames` 가 유일한 진실원천**이다.
- 인코더는 `FFMpegMp4Recorder`(libx264, `encoder_mode='cpu'`, 비트레이트 4M, preset 기본값 `medium`). 첫 프레임의 인코딩과 같으면
  raw 바이트를 그대로, 다르면 `cv_bridge` 로 변환한다 — **변환 실패(`InvalidFrameError`)는 프레임을 건너뛰지 않고 에피소드를
  실패시킨다**(1:1 대응이 깨지기 때문이다).
- 카메라 sink 는 첫 프레임 도착 시 지연 생성되고, 에피소드 `exit` 에서 finalize 된다. 에피소드 중에 한 번도 안 온 카메라는 mp4 도
  행도 없다.

### 9.3 재생이 mp4 를 찾는 법

`image_streams` 에는 `mp4_path` 가 **어느 루트 기준인지** 적혀 있지 않다(§5.2). 그래서 재생(`replay` · `replay_gui`)은
`_image_helpers.resolve_mp4_path` 로 `recordings_dir` → `output_mp4_dir` 순서로 찾아 **파일이 있는 첫 경로**를 쓴다. 두 경로의
이름 규칙(`session_*.mp4` · `episode_XXXXXXXX/…`)이 달라 겹치지 않는다. 어디에도 없으면 찾아 본 경로를 모두 적어 실패한다.
(2026-10-18 까지는 `output_mp4_dir` 만 봐서, 두 루트가 다른 구성에서 레코더 영상을 못 찾았다.) 루트를 컬럼으로 두는 것이 근본
해법이지만 스키마 이전이 필요해 하지 않았다.

## 10. 재실행 · 멱등성

### 10.1 중복 처리 정책 (`on_existing_episode`)

| 값 | 동작 |
|---|---|
| `skip` (기본) | 같은 `(start_sec, start_nanosec)` 가 `sessions` 에 있으면 그 에피소드 전체를 건너뛴다 (실행 로그 `episode_skipped`) |
| `replace` | 기존 행을 지우고(FK `ON DELETE CASCADE` 로 자식 행도) bag 경로의 `episode_<옛 id>/` 를 지운 뒤 **새 id** 로 다시 넣는다. 레코더 파일은 지우지 않고 새 행에 다시 등록된다 |
| `error` | 즉시 실패 |

### 10.2 장애 복구

- 에피소드 단위 트랜잭션이라 **부분 적재된 에피소드는 없다** — 실패한 에피소드는 통째로 롤백된다. 기본 `skip` 정책으로 다시 돌리면
  성공한 것은 건너뛰고 실패한 것만 다시 시도한다.
- 실행 로그(JSONL)에 `episode_done` 의 `(episode_id, row_counts, mp4_files)` 와 `episode_failed` 의 사유가 남는다(§11.3).

### 10.3 ⚠️ sim 시계 겹침 — 회차가 다른 bag 을 같은 `rosbag_dir` 에 두지 않는다

에피소드 키가 `(start_sec, start_nanosec)` 이므로 **시뮬레이터를 재기동해 sim 시계가 0 으로 되감기면 회차 간에 키와 시간 창이
겹칠 수 있다**(Isaac 처럼 `use_sim_time` 인 백엔드). 2026-09-20 실측 — 옛 bag(sim 31.9~896.6 s)과 새 bag(701.1~779.4 s)을 함께
적재하니 새 에피소드 둘이 `joint_states` · `motion_*` · `gripper_*` 전부 **0 건**으로 커밋됐고, 이미지만 sidecar 의 `episode_key` 로
정상 등록돼 겉보기에 멀쩡했다. 같은 bag 을 혼자 적재하면 정상이다.

그래서 **적재가 끝난 세션 디렉터리는 `rosbag_dir` 밖으로 뺀다**(운영 절차는 [운영 가이드 §8.1](데이터셋_적재_운영_가이드.md#81-수집--첫-적재)).
펑션베이처럼 stamp 를 벽시계로 정렬하는 백엔드는 키가 겹치지 않지만, 같은 습관을 유지한다.

### 10.4 적재 후 split 삭제 (`delete_splits_after_import`)

rosbag 을 임시 버퍼로만 쓸 때 적재가 끝난 split 을 지우는 옵션이다(기본 꺼짐).

- **지우는 단위는 에피소드가 아니라 split 파일**이고, 대상은 **이번 실행이 찾은 split 전부**다(날짜 · 토픽 선행 필터만 반영된다).
  split 을 지운 뒤 `metadata.yaml` 만 남은 세션 디렉터리도 지운다.
- 그래서 split 안의 에피소드가 전부 DB 에 들어갔다고 말할 수 없는 실행에서는 **지우지 않는다**(`import_cmd._split_deletion_blocker`,
  2026-10-18) — 실패한 에피소드가 있거나, 에피소드 필터가 감지된 에피소드를 하나라도 뺐을 때다. `rosbag export` 로 골라 적재하는
  것도 필터(`start_ns_in`)에 해당한다. 지우지 않으면 요약의 `delete_skipped` 에 사유를 남긴다.
- 남은 한계: 메시지 수 대조 같은 **무손실 검증은 없다**. 에피소드 단위로 지우려면 이 옵션 대신 `rosbag delete --exported` 를 쓴다.

## 11. 오류 처리

### 11.1 실패·스킵 규칙

| 상황 | 동작 |
|---|---|
| 설정 파일 · `topics_file` 없음, 설정 검증 실패 | 종료 코드 2 |
| `<rosbag_dir>` 이 없음 | 실패 (종료 코드 1) |
| 찾은 split 이 0 개 / 필터 뒤 에피소드가 0 개 | **성공(0)** — 빈 요약, DB 에 접속하지 않는다 |
| 찾은 split 어디에도 `/session` 이 없음 | 실패 (종료 코드 1) |
| 필요한 테이블 · 컬럼 · FK 가 DB 에 없음 | 실패 (§5.3) |
| 메시지 타입이 `registry` 에 없음 | 경고 후 그 토픽 무시 |
| `header.stamp` 가 없는 메시지 | 그 메시지만 건너뜀 (DEBUG) |
| `header.stamp` 가 에피소드 구간 밖 | 그 메시지만 버림 — 경고 없음 (§8.1) |
| 에피소드 안의 INSERT 실패 · bag 이미지 변환 실패 · `UnsupportedImageError` · `RecordingError` | 그 에피소드 롤백. **순차 모드는 거기서 멈추고**(종료 코드 1, 요약 없음), **병렬 모드는 나머지를 끝까지 돌고** 요약 출력 후 종료 코드 1 |
| DB 커넥션 단절 | 재시도하지 않는다 — 위와 같이 에피소드 실패 |

### 11.2 로깅 규약

- 로거 이름: 모듈마다 `logging.getLogger(__name__)` — `rdfp.dataset.*` · `rdfp.rosbag.*`.
- 레벨: 기본 `INFO`. CLI 공통 옵션 `--log-level debug` 로 올린다.
- 포맷: `%(asctime)s [%(levelname)s] %(name)s: %(message)s` (`cli_common.LOG_FORMAT`)
- 메시지는 **영어**로 쓴다 (프로젝트 규약).

### 11.3 실행 요약 JSONL

에피소드 처리가 끝날 때마다 `<output_mp4_dir>/_logs/postproc_run.jsonl` 에 한 줄씩 덧붙인다(`ingest/run_log.py`). 경로는 코드
상수다. 필터 뒤 에피소드가 없으면 파일을 만들지 않는다. 이벤트 종류의 요약표는 [운영 가이드 §9.2](데이터셋_적재_운영_가이드.md#92-실행-요약-jsonl),
아래는 레코드 형식이다.

**`episode_done`** — 정상 커밋:
```json
{"ts":"2026-04-19T10:15:03+09:00","event":"episode_done","episode_id":42,
 "start_ts":"2026-04-11T13:10:00+09:00[ns=123456789]",
 "stop_ts":"2026-04-11T13:12:30+09:00[ns=987654321]",
 "task_label":"pick_and_place",
 "row_counts":{"joint_states":45678,"pose_stampeds":12345,"image_streams":1,"image_frames":1500},
 "mp4_files":[]}
```

**`episode_failed`** — 트랜잭션 롤백된 실패:
```json
{"ts":"...","event":"episode_failed",
 "start_ts":"...","stop_ts":"...","task_label":"x","error":"..."}
```

**`episode_skipped`** — `on_existing_episode=skip` 으로 건너뜀:
```json
{"ts":"...","event":"episode_skipped","episode_id":-1,
 "start_ts":"...","stop_ts":"...","task_label":"..."}
```

`episode_skipped` 의 `episode_id` 는 순차 · 병렬 모두 **늘 `-1`** 이다 — 기존 행을 찾는 함수가 id 를 돌려주지 않는다. 어느 행인지는
`start_ts` 로 `sessions` 를 찾는다. (2026-10-18 까지 있던 `quality_warning` 레코드는 품질 게이트와 함께 없어졌다 — §12.)

- `ts` 는 기록 시각, `start_ts` · `stop_ts` 는 에피소드 경계를 로컬 시간대 ISO-8601 로 쓴다. 표준 datetime 은 마이크로초까지라
  `[ns=…]` 로 나노초를 덧붙인다.
- `row_counts` 는 그 에피소드의 테이블별 행 수다 — 메시지 테이블과 영상 두 테이블이 함께 들어간다. `mp4_files` 는 bag 경로가 새로
  인코딩한 mp4 만이라 레코더 등록만 쓰면 빈 목록이다.

## 12. 품질 게이트 — 제거 (2026-10-18)

토픽별 `header.stamp` 시퀀스를 보고 경고를 남기던 `ingest/quality_gate.py` 를 **뺐다** — 설정 블록 `quality_gate`, 실행 로그의
`quality_warning` 레코드, 요약의 `warnings` 카운터가 함께 없어졌다. 경고만 남기고 에피소드를 빼거나 실패시키지 않는 장치였다.

**뺀 이유 — 있다는 인상만 주고 실제로는 아무것도 잡지 못했다.**

| 검사 | 왜 무의미했나 |
|---|---|
| `stamp_regression` (같은 토픽의 stamp 역행, 기본 켜짐) | 게이트가 보는 것은 split 을 `header.stamp` 로 정렬해 머지한 스트림이라(§6.3) 역행이 **나올 수 없었다** |
| `idle_gap` (인접 stamp 간격이 임계 초과, 기본 꺼짐) | 동작은 했지만 출하 설정 · 수집 래퍼가 모두 꺼 두었고, **직렬 경로에만 연결돼 병렬 모드에서는 돌지 않았다** |

그래서 기본 설정에서 이 장치는 아무 경고도 낼 수 없었다. 옛 설정에 `quality_gate` 블록이 남아 있어도 모르는 키라 무시된다
(`test_config.py` 가 고정한다).

**남은 공백.** 의미 있는 순서 검사는 정렬 **전**의 **발행 순서(`log_time`)** 기준이다 — 미구현 I8. 다시 만든다면 리더가 정렬하기
전에 보아야 하고, 직렬 · 병렬 두 경로에 함께 연결해야 한다. 유휴 간격(메시지 공백) 검사가 필요해지면 같은 자리에 둔다.

## 13. 성능 참고

| 항목 | 기준값 | 비고 |
|---|---|---|
| DB 배치 삽입 버퍼 | 1000 행 | 레이턴시 vs. 메모리 |
| split 읽기 | split 하나를 통째로 메모리에 올려 정렬 | split 길이(§0.2)가 메모리 요구량을 정한다 |
| MCAP 머지 heap | split 개수만큼 | 수십 개 이하면 무시 가능 |
| bag 이미지 인코딩 | libx264 preset `medium`, 4M | 레코더 등록만 쓰면 인코딩 비용이 없다 |
| 레코더 등록 | sidecar 를 한 줄씩 읽어 `image_frames` 에 INSERT | 프레임 수에 비례 |

병렬 모드는 각 워커가 **split 을 처음부터 다시 읽고** `header.stamp` 로 자기 구간만 남긴다. 그래서 에피소드 수가 적고 split 이
길수록 이득이 줄고, 아주 짧은 bag 은 `parallelism=1` 이 낫다. 처리 시간 목표(이미지 포함 bag 재생 시간의 0.3~0.6 배)는 옛 설계의
목표치이고 현행 경로로 다시 재지 않았다.

## 14. 알려진 제약

- **`import` 는 ROS 소싱이 필요하다** — bag 을 읽는 데는 필요 없지만 bag 이미지 인코딩 모듈(`ffmpeg_sink`)이 `sensor_msgs` 를 top-level
  에서 import 하고 `cmd_import` 가 그것을 조건 없이 끌어온다. 반면 `rdfp/dataset/export/` 는 ROS import 가 없어 ROS 밖에서 돈다.
- `use_sim_time` 스택의 `header.stamp` 는 sim time 이다 — 적재는 시계를 구분하지 않고 그대로 쓴다. 회차 간 겹침은 §10.3.
- 메시지 순서 · 공백 검사가 없다 — 품질 게이트를 뺐고(§12), 발행 순서(`log_time`) 기준 검사는 미구현(I8)이다.
- `image_streams.mp4_path` 의 기준 루트가 컬럼에 없다 — 재생이 두 루트를 차례로 찾아 보완한다(§9.3).
- 설정의 **모르는 키는 오류 없이 무시된다** — 오타가 조용히 기본값으로 돈다(§4.4).
- 스키마 이전이 없다 — 컬럼이 늘면 옛 DB 는 재생성해야 한다(§5.2).
- `delete_splits_after_import` 는 split 단위이고 무손실 검증이 없다(§10.4).
- DB 커넥션 단절을 재시도하지 않는다(§11.1).
- 매우 큰 단일 에피소드(>1 GB mp4)는 ffmpeg 버퍼링 이슈가 있을 수 있다(bag 이미지 경로).

### 15.3 수동 스모크

- 실 운영 bag 중 짧은 샘플로 end-to-end 실행 → [운영 가이드 §3.1](데이터셋_적재_운영_가이드.md#31-적재-완료-확인) 의 완료 확인.
- 같은 bag 으로 2회 실행해 `skip` / `replace` 정책이 기대대로 동작하는지 확인.
- `parallelism=1` vs `>1` 결과(에피소드 수 · 테이블별 행 수 · 영상 등록 수)가 같은지 비교.

### 15.4 변경할 때

구현과 시험을 같은 추론으로 쓰면 둘이 같은 오류를 공유한다 — 실제로 writer 필드 이름 · 중력 보상 부호에서 그랬다. 동작을 고칠 때는
**옛 동작을 되살린 사본에서 새 시험이 실패하는지**(변이 시험) 확인한다.
