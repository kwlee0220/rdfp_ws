## 0. 판정 규칙 — 먼저 읽는다

**이 체크리스트의 목적은 합격/불합격이 아니라 "무엇이 달라졌는가"를 놓치지 않는 것이다.** 기준선과 다른 값이 나오면 세 가지 중 하나이며, 셋을 구분하지 않으면 오진한다.

| 판정 | 뜻 | 다음 행동 |
|---|---|---|
| **개선** | 벤더가 요청 항목을 반영했다 | 해당 벤더 요청(A-n/B-n)을 닫고 기준선을 갱신 |
| **회귀** | 전에 되던 것이 안 된다 | 벤더에 회귀 보고. 예: A-9 stamp 가 벽시계에서 경과시간으로 되돌아가는 것 |
| **변경** | 의도적 사양 변경인데 통보가 없었다 | **가장 위험하다.** 우리 코드의 전제가 조용히 깨진다 |

**"회차마다 바뀌는 항목"이 따로 있다** — A-9(stamp 기준) · A-10·A-11(잔차·진행률) · A-17(정지 길이)은 같은 빌드·같은 설정에서도 회차마다 달라진다(§G.1a). 이 넷은 기준선과 달라도 곧바로 회귀로 판정하지 않고 **§G.1a 의 범위 안인지**부터 본다.

### 측정 전 반드시 확인할 함정

1. **토픽이 목록에 있는 것과 발행되는 것은 다르다.** `ros_tcp_endpoint` 는 Unity 가 끊겨도 등록된 퍼블리셔를 유지한다. `ros2 topic list` 에 보여도 한 건도 안 올 수 있다 — **반드시 실제 수신 건수로 판정한다.** 2026-09-17 에도 겪었다: 이전 씬(`t1`)에서 등록된 `/output/endeffector` 가 r2 로 바꾼 뒤에도 "발행자 1, 수신 0" 으로 남았고, endpoint 를 새로 띄우자 그래프에서 사라졌다.
2. **`ros2` CLI 데몬이 눈이 멀 수 있다.** 데몬이 `ros_tcp_endpoint` 보다 늦게 뜨면 그래프를 하나도 못 보고, `ros2 topic list` 가 `/rosout` 만 낸다. 아무것도 안 보이면 **먼저 `--no-daemon` 으로 대조**한다. **`ros2 daemon stop && start` 로도 안 낫는 경우가 있다.** 데몬을 지운 직후에는 `ros2 node list` 가 수십 초 걸려 타임아웃으로 끝나기도 한다 — "스택이 안 떴다"로 판정하기 전에 launch 로그를 본다. `rclpy` 로 직접 구독하는 스크립트(`fb_*`)는 데몬을 안 타므로 무관하다.
3. **`ros2 topic hz` 는 창이 찰 때까지 기다려 읽는다.** 첫 줄을 읽으면 틀린다 — 한때 카메라를 4.4 Hz 로 오독했다.
4. **관절 하나·방향 하나로 "무반응"을 판정하지 않는다.** 한계 근처에 걸린 관절 하나를 전체 고착으로 오진한 적이 있다. `fb_raw` 처럼 7관절 전부를 본다.
5. **접촉을 고착이나 중력 처짐으로 읽지 않는다 — 단 그리퍼 `effort` 는 접촉력이 아니다.** `effort = Kp × 잔차`(그리퍼 `Kp=200`)이므로 **정지 상태에서만** 접촉 판정에 쓸 수 있다. `> 1 N·m` = `잔차 > 0.005 rad` 이고, **이동 중에는 접촉이 없어도 잔차가 크다.** 무반응처럼 보이면 **중력 토크가 없는 `joint1`/`joint7` 단독 명령**으로 명령 경로부터 가른다. (`t1` 6축 그리퍼에서는 막힌 쪽이 접촉축(2·3·5·6)에만 잔차를 남긴다 — 이력 파일 §B-12~14.)
6. **`stamp` 오프셋의 산포를 '지터'로 읽지 않는다.** 시뮬레이터가 **33.5초마다 약 1초 멈추고**(A-17) 그 사이 조금 빠르게 진행해서 오프셋은 **톱니**를 그린다(p2p 약 1.5 s). 창을 어디에 걸치느냐에 따라 평균이 크게 달라진다 — **180초 이상 관측해 정지를 5회 담는다.**
7. **진행률(`stamp_rate`)을 끝점 두 샘플로 재지 않는다.** 톱니 진폭이 잡음보다 커서 끝점 추정은 ±2% 가 흔들린다. `fb_stamp.py` 의 회귀값을 쓴다.
8. **정지 중에는 우리 Python 프로세스도 멈춘다 — 정지를 실시간으로 감지할 수 없다.** `rclpy.spin_once(timeout_sec=0.004)` 가 정지 길이만큼(약 1초) 블록되고, 스핀을 별도 스레드로 빼도 같다(DDS 대기가 GIL 을 잡는다). 귀결 둘: ① 정지 구간에 무언가를 **주입하는** 시험은 구독을 가진 Python 프로세스로는 할 수 없다. ② `spin_once` 체류시간이나 수신 공백으로 정지를 **사후에** 재는 것은 유효하다 — `fb_stall_when.py` 가 그렇게 한다. 해제 직후에는 **캐치업 발행**이 몰려 들어온다.
9. **발행 주기는 시뮬레이터 XML 로 정하는 설정값이다** — 고정 상수가 아니다. `r2` 는 `VariableModel/r2__panda_robotiq_ref_1_vm.xml` 의 `<ROS2_Topic Hz="0">`(**0 이면 약 50 Hz 로 나온다**), 카메라는 `r2__RGBCamera_1_vm.xml` 의 `Publish_Frequency="10"`·`Frequency="10"` 이다(`t1` 은 `t1__` 파일, 2026-09-17 현재 `Hz="50"`). 관측이 낮게 나왔다고 기준선을 고치지 말고 **설정을 먼저 확인**한다. **XML 은 시뮬레이션(Play) 시작 시점에 다시 읽힌다** — 앱 내 재시작으로 충분하다. 파일은 **BOM + CRLF** 이므로 편집 시 보존한다. ⚠️ **새 빌드는 값을 되돌려 온다** — `MMR-Build_260929` 의 `t1` 은 `Hz="10"` 으로 왔고(관절 보고 10.5 Hz) 50 으로 고쳐야 했다. ⚠️ **같은 값이 두 파일에 있다** — `BlockParameter/<씬>__panda_robotiq_ref_1_bp.json` 의 `{"Name":"Hz"}` 는 모델러가 읽는 쪽이라, vm.xml 만 고치면 **모델러로 씬을 저장할 때 되돌아갈 수 있다**(09-29 회차에서 bp.json 은 10 으로 남았다).
10. **팔만 안 움직이면 `Player.log` 부터 본다 — 시뮬레이터는 못 푼 명령을 조용히 버린다 (2026-09-14).** `/input/panda_joint` 의 `JointState` 에서 **`velocity` 가 비어 있으면** Unity 쪽 `JointStateMsg` 역직렬화가 `ArgumentException: Offset and length were out of bounds` · `OverflowException` 으로 실패하고 **ROS 쪽에는 아무 에러도 없다.** 그리퍼(`Float64MultiArray`)는 같은 순간에도 움직여 "명령 경로는 산다"로 오판하기 쉽다. 필드 조합 실측(joint7 +0.1 rad): name+position → **이동 0 · 예외 +62**, +velocity 0 → **+0.1000 rad · 예외 0**. **`velocity` 만 0 으로 채우면 된다** — 우리 쪽 발행부 전부가 그렇게 하며, **새 스크립트가 `JointState` 를 직접 만들면 같은 줄을 넣는다.** 로그 위치: `C:\Users\<user>\AppData\LocalLow\MetaMotionX\MetaMotionRobot\Player.log`(WSL 에서 `/mnt/c/Users/<user>/AppData/LocalLow/...`). **앱을 재기동하면 덮어써진다** — 옛 회차와 대조하려면 먼저 복사해 둔다.
11. **`ros_tcp_endpoint` 는 우리 launch 가 띄우지 않는다 (2026-09-17).** 시뮬레이터를 재시작했는데 endpoint 가 없으면 `readiness_gate` 가 *"Waiting for the simulator: first message on '/output/panda_joint' (timeout 60s)"* 로 끝나고 **launch 전체가 종료**된다. 이때 `Player.log` 끝에는 `Connection to 127.0.0.1:10000 failed … 연결을 거부` 가 계속 반복된다 — ROS 쪽만 보면 "시뮬레이터가 발행을 안 한다"로 보인다. **`ss -ltnp | grep :10000` 으로 먼저 확인**하고, 없으면 띄운다(§0 전제). 이미 떠 있는데 또 띄우면 포트가 충돌한다. endpoint 가 뜨면 Unity 는 스스로 재접속하며, 직후 `Not registered to publish topic` 몇 줄은 정상이다.
12. **설치본이 소스보다 낡았을 수 있다 — `install/` 은 링크가 아니라 복사본이다 (2026-09-17).** C-10 에서 `rdfp_collect.launch.py` 가 *"launch configuration 'enable_image_recorder_node' does not exist"* 로 첫 노드만 띄우고 멈췄는데, 원인은 설치본이 **09-08 판**, 소스가 **09-13 판**이었던 것이다(옛 판은 `backend:=` 인자도 모른다). **인수 전에 `colcon build --packages-select rdfp_msgs robot_control rdfp` 로 맞춘다.** 설정 파일(`config/backends/*.yaml` 등)도 같다 — 고친 뒤 재빌드하지 않으면 노드가 옛 값을 읽는다. ⚠️ **`rdfp_msgs` 를 빼면 안 된다 (2026-09-29)** — 설치본에 `MotionEvent`·`MotionTrajectory`(R1·R2, 09-18 신설)가 없어 `ee_pose_node` 가 `ImportError: cannot import name 'MotionEvent'` 로 **죽고 `/ee_pose` 가 한 건도 오지 않았다**(C-6 이 0건). launch 는 함께 죽지 않으므로 증상은 그 노드만 조용히 없는 것이다.
13. **관절 보고가 2~3건씩 묶여 도착한다 (A-21, 2026-09-17).** stamp 간격은 20 ms 로 고르지만 수신은 약 48 ms 마다 몰려 온다. **수신 시각으로 재는 값**(dead time, 정착 판정, servo 되읽기)은 그 간격만큼 뭉개진다 — B-6·B-13 의 dead time 이 약 31 ms 와 약 52 ms 두 무리로 갈리는 것이 그 흔적으로 보인다. 데이터셋은 stamp 로 정렬하므로 영향이 없다 — **우리 스택은 stamp 를 수신 시각이 아니라 시뮬레이터 stamp + 오프셋으로 정렬하므로**(§A-9 상세) `/joint_states`·카메라 stamp 는 이 묶음과 무관하다. `joint_state_fusion` 을 `stamp_source:=now` 로 되돌리면 절반 넘는 stamp 가 5 ms 안에 몰린다.
14. **씬의 솔버 프로세스가 떠 있는지 먼저 센다 — 없어도 토픽은 정상으로 보인다 (2026-09-29 오진).** `r2` 는 `solver/RecurDyn/SolverTCPServer.exe`, `t1` 은 `solver/Crisp/CrispSolver.exe` 가 돌아야 한다. **솔버 없이도** Unity 는 `/output/*` 를 **50 Hz 로 발행하고**(값이 전부 `0.0000` 에 고정된 채) `/clock` 도 진행하며, 명령을 보내면 `Player.log` 에 `[PandaCommandTopicApplier] 토픽 명령 감지 → 토픽 모드 전환` 까지 찍힌다 — **팔·그리퍼만 0 % 로 안 움직인다.** 그 증상은 벤더 A-4(수신 경로 고착)와 구별되지 않아 실제로 A-4 재현으로 오판했다. 지문 셋: ① **전 관절이 정확히 0.0000 이고 변하지 않는다**(정상 회차는 차트 종료 자세에 있다) ② `tasklist.exe | grep -iE "SolverTCP|Crisp"` 에 그 씬의 솔버가 없다 ③ A-17 정지가 **2.1 s 로 균일**해진다(솔버 응답을 기다리는 것으로 보인다 — 정상은 1.1~1.5 s 이고 편차가 있다). ⚠️ **다른 씬의 솔버가 남아 있을 수 있다** — 09-29 에 `CrispSolver.exe` 만 떠 있는 채로 r2 를 띄워서, 그 프로세스를 보고 "솔버는 돌고 있다"로 읽었다. **씬에 맞는 이름인지** 본다.
15. **씬을 바꾸면 우리 설정도 함께 바꾼다 (2026-09-17).** 순서: ① 시뮬레이터를 **닫고** `Database/SolverConfig/SolverConfig.json` 의 `MsFile` 을 바꾼다(**앱이 이 파일을 직접 쓰므로** 실행 중에 고치면 덮어써질 수 있다) ② `config/backends/functionbay.yaml` 의 `solver` 와 `gripper.profile_file`(`functionbay_gripper_{recurdyn,crisp}.json`)을 바꾸고 **`robot_control` 을 재빌드**한다 ③ 시뮬레이터를 띄운 뒤 **ROS 스택을 `kill_stack.sh --ros` 로 정리하고 다시 띄운다**(sim 시계가 0 으로 되감겨 살아남은 노드의 TF 버퍼가 `TF_OLD_DATA` 를 낸다). 확인은 기동 로그의 `convention: solver=RecurDyn scene=r2` 한 줄이다. 안 바꾸면 그리퍼 노드가 보고 축 수(2 대 6)와 선언을 대조해 **명령을 거부한다.**

### A-9 상세 — stamp 시간 기준은 **회차 속성**이다

| 분류 | 조건 | 뜻 |
|---|---|---|
| `wall-clock` | \|stamp − 수신시각\| < 5 s | 벽시계 epoch — 우리 노드·데이터셋과 같은 시간축 |
| `elapsed-since-start` | stamp − 수신시각 ≈ −(현재 epoch) | 시뮬레이터 기동 후 경과시간. 재시작마다 0 부터 |
| `skewed` | 그 사이 | 두 머신 시계 차이 |

**같은 빌드·같은 씬·같은 설정에서 벽시계 ↔ 경과시간이 오갔다**(§G.1a). 2026-09-17 은 두 솔버 모두 **경과시간**이었다. 빌드 이름으로 예측할 수 없다. 게다가 **벽시계 회차에도 원 stamp 는 실제 시각에서 초 단위로 흔들린다** — 2026-09-03 벽시계 회차의 `수신 − stamp` 가 −0.79 ~ +1.46 s 였다. 정지(A-17) 동안 sim 시각이 멈추고 정지 사이에는 5~7 % 빨리 가기 때문이다.

#### 우리 스택은 경계에서 stamp 를 벽시계로 정렬한다 (2026-09-17)

| 구성 | 하는 일 |
|---|---|
| `joint_state_fusion` (`stamp_source: aligned`, 기본) | 원 stamp 에 **오프셋**을 더해 `/joint_states` 로 낸다. 오프셋 = `수신 시각 − 원 stamp` 의 **최솟값**(0.5 s 창) — 묶음 대기·전달 지연이 빠진다. 수신 공백 0.3 s 초과(정지)면 창을 비운다. 표본마다 `sensor_msgs/TimeReference`(`header.stamp`=정렬 시각, `time_ref`=원 stamp)를 `/functionbay/stamp_reference` 로 낸다 |
| `fb_camera_restamp` | `/camera_image/compressed` 를 받아 **sim stamp 가 가장 가까운 관절 짝의 오프셋**으로 재stamp 해 `/camera_image_aligned/compressed` 로 낸다. 뒤쪽 짝이 올 때까지 보류(중앙 45 ms, 최대 2 s) |
| 공통 | 출력 stamp 가 **거꾸로 가지 않게** 누른다 (정지 직후 오프셋 변화로 역순이 날 수 있다) |
| 소비자 | 세션 레코더 · `camera_republish` 는 프로파일 `camera.compressed_topic`(=중계 출력)을 받는다. 원본은 `simulator.camera_compressed_topic` |

**정렬 stamp 의 뜻은 "시뮬레이터가 그 표본을 만든 벽시계 시각"** 이다. sim 간격을 보존하지 않는다 — 정지 사이 sim 이 빨리 가므로 20 ms 짜리 sim 간격이 벽시계로 19~20 ms 대부분, 약 10 % 는 13~15 ms 로 기록된다. 벽시계로 찍히는 명령 · `/session` 과 짝짓기에는 이 축이 맞다. 회차의 기준(벽시계/경과시간)을 몰라도 된다 — 오프셋이 수 ms 거나 epoch 규모로 잡힐 뿐이다.

**기준선 실측 (2026-09-17, 경과시간 회차, 100 s · 정지 3회)**

| 항목 | 값 |
|---|---|
| `/joint_states` stamp | **벽시계** · 역순 0 · 5 ms 미만 간격 0.12 % · 수신보다 중앙 14.0 ms 앞섬 (p99 39.4 ms) |
| 카메라 중계 | 959 → 958장 (끝의 1장은 보류 중) · 보류 중앙 45.5 ms · 역순 0 |
| 카메라 ↔ 관절 관계 | 프레임이 쓴 오프셋 − sim 짝 오프셋 = **958장 전부 0.000 ms** |
| 명령 ↔ 관측 (C-10) | 둘 다 벽시계 · **stamp 만으로** 잰 계단 응답 dead time 33.6 ms · τ 94.5 ms |
| 세션 레코더 (C-10) | 946장 · 98.7 s · 역순 0 |

**확인은 기동 로그 한 줄과 C-4 다** — `joint_state_fusion` 이 `stamp offset established: +1789622903.335 s (simulator stamps look elapsed-since-start)` 처럼 오프셋과 원 stamp 기준을 남긴다. `fb_checkup` `[3]` 은 **원 stamp** 를 보므로 벤더 추적(B-13)용으로 계속 적는다.

**되돌리기** — `panda_functionbay.launch.py` 의 `stamp_source` 를 `auto` 로, 프로파일 `camera.compressed_topic` 을 원본으로 바꾸고 `robot_control` 을 재빌드한다. 그러면 아래 문제가 돌아온다.

#### 정렬이 꺼진 채 경과시간 회차면 깨지는 것

- **데이터셋** — 적재가 `header.stamp` 로 에피소드 창을 거르므로 **rosbag 에는 남고 DB 에만 안 들어간다 — 조용하다.** `sessions.start_ts` 가 1970년이 되고, 재시작마다 0 부터라 `UNIQUE (start_sec, start_nanosec)` 가 세션 간에 충돌해 `on_existing_episode: skip` 이 **에러 없이 건너뛴다.**
- **명령·관측의 시간축이 갈린다** — `/joint_states` 는 경과시간, `/target_joint_cmds` · `/session` 은 벽시계다.
- **세션 레코더가 구간을 못 가른다** — 이미지 stamp 를 `/session` stamp 와 비교하기 때문이다.
- `stamp_source:=now` 는 대안이 못 된다 — 관절 보고가 묶여 도착해(A-21) stamp 가 몰리고, 카메라는 여전히 원 stamp 다.

`use_sim_time` 은 켜지 않는다 — 경과시간 회차에만 맞고, 시뮬레이터 재시작마다 `/clock` 이 0 으로 되감기며, `/clock` 자체도 묶여 오고 13.88 ms 단위다. 근본 해결은 벤더 B-13(시간축 고정)과 A-5(정지 제거)다 — 둘 다 반영되면 오프셋이 상수가 되어 정렬은 사실상 항등이 된다.

### A-15 상세 — `/clock` 은 있지만 **lockstep 이 아니다**

`/clock` 은 71.96 Hz, 증분 13.89 ms(시뮬레이터 내부 스텝 약 72 Hz)로 그냥 흘러간다 — 시뮬레이터가 우리를 기다리지 않으므로 sim time 의 본래 이점(스텝 동기)은 없다. 보고 주기를 바꿔도 이 값은 안 변한다.

**쓸모는 A-17 계측기다.** 수신 공백 동안 `/clock` 이 거의 진행하지 않는 것으로 **시뮬레이션 자체가 멈춘다**는 것을 직접 확인한다.

`use_sim_time` 을 켤지는 A-9 에 달렸다(위). 벽시계 회차에 켜면 우리 노드는 `/clock`(경과시간)을, 시뮬레이터 메시지는 벽시계를 써서 TF·데이터셋이 동시에 깨진다.

### A-6 상세 — 카메라는 `CompressedImage` 다

`/camera_image/compressed`(`sensor_msgs/CompressedImage`, `format=jpeg`, 640×480, 약 26 KB)로 발행한다(2026-09-08 부터; 그 전 빌드는 `/camera_image` `bgr8`). **대역폭이 36배 작다**(9.2 → 0.25 MB/s).

| 소비자 | 배선 |
|---|---|
| stamp 중계 `fb_camera_restamp` | 원본을 받아 관절과 같은 벽시계 축으로 재stamp 해 **`/camera_image_aligned/compressed`** 로 낸다 (§A-9 상세). **아래 소비자는 모두 이 출력을 받는다** — 프로파일 `camera.compressed_topic` |
| 세션 레코더 `rdfp_image_recorder` | 압축을 **직접** 받는다 — `FFMpegMp4Recorder(input_format='mjpeg')` 가 JPEG 을 풀지 않고 ffmpeg 에 넘겨 H.264 로 인코딩한다 |

### A-16 상세 — Unity 가 물체 TF 를 발행한다

**조작 대상 body 하나만**(`static="false"`) `world → peg_round_16` 으로 내보낸다. 고정물(`peg_hole_round_16` · `peg_tray_round_16`)은 `static="true"` 라 **없다** — 그 좌표는 `config/functionbay_fixtures.json` 이 갖는다. 로봇 링크는 발행하지 않으므로 우리 `robot_state_publisher` 와 충돌하지 않는다.

```bash
python3 - <<'PY'   # /tf 를 60 s 구독해 프레임쌍별 건수·주기·stamp 기준을 센다
import rclpy, time
from tf2_msgs.msg import TFMessage
rclpy.init(); n = rclpy.create_node('tf_probe'); pairs = {}
def cb(m):
    for t in m.transforms:
        k = (t.header.frame_id, t.child_frame_id); s = t.header.stamp.sec + t.header.stamp.nanosec * 1e-9
        e = pairs.setdefault(k, [0, s]); e[0] += 1; e[1] = s
n.create_subscription(TFMessage, '/tf', cb, 100)
t0 = time.time()
while time.time() - t0 < 60: rclpy.spin_once(n, timeout_sec=0.05)
for (p, c), (cnt, s) in sorted(pairs.items(), key=lambda kv: -kv[1][0]):
    print('%-14s -> %-20s %5.2f Hz  %s' % (p, c, cnt / 60.0, 'wall' if abs(time.time() - s) < 1e6 else 'elapsed'))
PY
```

**기준선 출력**: `world → peg_round_16` 27.2 Hz(1632건, 최대 공백 1124 ms = A-17 정지, 역행 0). `panda_link*` 쌍들은 우리 `robot_state_publisher` 몫이다(같은 60 s 에 16.6 Hz).

**회전은 ROS `xyzw`** 이다(알려진 자세로 검증, 2026-09-08). 단 **`w` 가 음수로 올 수 있다** — `q` 와 `−q` 는 같은 회전이라 tf2 는 정상이지만, 성분을 그대로 비교해 항등을 판정하는 코드는 오판한다. **XML 에 TF 설정 요소가 없다** — 벤더가 코드로 구현했으므로 조작 대상이 늘면 다시 문의해야 한다. 우리 쪽 `functionbay_scene_state_node` 가 이것을 `/scene/objects` 로 옮긴다. **`/scene/reset` 은 없다.**

### A-17 상세 — 시뮬레이터 주기적 정지 (가장 큰 미해결)

**시뮬레이터가 33.5초마다 약 1초 완전히 멈춘다.** 그동안 모든 토픽이 한 건도 오지 않는다.

**기준선 (2026-09-17)** — `fb_stall_when.py` 로 정지마다 시작·끝을 벽시계로 찍었다.

| 항목 | 값 |
|---|---|
| 정지 주기 | **33.44 ~ 33.63 s** (7구간, 편차 **0.4 %**) |
| 정지 지속 | **1.057 ~ 1.148 s** (8회). 180 s `fb_checkup` 창에서는 최대 **1.45 s** |
| 구조적 손실 | **3.2 %** (= 1.07 / 33.5). 180 s 창 실측 **3.3 %** |
| 두 솔버 차이 | **없다** — 같은 날 `t1` 60 s 창 3.8 %, `r2` 3.6 % |

**퍼센트가 창마다 다르게 나오는 것은 창 정렬 artifact 다.** 1초짜리 정지가 33.5초마다 오므로 120 s 창은 3회, 150~180 s 창은 5회를 담는다. 시뮬레이터가 회차마다 나빠진 것으로 읽지 않는다 — 다만 **지속 시간 자체는 회차마다 달랐다**(0.9~2.2 s, §G.1a).

**시뮬레이터 측 현상이라는 근거:**

1. 정지 중 `header.stamp` 와 `/clock` 이 거의 진행하지 않는다 → 전송 지연이 아니라 **시뮬레이션이 멈춘다.**
2. 모든 토픽이 수십 ms 안에 동시에 멈춘다.
3. 발행 주기를 절반으로 낮춰도 정지 주기가 1% 미만 변한다(2026-09-03) — 발행 부하가 원인이 아니다.
4. 정지를 제외하면 sim 시각 기준 발행률이 설정값과 일치한다.

**우리 쪽에서 배제한 원인 (2026-09-17)** — 벤더 조사 범위를 좁히려고 적는다.

| 가설 | 반증 |
|---|---|
| **GC** (Unity 6000.0.59f2 · Mono) | ① `MetaMotionRobot_Data/boot.config` 에 `gc-max-time-slice=3` — **Incremental GC 가 켜져** 프레임당 3 ms 로 잘린다. ② 주기 편차 **0.4 %** 는 할당 임계가 아니라 **타이머의 서명**이다. ③ 정지를 사이에 둔 프로세스 메모리가 **바이트까지 같고**(704,937,984), 200 샘플 변동이 **0.2 %** 다 |
| **`Resources.UnloadUnusedAssets()`** | `Player.log` 의 두 번이 **모두 솔버 초기화 이전 로딩 단계**다. 주기적이지 않다 |

**남은 단서** — 솔버는 **별도 프로세스**다(`[SolverTCPConnector]` `127.0.0.1:10001`, `solverStepDt=0.2`, 비동기 워커). `Player.log` 에 `updateTime 0.105~0.162s 뒤처짐 — 현재 시각으로 재정렬(폭주 방지)` 이 수백 줄 찍히지만, 정지 구간과 시각을 맞춰 보면 **겹치지 않았다** — 로그에 타임스탬프가 없고 flush 가 늦어 "무관하다"가 아니라 "이 방법으로는 못 붙였다"로 읽는다.

**데이터 결손은 없다** — sim 시각 기준 `header.stamp` 는 연속이다. 깨지는 것은 **실시간성**이다: 원격 조작 중 1초 무반응, 접촉 동역학 속도 불균일, 벽시계 기준 시간제한의 오발동.

> **`teleop_retarget` 의 `pedal_timeout` 을 켤 때 2.5 s 이상으로 잡는다.** 정지보다 짧으면 정지 때마다 하트비트가 끊겨 클러치가 자동 해제된다. **§0 함정 8 을 함께 읽는다.**

**수용 기준** — 180초 관측에서 **0.3 s 넘는 수신 공백 0회**. 벤더 발송 문안: [펑션베이_벤더_메일_20260903_정지.md](../../archive/functionbay/펑션베이_벤더_메일_20260903_정지.md) (발송 완료 · 회신 대기, 요청서 §A-5 가 최신 수치를 갖는다).

```bash
python3 - misc/fb_stamp/<라벨>.json <<'PY'   # 관절 수신 묶음 분석
import json, sys, statistics as st
from collections import Counter
rx = [r[0] for r in json.load(open(sys.argv[1]))['raw']['/output/panda_joint']]
bursts, cur = [], [rx[0]]
for a, b in zip(rx, rx[1:]):
    if b - a < 0.005: cur.append(b)
    else: bursts.append(cur); cur = [b]
bursts.append(cur)
gaps = [b[0] - a[-1] for a, b in zip(bursts, bursts[1:]) if b[0] - a[-1] < 0.3]
print('평균 %.2f건/묶음, 분포 %s, 간격 중앙 %.1f ms' % (len(rx) / len(bursts), dict(sorted(Counter(map(len, bursts)).items())), st.median(gaps) * 1000))
PY
```

### B-12 ~ B-14 (그리퍼)

### B-17 상세 — 말림은 **중력 보상이 살아 있는지 보는 창**이다

순수 수직 이동인데 손끝이 로봇 쪽으로 말렸다가 풀리는 현상이다. **보상 OFF 기준(2026-09-11): 1.6초에 −7.14 mm** 까지 말렸다가 풀리고 도달 오차 12.25 mm. 파지 정확도를 직접 망친다. 기존 항목(B-3·B-4 정지 오차, B-8 lag, B-9 비대칭)은 **이동 중 손끝이 옆으로 새는 양**을 보지 않는다.

**기준선 (보상 ON, `(0.50, 0.00, 0.12)` 에서 +45 mm):**

```
 t(s)    0.00  0.40  0.80  1.20  1.60  2.40  3.50  5.00
dz(mm)   0.00  1.27  3.39  6.89 13.24 28.81 43.62 45.00
dx(mm)  0.000 0.015 0.028 0.051 0.080 0.106 0.038 0.002
```

보상은 **조용히 망가질 수 있다** — 오류 없이 "팔이 몇 mm 어긋난 곳에 선다" 뿐이다.

| 관측 | 원인 |
|---|---|
| 말림이 **수 mm 로 복귀** | 보상이 꺼졌다 — 프로파일 키 누락, URDF 경로 파손, **설치본이 낡았다**(함정 12) |
| 말림이 **커졌는데 부호가 반대** | **이중 보정** — 벤더가 A-1 을 반영했는데 우리 보상을 안 껐다 |
| 말림은 작은데 **도달 오차만 큼** | `Kp` 가 2000 이 아니다 — A-19 |

> **B-3·B-4 의 보상 OFF 값으로는 "꺼짐"을 못 가른다** — 꺼지면 원래 처짐으로 돌아가는데 그 값이 기준선에 적혀 있기 때문이다. B-4 의 **보상 ON 행**과 B-17 이 그것을 가른다.

### B-18 상세 — peg-in-hole 왕복이 회피책 없이 된다

`./fb_move_peg.py` 한 줄이다. 목적지를 안 주면 현재 위치의 반대쪽 고정물을 고른다(`--dry-run` 은 계획만).

### C-8 — servo 경로를 키보드 없이 확인한다

servo 는 **`start_servo` 만 해도 명령 없이 팔을 끌고 가므로** 시험이 끝나면 곧바로 `stop_servo` 하고 `ready` 로 되돌린다.

```bash
python3 - <<'PY'
import rclpy, time
from std_srvs.srv import Trigger
from geometry_msgs.msg import TwistStamped
rclpy.init(); n = rclpy.create_node('c8_servo')
start = n.create_client(Trigger, '/servo_node/start_servo'); stop = n.create_client(Trigger, '/servo_node/stop_servo')
pub = n.create_publisher(TwistStamped, '/servo_node/delta_twist_cmds', 10)
start.wait_for_service(timeout_sec=10.0); rclpy.spin_until_future_complete(n, start.call_async(Trigger.Request()))
msg = TwistStamped(); msg.header.frame_id = 'panda_link0'; msg.twist.linear.z = 0.5
t0 = time.time()
while time.time() - t0 < 1.0:
    msg.header.stamp = n.get_clock().now().to_msg(); pub.publish(msg); rclpy.spin_once(n, timeout_sec=0.02)
rclpy.spin_until_future_complete(n, stop.call_async(Trigger.Request()))
PY
./scripts/functionbay/fb_recover.py 4.0
```

### C-10 상세 — 수집 계층에서 명령·관측·영상이 한 시간축에 모인다

2026-09-17 에 **처음으로 실제 시뮬레이터에서 통과**했다. 첫 시도는 0건이었는데 원인은 설치본이 낡은 것이었다(함정 12) — `rdfp` 를 재빌드한 뒤 `session_control_node` · `rdfp_image_recorder` · `target_joint_cmds_publisher` 가 떴고(`source='joint_state'`, 입력 `/input/panda_joint` — `backend:=functionbay` 가 프로파일에서 고른다), 팔을 움직이는 동안 `/target_joint_cmds` 가 통과했다.

같은 날 첫 통과 때는 `/target_joint_cmds` 가 벽시계, `/joint_states` 가 경과시간으로 **시간축이 갈려 있었다.** stamp 정렬(§A-9 상세)을 넣고 다시 쟀다:

- **명령과 관측이 같은 축이다** — `/target_joint_cmds`(수신 시각으로 재stamp, 벽시계)와 `/joint_states`(정렬, 벽시계)로 joint7 ±0.05 rad 계단 7개를 **stamp 만으로** 풀면 dead time 중앙 **33.6 ms**(20.3~44.7) · τ **94.5 ms**(81.9~114.8) 다. 수신 시각으로 잰 B-6·B-7(35.0 / 90.5 ms)과 같은 대역이다 — 축이 갈려 있으면 이 값이 수십 년이 된다.
- **세션 레코더가 정렬된 영상을 받는다** — 로그에 `subscribed to image topic (effective name=/camera_image_aligned/compressed …)`. 에피소드 98.7 s 에 946장, sidecar stamp 역순 0, 0.5 s 넘는 공백 3회(정지).

✅ **녹화 mp4 의 fps 선언을 소스에 맞췄다 (2026-09-17).** 레코더가 프로파일 `camera.fps: 5` 를 따라 `r_frame_rate=5` 로 만들었는데 소스는 약 9.6 Hz 라, 34.75 s 분량 334장이 **66.8 s 영상**(1.9배 느린 재생)이 됐다. 시뮬레이터 XML `Publish_Frequency` 와 같은 **10** 으로 고쳤다. 실측 9.54~9.60 Hz 와의 차이로 mp4 시간축은 여전히 약 4 % 짧으므로 프레임별 시각은 sidecar stamp 로 읽는다(ACT 문서 §1.3). **XML 주기를 바꾸면 프로파일 `camera.fps` 도 함께 바꾼다.**

**내릴 때는 launch 프로세스에 `SIGINT` 를 보낸다** — `setsid` 래퍼 PID 로 보내면 자식 노드가 남는다. 뷰어를 켜면 WSLg 창이 뜨므로 헤드리스 확인에서는 `enable_image_viewer:=false` 로 끈다.

### `/ee_pose` 는 `grasp_center` 를 가리킨다

description 이 Panda Hand 라 기본 프레임 `panda_hand` 는 실제 파지점에서 **149 mm + 90°** 어긋난다. launch 가 `panda_link7 → grasp_center` 정적 TF 를 띄우고 `ee_frame` 을 그쪽으로 둔다. **`/ee_pose` 만 맞춰진 것이고 TF 형상·충돌은 여전히 Panda Hand 다.**

> ### ⚠ `/ee_pose` 로 데카르트 목표를 만들면 안 된다
>
> 데카르트 목표는 **MoveIt 그룹의 tip link(`panda_link8`)** 기준으로 해석되는데 `/ee_pose` 의 프레임은
> launch 의 `ee_frame` 이 정한다 — 둘이 **z 로 149.3 mm** 어긋난다(C-5). `fb_ee.py` 가 실제로 이것
> 때문에 +20 mm 상승을 −129 mm 하강으로 지령한 적이 있다. **측정과 지령은 같은 링크여야 한다.**
> (트윈의 `move_linear` 는 기본이 `grasp_center` 기준이라 예외다 — CLAUDE.md.)
