## 1. 무엇을 만드는가

**연산 하나가 끝날 때마다, 그 연산이 무엇이었고 어떻게 끝났는지를 한 건의 메시지로 남기는 채널**이다. 연산마다 한 건이고, R1 의 실행 궤적과 **연산 식별자로 짝짓는다**.

왜 필요한가 — **실행 궤적만으로는 레이블을 만들 수 없기 때문이다.** 수집 설계 D5 가 정한 규칙은 구간마다 다르다:

| 구간 | plan(τ) |
|---|---|
| 연산 실행 중 | 실행 궤적 보간 |
| 정상 종료 뒤 | 궤적의 끝점 |
| **중단 · 실패 뒤** | **중단 시각의 궤적 값** |
| 첫 연산 이전 | 에피소드 시작 때의 관절 관측 |

가운데 두 줄이 R2 를 요구한다. 실행 궤적은 **끝까지 갔을 때의 모습**이므로, 연산이 중간에 멈췄는지 · 멈췄다면 언제인지를 궤적만 보고는 알 수 없다. 그 정보가 없으면 **중단된 연산 뒤의 레이블이 "가지 않은 자리"를 가리킨다.**

**R1 과 역할을 나눈다.** 같은 값을 두 메시지에 두지 않는다 — 궤적 · 배율 · t₀ 는 R1 이 갖고, 연산 이름 · 해석된 목표 · 결과 · 끝난 시각은 R2 가 갖는다. **실효 속도 배율은 R1 이 갖는다** — 미구현 목록 R2 행 · 생성 설계 권고 2 · 수집 설계 §6 이 그것을 R2 에 두었으나 R1 이 `velocity_scaling` · `time_scaling` 으로 이미 싣는다 — **세 문서를 고쳤다(2026-09-18).** `failed` 연산에는 배율이 안 남지만 계획 구간 자체가 없으므로 레이블에 영향이 없다.

**팔 동작 연산만 싣는다 — 그리퍼는 뺀다 (결정, 2026-09-18).** [좌표 공간 문서](학습_데이터의_좌표_공간_비교.md) §5.7 과 생성 설계 M3 은 `move_gripper_to_target` 의 심볼도 이 채널에 두었지만, 그리퍼 명령은 **이미 stamp 있는 이벤트**(`/gripper_cmds`)로 녹화되고 성패는 `/gripper_states` 의 `at_goal` 이 판정하므로 R2 가 더할 것이 없다. ACT 의 그리퍼 레이블도 `/gripper_cmds` 0차 유지다([ACT 문서](ACT_학습_샘플_구성.md) §3.2). **대가는 하나다** — 그리퍼가 `TIMEOUT` 으로 끝난 경우가 **어느 채널에도 안 남는다**(`gripper_cmds` 는 보낸 것만, `gripper_states` 는 상태만 싣는다). 그 판정이 필요해지면 R2 가 아니라 그리퍼 계약에서 다룬다. **좌표 공간 §5.7 을 이에 맞춰 고쳤다.**

⚠️ **"중단"은 드문 예외가 아니다.** 실패가 섞인 데이터를 일부러 모으는 것이 이 플랫폼의 목적 중 하나이고(생성 설계 §9.1 의 섭동 주입), 실제로 접촉 작업에서는 절차가 *"미착석이면 쥔 채로 두고 실패를 돌려준다"* 처럼 **실패로 끝나는 것이 정상 경로**다. 중단 처리를 나중으로 미루면 그 데이터가 통째로 못 쓰게 된다.

## 2. 현재 코드 — 연산의 끝을 아는 세 자리

**"자리"는 코드 상의 위치다** — 연산이 끝났다는 사실과 *어떻게* 끝났는지를 관측할 수 있는 함수·콜백을 말한다. R1 문서 §2 는 궤적이 만들어지는 **경로**를 넷으로 셌지만 **끝을 아는 자리는 셋**이다. 수가 안 맞는 이유가 양쪽으로 하나씩 있다 — isaac 의 두 경로는 **같은 콜백으로 합류**하고, 펑션베이는 반대로 **실행과 계획이 갈라진다**(계획 실패가 스트리머에 닿지 않는다). 자리마다 끝의 모양도 다르다.

| 경로 | 끝을 아는 자리 | 정상 종료 | 중단 · 실패 |
|---|---|---|---|
| **isaac 관절 공간** (`move_to_named_target` · `move_to_joints`) | **① `MoveGroupJtcClient` 의 결과 콜백** (`execute_trajectory_async`) | `MoveItErrorCodes.SUCCESS`(1) | 그 밖의 코드. 2026-09-18 실측에서 접촉 뒤 `CONTROL_FAILED`(−4) 를 봤다 |
| **isaac 데카르트** (`follow_trajectory`) | **① 같은 자리** | 같음 | 같음. 계획 단계 실패는 `fraction` 미달로 먼저 걸린다 |
| **펑션베이 실행** (관절 공간 · 데카르트) | **② `TrajectoryStreamer.stream` 안** | 샘플을 끝까지 발행했다 | `stop_event` 로 루프를 빠져나왔다 |
| **펑션베이 계획** (같은 두 연산) | **③ `MoveGroupJgpcClient._on_plan_done`** | — | 오류 코드 · `fraction` 미달 · 예외. **스트리머에 닿지 않는다** |
| (공통) 취소 | **자리가 따로 없다** — `cancel()` · `stop()` 은 ①·② 를 건드릴 뿐이고, 끝은 그 둘에서 관측된다 | — | ① 의 결과 코드 · ② 의 `stop_event` |

**이 셋이 그대로 §3.2 의 발행 지점 셋이 된다.**

**네 가지가 어긋나 있다.**

1. **끝의 모양이 다르다** — JTC 는 `MoveItErrorCodes`, 스트리머는 **정수(발행한 명령 수)** 다. 하나의 `result` 로 모으려면 어느 쪽이든 변환이 필요하다.
2. **중단 *시각*을 아무도 안 남긴다 — 그리고 호출자는 잘렸는지조차 모른다.** `stream` 은 `published`(정수)만 돌려주고 **계획한 샘플 수를 안 돌려준다.** 그 값은 module-private `_build_samples` 안에 있고, 균일 격자 뒤에 `duration` 을 덧붙이는 규칙까지 있어 호출자가 다시 계산할 수 없다. 즉 위 표의 "샘플을 끝까지 발행했다"를 **판정할 주체는 `stream` 안뿐이다.** JTC 쪽은 결과 코드만 주고 언제 멈췄는지는 안 준다.
3. **연산 식별자도 t₀ 도 새어 나오지 않는다** — R1 의 `MotionTrajectoryPublisher.publish()` 는 식별자를 돌려주지만 현재 호출부(`_publish_motion_trajectory`, `TrajectoryStreamer.stream`)가 **그 반환값을 버린다.** 게다가 `stamp=None` 으로 부르면 **발행자 안에서** t₀ 를 찍으므로 호출자는 그 값을 아예 모른다 — isaac 의 `truncated_at` 이 `끝난 시각 − t₀` 라 이것도 함께 이어야 한다(§3.3).
4. **펑션베이의 계획 실패는 스트리머에 닿지 않는다** — `_on_plan_done` 이 `result_future` 에 예외를 걸고 끝나므로 `stream` 이 아예 안 불린다. 비-`streamed` 변형(`move_to_joints_async` 등)도 전부 `*_streamed_async` 로 위임하므로 **네 진입점 모두** 그렇다. 그래서 펑션베이는 발행 지점이 하나가 아니다(§3.2).

## 3. 구현 작업

### 3.1 메시지 형식과 토픽 이름 (Q1 의 남은 절반)

R1 문서 §3.1 이 남긴 뼈대는 다음과 같다.

```
std_msgs/Header header    # 연산이 끝난 시각 (정상 종료 · 중단 · 실패 모두)
string operation_id       # MotionTrajectory 와 같은 값
string operation          # move_to_joints · move_to_named_target · follow_trajectory
string result             # succeeded · aborted · failed
# + 해석된 목표 (관절값 또는 pose) — R2 설계에서 정한다
```

**토픽 이름 — `motion/event` (결정).** R1 이 `motion/trajectory` 를 쓰므로 같은 묶음에 둔다. 규약([topic_naming_contract.md](../../topic_naming_contract.md))을 R1 과 같은 방식으로 따른다 — 루트 상대(앞에 `/` 없음), 구현체 이름 없음, 메시지 하나에 이벤트 하나라 **단수**. `motion/` 으로 묶는 것이 R1 과 짝이라는 관계를 이름에 드러낸다.

> 대안으로 `motion/operation` 도 검토했다. `event` 가 나은 것은 이 채널이 **연산 그 자체가 아니라 연산의 종료 사건**을 싣기 때문이다. `operation` 이면 "연산을 시키는 채널"로 읽힐 여지가 있는데, 명령 채널이 아니다(명령은 트윈 REST 로 들어온다).

**메시지 타입 — `rdfp_msgs/MotionEvent` (결정, 신설).** R1 과 같은 근거다. 적재가 토픽 이름이 아니라 **메시지 타입**으로 writer 와 테이블을 고르므로(규약 §2.4), 전용 타입이어야 채널의 뜻을 타입이 지킨다. 이름도 R1 과 짝을 맞춘다(`motion/trajectory` ↔ `MotionTrajectory`, `motion/event` ↔ `MotionEvent`).

#### 결정 (2026-09-18)

| 채널 | 토픽 이름 | 메시지 타입 |
|---|---|---|
| R1 실행 궤적 | `motion/trajectory` | `rdfp_msgs/MotionTrajectory` (구현 완료) |
| **R2 연산 이벤트** | **`motion/event`** | **`rdfp_msgs/MotionEvent`** (신설) |

위 둘로 정했다. **이로써 미구현 목록 Q1 이 닫힌다** — R2 구현을 막고 있던 유일한 선행이었다. 구현할 때 [토픽 이름 규약](../../topic_naming_contract.md) §2.1 의 정규 이름 표에 `motion/trajectory` 형제 행으로 올린다.

**해석된 목표도 (a) 타입별 필드 + `target_frame` 으로 정했다 — 아래 소절.** 이로써 `result` 의 경계 · `operation` 의 어휘 · `target_*` 의 구성이 모두 확정이라, **아래 「메시지 정의」를 그대로 `.msg` 로 옮기면 된다.** 남는 자유도는 `reason` 의 어휘뿐이고(Q4′) 그 값은 레이블 계산에 쓰이지 않는다.

#### 해석된 목표를 어떻게 실을 것인가 — 선택지 셋

"해석된 목표"는 **트윈이 받은 입력이 아니라 클라이언트가 실제로 겨냥한 값**이다. 예를 들어 `move_to_joints` 에 관절 하나만 줘도 클라이언트가 나머지 여섯을 현재값으로 채우므로(`_complete_joint_values`), 실제 목표는 일곱 개다. 그 차이를 남기지 않으면 레이블이 "무엇을 하려던 동작인가"를 잃는다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| **(a) 타입이 다른 필드를 둘 다 두고 판별자로 가른다** — `string target_kind`(`'joints'` \| `'pose'` — **어느 쪽을 봐야 하는지**) + `string[] target_joint_names` + `float64[] target_joint_values` + `geometry_msgs/Pose target_pose`. 여기에 **`string target_frame` 이 아래 소절에서 더해져 최종 5개**가 된다 | 스키마가 명시적이고 적재가 컬럼으로 바로 간다 | 한 쪽은 항상 비어 있다 |
| (b) JSON 문자열 하나 | 연산이 늘어도 메시지를 안 고친다 | **적재가 질의할 수 없다.** 타입 검사도 사라진다 — `rdfp_msgs` 의 다른 메시지가 쓰지 않는 방식이다 |
| (c) 목표를 싣지 않는다 (R1 궤적의 끝점으로 대신) | 가장 작다 | **중단된 연산에서 틀린다** — 끝점은 "가려던 곳"이고 실제로는 거기 못 갔다. 그리고 데카르트 목표의 자세 정보가 사라진다 |

**(a) 로 정했다 (2026-09-18).** (c) 가 매력적으로 보이지만 R2 가 존재하는 이유가 바로 중단 처리라 자기모순이고, (b) 는 적재·질의를 포기하는 대가가 크다. 아래 「pose 에는 프레임을 함께 싣는다」의 `target_frame` 까지 묶어서 한 결정이다.

##### ⚠️ pose 에는 프레임을 함께 싣는다

`geometry_msgs/Pose` 만으로는 **어느 프레임 기준인지 말할 수 없고, 그 답이 백엔드마다 다르다.** 트윈의 `_resolve_frame` 은 EE 프레임 목표를 **tip link 기준으로 옮긴 뒤** 클라이언트를 부르므로 클라이언트가 아는 것은 늘 tip 기준 pose 인데, **옮겨졌는지 아닌지가 갈린다** — 펑션베이는 `frames.ee: grasp_center` 라 사용자가 준 값에서 **149 mm 이동한 값**이고, isaac 은 프로파일에 `frames.ee` 가 없어 트윈 입력이 곧 tip 기준이라 **그대로**다. 필드 이름으로는 이 차이를 막을 수 없다.

그래서 `string target_frame` 을 함께 싣고 tip link 이름을 적는다. `geometry_msgs/PoseStamped` 를 쓰지 않는 것은 `header.stamp` 가 둘이 되어 *"어느 쪽이 끝난 시각인가"* 가 모호해지기 때문이다 — R1 이 `trajectory.header` 를 비운 것과 같은 이유다.

**TCP-도달점은 export 가 만든다.** [좌표 공간 문서](학습_데이터의_좌표_공간_비교.md) §5.7 은 `move_linear` 에 *"입력 pose 그대로"* 를, 관절 공간 연산에 *"트윈·클라이언트가 해석한 TCP pose"* 를 싣는다고 적었지만, **같은 절의 첫 문단이** *"데이터 계층은 FK 를 하지 않는다 — 스택 쪽 도구가 export 때 계산한다"* 고 못 박는다. R2 는 원칙 쪽을 따라 **관절 공간 연산에 관절값만, 데카르트 연산에 tip pose 만** 싣고 TCP 환산은 기구학 스냅샷(R3 · I2)을 가진 export 에 맡긴다. **좌표 공간 §5.7 을 이에 맞춰 고쳤다.**

#### 중단 시각을 어떻게 표현할 것인가 — 선택지 둘

D5 는 *"중단 시각의 궤적 값"* 을 쓰라고 한다. 그러려면 **중단이 궤적의 어느 시각이었는지**가 필요하다.

| 선택지 | 내용 | 판단 |
|---|---|---|
| **(a) 궤적 기준 경과 시간을 싣는다** — `builtin_interfaces/Duration truncated_at` | 소비자가 `L2(truncated_at)` 한 번으로 값을 얻는다. R1 의 `time_from_start` 와 같은 축이라 바로 맞는다 | **결정 (2026-09-18).** 스트리머는 발행한 샘플의 마지막 시각을 알고, JTC 는 `header.stamp − t₀` 로 얻는다 |
| (b) 끝난 벽시계 시각만 싣고 소비자가 뺀다 | 필드가 하나 준다 | 소비자가 t₀ 를 **다른 메시지에서** 가져와 빼야 한다. 두 메시지의 시계가 다르면(§6) 조용히 틀린다 |

정상 종료면 `truncated_at` 은 궤적 길이와 같고, 그 경우 굳이 안 봐도 된다.

#### `result` 의 경계 — 궤적을 컨트롤러로 넘겼는가

"시작조차 못 했다"를 사람 말로 두면 판정이 갈린다. **goal 거부와 시작 상태 허용 오차 위반(`CONTROL_FAILED`)은 R1 을 발행한 *뒤*에 온다** — `execute_trajectory_async` 가 `_publish_motion_trajectory` → `send_goal_async` → `goal_handle.accepted` 검사 순이기 때문이다. 둘 다 말로는 "시작 못 했다"인데 궤적은 이미 남아 있어서, 그대로 두면 §6 의 *"`failed` 는 짝이 없는 것이 정상"* 이 성립하지 않고 적재 검증(I5)의 고아 판정이 흐려진다.

**그래서 기준을 관측 가능한 것 하나로 바꾼다 — 궤적을 컨트롤러로 넘기려 했는가.**

| `result` | 기준 | 짝 궤적 | `truncated_at` |
|---|---|:-:|---|
| `succeeded` | 넘겼고 끝까지 실행했다 | 있다 | 궤적 길이 |
| `aborted` | **넘겼는데** 끝까지 못 갔다 — 취소 · 컨트롤러 실패 · **goal 거부** · **시작 오차 위반** | 있다 | 멈춘 시각 (한 점도 못 갔으면 **0**) |
| `failed` | **넘기지도 못했다** — 계획 실패 · 궤적 검증 실패 | **없다** | 0 |

레이블 값은 달라지지 않는다 — goal 거부든 계획 실패든 plan(τ) 는 "궤적 0초의 값을 유지"로 같다. 달라지는 것은 **짝 규칙이 정확해진다**는 점뿐이고, 그것이 I5 가 기댈 유일한 불변식이다.

⚠️ **"R1 메시지가 실제로 나갔는가"로 재면 안 된다.** `MotionTrajectoryPublisher.publish()` 는 발행 실패를 삼키고 `None` 을 돌려주므로(R1 §6 의 의도 — 기록이 동작을 막지 않는다), 그 기준으로는 **발행만 실패한 성공 동작**이 계획 실패와 같은 신호를 낸다. 기준은 어디까지나 **클라이언트가 넘기려 했는가**다. 마침 `_validate_trajectory` 가 발행보다 **앞**에 있어 잘못된 궤적은 R1 없이 `failed` 가 되고, 발행에만 실패한 연산은 `operation_id` 가 비어 I5 가 그것으로 가려낸다.

#### 메시지 정의 (확정)

```
# 팔 동작 연산 하나가 끝났다. 토픽 `motion/event` 로 연산마다 한 건 발행한다.
# 실행 궤적(R1, `motion/trajectory`)과 `operation_id` 로 짝지어 쓴다 — 그쪽이
# "무엇을 보냈나", 이쪽이 "어떻게 끝났나" 다.

# header.stamp 는 **연산이 끝난 시각**이다 (정상 종료 · 중단 · 실패 모두).
# 비워 두면 적재가 에피소드 창 밖으로 버린다.
#
# ⚠️ **레이블의 구간 끝이 아니다** — 결과를 받은 시각이라 goal tolerance 확인과
# 팔의 물리 지연(isaac 실측 120 ms)이 들어 있다. 구간 끝은 t₀ + truncated_at 로

#   'joints'        관절 목표값으로 이동 (관절 공간 계획)

string operation

#   'succeeded'  넘겼고 끝까지 실행했다
```

### 3.2 발행 지점 — 클라이언트인가 트윈인가

미구현 목록은 *"트윈 또는 클라이언트 발행부"* 로 열어 두었다. **R1 은 클라이언트로 정했고**, R2 도 같이 가는 것이 자연스럽지만 결론이 다를 수 있어 따로 따진다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| **(a) 클라이언트** (`MoveGroupJtcClient` · `MoveGroupJgpcClient` · `TrajectoryStreamer`) | **R1 과 같은 자리**라 `operation_id` 와 t₀ 를 그냥 넘길 수 있다. 트윈을 안 거치는 호출(스크립트 · 텔레오퍼레이션)도 덮는다. **중단 시각을 아는 유일한 자리다** | 트윈 REST 연산 이름을 모른다 |
| (b) 트윈 (`robot_twin/backends.py`) | 연산 이름 · 입력을 이미 갖고 있다 | **트윈이 보고하는 결과가 사실과 다른 경우가 셋이나 된다** — 아래 |
| (c) 둘 다 — 클라이언트가 내고 트윈이 이름을 주입 | 각자 아는 것만 낸다 | 배선이 늘고, 트윈 없이 도는 경우 이름이 빈다 |

**(b) 의 약점은 "중단 시각을 모른다"가 아니라 결과 자체가 틀린다는 것이다.**

| 어긋남 | 코드 | 드러나는 모습 |
|---|---|---|
| 계획 실패와 실행 중단이 안 갈린다 | `_run_sync` · `_run_async` 의 bare `except Exception` → `EXECUTION_ABORTED` | `ErrorCode.PLANNING_FAILED` 는 enum 에 **정의만 있고 어디서도 대입되지 않는다** |
| 잘린 스트리밍이 성공으로 보고된다 | `_on_stream_done` 이 `set_result(published)` — `stream` 이 중간에 멈춰도 예외가 아니다 | 펑션베이에서 중단된 연산이 트윈에서 **`COMPLETED`** 다 |
| `TIMEOUT` 은 결과가 아니라 포기다 | `_await` 는 `future.cancel()` 만 하고, 워치독도 `request_cancel()`(플래그 · `phase`)까지다 — `_stop_backend()` 는 `cancel_session` 만 부른다 | 팔은 계속 간다. 진짜 결과는 **나중에** 온다 |

세 번째가 특히 중요하다 — **트윈이 `TIMEOUT` 이라 말한 연산이 실제로는 `succeeded` 로 끝날 수 있다.** 그래서 학습 레이블의 정본은 이 채널이지 트윈 세션 상태가 아니다(§6).

**(a) 로 정했다 (2026-09-18).** 연산 이름 문제는 §3.1 이 `operation` 을 **트윈 REST 이름이 아니라 이동 방식 셋**(`named_target` · `joints` · `cartesian`)으로 정하면서 사라졌다 — 클라이언트 메서드가 그 값을 안다. 선택 인자도 트윈 배선도 필요 없고, 다른 문서가 실제로 요구한 것도 REST 이름이 아니라 이동 방식이다(좌표 공간 §5.3 *"관절 공간/직선을 함께 남긴다"*, 생성 설계 M3 *"연산 종류"*). 코드베이스에 `execute_trajectory(_async)` 를 클라이언트 밖에서 직접 부르는 곳이 없어 셋으로 전 경로가 덮인다.

#### 발행 지점은 셋이고, 펑션베이가 둘이다

**§2 의 세 자리가 그대로 발행 지점이 된다** — 끝을 아는 곳에서 내는 것이 (a) 의 뜻이다. R1 도 셋이었지만 **구성이 다르다**: R1 은 *궤적을 넘기는* 자리(JTC 두 곳 + 스트리머)이고, R2 는 *끝을 아는* 자리(JTC 결과 콜백 하나 + 스트리머 + JGPC 계획 콜백)다. 펑션베이만 둘로 갈린다.

| 경로 | 발행 지점 | 낼 수 있는 `result` |
|---|---|---|
| isaac (관절 공간 · 데카르트) | `MoveGroupJtcClient` 의 결과 콜백 | 셋 다 |
| 펑션베이 실행 | `TrajectoryStreamer.stream` | `succeeded` · `aborted` — **잘렸는지를 아는 유일한 자리**(§2 의 2) |
| 펑션베이 계획 | `MoveGroupJgpcClient._on_plan_done` | `failed` 만 |

**대안은 `stream` 의 반환을 바꾸는 것이다.** `published`(정수) 대신 `(published, 마지막 발행 시각)` 을 돌려주면 JGPC 클라이언트 **한 자리**에서 셋을 다 낼 수 있고 `operation_id` 배선도 한 겹 얕아진다. 대가는 공개 반환 타입이 바뀌어 `scripts/functionbay/` 의 호출 여덟 곳이 함께 움직인다는 점이다(전부 `published` 를 정수로 받는다). **둘 중 하나를 골라 이 절에 적는다** — 안 고르면 펑션베이의 계획 실패가 조용히 빠진다(Q6′).

### 3.3 `operation_id` 와 t₀ 를 R1 에서 R2 로 잇는다

**이것이 첫 번째 작업이다.** 지금 R1 발행부는 **식별자도 t₀ 도** 밖으로 내보내지 않는다(§2 의 3).

`publish()` 는 `operation_id` 만 돌려주고, `stamp=None` 으로 부르면 **자기 안에서** 노드 시계를 찍는다(`test_stamp_defaults_to_node_clock` 이 그 동작을 고정한다). 그런데 isaac 의 `truncated_at` 은 `끝난 시각 − t₀` 라 **t₀ 값 자체가 있어야 한다.** 둘 중 하나로 푼다.

| 방법 | 내용 |
|---|---|
| **(a) 호출자가 t₀ 를 만들어 넘긴다 — 결정 (2026-09-18)** | 호출부가 `node.get_clock().now()` 를 찍어 `stamp=` 로 넘기고 그 값을 보관한다. `publish()` 의 계약(*"호출자는 컨트롤러로 넘기기 직전에 불러야 한다"*)이 이미 그 순간을 가리키므로 **뜻이 안 바뀌고 R1 의 반환 타입도 시험도 그대로다** |
| (b) `publish()` 가 `(operation_id, stamp)` 를 돌려준다 | 반환 타입이 바뀌어 R1 시험 여러 건이 함께 움직인다 |

그 위에서 세 자리를 고친다.

* `MoveGroupJtcClient._publish_motion_trajectory` 가 `(operation_id, t₀)` 를 돌려주고, 호출부(`execute_trajectory_async` · `follow_trajectory_async`)가 **결과 콜백까지** 들고 간다.
* `TrajectoryStreamer.stream` 이 같은 값을 자기 안에 둔다 — 중단 판정이 거기 있다(§3.2).
* `MoveGroupJgpcClient._on_plan_done` 은 R1 이 없으므로 **`operation_id` 를 새로 만들어** 싣는다. 짝 없는 `failed` 이벤트가 정상이다(§3.1).

**`operation_id` 가 어긋나면 두 채널이 못 이어지고, 그것은 에러가 아니라 "레이블이 이상하다"로만 드러난다.**

### 3.4 중단 시각을 만든다

| 경로 | 얻는 방법 |
|---|---|
| 펑션베이 (스트리머) | **`samples[published − 1]` 의 시각**이다. 그 축에는 `time_scaling` 이 이미 반영돼 있어 R1 궤적과 바로 맞는다 |
| isaac (JTC) | 결과 콜백 시각에서 t₀ 를 뺀다. t₀ 는 §3.3 으로 이어 둔 값이다 |
| (공통) goal 거부 · 시작 상태 허용 오차 위반 | **0** — 한 점도 실행되지 않았다 (§3.1 의 `aborted`) |

⚠️ **"발행 수 × 주기" 로 계산하면 안 된다 — 두 모드 모두에서 틀린다.** `publish_rate` 가 `None` 이면 샘플 시각이 **경유점 시각**이라 균일하지 않고, 값을 줘도 `_build_samples` 가 균일 격자 뒤에 **`duration` 을 덧붙이므로** 마지막 간격이 `1/rate` 보다 짧다. 옳은 값은 언제나 `samples[published − 1][0]` 이다.

⚠️ **JTC 쪽은 "끝난 시각 − t₀" 가 궤적 길이를 넘을 수 있다** — 컨트롤러가 goal tolerance 를 확인하느라 궤적 끝보다 늦게 결과를 주기 때문이다. 정상 종료면 궤적 길이로 **자른다**(clamp). 안 자르면 `L2(truncated_at)` 가 궤적 밖을 가리켜 소비자가 외삽하게 된다.

## 6. 주의

- **`operation_id` 가 유일한 끈이다.** 어긋나면 두 채널이 못 이어지는데, **에러가 아니라 "레이블이 이상하다"로만 드러난다.** 적재 검증(미구현 목록 I5)에서 짝 없는 궤적·이벤트를 세는 것이 방어선이다.
- **`failed` 만 짝이 없고, 그것이 정상이다.** 궤적을 넘기지도 못한 경우이므로 R1 메시지가 없다(§3.1). 뒤집으면 **`aborted` 에는 반드시 짝이 있어야 한다** — goal 거부나 시작 오차 위반도 `aborted` 라 궤적이 남는다. 적재 검증(I5)은 `(R1 있음) ⇔ (result ≠ 'failed')` 를 불변식으로 쓰고, `failed` 의 짝 없음을 결함으로 세면 안 된다.
- **`header.stamp` 는 레이블의 구간 끝이 아니다.** [ACT 문서](ACT_학습_샘플_구성.md) §5.2 가 말하는 구간 끝은 `t₀ + truncated_at` 인데, 이 stamp 는 **결과를 받은 시각**이라 goal tolerance 확인과 팔의 물리 지연(isaac 실측 120 ms, R1 §3.5)이 들어 있다. stamp 는 **적재가 에피소드 창을 거르는 용도**이고, 구간 경계는 R1 의 t₀ 와 `truncated_at` 으로 계산한다. E3 가 stamp 를 구간 끝으로 쓰면 레이블이 경유점 하나 넘게 밀린다.
- **이 채널이 정본이고 트윈 세션 상태가 아니다.** 트윈의 `TIMEOUT` 은 기다리기를 포기한 것이지 동작이 끝난 것이 아니고(§3.2), 잘린 스트리밍은 `COMPLETED` 로 보고된다. **적재·export 는 트윈 상태를 보지 않는다.**
- **두 메시지의 시계를 맞춘다.** R1 의 t₀ 와 R2 의 끝난 시각이 같은 시계여야 `truncated_at` 을 계산할 수 있다. isaac 은 트윈 설정(`robot_twin_panda_isaac.yaml` 의 `ros.use_sim_time: true`)이 `main.py` 에서 노드 파라미터로 실리므로 **둘 다 sim 시계다 — 확인함(2026-09-18).** ⚠️ 그래도 `끝난 시각 − t₀`(sim 초)를 벽시계로 읽으면 안 된다 — isaac 배속이 0.95 라 같은 구간이 벽시계로 더 길다. 펑션베이(`use_sim_time: false`)는 회차마다 `/output/*` 의 stamp 기준이 갈리지만(CLAUDE.md 의 `joint_state_fusion` 항목) R1·R2 는 둘 다 **노드 시계**로 찍으므로 서로는 맞는다. **같은 노드가 같은 시계로 찍는 것**이 이 모두를 덮으며, 그래서 §3.2 가 (a) 를 권한다.
- **발행 실패가 연산을 막지 않게 한다.** R1 과 같다 — 기록용이므로 예외를 삼키고 경고를 남긴다. R1 은 `MotionTrajectoryPublisher.publish` 가 이미 그렇게 한다.
- ⚠️ **구현하며 드러난 결함 둘 (2026-09-18, 둘 다 R2 가 아니라 R1 이관이 남긴 것이다).**
  둘 다 **에러도 로그도 없이** 증상만 남겼다. `robot_control/moveit/tests/test_async_motion_wiring.py`
  가 구조로 막는다.
  - **비동기 관절 경로가 영영 안 끝났다** — `_execute_joint_goal_async` 가 계획 콜백 안에서
    `execute_trajectory_async` 를 부르는데, 그쪽은 goal 수락을
    `rclpy.spin_until_future_complete` 로 기다린다. executor 스레드 안이라 그 spin 이
    성립하지 않아 **45초를 기다려도 future 가 안 끝났다.** **트윈이 쓰는 바로 그 경로다.**
    데카르트 비동기처럼 `send_goal_async` + `add_done_callback` 으로 바꿔 고쳤다(1.2 s 에 완료).
    `plan_joints_async` 로 `externally_spun` 을 안 넘기던 것도 함께 고쳤다 — 그쪽은 `False` 면
    `_complete_joint_values` 가 노드를 직접 spin 한다.
  - **`TrajectoryStreamer` 의 발행자 필드가 `__init__` 에 없었다** — `stream()` 이
    `if self._motion_pub is None` 으로 지연 생성하는데 선언이 없어 **첫 호출이
    `AttributeError` 로 죽는다.** 즉 R1 의 펑션베이 경로는 한 번도 돈 적이 없다.
- **중단은 예외가 아니다.** §1 의 경고를 다시 적는다 — 실패 데이터를 모으는 것이 목적 중 하나이므로, 중단 경로를 "나중에"로 미루면 그 데이터가 못 쓰게 된다.

| | `_await` | `TIMEOUT` 때 `future.cancel()` 만 한다 — 팔은 계속 간다(§3.2) |
| `robot_twin/robot_twin/runtime.py` | `_run_sync` · `_run_async` | bare `except Exception` → `EXECUTION_ABORTED`. 계획 실패와 실행 중단이 안 갈린다(§3.2) |
| | `_tick_watchdog` | `request_cancel()`(플래그)까지다 — `_stop_backend()` 는 `cancel_session` 만 부른다 |
| `robot_twin/robot_twin/errors.py` | `ErrorCode` | `PLANNING_FAILED` 는 **정의만 있고 어디서도 대입되지 않는다**(Q4′) |
| `robot_twin/config/robot_twin_panda_isaac.yaml` | `operations:` | 팔 동작 연산 이름의 정본 — `move_to_named_target` · `move_to_joints` · `move_linear` 셋이다. 같은 파일의 `move_to_pose` · `move_gripper` 는 **명시적 미구현 스텁**이라(`backend: __not_implemented__`) 세지 않는다 |
| `rdfp_msgs/msg/MotionTrajectory.msg` | 전체 | R1 메시지. R2 는 이것과 필드를 겹치지 않게 만든다 |
