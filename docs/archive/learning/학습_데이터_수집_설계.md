## 1. 문제

모방학습 데이터는 (관측, 행동) 쌍이다. 행동(action)은 **추론기를 배치했을 때 출력할 값과 같은 의미**여야 한다. 현재 팔 action 은 `target_joint_cmds_publisher` 가 백엔드별 명령 채널을 `sensor_msgs/JointState` 로 변환해 `/target_joint_cmds` 로 발행하는 값이다.

이 정의는 Isaac·펑션베이·mock_jgpc 에서는 채워지지만, **mock(JTC) 스택에서 MoveIt 으로 팔을 움직이면 한 건도 남지 않는다.** 75초 녹화 중 MoveIt 이동 2회에서 `/target_joint_cmds`는 0건, `/joint_states` 는 7509건이었다(부록 A-1). 원인은 다음과 같다.

1. MoveIt 은 `moveit_simple_controller_manager` 를 통해 `FollowJointTrajectory` **액션**으로 궤적 전체를 컨트롤러에 보낸다.
2. 액션 goal 은 `…/_action/send_goal` **서비스**로 전송된다. Humble 의 rosbag2(0.15.16)는 서비스를 녹화하지 못한다.
3. JTC 는 보간 결과를 ros2_control command interface(프로세스 내부 메모리)에 쓰고, `mock_components/GenericSystem` 은 명령을 토픽으로 내지 않는다.
4. `target_joint_cmds_publisher` 는 JTC 의 토픽 입구(`~/joint_trajectory`)만 구독한다. 그 토픽에 쓰는 것은 servo(teleop)뿐이다.

   > **`~/joint_trajectory` 의 메시지 타입** — `trajectory_msgs/msg/JointTrajectory` 다. 실제 이름은
   > `/panda_arm_controller/joint_trajectory` 이며, `header` · `joint_names[]` · `points[]` 로 이뤄진다.
   > 각 `points[]` 원소(`JointTrajectoryPoint`)는 `positions` · `velocities` · `accelerations` ·
   > `effort` · `time_from_start` 를 갖는다. servo 는 여기에 **점 하나짜리** 궤적을 약 34 ms 마다
   > 발행하고, `target_joint_cmds_publisher`(`source: joint_trajectory`)는 **마지막 점**만 꺼내
   > `sensor_msgs/JointState` 로 바꾼다. JTC 는 새 메시지를 받으면 진행 중인 궤적을 그것으로 교체한다.

2번(액션 goal 은 서비스라 녹화할 수 없다)은 설계서 §2.2 가 그리퍼 명령을 토픽으로 설계한 근거와 같다.

이 문서는 두 방향을 비교한다.

- **저수준 action** — 컨트롤러가 하드웨어 쪽으로 보낸 조밀한 설정값. 원래 계획이며, mock 만 제외하면 지금 동작한다.
- **계획 수준 action** — 컨트롤러로 **들어가는** 성긴 명령(MoveIt 계획 경유점). mock 문제를 우회하려고 검토한 대안이다.

> **범위 (2026-09-17):** 데이터 출처는 당분간 트윈만 다룬다(§0 의 D1). 아래 분석 중 teleop 출처에 관한 부분은 나중에 teleop 을 다룰 때를 위해 남겨 두고 "현재 범위 밖"으로 표시한다.

## 2. 용어와 전제

| 용어 | 뜻 |
|---|---|
| 저수준 명령 | 컨트롤러(JTC) 또는 스트리머(`TrajectoryStreamer`)가 보간해 하드웨어 쪽으로 보낸 관절 설정값. 제어 주기(50~100 Hz)로 조밀하다 |
| 계획 수준 명령 | 컨트롤러로 들어가는 궤적의 경유점. MoveIt 관절 공간 계획은 100 ms 간격이다 |
| 관절-계획 · 관절-명령 | [좌표 공간 문서](학습_데이터의_좌표_공간_비교.md)의 레이블 이름이다. **관절-계획** 은 이 문서의 B(계획 수준, 생성 설계의 M2), **관절-명령** 은 A · A′(저수준 명령, 생성 설계의 M1)에 해당한다 |
| 컨트롤러 | JTC 스택(mock·Isaac)에서는 `panda_arm_controller`(JTC)다. JGPC 스택(mock_jgpc·펑션베이)에는 보간 주체가 없으므로 `TrajectoryStreamer` 를 컨트롤러로 간주한다 |
| Δ (선행 시간) | 계획 수준 레이블에서 관측 시각 t 에 대응시키는 목표 시각 t+Δ 의 간격 |
| δ (지연 보정) | 저수준 명령 레이블(A · A′)에서 관측 시각 t 에 짝지을 명령 시각 t+δ 의 간격. t 의 명령은 관측보다 먼저 나가 팔이 이미 쫓고 있는 값이므로, 관측 뒤에 나갈 명령을 레이블로 쓰려고 둔다 — mock 에서 `/joint_states` 는 JTC 출력을 정확히 1주기(9.9 ms) 늦게 따라간다(§7.1). 기본은 제어 1주기(mock · isaac 10 ms, 펑션베이 20 ms)이며, 학습과 배치가 같은 값을 써야 하므로 데이터셋 metadata 에 기록한다(§8.2). Δ 와 다르다 — Δ 는 계획 궤적에서 앞을 내다보는 간격이다(기준 100 ms, §11 의 8) |
| frame clock | export 시 모든 채널을 맞추는 기준 시각열 (고정 fps 또는 카메라 프레임 시각). 잠정안은 카메라 프레임 시각이다(§11 의 4) |

전제는 다음과 같다.

- 추론기는 관측을 받아 **팔 관절 목표**와 **그리퍼 심볼**을 낸다. EE 공간 action 은 이 문서의 범위 밖이다(§11 의 7).
- **적재(DB)는 비가역이고 action/observation 컬럼 매핑(export)은 번복할 수 있다.**
  [scene_objects 결정 문서](../../learning/scene_objects_observation_decision.md)와 같은 원칙이다. 따라서 **녹화는 넉넉히 하고 action 정의는 export 에서 정하는 것**이 기본 전략이다.

## 3. 현재 구조 — 출처·백엔드별 명령 경로

### 3.1 데이터 출처

| 출처 | 명령 생성 경로 | 현재 범위 (2026-09-17) |
|---|---|---|
| 키보드 teleop (`teleop_keyboard`) | EE twist → `/servo_node/delta_twist_cmds` → servo | 범위 밖 |
| leader-follower (`teleop_mirror`) | `teleop_retarget` 의 목표 `PoseStamped` → `ee_twist_node`(차분) → `/servo_node/delta_twist_cmds` → servo | 범위 밖 |
| 트윈 / LLM (`robot_twin`) | MoveIt 계획 → JTC 액션(JTC 스택) 또는 `MoveGroupJgpcClient` 스트리밍(JGPC 스택) | **대상** |

teleop 두 출처는 **servo** 를 거치고, 트윈만 **MoveIt 계획**을 거친다. 당분간은 트윈만 다룬다(§0 의 D1).

### 3.2 백엔드별 경로와 `/target_joint_cmds` 가 담는 값

| 백엔드 | servo 출력 경로 | MoveIt 실행 경로 | `/target_joint_cmds` 가 담는 값 |
|---|---|---|---|
| **mock** (JTC) | `/panda_arm_controller/joint_trajectory` 단일점 (토픽) | 액션 → JTC → `GenericSystem` (토픽 없음) | teleop: servo 단일점 · **MoveIt: 없음** |
| **mock_jgpc** | `/panda_arm_controller/commands` (`Float64MultiArray`) | `TrajectoryStreamer` → 같은 토픽. 프로파일에 `publish_rate` 가 없어 **경유점 시각에만, 보간 없이** 보낸다 | teleop: servo 출력 · MoveIt: 경유점 그대로 (관절 공간 계획이면 10 Hz 계단) |
| **isaac** (JTC) | `joint_trajectory` → JTC (`open_loop_control: true`) | 액션 → JTC | 두 출처 모두 **JTC 보간 출력**. `TopicBasedSystem` 이 컨트롤러 update 주기(100 Hz)로 `/isaac/arm_command` 에 낸다. 실측 277건 = 277건 |
| **functionbay** | `/servo_node/commands` → `servo_command_bridge` → `/input/panda_joint` | `TrajectoryStreamer` 50 Hz 선형 보간 **+ 중력 보상 오프셋** → `/input/panda_joint` | teleop: servo 출력(**보상 없음**) · MoveIt: 보간값 + **보상 포함** |

### 3.3 드러나는 불일치

1. **mock JTC + MoveIt 은 action 이 비어 있다** (§1).
2. **펑션베이 안에서 출처별로 의미가 다르다.** (teleop 이 현재 범위 밖이라 당장 걸리지는 않는다.) 중력 보상은 JGPC 스트리밍 경로 (`MoveGroupJgpcClient`·`TrajectoryStreamer`)에만 적용되고 `servo_command_bridge` 에는 없다. 오프셋은 `ready` 자세에서 joint4 **+9.67 mrad**, `extended` 자세에서 최대 2.23 mrad 다 (부록 A-5). 같은 자세에서 트윈이 낸 명령과 teleop 이 낸 명령이 그만큼 다르다.
3. **백엔드마다 보간 방식과 주기가 다르다.** Isaac 은 JTC 스플라인 100 Hz, 펑션베이는 선형 50 Hz, mock_jgpc 는 보간 없는 경유점이다.
4. **펑션베이 action 에는 그 시뮬레이터 전용 보정이 들어 있다.** Isaac·실기에는 없는 값이다.

## 4. 대안

### A. 저수준 action 유지, mock(JTC)의 MoveIt 수집은 포기

현행 정의(`/target_joint_cmds`)를 그대로 쓴다. 트윈 기반 수집은 Isaac·펑션베이·mock_jgpc에서만 한다. mock 에서 MoveIt 데이터가 필요하면 mock_jgpc 를 쓴다.

### A′. 저수준 action 유지, mock(JTC)은 `controller_state.output` 으로 보완

JTC 가 command interface 에 쓴 값은 `/panda_arm_controller/controller_state` (`control_msgs/JointTrajectoryControllerState`)의 `output` 필드로 발행된다. position 인터페이스에서는 `reference` 와 정확히 같다(최대 차 0, 부록 A-4). 다만 기본 설정으로는 샘플이 빠진다.

| `state_publish_rate` (컨트롤러 update 100 Hz) | 이동 구간 샘플 | 간격 |
|---|---:|---|
| 50 (기본) | 38% | 20 ms / 30 ms |
| 100 을 **런타임**에 설정 | 37% | 변화 없음 — 값은 바뀌지만 configure 시점에만 읽힌다 |
| 100 을 **기동 시점**에 설정 | 59% | 10 ms ×74, 20 ms ×140 |
| **1000** 을 기동 시점에 설정 | **98%** | **10 ms ×354** |

update 주기보다 높게 주어야 매 주기가 발행된다. 주기와 같게 주면 경과 시간이 주기보다
약간 짧게 측정되는 틱에서 발행을 건너뛴다. 적용 방법은 다음과 같다.

1. `panda_arm_controller` 에 `state_publish_rate: 1000.0` 을 넣은 컨트롤러 yaml 복사본을 만든다. Humble 은 컨트롤러 파라미터를 params 파일로만 받는다(선례: `config/panda_isaac_ros2_controllers.yaml`).
2. `config/backends/mock.yaml` 의 `ros2_control.controllers_file` 로 그 파일을 지정한다.
3. `target_joint_cmds_publisher` 에 `source: controller_state` (`output` → `JointState`)를 추가한다.
4. `rdfp_collect` 의 `backend:=mock` 파생이 그 source 를 고르게 한다.

mock 의 action 이 Isaac 과 **체인상 같은 위치**(컨트롤러 출력)가 된다.

### B. 계획 수준 action + 오프라인 레이블 생성

MoveIt 이 컨트롤러로 보내는 계획 궤적을 저장하고, export 시 관측 시각 t 마다 **계획을 t+Δ 에서 보간한 값**을 action 레이블로 만든다.

녹화 채널은 다음과 같다 — **이벤트로 녹화한다**(결정, 2026-09-16. [생성 설계](MoveIt_명령_체인과_트윈_데이터_생성.md) 권고 2).

- **실행 궤적 채널** — 연산마다 한 건. 클라이언트가 속도 배율을 적용한 실행 궤적(L2)을 `header.stamp` = 실행 시작 시각 t₀ 로 발행한다.
- **연산 이벤트 채널** — 연산마다 한 건. 연산 종류(이동 방식) · 해석된 목표 · 결과(정상 종료 / 중단 · 실패) · 끝난 시각 · 궤적 기준 중단 시각. **실효 속도 배율은 실행 궤적 채널이 싣는다**([R2 문서](R2_연산_이벤트_채널_구현_설계.md) §1).

처음 검토한 `/display_planned_path` + 실행 시작 기준 채널 안은 쓰지 않는다. `DisplayTrajectory` 는 `header.stamp` 가 0 이라 적재가 에피소드 창 밖으로 버리고, 발행 후 실제 움직임 시작까지 53~66 ms 가 벌어지며(부록 A-7), 데카르트 구간은 속도 배율을 적용하기 전 시각이라 시간이 1/vs 배 틀린다(생성 설계 §5.3).

**계획은 연산이 실행될 때만 있으므로, 공백은 export 가 규칙으로 채운다.** 실행 중에 10 Hz 목표 토픽을 발행해 녹화하지 않는다. 규칙은 §8.2 의 B 행과 [ACT 문서](ACT_학습_샘플_구성.md) §5.2 에 있다.

레이블 규칙은 다음과 같이 비교된다.

| 규칙 | 레이블 | 문제 |
|---|---|---|
| 이미 지난 가장 최근 경유점을 반복 (0차 유지) | 로봇이 이미 있거나 막 지난 위치 | 정책이 "현재 위치"를 명령하도록 학습된다 → 배치 시 **팔이 전진하지 않는다** |
| 다음 경유점을 반복 | 0~100 ms 앞, 구간 내 위상에 따라 변동 | 관측으로 위상을 알 수 없어 **같은 상태에 다른 레이블**이 붙는다. 전환 시점에 계단이 생긴다 |
| **t+Δ 보간** | 선행량이 일정한 매끄러운 목표 | 계획이 개루프라 접촉 편차 구간에서 반사실적 레이블이 된다(§5.3) |
| **t+Δ₁ … t+Δₖ 묶음 (action chunk) — 채택** | 미래 k 개 목표 | 위와 같다. ACT·Diffusion Policy 계열의 출력 형식과 맞는다. 잠정안은 Δ = 100 ms, 스텝 100 ms, k = 10~20 (ACT 문서 경우 B) |

teleop 출처에는 계획이 없으므로, teleop 을 다룰 때는 B 에서도 servo 출력을 써야 한다. **B 가 바꾸는 것은 MoveIt 기반 데이터뿐이다.** 데이터 출처를 당분간 트윈만 다루므로 지금은 모든 데이터에 B 가 적용된다(§0 의 D1 · D2).

> **0차 유지 (zero-order hold)** — 다음 값이 올 때까지 **직전 값을 그대로 붙들어** 빈 시각을 채우는 방식이다. "0차"는 보간 다항식의 차수다 — **0차는 상수(계단)**, 1차는 선형, 3차는 Hermite(경유점의 속도까지 맞춘다, [ACT 문서](ACT_학습_샘플_구성.md) §9 의 4). 성긴 이벤트를 조밀한 frame clock 격자에 얹을 때 쓴다.
>
> **이 설계에서는 채널마다 쓰임이 갈린다.**
>
> | 채널 | 0차 유지 | 이유 |
> |---|:-:|---|
> | 그리퍼 (`/gripper_cmds`) | **쓴다** | 심볼은 지나가는 점이 아니라 **유지되는 의도 상태**다 — `grasp` 를 한 번 보내면 다음 명령까지 쥐고 있는 것이 사실이다 (§7.2) |
> | 팔 (계획 경유점) | **안 쓴다** | 위 표 첫 행 — 이미 지난 경유점을 반복하면 정책이 "현재 위치"를 명령하도록 배워 **배치 때 팔이 전진하지 않는다.** 대신 시각으로 보간한다(t+Δ) |
>
> **혼동하기 쉬운 곳이 하나 있다.** 팔에도 "직전 값 유지"가 나오지만 그것은 다른 경우다 — 연산이 끝난 뒤나 연산 사이처럼 **계획 자체가 없는 구간**을 궤적 끝점으로 채우는 것이고(§8.2 의 B 행, [ACT 문서](ACT_학습_샘플_구성.md) §5.2), 그 구간에는 컨트롤러가 실제로 마지막 설정값을 붙들고 있으므로 사실에 맞는다. 금지되는 것은 **팔이 움직이는 동안** 성긴 경유점을 반복하는 쪽이다(ACT 문서 §4.2, §8.2).

### 5.3 모든 대안에 공통인 한계

- **MoveIt 계획은 개루프 기준이다.** 펑션베이 peg 삽입처럼 접촉으로 궤적이 밀린 구간에서는 "있어야 할 위치"와 "실제 위치"가 어긋나고, 그 구간의 레이블은 교정 동작을 가르치지 못한다. A·A′ 의 컨트롤러 출력도 같은 계획을 보간한 값이라 같은 한계를 갖는다. 교정 행동은 반응적 시연(teleop)에서만 얻는다. **데이터 출처를 트윈만 다루는 동안에는 교정 행동이 데이터에 없다** — 대응 후보(초기 조건 무작위화, 섭동 주입)는 [생성 설계](MoveIt_명령_체인과_트윈_데이터_생성.md) §9.1 에 있다.
- **펑션베이는 작은 명령에 비선형으로 응답한다.** 8.2 mm 보정 명령이 29% 만 반영된 실측이 있다. action 과 관측의 괴리가 명령 크기에 따라 달라진다.
- **servo 기반 teleop 에서 명령 없이 팔이 흐른 관찰이 있었다**(2026-09-06, Isaac). 이후 재현되지 않았으나, teleop action 을 쓸 때는 정지 구간의 품질을 확인한다 ([servo_vs_planned_motion.md](../../teleop/servo_vs_planned_motion.md)). teleop 은 현재 범위 밖이다.

### 5.4 대안 A (mock 포기)에 대한 판단

A 는 **지금 바로 쓸 수 있고 배치 정합이 가장 직접적**이다. 제어 주기의 설정값을 학습하고
같은 주기로 넣으면 되므로 레이블 생성 규칙이 필요 없다. 포기하는 것은 "mock JTC 스택에서
트윈으로 만든 데이터" 하나이며, mock 에서 MoveIt 데이터가 필요하면 mock_jgpc 가 대신한다.

그러나 mock 포기의 대가보다 **A 자체가 가진 두 문제**가 더 크다.

1. 펑션베이의 teleop 데이터와 트윈 데이터가 최대 약 10 mrad 다른 의미를 갖는다. mock 포기와 무관하게 남는다. (teleop 이 현재 범위 밖이라 당장은 걸리지 않는다.)
2. 펑션베이 action 에 시뮬레이터 전용 오프셋이 들어 있어 Isaac·실기 데이터와 섞으면 편향이 된다.

또한 mock 공백은 A′ 로 작은 비용에 메울 수 있다. 따라서 **mock 을 포기할 이유는 약하다.**

### 5.5 대안 B 에 대한 판단

B 의 장점은 **백엔드 간 의미 일관성**이다. 여러 시뮬레이터에서 스크립트 데이터를 모아 섞는 것이 목표라면 가장 깨끗하다. 단점은 비용과 불확실성이다. 실행 시작 기준, JGPC 클라이언트 경로의 계획 발행 여부, 배치 어댑터가 모두 미검증·미구현이며, teleop 데이터에는 적용되지 않는다.

**결정 (2026-09-16 ~ 17): MoveIt 생성 데이터에서는 B 를 택했다.** 단점으로 든 불확실성 중 실행 시작 기준은 실행 궤적 채널의 t₀ 로, JGPC 클라이언트 경로의 계획 발행 여부는 클라이언트가 채널을 직접 발행하는 것으로 풀린다. 남는 것은 isaac 의 t₀ 정의, 배치 어댑터, 채널 구현 비용이다. teleop 데이터에 적용되지 않는다는 한계는, 데이터 출처를 당분간 트윈만 다루기로 하면서 당장은 걸리지 않는다(§0 의 D1).

## 6. 권고

**수집 단계와 export 단계를 분리한다.** 녹화는 두 방향을 모두 지원하도록 하고, 학습 action의 정의는 export 에서 정한다.

이전 판(2026-09-13)은 A′ 구현과 export 1차안 A′ 를 권고하고 B 를 비교 실험으로 두었다. 2026-09-17 결정으로 순서가 바뀌었다.

1. **B(관절-계획)의 원천을 이벤트로 녹화 · 적재한다 (결정, 2026-09-16).**
   생성 설계 권고 2 의 실행 궤적 · 연산 이벤트 채널이다(§4 의 B). `/display_planned_path` 는 쓰지 않는다. 이 채널 없이 모은 데이터에서는 B 레이블을 만들 수 없으므로 **학습용 수집의 전제**로 둔다 — 채널 전에 모은 데이터는 수집 · 적재 파이프라인 검증에만 쓴다.
2. **export(설계서 §5.6, 미구현)의 1차안은 B(관절-계획)의 action chunk 로 한다 (2026-09-17).**
   frame clock 은 카메라 프레임이고, 행동은 레이블 함수를 t + Δ + j × 스텝에서 뽑은 k 스텝 chunk 다. 잠정 주기는 영상 10 Hz · 행동 10 Hz · 관절 관측 50 Hz 이며, 샘플 구조는 [ACT 문서](ACT_학습_샘플_구성.md) 경우 B 다. A · A′(관절-명령)는 같은 DB 에서 뽑는 비교 기준으로 둔다.
3. **관절-명령(`/target_joint_cmds`)은 계속 녹화 · 적재한다.**
   단일 백엔드 비교 기준이다. 나중에 teleop 을 다루면 그 출처의 action 원천도 된다. 설계서 §2.2 의 채널 정의도 그대로 둔다.
4. **A′ 는 필요할 때 구현한다.**
   mock(JTC)에서 관절-명령을 채우는 방법이다. mock 은 학습 데이터를 만들지 않으므로(생성 설계 §1.1) 우선순위를 낮춘다. mock 에서 관절-명령 경로를 검증하거나 A′ 기준선이 필요해지면 구현한다.
5. **펑션베이 중력 오프셋을 관절-명령에서 분리할 수 있게 한다.**
   방법은 두 가지다. (a) 보상 전 명령을 별도 토픽으로 함께 발행한다. (b) 적재 시 역보상한다 — 오프셋이 `q` 의 결정적 함수이므로 `cmd = q + offset(q)` 를 고정점 반복으로 푼다(§11 의 3). B 레이블에는 오프셋이 없으므로 이 권고는 관절-명령을 레이블로 쓰는 경우(A · A′, 나중의 teleop)에 해당한다. 결정 전에는 **펑션베이의 관절-명령 데이터를 Isaac 데이터와 섞지 않는다.**
6. **대안 A(mock 포기)는 채택하지 않는다.**
   A′ 의 비용이 작고, A 의 실제 문제(§5.4)는 mock과 무관하게 남기 때문이다.

## 7. 관측·그리퍼·영상 채널

### 7.1 팔 관측

| 백엔드 | `/joint_states` 출처 | 주기 |
|---|---|---|
| mock · mock_jgpc | `joint_state_broadcaster` | 100 Hz (실측 7509건 / 75.08 s). mock JTC 는 `output` 을 **정확히 1주기(9.9 ms) 늦게** 따라간다 — 동역학이 없는 `GenericSystem` 의 성질이다 |
| isaac | `joint_state_broadcaster` (`TopicBasedSystem` 의 state) | 컨트롤러 update 100 Hz |
| functionbay | `joint_state_fusion` ← `/output/panda_joint` | 시뮬레이터 XML 설정값. 현재 50 Hz (실측 49.85 Hz) |

위 주기는 연동 확인용 설정의 값이다(§0 의 D12). 잠정 운영안은 **관절 관측 50 Hz** 이며 최종 운영 설정에서 정한다(D10). 1차 학습(ACT)에서는 이 관측을 카메라 프레임 시각에서 선형 보간해 `qpos` 로 쓴다(§8.2).

mock 에서 `/joint_states` 를 한 틱 당겨 명령으로 쓰는 방식은 mock 에서만 성립하므로 action
채널로 일반화하지 않는다.

`/ee_pose` 는 `/joint_states` 의 순기구학 결과라 독립 관측이 아니다. 펑션베이에서는
`grasp_center` 기준이다.

### 7.2 그리퍼

action 은 `/gripper_cmds`(심볼 `open`/`close`/`grasp`), 관측은 `/gripper_states`(개구 폭 m, `at_goal`, `stalled`)다. 설계서 §2.2 의 결정을 유지한다.

`/gripper_cmds` 는 **명령할 때만** 발행된다(트윈 연산. teleop 에서는 키 입력). 그리퍼 심볼은 경유점이 아니라 **유지되는 의도 상태**이므로, 팔과 달리 frame clock 에서 **t 이전의 마지막 명령을 0차 유지**하는 것이 옳다. 에피소드의 첫 명령 이전 구간은 값을 정하는 규칙이 필요하다 (§11 의 5).

### 7.3 영상

- **영상은 rosbag 에 담지 않는다.** `rdfp_image_recorder` 가 `/session` 의 `IN_EPISODE` 구간을 에피소드마다 mp4 + 프레임별 sidecar(jsonl, `frame_index` · `header.stamp`) + metadata 로 직접 녹화하고, 적재가 그 mp4 를 `image_streams` · `image_frames` 에 등록한다. 녹화 목록에 있는 이미지 토픽은 rosbag 녹화와 레코더 mp4 의 부하를 비교하려는 임시 항목이다.
- **등록 경로는 2026-09-18 에 생겼다 (R5 · R6 · I4).** 레코더가 에피소드 키(`/session` 시작 stamp) · 에피소드별 metadata · topic · codec · fps 를 싣고(R5) 출력 위치를 `/data/rdfp/recordings` 로 옮겼으며(R6), 적재가 `ingest/media/recorder_registry.py` 로 그 mp4 를 `image_streams` · `image_frames` 에 등록한다(I4 — 에피소드 트랜잭션 안에서 커밋 직전, 직렬·병렬 두 경로 모두). **붙이는 열쇠는 `episode_key` 이고 파일 이름이 아니다** — 이름은 벽시계, 키는 스택 시계라 `use_sim_time` 스택에서는 무관하다. 설정 키는 `recordings_dir`(없으면 등록하지 않는다). 배경은 [좌표 공간 문서](학습_데이터의_좌표_공간_비교.md) §3.4 · 권고 12 와 [생성 설계](MoveIt_명령_체인과_트윈_데이터_생성.md) 권고 7 에 있다.
- **영상의 손실 압축은 녹화 시점에 확정되고, mp4 는 DB 와 함께 장기 원본이다.** rosbag 을 적재 뒤 지워도 mp4 는 남겨야 한다.
- 카메라 주기는 백엔드별 설정값이다 — mock `image_pipeline.yaml` 10 fps, Isaac `isaac_scene.json` 10 fps, 펑션베이 XML 10 fps(프로파일 `camera.fps` 도 10 — [펑션베이_인수_체크리스트.md](../../backends/functionbay/펑션베이_인수_체크리스트.md) A-4). 지금 값은 연동 확인용이며, 잠정 운영안은 10 Hz 로 최종 운영 설정에서 정한다. 관절 관측(50~100 Hz)보다 낮으므로 frame clock 으로 쓴다(잠정, §11 의 4).
- 녹화 경계는 레코더가 카메라 `header.stamp` 와 `/session` stamp 를 비교해 정한다. 둘이 같은 시계가 아니면 프레임이 조용히 빠진다([좌표 공간 문서](학습_데이터의_좌표_공간_비교.md) §8 의 11). 레코더의 `image_topic` · `input_format` 이 백엔드의 카메라 토픽·형식과 어긋나도 오류 없이 0 프레임만 담긴다(펑션베이는 `mjpeg`).
- `scene_objects` 는 적재하되 관측 컬럼에는 넣지 않는다 ([scene_objects 결정 문서](../../learning/scene_objects_observation_decision.md) §6).

## 8. 시간과 정렬

### 8.1 기준 시각

- 적재는 `header.stamp` 로 에피소드 창을 거른다. **stamp 가 0 이면 rosbag 에는 남고 DB 에는 들어가지 않는다.**
- `target_joint_cmds_publisher` 는 모든 입력을 **수신 시각**으로 재stamp 한다. DDS 전달 지연이 포함된다.
- Isaac 은 `use_sim_time:=true` 다. 수집 계층도 같아야 하며 `rdfp_collect backend:=isaac` 이 맞춘다.
- 펑션베이 `/output/*` 의 시간 기준(벽시계/경과시간)은 **회차마다 바뀐다.** 수집 전에 `fb_checkup.py` 로 확인한다.
- 실행 궤적 채널은 `header.stamp` 에 실행 시작 시각 t₀ 를 싣는다. isaac 의 t₀ 정의는 미정이다(생성 설계 §10.2). `DisplayTrajectory` 는 `header.stamp` 가 0 이라 쓰지 않는다(§4 의 B).

### 8.2 frame clock 과 재표본화

export 는 모든 채널을 하나의 frame clock 에 맞춘다. 잠정안은 **카메라 프레임 시각**이다. 채널 성격에 따라 규칙이 다르다.

| 채널 | 성격 | frame 시각 t 에서의 값 |
|---|---|---|
| 팔 관측 `/joint_states` | 연속·조밀 | t 에서 선형 보간 |
| 팔 action (A·A′) | 연속·조밀 | t (또는 t+δ, δ = 제어 1주기) 에서 선형 보간. 명령이 끊긴 공백은 직전 명령 유지 |
| 팔 action (B, 채택) | 연산마다 한 건인 계획 | 레이블 함수를 t+Δ (chunk 는 t+Δ+j×스텝) 에서 평가한다. 연산 실행 중은 실행 궤적 보간, 연산이 끝난 뒤는 끝점(중단 · 실패면 중단 시각의 궤적 값), 첫 연산 이전은 에피소드 시작 관측 ([ACT 문서](ACT_학습_샘플_구성.md) §5.2) |
| 그리퍼 action | 이벤트·상태 유지 | t 이전의 마지막 명령 (0차 유지) |
| 그리퍼 관측 | 주기 | t 에서 가장 가까운 샘플 |
| 영상 | 프레임 | frame clock 이 카메라 프레임이면 그 프레임, 고정 fps 면 가장 가까운 프레임 |

**성긴 팔 명령을 조밀한 관측 주기에 맞춰 0차 유지로 반복하는 방식은 쓰지 않는다**(§4 의 B 레이블 규칙 표). 이것은 **움직이는 동안** 경유점을 반복하는 경우의 금지다. 연산 사이처럼 계획 · 명령이 없는 구간을 직전 값으로 유지하는 것과는 다르다 — 컨트롤러가 실제로 마지막 설정값을 붙들고 있다.

## 9. 추론 시 배치 규약

학습 레이블의 정의와 배치 인터페이스는 **같은 규약을 공유해야 한다.** 컨트롤러가 보간한다고
해서 학습 때의 의미가 자동으로 보존되지는 않는다.

| action 정의 | 추론기 출력 | 로봇에 넣는 방법 | 주의 |
|---|---|---|---|
| A · A′ (저수준 설정값) | 제어 주기의 관절 설정값 | JTC: 단일점, `time_from_start` ≈ 1주기, **`open_loop_control: true`** · JGPC: `commands` 에 직접 | 측정 상태에서 보간을 다시 시작하면 부하 처짐이 명령에 적분된다(servo 래칫 사례, [servo_vs_planned_motion.md](../../teleop/servo_vs_planned_motion.md) §3~§4) |
| B (t+Δ 목표, 채택) | t+Δ 의 목표 또는 chunk | 명령 기준으로 이어지는 스트리밍 — JTC 단일점 `time_from_start = Δ` + `open_loop_control: true` · JGPC 는 직전 명령에서 보간 | Δ 만큼 지연된다. 한 점씩 받는 `TrajectoryStreamer` 는 보간할 다음 점이 없다. **잠정 10 Hz 출력을 컨트롤러에 계단으로 넣지 않는다** — isaac 은 JTC, 펑션베이는 스트리머(50 Hz)가 보간한다. 펑션베이에서 10 Hz 계단 명령으로 peg 삽입이 실패한 실측이 있다([ACT 문서](ACT_학습_샘플_구성.md) §7). 펑션베이는 레이블에 보상이 없으므로 배치 경로에서 보상을 건다 |
| 펑션베이 공통 | — | 학습 데이터에 오프셋이 포함됐는지에 따라 배치 시 보상기를 끄거나 켠다 | 이중 보상이나 누락이 오류 없이 발생한다 |

추론기 배치 노드는 아직 없다. 가장 가까운 기존 구성요소는 재생용 `target_joint_cmds_executor` 다 — `JointState` 를 단일점 `JointTrajectory` (`time_from_start` 기본 0)로 감싸 JTC 에 넣으며, A·A′ 배치 어댑터의 출발점이 될 수 있다.

## 10. 저장·스키마·export 에 미치는 영향

| 항목 | A | A′ | B |
|---|---|---|---|
| 녹화 목록 | 변경 없음 | 변경 없음 (`/target_joint_cmds` 로 변환된다) | 실행 궤적 · 연산 이벤트 채널 추가 |
| 레지스트리·스키마 | 변경 없음 | 변경 없음 (`JointState` → `joint_states`) | 두 채널의 메시지 바인딩 · 테이블 신설 |
| 코드 | 없음 | `target_joint_cmds_publisher` source, yaml 복사본, 프로파일, `rdfp_collect` 파생 | 두 클라이언트의 채널 발행, writer·reader, export 레이블 함수 · chunk 생성기, 배치 어댑터 |
| export (§5.6) | frame clock 보간 | 같다 | 레이블 함수를 t+Δ 격자에서 평가한 chunk (채택) |

`joint_states` 테이블은 2026-09-18 부터 관절 이름을 싣는다(`joint_names TEXT[]`, I3) — **그 전 데이터는 비어 있고**,
발행자가 `JointState.name` 을 안 채우면 지금도 빈다. 그래서 export 의 `load_joint_series` 는 **이름 없는 행을
거부한다**(순서로 때우면 관절이 뒤바뀌어도 데이터에서 안 드러난다). action 과 관측은 여전히 같은 테이블에
`topic_id` 로만 구분되므로 export 는 토픽 등록부로 둘을 가르고, **관절 순서 규약을 명시한다** — 그 규약은
데이터셋 metadata 의 `spec.arm_joints` 이고 `.npz` 의 `qpos` · `action_arm` 이 그 순서를 따른다
([E7 문서](../../learning/저장_형식.md) §6.2).
