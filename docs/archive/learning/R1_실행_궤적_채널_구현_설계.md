## 1. 무엇을 만드는가

**연산 하나를 실행할 때마다, 컨트롤러로 실제로 보낸 궤적을 한 건의 메시지로 남기는 채널**이다. 1차 학습 행동인 관절-계획(수집 설계 D2)의 원천이며, 생성 설계의 L2(실행 궤적)에 해당한다.

| 담을 것 | 뜻 |
|---|---|
| 경유점의 관절 위치 | 보간 전 · **중력 보상 전** 값 |
| 경유점의 속도 · 가속도 | MoveIt 시간 파라미터화가 채운 값. 재생 배율을 적용했다면 그에 맞게 고친 값(§3.2) |
| 경유점마다 `time_from_start` | **속도 배율과 재생 배율이 모두 적용된** 실제 실행 시간 |
| `header.stamp` = t₀ | 궤적의 0초가 실제로 시작된 시각 |
| 관절 이름 | 궤적의 `joint_names` |

export 는 이 메시지로 "시각 τ 에 계획상 팔이 있어야 할 자세"를 계산한다. 연산 사이의 공백은 규칙으로 채운다(수집 설계 D5, [ACT 문서](ACT_학습_샘플_구성.md) §5.2).

**주기 토픽이 아니다.** 연산마다 한 건만 발행한다. 실행 중에 10 Hz 목표 토픽을 발행하지 않는다(수집 설계 D4).

**채널은 토픽 이름 하나가 아니라, 아래 항목을 정해 둔 토픽이다.** [토픽 이름 규약](../../topic_naming_contract.md)이 말하는 "논리 채널"과 같은 뜻이다. 서비스나 액션이 아니라 토픽이어야 하는 이유는, ROS 2 Humble 의 rosbag2 가 서비스 · 액션을 녹화하지 못해 **토픽만 데이터로 남기** 때문이다. 지금 MoveIt 이 컨트롤러로 궤적을 넘기는 액션 goal 이 녹화되지 않는 것도, 그리퍼 명령을 토픽(`/gripper_cmds`)으로 설계한 것도 같은 이유다([설계서](../../rdfp_framework_design.md) §2.2).

| 항목 | 정할 내용 | 어기면 |
|---|---|---|
| 이름 | `motion/trajectory` — 토픽 이름 규약에 따른 상대 이름 (§3.1) | 네임스페이스 · remap 이 먹지 않는다 |
| 타입 | `rdfp_msgs/MotionTrajectory` (신설, §3.1) | 적재 writer 를 만들 수 없다 |
| 값의 뜻 | 위 표 — 보간 전 · 중력 보상 전 경유점, 배율을 적용한 `time_from_start`, `header.stamp` = t₀ | 에러 없이 레이블만 조용히 틀린다 |
| 발행 시점 | 연산마다 한 건, 실행 직전 | 중복되거나 빠진다 |
| QoS | RELIABLE · VOLATILE · 큐 깊이 10 이상 | 아래 참고 |

**QoS 는 RELIABLE · VOLATILE 로 한다.**

- **RELIABLE** — 한 건을 잃으면 그 연산의 레이블을 만들 수 없다. 주기 토픽처럼 다음 메시지가 메워 주지 않는다.
- **VOLATILE — TRANSIENT_LOCAL(latched)로 두지 않는다.** 실행 궤적은 지나간 사건이다. `/session` 은 늦게 뜬 노드가 현재 상태를 봐야 해서 TRANSIENT_LOCAL 이지만, 실행 궤적을 latched 로 두면 녹화기가 늦게 붙었을 때 이전 연산의 궤적을 다시 받아 **중복 기록**되고, 그 stamp 가 에피소드 창 밖이면 적재가 버린다. 대신 녹화기를 수집 전에 먼저 띄운다.
- **큐 깊이** — 연산이 짧게 연달아 실행돼도 빠지지 않게 10 이상으로 둔다.

**발행만으로는 데이터가 되지 않는다.** 녹화 목록 추가(R7)와 적재 writer · 테이블(I1)이 함께 있어야 DB 에 남고, 중단 시각은 연산 이벤트(R2)가 준다(§4).

## 2. 현재 코드 — 궤적이 만들어지는 네 경로

트윈 연산은 모두 `create_move_group_client()` 가 만든 클라이언트를 거친다. 그래서 **클라이언트에 발행을 넣으면 트윈으로 만든 데이터가 모두 덮인다.** 다만 클라이언트 두 종류와 연산 두 종류에 따라 궤적이 만들어지는 위치가 다르고, 한 경로에서는 클라이언트가 궤적을 보지 못한다.

| 경로 | 계획 | 속도 배율이 적용되는 곳 | 컨트롤러로 넘기는 곳 | 클라이언트가 실행 궤적을 아는가 |
|---|---|---|---|:-:|
| **펑션베이 관절 공간** (`move_to_joints` · `move_to_named_target`) | `plan_joints` (계획만, `plan_only=True`) | MoveIt 시간 파라미터화 (요청의 속도 배율) | `TrajectoryStreamer.stream` | ○ |
| **펑션베이 데카르트** (`follow_trajectory`) | `GetCartesianPath` | 클라이언트의 `scale_trajectory_velocity` | `TrajectoryStreamer.stream` | ○ |
| **isaac 데카르트** (`follow_trajectory`) | `GetCartesianPath` | 클라이언트의 `scale_trajectory_velocity` | `ExecuteTrajectory` goal | ○ |
| **isaac 관절 공간** (`move_to_joints` · `move_to_named_target`) | **move_group 이 계획과 실행을 한꺼번에** (`_execute_joint_goal`, `plan_only=False`) | MoveIt 안에서 | move_group → JTC | **✗** |

데카르트 계획은 `GetCartesianPath` 가 속도 배율을 적용하기 전의 궤적(L1)을 돌려주므로, 클라이언트가 배율을 적용한 뒤의 궤적(L2)을 실어야 시간이 맞는다. 생성 설계 §5.3 의 실측에서 속도 배율 0.1 일 때 발행 궤적은 0.59 s, 실제 실행은 5.92 s 였다.

## 3. 구현 작업

### 3.1 메시지 형식과 토픽 이름

검토한 선택지는 다음과 같다. 결정은 아래에 있다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| **표준 `trajectory_msgs/JointTrajectory`** | 새 메시지 타입이 필요 없다. `header.stamp` 를 JTC 도 "궤적 시작 시각"으로 해석하므로 뜻이 맞는다 | R2(연산 이벤트)와 짝지을 연산 ID 를 담을 필드가 없어 t₀ 로 짝지어야 한다. 속도 배율 · 재생 배율 같은 부가 정보도 담을 곳이 없다 |
| **신설 타입** (예: `rdfp_msgs` 에 연산 ID · `JointTrajectory` · 속도 배율 · 재생 배율) | R2 와 연산 ID 로 확실히 짝짓는다. 부가 정보를 함께 남긴다 | `rdfp_msgs`(별도 저장소)에 타입을 추가하고 빌드 순서를 지켜야 한다 |

- `robot_control` 은 이미 `rdfp_msgs` 에 의존하므로, 신설 타입을 써도 계층 경계 시험(`test_layer_boundary.py`)에 걸리지 않는다. 금지되는 것은 `SessionCommand` import 다.
- 적재 쪽(미구현 목록 I1)은 결정한 타입에 writer · 테이블을 묶는다.

#### 결정 (2026-09-17)

| 채널 | 토픽 이름 | 메시지 타입 |
|---|---|---|
| R1 실행 궤적 | **`motion/trajectory`** | **`rdfp_msgs/MotionTrajectory`** (신설) |
| R2 연산 이벤트 (짝) | **`motion/event`** (2026-09-18, [R2 문서](R2_연산_이벤트_채널_구현_설계.md) §3.1) | **`rdfp_msgs/MotionEvent`** (신설) |

**토픽 이름을 `motion/trajectory` 로 정한 이유** — [토픽 이름 규약](../../topic_naming_contract.md)에 맞췄다.

- 루트 상대로 적고 앞에 `/` 를 붙이지 않는다(규약 §2). 로봇별 네임스페이스가 나중에 자동으로 붙는다.
- 구현체 이름을 넣지 않는다. `~/` 나 노드 이름을 붙이면 노드를 바꿀 때 채널 이름이 따라 바뀐다(규약 §2.2 의 그리퍼 사례).
- 단수로 쓴다. 메시지 하나에 궤적 하나이고, 규약은 단수/복수를 메시지 모양에 따르게 한다(규약 §2.1).
- `motion/` 으로 묶는다. 팔 동작 연산에서 나오는 채널을 한 묶음에 두어, 같은 생산자(MoveGroup 클라이언트)가 내는 짝 채널(R2)과의 관계를 이름에 드러낸다. `scene/objects` · `camera/image_raw` 와 같은 방식이다.
- 묶음 안에서는 짧게 `trajectory` 로 쓴다. `motion/` 묶음이 범위를 좁혀 주기 때문이다. **어떤 궤적인지는 이름이 아니라 메시지 타입의 주석이 정의한다** — 실행 궤적(L2)이고, 보간 전 · 중력 보상 전 경유점이며, 시간은 배율을 적용한 뒤의 값이다. 이름만으로는 MoveIt 의 계획 궤적(`/display_planned_path`, L1)과 구분되지 않으므로, 타입 주석 첫머리에 "계획 궤적이 아니다"를 적는다.
- 구현할 때 규약 문서의 정규 이름 표(§2.3)에 올린다.

**메시지 타입을 신설 타입 `rdfp_msgs/MotionTrajectory` 로 정한 이유** — 위에서 검토한 표준 `JointTrajectory` 를 쓰지 않는다.

1. **적재는 토픽 이름이 아니라 메시지 타입으로 writer 와 테이블을 고른다**(`resolve_message_type`, 규약 §2.4). 표준 `JointTrajectory` 를 이 채널에 묶으면, 뜻이 다른 `JointTrajectory` 토픽이 녹화 목록에 들어오는 순간 같은 테이블에 섞인다. 예를 들어 servo 가 JTC 로 보내는 단일점 궤적(`/panda_arm_controller/joint_trajectory`)이 그렇다. 전용 타입이면 "t₀ · 보상 전 · 배율 적용"이라는 채널의 뜻을 타입이 지킨다.
2. **R2 와 연산 ID 로 짝짓는다.** t₀ 로 짝지으면 지터와 연달아 실행한 연산에 취약하다. `GripperState` 가 `goal` 을 함께 실어 자기 완결적으로 만든 것과 같은 이유다.
3. **배율 같은 부가 정보를 함께 남긴다.**
4. **타입 이름은 토픽 이름과 짝을 맞췄다.** `gripper_cmds` 와 `GripperCommand`, `scene/objects` 와 `SceneObjects` 처럼 채널과 타입 이름이 대응한다.

**역할을 나눈다.** R1 은 "무엇을 보냈나"(궤적과 그 시간 조건)를, R2 는 "어떤 연산이었고 어떻게 끝났나"(연산 이름, 해석된 목표, 결과, 끝난 시각)를 싣는다. 같은 값을 두 메시지에 두지 않는다.

`rdfp_msgs/MotionTrajectory` 의 필드는 다음과 같다. 기존 `rdfp_msgs` 처럼 필드마다 뜻과 이유를 주석으로 적는다.

```
# 연산 하나를 실행할 때 컨트롤러로 보낸 궤적(L2, 실행 궤적). 토픽 `motion/trajectory` 로 연산마다 한 건 발행한다.
# 학습 데이터 관절-계획 레이블의 원천이다 (docs/collect/R1_실행_궤적_채널_구현_설계.md).
#
# **계획 궤적(`/display_planned_path`, L1)이 아니다.** 데카르트 연산은 속도 배율 때문에 두 궤적의 시간이
# 다르다 — 속도 배율 0.1 에서 계획 궤적은 0.59 s, 실제 실행은 5.92 s 였다.
#
# header.stamp 는 **궤적의 0초가 실제로 시작된 시각(t₀)** 이다. 발행 시각이 아니다 —
# '이 메시지를 내보낸 때'를 무심코 찍으면 안 된다는 뜻이다. **두 백엔드 모두 t₀ 를
# 발행 직전 순간으로 정했으므로 결과적으로 값은 같아지지만**(isaac 은 goal 전송 직전,
# 펑션베이는 첫 명령 발행 시각 — §3.5), 그것은 발행 지점을 t₀ 에 맞춰 고른 결과이지
# '발행 시각을 쓴다'는 규칙이 아니다. 발행이 늦어지면 t₀ 는 따라가면 안 된다.
# **비워 두면 안 된다** — 적재가 이 값으로 에피소드 창을 거르므로, 비면 어느 에피소드에도
# 속하지 못한다. frame_id 는 ''.
std_msgs/Header header

# 연산 식별자. 같은 연산의 연산 이벤트(R2)와 짝짓는다. 클라이언트가 연산마다 새로 만든다(UUID).
string operation_id

# 계획에 적용한 속도 배율과 스트리밍 재생 배율. trajectory 의 time_from_start 에는 이미 반영돼 있다.
float64 velocity_scaling
float64 time_scaling

# 경유점. **보간 전 · 중력 보상 전** 값이다. time_from_start 는 두 배율을 적용한 실제 실행 시간이고,
# velocities · accelerations 도 그에 맞게 고친 값이다. trajectory.header 는 비운다
# — 시각은 위 header 하나에만 둔다.
trajectory_msgs/JointTrajectory trajectory
```

R2 의 토픽 이름과 메시지 타입은 R2 설계에서 정한다. R1 과 짝을 맞추는 데 필요한 뼈대는 다음과 같다.

```
std_msgs/Header header    # 연산이 끝난 시각 (정상 종료 · 중단 · 실패 모두)
string operation_id       # MotionTrajectory 와 같은 값
string operation          # move_to_joints · move_to_named_target · follow_trajectory
string result             # succeeded · aborted · failed
# + 해석된 목표 (관절값 또는 pose) — R2 설계에서 정한다
```

QoS 는 §1 대로 RELIABLE · VOLATILE · 큐 깊이 10 이상이다.

### 3.2 펑션베이 — 발행 지점은 `TrajectoryStreamer.stream` 한 곳

스트리밍 진입점은 넷이지만 모두 `TrajectoryStreamer.stream` 으로 모인다.

| 진입점 | 경로 |
|---|---|
| 동기 (`move_to_joints_streamed` 등) | `stream_trajectory` → `stream` |
| 비동기 세 경로 (`move_to_joints_streamed_async` · `follow_trajectory_async` 등) | `stream_async` 가 스레드에서 `stream` 을 부른다 |

`stream` 은 발행에 필요한 것을 모두 안다.

- **최종 시간** — 경유점 시각에 `time_scaling` 을 곱해 발행 시각을 만든다(`_build_samples`).
- **시작 순간** — 첫 명령을 보내기 직전이다.
- **중력 보상 전 값** — 보상은 명령을 만들 때(`_build_command` → `_apply_gravity`) 더해지므로, 입력 궤적의 경유점은 보상 전이다.

그래서 **첫 명령을 보내기 직전에 노드 시계로 t₀ 를 찍고, 실행 궤적을 한 건 발행한다.**

- **경유점을 싣는다.** `publish_rate` 로 보간한 50 Hz 샘플이 아니다. 정보는 경유점에 있고, 보간은 export 에서 다시 할 수 있다.
- **재생 배율을 궤적에 반영한다.** `time_from_start` 에 `time_scaling` 을 곱할 때, 경유점의 속도는 `time_scaling` 으로, 가속도는 `time_scaling²` 으로 나눈다. 그래야 export 가 3차 Hermite 보간(ACT 문서 §9 의 4)을 쓸 때 위치와 속도가 어긋나지 않는다.
- 중단(`stop()`)되더라도 이 메시지는 고치지 않는다. 중단 시각은 R2 가 남기고, export 가 그 시각에서 궤적을 자른다(수집 설계 D5).

### 3.3 isaac 데카르트 — `execute_trajectory` 에서 발행

`follow_trajectory(_async)` 는 속도 배율을 적용한 궤적으로 `ExecuteTrajectory` goal 을 만든다. `execute_trajectory(_async)` 도 같은 goal 을 보낸다. **goal 을 보내기 직전에 실행 궤적을 발행한다.**

궤적은 이미 클라이언트에 있고, **t₀ 는 그 발행 순간(goal 전송 직전)으로 정했다**(§3.5). 즉 `header.stamp` 는 발행하는 쪽이 자기 시계로 찍으면 되고, 응답을 기다리거나 컨트롤러 토픽을 구독할 필요가 없다.

### 3.4 isaac 관절 공간 — 계획과 실행을 나눈다

지금은 `MoveGroup` 액션을 `plan_only=False` 로 보내므로, move_group 이 계획과 실행을 함께 하고 클라이언트는 궤적을 받지 못한다.

| 방법 | 내용 | 판단 |
|---|---|---|
| **(a) 계획과 실행을 나눈다 — 채택** | `plan_joints` · `plan_named_target` 으로 계획한 뒤 `execute_trajectory` 로 실행하고, 그 직전에 실행 궤적을 발행한다(§3.3 과 같은 지점) | **부품이 이미 있다** — 계획 전용 함수는 기반 클래스에, `execute_trajectory` 는 JTC 클라이언트에 있다. 펑션베이 경로가 이미 "계획 → 스트리밍"이라 **네 경로가 같은 구조**가 된다. 대가는 계획 · 실행 사이에 왕복이 한 번 늘고, 실행 시작 상태 허용 오차 검사가 move_group 의 일괄 실행과 달라질 수 있어 **isaac 에서 트윈 동작을 다시 검증해야 한다**는 점이다 |
| (b) `/display_planned_path` 를 쓴다 | 관절 공간 계획은 계획 궤적 = 실행 궤적이므로, move_group 이 발행하는 계획을 녹화한다 | 코드 변경은 적다. 그러나 `header.stamp` 가 0 이라 적재가 에피소드 창 밖으로 버리고(별도 적재 경로 필요), 어느 연산의 궤적인지 짝짓는 방법과 t₀ 를 따로 정해야 한다. 데카르트 경로와 원천이 갈린다 |

**(a) 로 정했다 (2026-09-18).** 모든 경로에서 클라이언트가 실행 궤적을 직접 발행하게 되어 채널의 뜻이 한 가지로 정리되기 때문이다. 대가인 왕복 한 번과 실행 시작 상태 허용 오차 검사의 차이는 §5 의 isaac 검증과 §6 의 트윈 재검증에서 확인한다. 생성 설계 §13 의 10 에서 같은 두 안을 비교했다.

#### 결정 (2026-09-18) — isaac 의 t₀ 는 **goal 을 보낸 시각**

**먼저 t₀ 의 뜻을 못 박는다.** 실측값이 두 무리로 갈린다 — **명령 시간축이 시작된 시각** (후보 넷, 2~32 ms)과 **팔이 실제로 움직인 시각**(120 ms)이다. 어느 쪽을 t₀ 라 부르냐에 따라 답이 100 ms 넘게 달라진다. §3.1 의 정의가 *"궤적의 0초가 실제로 시작된 시각"* 이고 이 채널이 싣는 것은 **L2 = 컨트롤러로 보낸 명령**이므로, 명령 기록의 0초는 **컨트롤러가 그 궤적을 보간하기 시작한 순간**이다. 팔이 물리적으로 반응한 순간이 아니다. 그래서 앞 무리에서 고른다.

| 후보 | 중앙값 | 폭 | 판단 |
|---|---|---|---|
| **goal 전송** | 0 (정의) | — | **채택** — 클라이언트 자기 시계, 샘플링이 없다 |
| ① `ExecuteTrajectory` 수락 | 1.9 ms | 1.9 | 전송과 1.9 ms 차이뿐인데 발행을 goal 응답 콜백 뒤로 옮겨야 한다 |
| ② JTC 수락 | 3.6 ms | 4.7 | 1.7 ms 더 정확하자고 JTC 액션 상태 구독을 새로 붙여야 한다 |
| ③ `controller_state.reference` 첫 변화 | 12.6 ms | **36.5** | 뜻은 가장 가까운데 **수치가 가장 나쁘다** |
| ④ `/isaac/arm_command` 첫 변화 | 31.9 ms | 19.3 | 더 늦고 배선도 더 든다 |

**③ 이 함정이다.** 의미상 "JTC 가 보간을 시작한 순간"에 가장 가깝지만 57 Hz 로 샘플되므로 폭이 4.4~40.9 ms 다. 의미가 가깝다고 고르면 **가장 흔들리는 값**을 쓰게 된다.

**전송 시각은 §3.3 이 이미 정한 발행 지점과 같은 순간이다** — *"goal 을 보내기 직전에 발행한다"*. 그 자리에서 `header.stamp` 를 자기 시계로 찍으면 끝이고, 구조를 바꿀 필요도 기다릴 필요도 없다. ①·② 는 각각 1.9 ms · 3.6 ms 를 얻자고 발행 지점을 옮기거나 구독을 늘려야 해서 값어치가 안 맞는다.

**남는 편향을 숨기지 않는다.** 전송 시각을 쓰면 t₀ 가 실제 보간 시작보다 **약 12 ms 이르다** (② 가 3.6 ms 이고 JTC 는 다음 주기에 시작하므로 3.6~21 ms, ③ 실측 중앙값 12.6 ms 와 일치). 경유점 간격 100 ms 의 12 % 다.

⚠️ **보정 상수를 넣지 않는다.** 넣으려면 그 12 ms 를 한 제어 주기(17.5 ms)보다 잘 알아야 하는데 지금 관측 수단으로는 안 된다 — ±17.5 ms 로만 아는 값을 상수로 박으면 정확도가 아니라 부채가 는다. 펑션베이 t₀ 도 1~11 ms 의 slop 을 안고 있어(위 표) 두 백엔드가 같은 수준이다. 더 좁혀야 할 근거가 생기면 그때 **한 곳에서** 더한다.

**정작 봐야 할 것은 여기가 아니다.** 팔의 물리 지연 **120 ms 는 t₀ 를 무엇으로 고르든 사라지지 않고**, 경유점 간격 100 ms 를 넘는다. 같은 시각 T 에서 레이블(명령)과 관측 (이미지 · 관절)이 120 ms 어긋난다는 뜻이며, 이것은 t₀ 선택이 아니라 **ACT 레이블 설계**의 문제다 — [ACT_학습_샘플_구성.md](ACT_학습_샘플_구성.md) §5.2 로 넘긴다.

**실제 움직임 시작이 120 ms 다 — 경유점 간격(100 ms)보다 크다.** 이 설계가 걱정한 경우가 실제로 일어난다. mock(53~66 ms)의 2.4 배이므로 **mock 값을 isaac 에 옮기면 안 된다.** 따라서 t₀ 를 ①(1.9 ms)로 두면 궤적 전체가 경유점 하나보다 더 밀린다.

궤적 길이와 실제 실행 시간의 차이는 **시뮬레이터 배속으로 설명된다** — 실측 배속이 0.95 라 `길이 ÷ 0.95` 가 각각 2.58 · 3.91 · 11.14 s 이고 나머지가 위 시작 지연이다. `time_from_start` 는 sim 시간 기준으로 지켜진다.

**후보 ④ 는 '첫 발행'으로 쓸 수 없다.** `TopicBasedSystem::write()` 는 무조건 발행하지 않고 `Σ|측정 − 명령| ≤ trigger_joint_command_threshold`(기본 **1e-5** rad, 우리 xacro 는 안 준다) 면 건너뛴다. 그런데 **이동을 한 번이라도 하면 잔여 추종 오차가 5.458e-04 rad** (임계의 55 배)로 남아, 팔이 서 있어도 **57 Hz 로 끝없이 발행한다**(40 초 관찰, 값은 상수). 기동 직후 한 번도 안 움직인 상태에서만 0 건이다. 그래서 쓸 수 있는 것은 **'첫 변화'** 뿐이고, 그 값이 위 31.9 ms 다.

**③ 의 해상도 상한은 `state_publish_rate` 가 아니라 sim 스텝이다.** 이 설계는 "기동 시점에 1000 으로 주면 98 %" 라고 적었지만, isaac 에서는 `panda_isaac_ros2_controllers.yaml` 에 `state_publish_rate: 1000.0` 을 넣어도(파라미터 조회로 1000.0 확인) 실측 발행율이 **57 Hz** 였다. 이유가 둘 겹친다 — JTC 는 `update()` 안에서 발행하므로 `update_rate: 100` 이 1차 상한이고, `use_sim_time: true` 라 controller_manager 가 **sim 시계보다 빨리 돌 수 없는데** Isaac 이 60 Hz 로 스텝한다(`headless_bringup.py` 의 `PHYSICS_PERIOD_SEC = 1/60`, 실측 배속 0.95 → 57 Hz). `/clock` · `/joint_states` · `controller_state` 가 모두 같은 57 Hz 다. **그래도 기본 50 Hz 보다는 낫고, 넣어 두는 편이 맞다.**

⚠️ **측정 방법 주의 — 구독 노드를 본 스레드에서 `spin_once` 로 돌리면 안 된다.** goal 을 보내는 동안 그 루프가 멈춰 메시지가 DDS 큐에 쌓였다가 한꺼번에 배달되므로, '첫 수신'이 토픽의 성질이 아니라 **자기 스핀 간격**을 잰 값이 된다. 처음에 그렇게 재서 57 Hz(주기 17.5 ms) 토픽의 첫 수신이 22~34 ms 로 나왔다. 위 수치는 구독 노드를 **별도 스레드의 executor** 로 돌려 다시 잰 것이다. 측정 호스트는 `time.monotonic()` 과 벽시계가 0.000 %로 일치하고 역행이 없음을 확인했다 (§6 의 WSL2 경고는 펑션베이 쪽 다른 호스트 것이다).

| 0.3 | 3 | 0.649 s | 2.163 s | 3.333 | 3.333 | 2.257 s | +0.094 | −0.020 |
| 0.1 | 4 | 0.645 s | **6.451 s** | **10.000** | 10.000 | 6.881 s | +0.430 | +0.090 |

**§5 의 공통 행이 통과한다.** 배율 0.1 에서 L2 가 L1 의 **정확히 10 배**이고, 실제 실행 시간은 L2 를 시뮬레이터 배속(0.95)으로 나눈 값과 **90 ms** 안에서 맞는다 — 그 잔차가 아래 시작 지연이다. **L1 을 실으면 0.1 배율에서 시간이 10 배 틀린다** (0.645 s 대 6.451 s). §3.1 주석이 경고한 그대로다.

t₀ 후보는 **관절 공간과 같다** — 경로가 달라도 `execute_trajectory` → JTC 로 합류하기 때문이다.

| 후보 | 데카르트 (중앙값) | 관절 공간 |
|---|---|---|
| ① `ExecuteTrajectory` 수락 | 2.5 ms | 1.9 ms |
| ② JTC 수락 | 5.1 ms | 3.6 ms |
| ③ `controller_state.reference` 첫 변화 | 9.2 ms | 12.6 ms |
| ④ `/isaac/arm_command` 첫 변화 | 32.1 ms | 31.9 ms |
| (참고) 실제 움직임 | 130.6 ms | 120.0 ms |

#### 측정 중 만난 `allowed_start_tolerance` 실패 — 원인은 스택이 아니라 시험 동작이었다

데카르트 하강 뒤 `move_to_named_target('ready')` 가 13 ms 만에 `CONTROL_FAILED`(-4) 로
죽는 일이 반복됐다. move_group 로그는 이렇게 찍힌다:

```
Invalid Trajectory: start point deviates from current robot state more than 0.01
joint 'panda_joint7': expected: -0.5269, current: -0.5169
```

그 자세에서 `/joint_states` 의 joint7 이 매 표본마다 두 값만 교대했고(폭 정확히
0.01000 rad = `allowed_start_tolerance` 기본값), 계획과 검증이 반대 위상에서 샘플되면
걸려 **간헐적으로** 실패했다(복귀가 2~5 회째에 통과).

**원인을 Isaac 의 drive 게인으로 의심했는데, 아니었다.** `tune_drive.py` 가 stiffness 를
25 배(400→10000) 올리면서 `maxForce` 는 에셋 기본값(joint1~4 **87** · joint5~7 **12** N·m)
으로 두어, K=10000 에서 오차 1.2 mrad 만에 포화한다는 점이 그럴듯해 보였다. 실제로 그
자세에서 joint4·5·6·7 이 전부 포화 판정이었고 joint7 은 필요 토크가 한계의 1000 배였다.

**진짜 원인은 시험 동작이 손을 탁자에 박은 것이다.** `ready` 의 `panda_link8` 은 z=0.5901
이고 **손끝은 그보다 약 103 mm 아래**다(`panda_link8 → panda_leftfinger` 가 58.4 mm,
패드가 그 아래). 탁자 상면은 0.4 이므로 **안전 하강 한계는 87 mm** 인데 120 mm 를 내려
손끝이 33 mm 파고들었다. joint7 의 1.2 rad 어긋남도, 0.01 rad 진동도 **접촉 반력과 접촉
채터**였다.

대조로 확인했다 — 같은 절차를 **60 mm** 하강으로 바꾸면:

| 하강 | joint7 오차 | 포화 관절 | 최대 오차(일곱 관절) |
|---|---|---|---|
| 120 mm (손끝이 탁자 33 mm 아래) | **1.2014 rad** | 4 · 5 · 6 · 7 | 1.2014 |
| **60 mm (여유 안)** | **0.0000 rad** | 없음 | **0.0002** |

`ready` 정지 상태에서도 일곱 관절 오차 ≤ 0.0003 이고, 관절 하나씩 0.4~0.5 rad 씩
움직여도 오차 ≤ 0.0001 이다. **드라이브 게인 결함은 없다** — `tune_drive.py` 는 건드리지
않았다. (`maxForce` 를 안 올린 것은 사실이지만, 접촉이 없으면 문제가 드러나지 않는다.
접촉 작업을 본격적으로 하게 되면 그때 따로 볼 항목이다.)

**남는 교훈 둘.**
① **손끝 여유를 먼저 계산한다** — `/ee_pose`(= `panda_hand`)의 z 를 탁자 높이와 비교하면 103 mm 를 놓쳐 "여유가 있다"고 오판한다. 펑션베이 쪽 `grasp_center` 함정(CLAUDE.md)과 같은 실수다.
② **접촉이 생긴 뒤에는 계획·실행 분리 경로가 간헐적으로 깨진다** — 접촉 채터의 진폭이 `allowed_start_tolerance`(0.01)를 넘을 수 있기 때문이다. (a) 는 계획과 실행 사이에 왕복이 하나 더 들어가 그 창이 넓으므로, **접촉을 다루는 연산에서는 재시도나 정착 대기가 필요하다.**

## 6. 주의

- **개발 호스트(WSL2)에서는 시각이 어긋난다.** 펑션베이에서 `header.stamp` 는 노드 시계(벽시계)를 따르지만, 스트리머는 명령 간격을 `time.monotonic()` 으로 잰다. 이 호스트는 monotonic 이 약 5.7 % 빠르고 벽시계가 약 32 s 마다 약 1.7 s 되돌아간다(생성 설계 §5.6). "t₀ + `time_from_start`" 로 계산한 시각과 실제 발행 시각이 그만큼 어긋날 수 있다. **학습 데이터 생성은 이 현상이 없는 호스트에서 한다.**
- **보상 전 값을 싣는다.** 관절-계획 레이블에는 중력 보상 오프셋이 없어야 백엔드를 섞을 수 있다(수집 설계 D2). 배치 때는 배치 경로에서 보상을 건다.
- **isaac 트윈 동작을 다시 검증한다.** (a) 로 정했으므로 isaac 에서 관절 공간 연산의 실행 방식이 바뀐다. 트윈 REST 로 하던 수집 전 과정(세션 → 리셋 → 에피소드 → rosbag → mp4 → DB)을 다시 통과시킨다. **접촉을 만드는 연산에서 `allowed_start_tolerance` 간헐 실패를 함께 본다** — §3.5 에서, 손끝이 탁자에 눌린 뒤 접촉 채터가 0.01 rad 를 넘어 계획·실행 분리 경로가 위상에 따라 `CONTROL_FAILED`(-4) 로 죽는 것을 실측했다. 접촉이 없으면 추종 오차는 0.0002 rad 이라 문제가 없다. 재시도 없이 돌리면 "가끔 안 된다"로 나타난다.
- **발행 실패가 연산을 막지 않게 한다.** 실행 궤적 발행은 기록용이므로, 발행에서 예외가 나도 팔 동작은 계속되게 하고 경고를 남긴다. 다만 발행되지 않은 연산은 학습에 쓸 수 없으므로 적재 검증(미구현 목록 I5)에서 드러나야 한다.
