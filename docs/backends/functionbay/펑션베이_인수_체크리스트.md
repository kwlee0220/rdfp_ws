>
> **호출** "체크리스트 확인해줘" 라고 하면 A 단계를 돌리고 결과를 표로 낸다. B·C 단계는 팔이 실제로
> 움직이므로 **결과를 보여 준 뒤 따로 승인을 받고** 진행한다.

**한 회차의 순서**

1. **빌드와 씬을 식별한다** — 실행 파일 · 설정 DB · 활성 씬 · 솔버 프로세스 (§0 빌드 이름).
2. **띄운다** — 솔버 → 시뮬레이터 → `ros_tcp_endpoint` → `/scene/start` → 설치본 재빌드 → 제어 스택 → **차트 종료 대기** (§0 전제).
3. **A 단계**(팔 안 움직임)를 돌려 표로 낸다 → 승인을 받는다.
4. **B 단계**(팔 움직임) → **C 단계**(스택 통합).
5. **결과 문서**를 `checklist_results/` 에 쓴다 (§F). 새로 드러난 함정·절차 변경은 **이 문서**에 반영한다.

## 0. 판정 규칙 — 먼저 읽는다

**이 체크리스트의 목적은 합격/불합격이 아니라 "무엇이 달라졌는가"를 놓치지 않는 것이다.** 직전 결과와 다른 값이 나오면 세 가지 중 하나이며, 셋을 구분하지 않으면 오진한다.

| 판정 | 뜻 | 다음 행동 |
|---|---|---|
| **개선** | 벤더가 요청 항목을 반영했다 | 해당 벤더 요청(A-n/B-n)을 닫는다 — [요청 목록](펑션베이_요청_목록.md) §0 |
| **회귀** | 전에 되던 것이 안 된다 | 벤더에 회귀 보고. 예: A-9 stamp 가 벽시계에서 경과시간으로 되돌아가는 것 |
| **변경** | 의도적 사양 변경인데 통보가 없었다 | **가장 위험하다.** 우리 코드의 전제가 조용히 깨진다 |

**대조는 같은 씬끼리 한다.** 같은 빌드라도 씬(솔버)이 다르면 dead time · τ · 주기적 정지 · 처짐 · 관절 한계 강제 · 파지 거동이 통째로 다르다 — `r2` 와 `t1` 은 응답 속도부터 약 2배 차이가 난다. 다른 씬의 값과 비교해 "회귀"라고 하면 안 된다.

**보상 조건을 함께 적는다.** 처짐에 걸리는 항목(B-3 · B-4 · B-8 · B-9 · B-17 · C-8)은 중력 보상의 **주체**(우리 / 벤더 / 없음)에 따라 값이 바뀐다. 결과가 같아 보여도 주체가 다르면 같은 장치로 잰 것이 아니다.

### 회차마다 바뀌는 항목 — 곧바로 회귀로 판정하지 않는다

**A-9(stamp 기준) · A-10 · A-11(잔차 · 진행률) · A-17(정지 길이)은 같은 빌드 · 같은 씬 · 같은 설정에서도 회차마다 달라진다.** `r2` 에서는 같은 실행 파일로 잰 세 회차의 `/output/*` stamp 가 벽시계 → 경과시간 → 경과시간으로 바뀌었고, 정지 비율·길이도 회차마다 달랐다(회차별 표는 [이력_20261001](../../archive/functionbay/펑션베이_인수_체크리스트_이력_20261001.md) §G.1a). 이 넷은 직전 결과와 달라도 **지금까지 관측된 범위 안인지**부터 본다.

세 값은 한 현상의 세 측면이다 — **정지(A-17)가 있으면 잔차가 톱니를 그리고(A-10) 진행률이 1 에서 벗어난다(A-11).** 정지가 없으면 셋이 함께 정상이 된다. 그래서 A-10 · A-11 은 A-17 과 함께 읽는다.

### 측정 전 반드시 확인할 함정

1. **토픽이 목록에 있는 것과 발행되는 것은 다르다.** `ros_tcp_endpoint` 는 Unity 가 끊겨도 등록된 퍼블리셔를 유지한다. `ros2 topic list` 에 보여도 한 건도 안 올 수 있다 — **반드시 실제 수신 건수로 판정한다.** 2026-09-17 에도 겪었다: 이전 씬(`t1`)에서 등록된 `/output/endeffector` 가 r2 로 바꾼 뒤에도 "발행자 1, 수신 0" 으로 남았고, endpoint 를 새로 띄우자 그래프에서 사라졌다.
2. **`ros2` CLI 데몬이 눈이 멀 수 있다.** 데몬이 `ros_tcp_endpoint` 보다 늦게 뜨면 그래프를 하나도 못 보고, `ros2 topic list` 가 `/rosout` 만 낸다. 아무것도 안 보이면 **먼저 `--no-daemon` 으로 대조**한다. **`ros2 daemon stop && start` 로도 안 낫는 경우가 있다.** 데몬을 지운 직후에는 `ros2 node list` 가 수십 초 걸려 타임아웃으로 끝나기도 한다 — "스택이 안 떴다"로 판정하기 전에 launch 로그를 본다. `rclpy` 로 직접 구독하는 스크립트(`fb_*`)는 데몬을 안 타므로 무관하다.
3. **`ros2 topic hz` 는 창이 찰 때까지 기다려 읽는다.** 첫 줄을 읽으면 틀린다 — 한때 카메라를 4.4 Hz 로 오독했다.
4. **관절 하나·방향 하나로 "무반응"을 판정하지 않는다.** 한계 근처에 걸린 관절 하나를 전체 고착으로 오진한 적이 있다. `fb_raw` 처럼 7관절 전부를 본다.
5. **접촉을 고착이나 중력 처짐으로 읽지 않는다 — 단 그리퍼 `effort` 는 접촉력이 아니다.** `effort = Kp × 잔차`(그리퍼 `Kp=200`)이므로 **정지 상태에서만** 접촉 판정에 쓸 수 있다. `> 1 N·m` = `잔차 > 0.005 rad` 이고, **이동 중에는 접촉이 없어도 잔차가 크다.** 무반응처럼 보이면 **중력 토크가 없는 `joint1`/`joint7` 단독 명령**으로 명령 경로부터 가른다. (`t1` 6축 그리퍼에서는 막힌 쪽이 접촉축(2·3·5·6)에만 잔차를 남긴다 — [이력_20260917](../../archive/functionbay/펑션베이_인수_체크리스트_이력_20260917.md) §B-12~14.)
6. **`stamp` 오프셋의 산포를 '지터'로 읽지 않는다.** 정지(A-17)가 있는 씬에서는 시뮬레이터가 약 34초마다 1~2초 멈추고 그 사이 조금 빠르게 진행해서 오프셋이 **톱니**를 그린다. 창을 어디에 걸치느냐에 따라 평균이 크게 달라진다 — **180초 이상 관측해 정지를 5회 담는다.**
7. **진행률(`stamp_rate`)을 끝점 두 샘플로 재지 않는다.** 톱니 진폭이 잡음보다 커서 끝점 추정은 ±2% 가 흔들린다. `fb_stamp.py` 의 회귀값을 쓴다.
8. **정지 중에는 우리 Python 프로세스도 멈춘다 — 정지를 실시간으로 감지할 수 없다.** `rclpy.spin_once(timeout_sec=0.004)` 가 정지 길이만큼 블록되고, 스핀을 별도 스레드로 빼도 같다(DDS 대기가 GIL 을 잡는다). 귀결 둘: ① 정지 구간에 무언가를 **주입하는** 시험은 구독을 가진 Python 프로세스로는 할 수 없다. ② `spin_once` 체류시간이나 수신 공백으로 정지를 **사후에** 재는 것은 유효하다 — `fb_stall_when.py` 가 그렇게 한다. 해제 직후에는 **캐치업 발행**이 몰려 들어온다.
9. **발행 주기는 시뮬레이터 XML 로 정하는 설정값이다** — 고정 상수가 아니다. `r2` 는 `VariableModel/r2__panda_robotiq_ref_1_vm.xml` 의 `<ROS2_Topic Hz="0">`(**0 이면 약 50 Hz 로 나온다**), 카메라는 `r2__RGBCamera_1_vm.xml` 의 `Publish_Frequency="10"`·`Frequency="10"` 이다(`t1` 은 `t1__` 파일). 관측이 낮게 나왔다고 결과를 그대로 적지 말고 **설정을 먼저 확인**한다. **XML 은 시뮬레이션(Play) 시작 시점에 다시 읽힌다** — 앱 내 재시작으로 충분하다. 파일은 **BOM + CRLF** 이므로 편집 시 보존한다. ⚠️ **새 빌드는 값을 되돌려 온다** — `MMR-Build_260929` 의 `t1` 은 `Hz="10"` 으로 왔고(관절 보고 10.5 Hz) 50 으로 고쳐야 했다. ⚠️ **같은 값이 두 파일에 있다** — `BlockParameter/<씬>__panda_robotiq_ref_1_bp.json` 의 `{"Name":"Hz"}` 는 모델러가 읽는 쪽이라, vm.xml 만 고치면 **모델러로 씬을 저장할 때 되돌아갈 수 있다.** 고쳤으면 결과 문서에 어느 파일을 고쳤는지 적는다.
10. **팔만 안 움직이면 `Player.log` 부터 본다 — 시뮬레이터는 못 푼 명령을 조용히 버린다 (2026-09-14).** `/input/panda_joint` 의 `JointState` 에서 **`velocity` 가 비어 있으면** Unity 쪽 `JointStateMsg` 역직렬화가 `ArgumentException: Offset and length were out of bounds` · `OverflowException` 으로 실패하고 **ROS 쪽에는 아무 에러도 없다.** 그리퍼(`Float64MultiArray`)는 같은 순간에도 움직여 "명령 경로는 산다"로 오판하기 쉽다. 필드 조합 실측(joint7 +0.1 rad): name+position → **이동 0 · 예외 +62**, +velocity 0 → **+0.1000 rad · 예외 0**. **`velocity` 만 0 으로 채우면 된다** — 우리 쪽 발행부 전부가 그렇게 하며, **새 스크립트가 `JointState` 를 직접 만들면 같은 줄을 넣는다.** 로그 위치: `C:\Users\<user>\AppData\LocalLow\MetaMotionX\MetaMotionRobot\Player.log`(WSL 에서 `/mnt/c/Users/<user>/AppData/LocalLow/...`). **앱을 재기동하면 덮어써진다** — 옛 회차와 대조하려면 먼저 복사해 둔다.
11. **`ros_tcp_endpoint` 는 우리 launch 가 띄우지 않는다 (2026-09-17).** 시뮬레이터를 재시작했는데 endpoint 가 없으면 `readiness_gate` 가 *"Waiting for the simulator: first message on '/output/panda_joint' (timeout 60s)"* 로 끝나고 **launch 전체가 종료**된다. 이때 `Player.log` 끝에는 `Connection to 127.0.0.1:10000 failed … 연결을 거부` 가 계속 반복된다 — ROS 쪽만 보면 "시뮬레이터가 발행을 안 한다"로 보인다. **`ss -ltnp | grep :10000` 으로 먼저 확인**하고, 없으면 띄운다(§0 전제). 이미 떠 있는데 또 띄우면 포트가 충돌한다. endpoint 가 뜨면 Unity 는 스스로 재접속하며, 직후 `Not registered to publish topic` 몇 줄은 정상이다.
12. **설치본이 소스보다 낡았을 수 있다 — `install/` 은 링크가 아니라 복사본이다 (2026-09-17).** C-10 에서 `rdfp_collect.launch.py` 가 *"launch configuration 'enable_image_recorder_node' does not exist"* 로 첫 노드만 띄우고 멈췄는데, 원인은 설치본이 소스보다 옛 판이었던 것이다(옛 판은 `backend:=` 인자도 모른다). **인수 전에 `colcon build --packages-select rdfp_msgs robot_control rdfp` 로 맞춘다.** 설정 파일(`config/backends/*.yaml` 등)도 같다 — 고친 뒤 재빌드하지 않으면 노드가 옛 값을 읽는다. ⚠️ **`rdfp_msgs` 를 빼면 안 된다 (2026-09-29)** — 설치본에 `MotionEvent`·`MotionTrajectory`(R1·R2, 09-18 신설)가 없어 `ee_pose_node` 가 `ImportError: cannot import name 'MotionEvent'` 로 **죽고 `/ee_pose` 가 한 건도 오지 않았다**(C-6 이 0건). launch 는 함께 죽지 않으므로 증상은 그 노드만 조용히 없는 것이다.
13. **관절 보고가 묶여 도착한다 (A-21, 2026-09-17).** stamp 간격은 고르지만 수신은 2~3건씩 몰려 온다. **수신 시각으로 재는 값**(dead time, 정착 판정, servo 되읽기)은 그 간격만큼 뭉개진다 — B-6·B-13 의 dead time 이 두 무리로 갈리는 것이 그 흔적으로 보인다. 데이터셋은 stamp 로 정렬하므로 영향이 없다 — **우리 스택은 stamp 를 수신 시각이 아니라 시뮬레이터 stamp + 오프셋으로 정렬하므로**(§A-9 상세) `/joint_states`·카메라 stamp 는 이 묶음과 무관하다. `joint_state_fusion` 을 `stamp_source:=now` 로 되돌리면 절반 넘는 stamp 가 5 ms 안에 몰린다.
14. **씬의 솔버 프로세스가 떠 있는지 먼저 센다 — 없어도 토픽은 정상으로 보인다 (2026-09-29 오진).** `r2` 는 `solver/RecurDyn/SolverTCPServer.exe`, `t1` 은 `solver/Crisp/CrispSolver.exe` 가 돌아야 한다. **솔버 없이도** Unity 는 `/output/*` 를 **50 Hz 로 발행하고**(값이 전부 `0.0000` 에 고정된 채) `/clock` 도 진행하며, 명령을 보내면 `Player.log` 에 `[PandaCommandTopicApplier] 토픽 명령 감지 → 토픽 모드 전환` 까지 찍힌다 — **팔·그리퍼만 0 % 로 안 움직인다.** 그 증상은 벤더 A-4(수신 경로 고착)와 구별되지 않아 실제로 A-4 재현으로 오판했다. 지문 셋: ① **전 관절이 정확히 0.0000 이고 변하지 않는다**(정상 회차는 차트 종료 자세에 있다) ② `tasklist.exe | grep -iE "SolverTCP|Crisp"` 에 그 씬의 솔버가 없다 ③ A-17 정지가 **약 2.1 s 로 균일**해진다(솔버 응답을 기다리는 것으로 보인다 — 정상 정지는 길이에 편차가 있다). ⚠️ **다른 씬의 솔버가 남아 있을 수 있다** — `CrispSolver.exe` 만 떠 있는 채로 r2 를 띄워서, 그 프로세스를 보고 "솔버는 돌고 있다"로 읽었다. **씬에 맞는 이름인지** 본다. 그 조건에서 잰 회차는 **폐기하고 결과 문서에 이유를 적는다.**
15. **씬을 바꾸면 우리 설정도 함께 바꾼다 (2026-09-17).** 순서: ① 시뮬레이터와 솔버를 **닫고**, 새 씬의 솔버를 띄운 뒤 시뮬레이터를 **`-Scene LAB_ETRI -Model <씬>_ms`** 로 다시 띄우고 `/scene/start` 로 시작한다 — **시작할 때** 앱이 `Database/SolverConfig/SolverConfig.json` 의 `MsFile` 을 **스스로 고쳐 쓴다**(손으로 고치지 않는다 — 실행 중에 고치면 덮어써진다. 시작 전에는 이전 씬을 가리키므로 `fb_gains.py` 는 시작한 뒤에 돌린다. 절차: [펑션베이_시뮬레이터_사용법.md](펑션베이_시뮬레이터_사용법.md) §4) ② `config/backends/functionbay.yaml` 의 `solver` · `gripper.profile_file`(`functionbay_gripper_{recurdyn,crisp}.json`) · **`motion.gravity_compensation` 블록**(벤더가 보상하는 씬은 없음, 아닌 씬은 블록 + 그 씬의 `kp` — A-19)을 바꾸고 **`robot_control` 을 재빌드**한다 ③ 시뮬레이터를 띄운 뒤 **ROS 스택을 `kill_stack.sh --ros` 로 정리하고 다시 띄운다**(sim 시계가 0 으로 되감겨 살아남은 노드의 TF 버퍼가 `TF_OLD_DATA` 를 낸다). 확인은 기동 로그의 `convention: solver=RecurDyn scene=r2` 한 줄이다. 그리퍼 규약을 안 바꾸면 그리퍼 노드가 보고 축 수(2 대 6)와 선언을 대조해 **명령을 거부한다.**
16. **스크립트의 첫 상태 대기 타임아웃은 다시 돌린다 (2026-09-29~30).** `fb_ready.wait_for_state`(5 s)가 `no JointState received on /output/...` 로 끝나는 일이 회차마다 몇 번씩 있다 — 정지가 없는 회차에도 나왔으므로 **구독 디스커버리 경합**으로 본다. 재시도하면 통과한다. `fb_stamp` 가 같은 이유로 한 건도 못 받을 수 있다 — **로그에 `경고: 그래프에 없는 토픽` 이 있으면 결과를 버리고 다시 돌린다.** 재시도한 것은 결과 문서에 적는다.
17. **시뮬레이션을 시작하면 차트가 자동으로 돈다 — 끝나기 전에 `/input/*` 로 명령을 보내면 차트가 끊긴다 (2026-10-01).** `/scene/start` 와 함께 씬의 SignalChart(t1 `panda_peginhole_file` 11 s · r2 `panda_peginhole_g2` 20 s)가 재생되어 팔이 peg 를 집어 구멍에 넣는다. 그 도중 `/input/panda_joint` · `/input/gripper_joint` 로 명령이 하나라도 가면 시뮬레이터가 `[PandaCommandTopicApplier] 토픽 명령 감지 → 토픽 모드 전환 (이후 커맨드 파일 무시).` 로 바꾸고 **차트를 버린다** — 팔은 차트 중간 자세에, peg 는 엉뚱한 곳에 남아 B 단계의 시작 상태(peg 가 `peg_hole` 안)가 깨진다. **`./scripts/functionbay/fb_wait_chart.py` 가 끝날 때까지 팔·그리퍼를 움직이지 않는다**(§0 전제 9). 로봇 스택은 기동만으로는 `/input/*` 에 아무것도 내지 않으므로 먼저 띄워도 된다.

```bash
export ROS_DOMAIN_ID=31
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp     # 시뮬레이터 브리지와 반드시 같아야 한다
```

솔버 · 시뮬레이터 · endpoint · 로봇 스택을 띄우는 명령은 [펑션베이_시뮬레이터_사용법.md](펑션베이_시뮬레이터_사용법.md) 에 있다. 여기서는 순서와 인수 때 확인할 것만 적는다.

1. **씬을 정한다** — 시뮬레이터 인자 `-Model <씬>_ms` 가 정한다(`r2_ms` · `t1_ms`). 시뮬레이션을 시작할 때 앱이 `SolverConfig.json` 의 `MsFile` 을 그 씬으로 고쳐 쓴다(함정 15).
2. **그 씬의 솔버를 먼저 띄우고 시뮬레이터를 띄운다** — 시뮬레이터는 모델까지 로드하고 **기다린다**(저절로 시작하지 않는다). **그 씬의 솔버 프로세스가 떴는지 센다**(함정 14):
   ```bash
   tasklist.exe | grep -iE "SolverTCP|Crisp"
   ```
3. **`ros_tcp_endpoint`** — 먼저 떠 있는지 본다(함정 11). 없으면 띄운다 — **Claude Code 의 Bash 샌드박스 안에서는 띄우지 않는다**(TCP 는 열려도 DDS 가 막혀 토픽이 안 보인다):
   ```bash
   ss -ltnp | grep :10000
   source ~/development/ros/tcp_ws/install/setup.bash
   ros2 daemon start                                   # 먼저 데몬
   ros2 run ros_tcp_endpoint default_server_endpoint   # 그다음 endpoint (기본 0.0.0.0:10000)
   ```
4. **시뮬레이션을 시작한다** — `/output/*` 는 이 뒤에 생긴다. `Player.log` 에 `On Start Simulation` 과 솔버 연결(`[SolverTCPConnector] vm.xml: 127.0.0.1:<포트>` → `비동기 워커 모드로 통신 시작.`)이 찍힌다:
   ```bash
   ros2 topic pub --once -w 1 /scene/start std_msgs/msg/String "{data: ''}"
   ```
5. **우리 설정이 씬과 맞는지** 본다 — `config/backends/functionbay.yaml` 의 `solver` · `gripper.profile_file` · `motion.gravity_compensation`(함정 15), 그리고 `./scripts/functionbay/fb_gains.py`(A-19).
6. **설치본을 소스와 맞춘다**(함정 12): `colcon build --packages-select rdfp_msgs robot_control rdfp`
7. **제어 스택**: `./scripts/run_panda_functionbay.sh` — `readiness_gate` 가 `/output/panda_joint` 첫 메시지를 60 s 기다린다.
8. 기동 로그에서 **그리퍼 규약이 씬과 맞는지** 본다(`convention: solver=… scene=…`, 함정 15).
9. **차트가 끝날 때까지 기다린다** — 시작과 함께 재생된 SignalChart 가 끝나기 전에 팔·그리퍼에 명령을 보내면 차트가 끊긴다(함정 17):
   ```bash
   ./scripts/functionbay/fb_wait_chart.py     # 종료 코드 0 = 끝났다
   ```

| **A-19** | **제어 게인 `Kp`·`Kd`** | `fb_gains.py` | **우리 설정과 일치** (종료 코드 0). 우리 보상 블록이 없는 씬은 게인만 기록 | **우리 중력 보상의 입력이다.** 바뀌어도 에러가 안 난다 (§A-19 상세) |
| **A-20** | **접촉 정의 목록** | §A-20 상세의 명령 | 직전 결과와 **파일 단위로** 대조. **peg ↔ 탁자** 유무를 적는다 | 씬으로 할 수 있는 일을 정한다 (벤더 B-14) |
| **A-21** | **관절 보고 도착 간격** | stamp [3] · §A-21 상세의 분석 | 기록 — 묶음 크기 · 묶음 간격 · 5 ms 미만 비율 | 실시간 소비자의 실효 갱신 주기를 정한다 (함정 13) |

### A-9 상세 — stamp 시간 기준은 **회차 속성**이다

| 분류 | 조건 | 뜻 |
|---|---|---|
| `wall-clock` | \|stamp − 수신시각\| < 5 s | 벽시계 epoch — 우리 노드·데이터셋과 같은 시간축 |
| `elapsed-since-start` | stamp − 수신시각 ≈ −(현재 epoch) | 시뮬레이터 기동 후 경과시간. 재시작마다 0 부터 |
| `skewed` | 그 사이 | 두 머신 시계 차이 |

**같은 빌드·같은 씬·같은 설정에서 벽시계 ↔ 경과시간이 오간다**(§0 회차마다 바뀌는 항목). 빌드 이름으로 예측할 수 없다. 게다가 **벽시계 회차에도 원 stamp 는 실제 시각에서 초 단위로 흔들릴 수 있다** — 정지(A-17) 동안 sim 시각이 멈추고 정지 사이에는 조금 빨리 가기 때문이다.

#### 우리 스택은 경계에서 stamp 를 벽시계로 정렬한다

| 구성 | 하는 일 |
|---|---|
| `joint_state_fusion` (`stamp_source: aligned`, 기본) | 원 stamp 에 **오프셋**을 더해 `/joint_states` 로 낸다. 오프셋 = `수신 시각 − 원 stamp` 의 **최솟값**(0.5 s 창) — 묶음 대기·전달 지연이 빠진다. 수신 공백 0.3 s 초과(정지)면 창을 비운다. 표본마다 `sensor_msgs/TimeReference`(`header.stamp`=정렬 시각, `time_ref`=원 stamp)를 `/functionbay/stamp_reference` 로 낸다 |
| `fb_camera_restamp` | `/camera_image/compressed` 를 받아 **sim stamp 가 가장 가까운 관절 짝의 오프셋**으로 재stamp 해 `/camera_image_aligned/compressed` 로 낸다. 뒤쪽 짝이 올 때까지 보류한다 |
| 공통 | 출력 stamp 가 **거꾸로 가지 않게** 누른다 (정지 직후 오프셋 변화로 역순이 날 수 있다) |
| 소비자 | 세션 레코더 · `camera_republish` 는 프로파일 `camera.compressed_topic`(=중계 출력)을 받는다. 원본은 `simulator.camera_compressed_topic` |

**정렬 stamp 의 뜻은 "시뮬레이터가 그 표본을 만든 벽시계 시각"** 이다. sim 간격을 보존하지 않는다 — 정지 사이 sim 이 빨리 가는 씬에서는 20 ms 짜리 sim 간격이 벽시계로 더 짧게 기록된다(C-4 의 간격 분포). 벽시계로 찍히는 명령 · `/session` 과 짝짓기에는 이 축이 맞다. 회차의 기준(벽시계/경과시간)을 몰라도 된다 — 오프셋이 수 ms 거나 epoch 규모로 잡힐 뿐이다.

**확인은 기동 로그 한 줄과 C-4 다** — `joint_state_fusion` 이 `stamp offset established: +1789622903.335 s (simulator stamps look elapsed-since-start)` 처럼 오프셋과 원 stamp 기준을 남긴다. `fb_checkup` `[3]` 은 **원 stamp** 를 보므로 벤더 추적(B-13)용으로 계속 적는다.

**되돌리기** — `panda_functionbay.launch.py` 의 `stamp_source` 를 `auto` 로, 프로파일 `camera.compressed_topic` 을 원본으로 바꾸고 `robot_control` 을 재빌드한다. 그러면 아래 문제가 돌아온다.

#### 정렬이 꺼진 채 경과시간 회차면 깨지는 것

- **데이터셋** — 적재가 `header.stamp` 로 에피소드 창을 거르므로 **rosbag 에는 남고 DB 에만 안 들어간다 — 조용하다.** `sessions.start_ts` 가 1970년이 되고, 재시작마다 0 부터라 `UNIQUE (start_sec, start_nanosec)` 가 세션 간에 충돌해 `on_existing_episode: skip` 이 **에러 없이 건너뛴다.**
- **명령·관측의 시간축이 갈린다** — `/joint_states` 는 경과시간, `/target_joint_cmds` · `/session` 은 벽시계다.
- **세션 레코더가 구간을 못 가른다** — 이미지 stamp 를 `/session` stamp 와 비교하기 때문이다.
- `stamp_source:=now` 는 대안이 못 된다 — 관절 보고가 묶여 도착해(A-21) stamp 가 몰리고, 카메라는 여전히 원 stamp 다.

`use_sim_time` 은 켜지 않는다 — 경과시간 회차에만 맞고, 시뮬레이터 재시작마다 `/clock` 이 0 으로 되감기며, `/clock` 자체도 묶여 오고 내부 스텝 단위로 뛴다. 근본 해결은 벤더 B-13(시간축 고정)과 A-5(정지 제거)다 — 둘 다 반영되면 오프셋이 상수가 되어 정렬은 사실상 항등이 된다.

### A-15 상세 — `/clock` 은 있지만 **lockstep 이 아니다**

`/clock` 은 시뮬레이터 내부 스텝 주기로 그냥 흘러간다 — 시뮬레이터가 우리를 기다리지 않으므로 sim time 의 본래 이점(스텝 동기)은 없다. 보고 주기를 바꿔도 이 값은 안 변한다.

**쓸모는 A-17 계측기다.** 수신 공백 동안 `/clock` 이 거의 진행하지 않으면 **시뮬레이션 자체가 멈춘** 것이다.

`use_sim_time` 을 켤지는 A-9 에 달렸다(위). 벽시계 회차에 켜면 우리 노드는 `/clock`(경과시간)을, 시뮬레이터 메시지는 벽시계를 써서 TF·데이터셋이 동시에 깨진다.

### A-6 상세 — 카메라는 `CompressedImage` 다

`/camera_image/compressed`(`sensor_msgs/CompressedImage`, `format=jpeg`, 640×480)로 발행한다(2026-09-08 빌드부터; 그 전 빌드는 `/camera_image` `bgr8`). **대역폭이 36배 작다**(9.2 → 0.25 MB/s).

| 소비자 | 배선 |

### A-16 상세 — Unity 가 물체 TF 를 발행한다

**조작 대상 body 하나만**(`static="false"`) `world → peg_round_16` 으로 내보낸다. 고정물(`peg_hole_round_16` · `peg_tray_round_16`)은 `static="true"` 라 **없다** — 그 좌표는 `config/functionbay_fixtures.json` 이 갖는다. 로봇 링크는 발행하지 않으므로 우리 `robot_state_publisher` 와 충돌하지 않는다.

```bash
python3 - <<'PY'   # /tf 를 60 s 구독해 프레임쌍별 건수·주기·stamp 기준을 센다
import rclpy, time
from tf2_msgs.msg import TFMessage
rclpy.init(); n = rclpy.create_node('tf_probe'); pairs = {}
def cb(m):
    for t in m.transforms:
        k = (t.header.frame_id, t.child_frame_id); s = t.header.stamp.sec + t.header.stamp.nanosec * 1e-9
        e = pairs.setdefault(k, [0, s]); e[0] += 1; e[1] = s
n.create_subscription(TFMessage, '/tf', cb, 100)
t0 = time.time()
while time.time() - t0 < 60: rclpy.spin_once(n, timeout_sec=0.05)
for (p, c), (cnt, s) in sorted(pairs.items(), key=lambda kv: -kv[1][0]):
    print('%-14s -> %-20s %5.2f Hz  %s' % (p, c, cnt / 60.0, 'wall' if abs(time.time() - s) < 1e6 else 'elapsed'))
PY
```

출력의 `panda_link*` 쌍들은 우리 `robot_state_publisher` 몫이다 — 시뮬레이터 몫과 섞어 읽지 않는다. 정지(A-17)가 있는 씬에서는 `world → peg_round_16` 에도 같은 길이의 공백이 보인다.

**회전은 ROS `xyzw`** 이다(알려진 자세로 검증, 2026-09-08). 단 **`w` 가 음수로 올 수 있다** — `q` 와 `−q` 는 같은 회전이라 tf2 는 정상이지만, 성분을 그대로 비교해 항등을 판정하는 코드는 오판한다. **XML 에 TF 설정 요소가 없다** — 벤더가 코드로 구현했으므로 조작 대상이 늘면 다시 문의해야 한다. 우리 쪽 `functionbay_scene_state_node` 가 이것을 `/scene/objects` 로 옮긴다. **`/scene/reset` 은 없다.**

### A-17 상세 — 시뮬레이터 주기적 정지

**시뮬레이터가 일정한 주기(지금까지 약 33.5~34 s)로 1~2 s 완전히 멈추는 결함이다.** 그동안 모든 토픽이 한 건도 오지 않는다. **씬(솔버)에 따라 있거나 없다** — `MMR-Build_260929` 에서는 `r2` 에 없고 `t1` 에 있었다. 그래서 **씬마다 따로 판정한다.**

**재는 법** — `fb_checkup.py 180` 의 `[2]` 블록(정지 횟수 · 비율 · 최대)과 `fb_stall_when.py 180`(정지마다 시작·끝 벽시계 시각 · 주기)을 함께 돌린다. **0회 판정은 두 도구로 각각 확인한다.**

**수용 기준** — 180초 관측에서 **0.3 s 넘는 수신 공백 0회** (벤더 A-5).

**정지인지 전송 지연인지 가르는 법:**

1. 공백 동안 `header.stamp` 와 `/clock` 이 거의 진행하지 않는다(한 틱) → 전송 지연이 아니라 **시뮬레이션이 멈춘다.**
2. 모든 토픽이 수십 ms 안에 동시에 멈춘다.
3. 정지를 제외하면 sim 시각 기준 발행률이 설정값과 일치한다.
4. 공백 길이가 **약 2.1 s 로 균일**하면 정지가 아니라 **솔버 미기동**을 의심한다(함정 14).

**해석 주의:**

- **퍼센트는 창 정렬에 따라 달라진다.** 30여 초 주기라 180 s 창이 5회를 담느냐 6회를 담느냐는 창 위치가 정한다 — 같은 회차를 두 도구로 재도 횟수가 하나 차이 날 수 있다. 횟수 · 비율보다 **정지 하나의 길이와 주기**를 본다.
- **개별 길이는 무엇으로 재느냐에 따라 조금 다르다** — 관절 수신 공백 · 카메라 수신 공백 · `fb_stall_when` 의 값이 수십 ms 씩 다르다. 결과 문서에 어느 도구 값인지 적는다.
- **지속 시간은 회차마다 다르다** (§0 회차마다 바뀌는 항목) — 직전 결과의 범위와 대조한다.
- 정지 중에는 우리 Python 프로세스도 멈춘다 (함정 8).

**데이터 결손은 없다** — sim 시각 기준 `header.stamp` 는 연속이다. 깨지는 것은 **실시간성**이다: 원격 조작 중 무반응, 접촉 동역학 속도 불균일, 벽시계 기준 시간제한의 오발동. C-10 에서는 영상 sidecar 의 0.5 s 넘는 공백으로 다시 보인다.

> **`teleop_retarget` 의 `pedal_timeout` 을 켤 때 정지 최대 길이보다 길게(2.5 s 이상) 잡는다.** 정지보다 짧으면 정지 때마다 하트비트가 끊겨 클러치가 자동 해제된다. **함정 8 을 함께 읽는다.**

원인 조사(우리 쪽에서 배제한 가설 — GC · 에셋 언로드)와 벤더 발송 문안은 [요청 목록](펑션베이_요청_목록.md) A-5 절과
[벤더 메일 20260903](../../archive/functionbay/펑션베이_벤더_메일_20260903_정지.md) 에 있다.

### A-19 상세 — 제어 게인은 **우리 중력 보상의 입력**이다

처짐을 `Δq = −τ_g(q)/Kp` 로 상쇄하는데, 그 `Kp` 는 **씬 XML 에서 옮겨 적은 값**이다(`<씬>__Manipulator_1_vm.xml` 의 `<Gain Kp=... Kd=...>`). 새 빌드가 바꾸면 **보상량이 그만큼 틀어지고 에러는 안 난다** — 증상은 "팔이 몇 mm 어긋난 곳에 선다" 뿐이다.

```bash
./scripts/functionbay/fb_gains.py [MMR_Database 경로]
```

- 모든 씬의 팔 · 그리퍼 게인을 나열하고, **활성 씬**(`SolverConfig.json` 의 `MsFile`)의 팔 `Kp` 를 프로파일 `motion.gravity_compensation.kp` 와 대조한다. 불일치면 비율(실제/설정)을 내고 **종료 코드 1** 이다.
- **우리 보상 블록이 없으면**(벤더가 보상하는 씬) "중력 보상 꺼짐" 을 내고 대조 없이 끝난다 — 그 씬이 정말 벤더 보상 씬인지는 B-3 · B-4 가 판정한다.
- **게인은 씬마다, 같은 씬도 빌드마다 다르다** — `MMR-Build_260929` 에서 `t1` 팔이 2000 → 20000 으로 10배가 됐다. `r1` 처럼 팔 게인이 1/10 인 씬도 있다. **씬을 바꿀 때마다 먼저 돌린다.**
- `r2__Gripper_1` 의 `<Gain>` 은 스칼라 하나이고 두 관절에 같이 걸린다.

**게인 변경은 B-3 처짐으로 교차 확인된다** — 게인이 k배가 되면 같은 자세의 정착 오차가 **정확히 1/k** 이 된다. 1/k 이 아니면 게인이 아니라 다른 것(보상 · 접촉 · 솔버)이 바뀐 것이다.

**불일치일 때** — `config/backends/functionbay.yaml` 의 `motion.gravity_compensation.kp` 를 실제 값으로 고치고 **재빌드**한 뒤(함정 12) 스택을 다시 띄운다.

### A-20 상세 — **접촉 정의가 그 씬으로 할 수 있는 일을 정한다**

물리 접촉은 **명시적으로 선언된 것에서만** 일어난다. 선언되지 않은 조합은 화면에는 보여도 서로를 통과한다. **두 씬은 선언 방식이 다르다.**

| 물체를 쥐고 든다 | peg ↔ 좌·우 손끝 | **B-14 · B-16 으로 판정한다** — 설정만으로 하지 않는다 (아래) |

**⚠️ `t1` 은 설정만 보면 판정을 그르친다** — body 별 SDF 등록이고 **손끝은 목록에 없다.** 그래서 설정상으로는 늘 "손끝 접촉 없음" 인데, `MMR-Build_260929` 에서는 그런데도 파지가 유지됐다(솔버 실행 파일 쪽 수정으로 보인다). 반대로 그 전 빌드에서는 마찰계수를 667배 올려도 놓쳤다. **판정은 B-14 · B-16 으로 한다.**

**`t1` 은 접촉계수와 솔버 설정도 함께 본다** — `stffiness_coefficient` · `friction_coefficient` 와 `t1__SNU_1_vm.xml` 의 `step` · `max_iter` · `con_margin` 이 빌드마다 바뀐 적이 있다. 직전 결과의 값과 대조해 결과 문서에 적는다.

**`peg ↔ 탁자` 가 없으면** — 고정물 밖에서 놓은 peg 이 탁자를 통과해 **자유낙하한다**(가속도 −11.25 m/s², "튕겨 나간다"로 읽으면 원인을 못 찾는다). `/scene/reset` 이 없어 **복구는 시뮬레이터 재시작뿐**이다. 그래서 B 단계의 peg 항목(B-14·B-16·B-18)은 **고정물 바로 위에서만** 다룬다. 표면 정의는 빌드에 있다(`ConstantModel/geosurfs/ground_table_surf.xml`) — 접촉 쌍으로 연결만 안 돼 있다.

### A-21 상세 — 관절 보고가 **묶여서** 도착한다

`fb_stamp` 의 `[3]` 에서 관절 토픽의 **수신 간격 중앙값이 stamp 간격보다 훨씬 작게**(수 ms) 나오면 묶음이다. 원자료로 묶음을 센다:

```bash
python3 - misc/fb_stamp/<씬>_<YYYYMMDD>.json <<'PY'   # 관절 수신 묶음 분석
import json, sys, statistics as st
from collections import Counter
rx = [r[0] for r in json.load(open(sys.argv[1]))['raw']['/output/panda_joint']]
bursts, cur = [], [rx[0]]
for a, b in zip(rx, rx[1:]):
    if b - a < 0.005: cur.append(b)
    else: bursts.append(cur); cur = [b]
bursts.append(cur)
gaps = [b[0] - a[-1] for a, b in zip(bursts, bursts[1:]) if b[0] - a[-1] < 0.3]
print('평균 %.2f건/묶음, 분포 %s, 간격 중앙 %.1f ms' % (len(rx) / len(bursts), dict(sorted(Counter(map(len, bursts)).items())), st.median(gaps) * 1000))
PY
```

**적을 것** — 평균 건수/묶음 · 묶음 크기 분포 · 묶음 사이 간격(중앙 · p90, 정지 제외) · 수신 간격 5 ms 미만 비율. 카메라는 묶이지 않는다(대조용).

**묶음의 정도는 씬을 따라간다** — 같은 씬은 빌드가 바뀌어도 거의 그대로였고 씬이 바뀌면 달랐다. 그래서 같은 씬끼리 대조한다. 정지 해제 직후에는 캐치업으로 큰 묶음이 하나씩 생긴다 — 분포의 꼬리로 읽고 결함으로 적지 않는다.

**영향** — 데이터셋은 stamp 로 정렬하므로 **없다**(정렬 stamp 도 원 stamp + 오프셋이라 묶음과 무관하다). 수신 시각을 쓰는 곳은 묶음 간격 계단으로 갱신된다: servo 의 되읽기, 스트리밍 뒤 정착 판정(`wait_until_still`), dead time 측정(B-6·B-13 이 두 무리로 갈린다).

### B-4 상세 — **자세를 적지 않은 결과는 되살릴 수 없다**

세 자세를 **관절값으로** 정의한다. 결과에는 반드시 자세 이름을 함께 적는다.

| 자세 | j1 | j2 | j3 | j4 | j5 | j6 | j7 | 성격 |
|---|---|---|---|---|---|---|---|---|
| `ready` | 0 | −0.785 | 0 | −2.356 | 0 | 1.571 | 0.785 | SRDF, 접힌 자세 |
| `extended` | 0 | 0 | 0 | 0 | 0 | 1.571 | 0.785 | SRDF, **위로 곧게 선** 자세 — 모멘트 암이 짧아 처짐이 작다 |
| `horizontal` | 0 | −1.571 | 0 | −0.0698 | 0 | 1.571 | 0.785 | **수평** — joint2 중력 토크 최대 (FK 최저점 z +0.360 m) |

**재는 법** — `fb_sag_pose` 는 `TrajectoryStreamer` 를 거치지 않고 `/input/panda_joint` 로 직접 발행하므로(`velocity` 0) **OFF** 값이 처짐 그대로 나온다. 같은 자세에서 지령에만 우리 보상을 얹어 **ON** 을 잰 뒤 `ready` 로 되돌린다. 잔차는 `실제 − 지령`(rad)으로 적는다.

**OFF 값은 중력 모델로 미리 예측할 수 있다** — 우리 보상을 쓰는 씬에서는 `horizontal` 의 joint2 처짐이 모델 예측(`τ_g/Kp`)과 1 % 안에서 맞아야 한다. 어긋나면 게인(A-19)이나 모델 입력이 바뀐 것이다.

**벤더 보상 씬에서는 읽는 법이 바뀐다.**

- 프로파일에 우리 블록이 **없으면** ON 단계는 OFF 와 같은 지령이 된다 — `--off` 로 OFF 만 잰다. OFF 가 **0.0000** 이면 벤더 보상이 작동하는 것이다.
- **우리 블록을 남긴 채 벤더도 보상하면 이중 보정**이 되어, ON 의 잔차가 OFF 처짐과 **크기는 같고 부호가 반대**로 나온다(예: −0.0097 → +0.0097). 그 지문이 나오면 프로파일에서 `motion.gravity_compensation` 을 지운다 — [중력 보상 문서](펑션베이_중력_보상.md) §5 절차.

### B-8 상세 — 정착 오차 필드는 **보상 오프셋을 포함한다**

`fb_probe` 의 `settle_err_rad` 는 **마지막 지령과 마지막 실제값의 차**다. 우리 보상이 켜져 있으면 지령에 오프셋이 섞이므로, 이 값은 오차가 아니라 **오프셋의 크기**에 가깝다 — `final_cmd` 와 `final_out` 을 따로 보면 실제 도달값이 목표와 일치하는지 알 수 있다. 보상이 꺼지면 이 필드가 오히려 0 에 가까워지므로, **이 값 하나로 좋아졌다·나빠졌다를 읽지 않는다.** 게인이 k배가 되면 오프셋도 1/k 이 되어 이 필드가 함께 줄어든다(A-19).

`fb_probe` 의 최적 lag 탐색 범위는 0~0.30 s 다. 응답이 느린 씬(`t1`)은 최적 lag 가 상한에 가깝다 — **`best_lag_sec` 가 0.300 이면 상한에 걸린 것이니 `LAG_STEPS` 를 늘려 다시 잰다.**

### B-9 상세 — 0 mm 는 **보상의 결과**다

`fb_ee.py` 는 방향 의존이 0 이면 *"벤더 A-1 을 닫을 근거가 된다"* 고 출력하는데 **그렇게 읽지 않는다.** 우리 보상이 켜져 있으면 이 값은 스트리밍 경로에 얹힌 **우리 중력 보상**이 만든 것이다. 벤더 A-1 의 반영 여부는 B-3 · B-4 의 OFF 값으로 판정한다. 결과에는 **보상 주체**(우리 / 벤더)를 함께 적는다 — 우리 보상은 부하·속도 성분·servo 경로를 못 잡는다.

참고로 같은 출력의 `/ee_pose` 는 tip(`panda_link8`) 대비 **z −0.1493 m** 다 — `fb_ee` 는 그래서 `/ee_pose` 가 아니라 `panda_link8` TF 로 목표를 만든다(§C 끝 경고).

### B-10·B-11 상세 — 관절 한계를 **강제하는 씬과 안 하는 씬**이 있다

`fb_limit` 은 `ready` 에서 출발해 지령을 천천히 올리며(URDF 한계 + 0.25 rad 까지) 실제가 따라오기를 멈추는 지점을 찾는다. 수신 공백이 낀 표본은 정지(A-17)로 보고 판정에서 뺀다.

**적을 것** — joint7+ · joint4− · joint4+ 각각의 도달값과 그때의 지령 상한, 그리고 URDF 한계(joint7 +2.9671 · joint4 −3.1416 ~ +0.0873). **지령 상한까지 따라오면 강제하지 않는 것**이다. `r2` 는 강제하지 않고 `t1` 은 joint4+ 에서 URDF 안쪽에 선다 — 이 성질이 바뀌면 변경으로 적는다.

**스크립트가 출력하는 "기준선"·"차" 열은 Crisp 시절 상수라 무시한다.** 한계를 강제하지 않는 씬에서는 URDF 밖 자세로 갈 수 있으므로 **MoveIt 계획이 한계를 지키는 것이 유일한 방어**다 — 직접 발행하는 스크립트가 한계 밖을 지령하면 그대로 간다. 벤더 B-3(클램프)·B-9(한계 사양)의 근거다.

### B-12 ~ B-14 (그리퍼)

**그리퍼 규약은 씬마다 다르다** — r2 는 **2축 · 도(degree) · 관절당 `(position, velocity, force)`**, t1 은 **6축 · rad · position** 이다(보고는 어느 쪽이든 라디안). 규약은 `config/functionbay_gripper_{recurdyn,crisp}.json` 이 갖고, `fb_gripper` 는 보고 축 수로 규약을 고른다. 라디안을 도 자리에 보내면 1.745 % 만 움직이고 에러가 안 난다.

**`effort` 는 측정된 토크가 아니다** — `effort = Kp(200) × (지령 − 실제)` 인 드라이브 비례 오차항이다. 그래서 B-14 의 파지 판정은 **잔차로 한 판정**이고 접촉력을 재지 않는다. **씬마다 파지 effort 의 크기가 다르다**(관절 수·링키지 차이) — 다른 씬의 값과 비교하지 않는다. `stall_velocity` 는 지터 대역 위인 **0.01** 로 둔다 — 기본 0.001 이면 성공한 파지가 `TIMEOUT` 으로 보고된다.

**B-13 은 `fb_gripper_step.py` 로 잰다** — `fb_gripper` 는 2초 램프라 계단 응답을 못 잰다. 구동값 `s` 를 한 번에 바꾸고 `fb_step` 과 **같은 분석**(10 %·63.2 % 교차점, 정지가 낀 계단은 버림)을 쓰며 99 % 도달(최종값 1 % 대역에 들어와 다시 안 나가는 시각)을 더한다. **빈손에서만** 잰다(시작 시 `|effort|` 가 1 N·m 을 넘으면 거부한다). 첫 계단이 이상값으로 나올 수 있다 — 유효 개수(예: 9/10)를 함께 적는다.

### B-16 상세 — 파지 유지

`fb_grasp_hold.py` 가 절차다. **고정물에 꽂힌 peg 을 쥐고 → 그 자리에서 수직으로 들어 → 유지하며 1초마다 `peg − tcp` 간격과 effort 를 보고 → 같은 경로로 내려 앉음을 확인한 뒤에만 놓는다.** 유지 중에 놓쳐도 peg 은 접촉이 정의된 고정물 위로 떨어진다. 탁자 위에 있는 peg 은 거부한다.

**적을 것** — 구간별(빈손 · 파지 · 들기 완료 · 유지 끝 · 되꽂기) tcp z · peg z · \|eff\| · 간격 변화, 그리고 되꽂기 밀림.

**느린 미끄러짐을 본다** — peg 이 그리퍼 안에서 거의 일정한 속도로 내려가는 씬이 있다(`r2`, 30 s 에 약 0.5 mm). 30초 유지에는 문제가 없지만 **긴 이송 에피소드에서는 누적**되고, B-18 의 기하 확인(손끝이 고정물 상면 위에 남는가)을 잠식한다. 간격 변화를 시간에 따라 적어 추세를 남긴다.

**놓치면** — 접촉 정의(A-20)부터 본다. `t1` 은 설정에 손끝 접촉이 없으므로 이 항목이 유일한 판정이다. 마찰계수를 올려 우회를 시험했다면 **시험 뒤 원래 값으로 되돌린다** — 남겨 두면 벤더가 손끝 접촉을 넣었을 때 원인 분리가 어려워진다.

### B-17 상세 — 말림은 **중력 보상이 살아 있는지 보는 창**이다

순수 수직 이동인데 손끝이 로봇 쪽으로 말렸다가 풀리는 현상이다. 보상이 없으면 수 mm 말리고 도달 오차가 10 mm 를 넘는다(2026-09-11 보상 OFF 실측: 1.6초에 −7.14 mm, 도달 오차 12.25 mm). 파지 정확도를 직접 망친다. 다른 항목(B-3·B-4 정지 오차, B-8 lag, B-9 비대칭)은 **이동 중 손끝이 옆으로 새는 양**을 보지 않는다.

**재는 법** — `(0.50, 0.00, 0.12)` 에서 +45 mm 수직 이동 중 시간별 dz · dx 를 기록한다. **판정: 이동 중 최대 \|dx\| < 0.5 mm, 도달 < 1 mm.**

보상은 **조용히 망가질 수 있다** — 오류 없이 "팔이 몇 mm 어긋난 곳에 선다" 뿐이다.

| 관측 | 원인 |
|---|---|
| 말림이 **수 mm 로 복귀** | 보상이 꺼졌다 — 프로파일 키 누락, URDF 경로 파손, **설치본이 낡았다**(함정 12), 또는 벤더가 보상을 뺐다 |
| 말림이 **커졌는데 부호가 반대** | **이중 보정** — 벤더가 A-1 을 반영했는데 우리 보상을 안 껐다 |
| 말림은 작은데 **도달 오차만 큼** | `Kp` 가 설정과 다르다 — A-19 |

> **B-3·B-4 의 보상 OFF 값으로는 "꺼짐"을 못 가른다** — 꺼지면 원래 처짐으로 돌아가는데 그 값이 직전 결과에 적혀 있기 때문이다. B-4 의 **보상 ON 행**과 B-17 이 그것을 가른다.

### B-18 상세 — peg-in-hole 왕복이 회피책 없이 된다

`./fb_move_peg.py` 한 줄이다. 목적지를 안 주면 현재 위치의 반대쪽 고정물을 고른다(`--dry-run` 은 계획만). **두 번 돌려 왕복**(`peg_hole` → `peg_tray` → `peg_hole`)을 잰다.

**적을 것** — 방향별로 접근 오차 · 파지 오프셋 · 정렬 후 peg 수평 오차 · 하강 시간과 횟수 · tcp 도달 오차 / 밀림 · **삽입 오차**.

**세 판정이 절차의 실체다.** ① **파지 오프셋 보정** — peg 을 정렬한다, tcp 가 아니다(방향과 무관하게 일정한 파지 오프셋이 반경 여유의 대부분을 먹을 수 있다). ② **기하 사전 확인** — 완전 삽입 때 손끝이 고정물 상면 위에 남는가(정상 `peg − tcp` 간격 약 −54 mm). peg 이 그리퍼 안에서 밀려 올라갔으면 **움직이기 전에** 거부한다. ③ **앉음 확인** — 안 앉았으면 **쥔 채로 두고** 실패를 돌려준다(놓으면 물체가 씬을 이탈하고 복구는 재시작뿐이다).

**트레이는 구멍보다 까다롭다** — 구멍은 입구 모따기가 오차를 1.47 mm 까지 흡수하지만 트레이는 0.50 mm 뿐이다. 실패하면 방향(구멍 → 트레이인지)을 함께 적는다. **되던 것이 안 되기 시작하면 지령 주기부터 본다** — 계단 지령(`publish_rate` 미설정)이 peg 을 입구에서 튕겨낸 적이 있다.

### C-8 — servo 경로를 키보드 없이 확인한다

servo 는 **`start_servo` 만 해도 명령 없이 팔을 끌고 가므로** 시험이 끝나면 곧바로 `stop_servo` 하고 `ready` 로 되돌린다.

```bash
python3 - <<'PY'
import rclpy, time
from std_srvs.srv import Trigger
from geometry_msgs.msg import TwistStamped
rclpy.init(); n = rclpy.create_node('c8_servo')
start = n.create_client(Trigger, '/servo_node/start_servo'); stop = n.create_client(Trigger, '/servo_node/stop_servo')
pub = n.create_publisher(TwistStamped, '/servo_node/delta_twist_cmds', 10)
start.wait_for_service(timeout_sec=10.0); rclpy.spin_until_future_complete(n, start.call_async(Trigger.Request()))
msg = TwistStamped(); msg.header.frame_id = 'panda_link0'; msg.twist.linear.z = 0.5
t0 = time.time()
while time.time() - t0 < 1.0:
    msg.header.stamp = n.get_clock().now().to_msg(); pub.publish(msg); rclpy.spin_once(n, timeout_sec=0.02)
rclpy.spin_until_future_complete(n, stop.call_async(Trigger.Request()))
PY
./scripts/functionbay/fb_recover.py 4.0
```

EE 변위는 전후로 `tf2_echo panda_link0 panda_link8` 의 z 를 비교한다. **변위는 `servo.linear_scale` 과 보상 주체에 따라 달라진다** — 우리 보상은 servo 경로에 얹히지 않으므로, 벤더가 보상하는 씬에서는 같은 scale 에서 변위가 커진다(처짐 되읽기가 먹던 이동량이 돌아온다). 결과에 scale 과 보상 주체를 함께 적고, 크게 바뀌면 `teleop_keyboard` 의 `linear_step` 재조정을 검토한다.

### C-10 상세 — 수집 계층에서 명령·관측·영상이 한 시간축에 모인다

`rdfp_collect` 를 띄우면 `session_control_node` · `rdfp_image_recorder` · `target_joint_cmds_publisher` 가 뜬다(`source='joint_state'`, 입력 `/input/panda_joint` — `backend:=functionbay` 가 프로파일에서 고른다). 팔을 움직이는 동안 `/target_joint_cmds` 가 통과해야 한다. 0건이면 먼저 설치본을 본다(함정 12).

**확인할 것:**

- **명령과 관측이 같은 축이다** — `/target_joint_cmds`(수신 시각으로 재stamp, 벽시계)와 `/joint_states`(정렬, 벽시계)로 joint7 ±0.05 rad 계단을 **stamp 만으로** 풀어 dead time · τ 를 낸다. 같은 회차의 수신 기준 값(B-6 · B-7)과 **같은 대역**이어야 한다 — 축이 갈려 있으면 이 값이 수십 년이 된다.
- **세션 레코더가 정렬된 영상을 받는다** — 로그에 `subscribed to image topic (effective name=/camera_image_aligned/compressed …)`. 에피소드 길이 · 장수 · 드롭 · sidecar stamp 역순 · **0.5 s 넘는 공백 수**(정지 횟수와 맞아야 한다)를 적는다.
- **mp4 의 fps 선언이 소스와 맞는다** — 레코더는 프로파일 `camera.fps` 를 따르는 CFR 이다. 선언이 소스보다 낮으면 영상이 느리게 재생된다(5 로 두었을 때 34.75 s 녹화가 66.8 s 영상이 됐다). 시뮬레이터 XML `Publish_Frequency` 와 같은 값(10)을 둔다. 실측 주기가 설정보다 조금 낮으므로 mp4 시간축은 약간 짧다 — 프레임별 시각은 sidecar stamp 로 읽는다. **XML 주기를 바꾸면 프로파일 `camera.fps` 도 함께 바꾼다.**

**레코더 출력 경로** — 기본 `/data/rdfp/recordings` 에 쓰기 권한이 없으면 레코더가 `FATAL` 로 죽는다. 시험에서는 `image_recorder_output_dir:=/tmp/recordings_<씬>` 으로 우회하고 결과에 적는다.

**내릴 때는 launch 프로세스에 `SIGINT` 를 보낸다** — `setsid` 래퍼 PID 로 보내면 자식 노드가 남는다. 뷰어를 켜면 WSLg 창이 뜨므로 헤드리스 확인에서는 `enable_image_viewer:=false` 로 끈다.

### `/ee_pose` 는 `grasp_center` 를 가리킨다

description 이 Panda Hand 라 기본 프레임 `panda_hand` 는 실제 파지점에서 **149 mm + 90°** 어긋난다. launch 가 `panda_link7 → grasp_center` 정적 TF 를 띄우고 `ee_frame` 을 그쪽으로 둔다. **`/ee_pose` 만 맞춰진 것이고 TF 형상·충돌은 여전히 Panda Hand 다.**

> ### ⚠ `/ee_pose` 로 데카르트 목표를 만들면 안 된다
>
> 데카르트 목표는 **MoveIt 그룹의 tip link(`panda_link8`)** 기준으로 해석되는데 `/ee_pose` 의 프레임은
> launch 의 `ee_frame` 이 정한다 — 둘이 **z 로 149.3 mm** 어긋난다(C-5). `fb_ee.py` 가 실제로 이것
> 때문에 +20 mm 상승을 −129 mm 하강으로 지령한 적이 있다. **측정과 지령은 같은 링크여야 한다.**

## E. 매 회차 볼 것

1. **씬을 바꿀 때마다 `fb_gains.py` 를 먼저 돌린다** — `Kp` 는 씬·빌드 속성이다(A-19).
2. **우리 중력 보상 블록이 그 씬과 맞는지** 본다 — 벤더가 보상하는 씬은 블록 없음, 아닌 씬은 블록 + 그 씬의 `kp`. 프로파일 주석에 지운 블록의 내용이 남아 있다(함정 15 · B-4 상세).
3. **XML 주기 설정이 두 파일에서 갈려 있지 않은지** — `vm.xml` 과 `bp.json` 의 `Hz`(함정 9).
4. **C-4 — 수집 전에 `/joint_states` 가 벽시계인지.** 정렬이 켜져 있으면 A-9(원 stamp)가 경과시간이어도 수집은 성립한다.
5. **직전 결과의 "다음 회차에서 볼 것"** 을 결과 문서에서 확인한다.

**회귀 감시** — A-8(축 수) · A-12(jpeg) · **A-19(게인 — 씬마다)** · A-20(접촉) · 함정 10(빈 `velocity`) · **B-16(파지 유지)**. 이 여섯은 한 번 바뀌면 우리 코드의 전제가 조용히 깨진다.

## F. 결과 기록

결과는 워크스페이스 루트의 **`checklist_results/`** 에 회차마다 문서로 남긴다. 이 문서는 절차만 갖고, **값은 결과 문서가 갖는다.**

**이름** — 빌드 · 씬 · 측정일이 드러나게 한다. 원자료는 `misc/fb_stamp/<씬>_<YYYYMMDD>.json` 에 두고 결과 문서가 그 경로를 적는다.
