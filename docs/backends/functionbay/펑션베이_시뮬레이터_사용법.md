# 펑션베이 시뮬레이터 — 사용법 (띄우는 순서)

> **용도** 펑션베이 시뮬레이터를 솔버부터 로봇 스택까지 띄우고, 씬을 바꾸고, 내리는 절차다.
> 새 빌드를 받았을 때 무엇이 바뀌었는지 재는 절차는 [펑션베이_인수_체크리스트.md](펑션베이_인수_체크리스트.md),
> 백엔드의 구조와 채널은 [펑션베이_백엔드_설계.md](펑션베이_백엔드_설계.md) 에 있다.
>
> **순서는 여섯이다** — ① 솔버 → ② 시뮬레이터(모델 로드까지) → ③ `ros_tcp_endpoint` → ④ 시뮬레이션 시작(`/scene/start`) → ⑤ 로봇 스택 → ⑥ 차트 종료 대기.
> ①②는 Windows, ③~⑥은 WSL 에서 한다. **시뮬레이터는 띄워도 저절로 시작하지 않는다** — ④ 의 토픽으로 시작한다(정지 · 재시작은 §3).

---

## 0. 폴더 — 기준 폴더 하나에서 나머지가 정해진다

기준 폴더(`build_dir`)를 먼저 정한다. 지금은 **`D:\MMR-Build_260929`** 다(WSL 에서는 `/mnt/d/MMR-Build_260929`).

| 이름 | 경로 | 들어 있는 것 |
|---|---|---|
| `build_dir` | `D:\MMR-Build_260929` | 빌드 전체 |
| `sim_folder` | `<build_dir>\sim\build_0929` | 시뮬레이터 `MetaMotionRobot.exe` · 읽을 설정 DB 를 가리키는 `database_config.txt` |
| `crisp_folder` | `<build_dir>\solver\Crisp` | Crisp 솔버 `CrispSolver.exe` |
| `recurdyn_folder` | `<build_dir>\solver\RecurDyn` | RecurDyn 솔버 `SolverTCPServer.exe` |
| 설정 DB | `<build_dir>\MMR_Database` | 씬 정의(`Database\ModelSystem\<씬>_ms.xml`) · 씬별 설정 XML(`Database\VariableModel\<씬>__*.xml`) · 활성 씬 기록(`Database\SolverConfig\SolverConfig.json`) |

**새 빌드를 받으면** `build_dir` 과 `sim_folder` 의 `build_xxxx` 이름을 바꾸고, `sim_folder\database_config.txt` 가 그 빌드의 `MMR_Database` 를 가리키는지 본다. **`scripts/functionbay/fb_gains.py` 의 `DEFAULT_DATABASE` 도 새 빌드로 바꾼다**(또는 `FB_MMR_DATABASE` 를 둔다) — `fb_gains` · `fb_wait_chart` 가 그 경로의 `SolverConfig.json` 으로 씬을 판별하므로, 옛 빌드를 가리키면 조용히 틀린다. `solver\KHU` 도 들어 있지만 우리가 쓰는 씬과는 짝이 아니다.

## 1. 씬과 솔버는 짝이다

| 씬 | 솔버 | 솔버 실행 파일 | 솔버 포트 | 시뮬레이터 인자 |
|---|---|---|:-:|---|
| `r2` | RecurDyn | `<recurdyn_folder>\SolverTCPServer.exe` | 10001 | `-Scene LAB_ETRI -Model r2_ms` |
| `t1` | Crisp | `<crisp_folder>\CrispSolver.exe` | 10002 | `-Scene LAB_ETRI -Model t1_ms` |

**씬에 맞지 않는 솔버를 띄우면 에러 없이 팔만 안 움직인다.** 솔버가 없어도 시뮬레이터는 `/output/*` 를 50 Hz 로 내보내므로(값이 전부 `0.0000` 에 고정) 토픽만 보면 정상처럼 보인다 — [체크리스트 함정 14](펑션베이_인수_체크리스트.md). 다른 씬의 솔버가 남아 있으면 끈다.

## 2. 띄우는 순서

### ① 솔버 (Windows)

띄울 씬의 솔버 **하나만** 띄운다. 솔버 폴더에서 실행한다.

```bat
:: r2 씬 — RecurDyn
cd /d D:\MMR-Build_260929\solver\RecurDyn
SolverTCPServer.exe

:: t1 씬 — Crisp
cd /d D:\MMR-Build_260929\solver\Crisp
CrispSolver.exe
```

확인 (WSL 에서):

```bash
tasklist.exe | grep -iE "SolverTCP|Crisp"     # 그 씬의 솔버 하나만 보여야 한다
```

### ② 시뮬레이터 (Windows)

**실행 파일은 `sim_folder` 에 있다** — 솔버 폴더가 아니다.

```bat
cd /d D:\MMR-Build_260929\sim\build_0929

:: r2 씬 (RecurDyn 솔버)
MetaMotionRobot.exe -Scene LAB_ETRI -Model r2_ms

:: t1 씬 (Crisp 솔버)
MetaMotionRobot.exe -Scene LAB_ETRI -Model t1_ms
```

**인자를 주면 씬과 모델까지 로드하고 기다린다 — 시뮬레이션은 저절로 시작하지 않는다.** 시작은 ④ 에서 `/scene/start` 로 한다
(2026-10-01 실측: t1 으로 띄워 3분을 기다려도 시작하지 않았고, `/scene/start` 를 보내자 바로 시작했다).

**시작할 때** 앱이 `SolverConfig.json` 의 `MsFile` 을 그 모델로 고쳐 쓴다 — 씬을 고르려고 손으로 고칠 필요가 없다. ⚠️ **시작 전에는
그 파일이 이전 씬을 가리킨다** — `fb_gains.py` 처럼 그 파일로 씬을 판별하는 도구는 ④ 뒤에 돌린다.

`Player.log`(`C:\Users\<user>\AppData\LocalLow\MetaMotionX\MetaMotionRobot\Player.log`)에서 이 단계까지 보이면 된다:

| 줄 | 뜻 |
|---|---|
| `[CliAutoStartBootstrap] CLI 인자 감지 → Lobby 경유` | 인자를 읽었다 |
| `[SimulationAPIServer] CLI 모델 로드 완료: '…\ModelSystem\t1_ms.xml'` | 모델 로드 — 여기서 ④ 를 기다린다 |

`Connection to 127.0.0.1:10000 failed … 연결을 거부` 와 `Queue full! Messages are getting dropped!` 가 반복되는 것은 ③ 전까지 정상이다. **앱을 다시 띄우면 `Player.log` 가 덮어써진다** — 옛 회차와 대조하려면 먼저 복사해 둔다.

### ③ `ros_tcp_endpoint` (WSL)

우리 launch 는 endpoint 를 띄우지 않는다 — **자기 터미널에서** 따로 띄운다. **이미 떠 있으면 또 띄우지 않는다**(포트 충돌).

```bash
export ROS_DOMAIN_ID=31
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp     # 로봇 스택과 반드시 같아야 한다

ss -ltnp | grep :10000                          # 떠 있는지 먼저 본다
source ~/development/ros/tcp_ws/install/setup.bash

ros2 daemon start
ros2 run ros_tcp_endpoint default_server_endpoint
```

**`ros2 daemon start` 를 먼저 실행하고 endpoint 를 띄운다** — 이 순서로 한다. 이후 `ros2 topic list` 는 데몬의 탐색 결과를 쓴다.
endpoint 는 인자 없이 띄운다 — 기본값이 `ROS_IP=0.0.0.0` · `ROS_TCP_PORT=10000` 이다(`ros_tcp_endpoint/server.py`). 바꿀 때만 `--ros-args -p ROS_TCP_PORT:=<포트>` 를 준다.

endpoint 가 뜨면 시뮬레이터가 스스로 다시 붙는다(endpoint 로그 `Connection from 127.0.0.1`). 직후의 `Not registered to publish topic` 몇 줄은 정상이다.
이 단계에서 보이는 것은 시뮬레이터 제어 토픽뿐이다 — `/scene/start` · `/scene/stop` · `/scene/state` · `/clock` · `/tf` 등. **`/output/*` 는 ④ 뒤에 생긴다.**

> ⚠️ **Claude Code 의 Bash 샌드박스 안에서 띄우지 않는다.** 샌드박스 안에서 띄운 endpoint 는 TCP 10000 이 열려 시뮬레이터가 붙고 토픽
> 등록까지 되지만 **DDS 가 막혀** 다른 프로세스에서 토픽이 보이지 않는다(2026-10-01). 같은 날 **처음부터 샌드박스 밖에서** 데몬 → endpoint
> 순서로 띄운 것은 정상이었다. 샌드박스 안 endpoint 를 내린 직후 다시 띄운 것은 탐색이 들쭉날쭉했다 — 그때는 시뮬레이터까지 새로 띄운다.

### ④ 시뮬레이션 시작 (WSL)

```bash
ros2 topic pub --once -w 1 /scene/start std_msgs/msg/String "{data: ''}"
```

`Player.log` 에 이어서 이 줄들이 찍힌다:

| 줄 | 뜻 |
|---|---|
| `[SimulationConfigManager] SolverConfig saved: …` | 활성 씬 기록 (`MsFile` 이 그 씬이 된다) |
| `On Start Simulation` | 시뮬레이션 시작 |
| `[SolverTCPConnector] vm.xml: 127.0.0.1:10002, …` → `비동기 워커 모드로 통신 시작.` | **솔버와 붙었다** (r2 는 10001) |

확인 — `/output/*` 가 생기고 값이 0 이 아니어야 한다:

```bash
ros2 topic hz /output/panda_joint                # 약 50 Hz (창이 찰 때까지 기다려 읽는다)
ros2 topic echo /output/panda_joint --once       # 값이 전부 0.0000 이면 솔버가 없다 (①)
ros2 topic echo /output/gripper_joint --once     # position 개수: t1 6 · r2 2
```

시작과 함께 **차트가 재생되어 팔·그리퍼가 움직인다** — 끝날 때까지 명령을 보내지 않는다(⑥).

./scripts/run_collect_functionbay.sh            # (선택, 다른 터미널) 학습 데이터 수집 — 위 수집 계층 + rosbag + 적재 설정.
                                                #   ⑥ 차트 종료까지 확인한다. --with-stack 이면 제어 계층 · 트윈도 띄운다
./scripts/run_robot_twin.sh --twin rdfp01   # (선택, 다른 터미널) REST 트윈 rdfp01 · :8801 — 팔 연산은 ⑥ 뒤

**띄우기 전에 프로파일의 `sim_scene` 이 시뮬레이터 씬과 같은지 본다** — `src/robot_control/config/backends/panda_functionbay.yaml`
의 `sim_scene: t1` **한 줄**이다(2026-10-20 부터). 씬마다 다른 값은 같은 파일의 `sim_scenes.<씬>` 에 함께 들어 있다:

| 키 (`sim_scenes.<씬>`) | `r2` | `t1` |
|---|---|---|
| `solver` | `RecurDyn` | `Crisp` |
| `gripper.profile_file` | `config/functionbay_gripper_recurdyn.json` | `config/functionbay_gripper_crisp.json` |
| `motion.gravity_compensation` | **`null`** (`MMR-Build_260929` 은 솔버가 보상한다) | **있음** — `kp` 는 그 씬 게인(260929 기준 20000) |

**어긋나면 로봇 스택이 기동을 멈춘다** — `readiness_gate` 가 시뮬레이터의 그리퍼 보고 축 수(r2 2 · t1 6)를 프로파일 씬과
대조해 다르면 `Scene mismatch: …` 를 내고 종료 코드 2 로 끝난다. 맞으면 `Scene check passed` 가 찍힌다.

고쳤으면 `robot_control` 을 재빌드한다. 그다음 게인을 대조한다 — **④ 로 시작한 뒤에** 돌린다(시작 전에는 `SolverConfig.json` 이 이전 씬을 가리킨다):

```bash
./scripts/functionbay/fb_gains.py       # 종료 코드 1 = 우리 kp 와 씬 게인이 다르다
```

**기동 확인** — `readiness_gate` 가 `/output/panda_joint` 첫 메시지를 60 s 안에 받고 끝나며(`got 7 joint position(s)`),
기동 로그에 `convention: solver=RecurDyn scene=r2`(t1 이면 `solver=Crisp scene=t1`)가 찍힌다.

**팔을 움직이는 작업은 ⑥ 이 끝난 뒤에 한다.**

### ⑥ 차트 종료 대기 (WSL)

시뮬레이션을 시작하면 씬에 딸린 **SignalChart 가 자동으로 재생**되어 팔과 그리퍼가 움직인다. 끄는 설정은 없다 — 씬 XML 의
`<Input Type="SignalChart">` 가 유일한 입력 모드다. 그래서 **벤더 차트를 우리 차트로 바꿔 끼워 쓴다**(2026-10-21, 아래 「우리 차트」).
**어느 차트든 끝날 때까지 팔·그리퍼에 명령을 보내지 않는다.**

| 씬 | 차트 (`<씬>__panda_robotiq_ref_1_vm.xml` 의 `Chart_File_Name`) | 길이 | 끝난 뒤 |
|---|---|:-:|---|
| `r2` · `t1` | **우리 차트** `rdfp_ready_r2` · `rdfp_ready_t1` | 4 s | 팔은 **`ready`**, 그리퍼는 **열림**, peg 는 **처음 자리(`peg_tray`)** |
| `t1` | (벤더) `panda_peginhole_file` | 11 s | 팔은 P0, **그리퍼가 peg 를 문 채**로 남는다(\|effort\| 약 7 N·m) · peg 는 `peg_hole` |
| `r2` | (벤더) `panda_peginhole_g2` | 20 s | 팔은 11 s 에 P0, 그다음 9 s 동안 **그리퍼를 연다** · peg 는 `peg_hole` |

**새 빌드에는 벤더 차트가 걸려 있다** — 받으면 아래 「우리 차트」의 설치를 다시 한다.

#### 우리 차트 (`scripts/functionbay/charts/`)

벤더 차트는 peg 를 집어 구멍에 넣는 **시연**이라 시작할 때마다 씬이 바뀌고(t1 은 그리퍼가 peg 를 문 채 끝난다), 끝나기 전에
명령이 가면 중간 자세로 끊긴다. 우리 차트는 **아무것도 집지 않는다** — `q0`(벤더 차트의 t=0 자세)에서 1 s 머문 뒤 3 s 동안
관절공간 직선으로 `ready` 에 가고, 그리퍼는 처음부터 연다. `q0` 는 손끝이 `peg_tray` 바로 위 0.38 m 이고 `ready` 까지 링크4~손끝의
최저 높이도 0.38 m 라 고정물 근처로 내려가지 않는다(FK 계산).

실측(2026-10-21, r2): 시작 후 **4.8 s 에 `ready` 에 정지**(일곱 관절 오차 0.00001 rad 이하), 그리퍼 `[0.0001, −0.0001]`, peg
`peg_tray` · 기울기 0°. 이어서 트윈으로 close → open 이 각각 `[0.725, −0.725]` · `[0.0001, −0.0001]`, 빈손 \|effort\| 0.003~0.014 로
0929 회차 기준값과 같았다. `fb_wait_chart` 는 이 차트를 읽어 종료 코드 0 으로 끝났다. `Player.log` 에 `[RobotSys] Operation 로드: …
Chart_File_Name=rdfp_ready_r2` 가 찍히면 우리 차트가 걸린 것이다. t1 은 아직 돌려 보지 않았다.

> ⚠️ **차트는 모든 관절에 `Position` · `Velocity` · `Torque` 세 줄을 다 가져야 한다 — 하나라도 빠지면 그리퍼가 조용히 고장 난다.**
> 솔버 입력은 관절당 세 값이다(r2 = 팔 7×3 + 그리퍼 2×3 = **27**, t1 = 7×3 + 6×3 = **39**). 우리 r2 차트 첫 판이 그리퍼 두 축의
> `Velocity` · `Torque` 를 빠뜨렸더니(벤더 차트를 줄을 걸러 읽고 "Position 만 있다"고 오독했다) 시뮬레이터는 멈추지 않고
> `[mmr_model] BuildUserInputs 채운 개수(23) != num_user_inputs(27)` 만 매 주기 남긴 채 돌았다. 증상은 **그리퍼가 명령을 안 따르고**
> (close 15 s 뒤에도 측정 −0.0003), **보고값이 얼어**(위치 0 인데 속도 567 rad/s · effort 306.9 가 소수점까지 그대로) 시작 직후 둘째 축이
> `−99.89` 같은 값을 냈다. 토픽 모드로 넘어가도 낫지 않는다. **차트를 바꾼 뒤에는 `Player.log` 의 이 경고가 0 인지부터 본다:**
>
> ```bash
> grep -c BuildUserInputs /mnt/c/Users/<user>/AppData/LocalLow/MetaMotionX/MetaMotionRobot/Player.log   # 시작 이후 0 이어야 한다
> ```

**설치** — 빌드 폴더의 원본을 먼저 백업하고, 씬 XML 은 속성값 한 곳만 바꾼다(BOM · CRLF 가 그대로 남는다):

```bash
DB=/mnt/d/MMR-Build_<빌드>/MMR_Database
mkdir -p $DB/rdfp_backup && cp -p $DB/Database/VariableModel/{r2,t1}__panda_robotiq_ref_1_vm.xml $DB/rdfp_backup/
cp scripts/functionbay/charts/rdfp_ready_{r2,t1}.xml $DB/Database/SignalChart/
sed -i 's/Chart_File_Name="panda_peginhole_g2"/Chart_File_Name="rdfp_ready_r2"/'   $DB/Database/VariableModel/r2__panda_robotiq_ref_1_vm.xml
sed -i 's/Chart_File_Name="panda_peginhole_file"/Chart_File_Name="rdfp_ready_t1"/' $DB/Database/VariableModel/t1__panda_robotiq_ref_1_vm.xml
grep -h Chart_File_Name $DB/Database/VariableModel/{r2,t1}__panda_robotiq_ref_1_vm.xml   # 확인
```

- **새 빌드에서는 `q0` 부터 대조한다** — 벤더 차트의 t=0 값이 우리 차트의 t=0 과 다르면 시작 순간 팔이 그 차이만큼 튄다.
  다르면 우리 차트의 t=0 · t=1 값을 벤더 값으로 고친다. **관절 수 · 줄 구성도 대조한다** — 벤더 차트와 관절별 `Position` ·
  `Velocity` · `Torque` 구성이 같아야 한다(위 경고). 설치 뒤 `/scene/start` 하고 `Player.log` 의 `BuildUserInputs` 경고가 0 인지 본다.
- 시뮬레이터는 **`/scene/start` 때마다** 씬 XML 과 차트를 다시 읽는다 — 앱을 재시작할 필요가 없다(`/scene/stop` → `/scene/start`).
- **되돌리기** — 백업한 씬 XML 을 제자리로 복사하거나 `Chart_File_Name` 을 벤더 이름으로 돌린다. `MMR-Build_260929` 의 백업은
  `MMR_Database/rdfp_backup_20261021/` 에 있다.

> ⚠️ **차트 도중에 `/input/panda_joint` · `/input/gripper_joint` 로 명령이 하나라도 가면 차트가 끊긴다.** 시뮬레이터가
> `[PandaCommandTopicApplier] 토픽 명령 감지 → 토픽 모드 전환 (이후 커맨드 파일 무시).` 로 바꾸고 차트를 버린다(`Player.log`).
> 팔은 차트 중간 자세에, peg 는 엉뚱한 곳에 남는다. **로봇 스택은 기동만으로는 `/input/*` 에 아무것도 내지 않으므로**(그리퍼
> 노드는 목표가 올 때만, servo 다리는 servo 출력이 올 때만 발행한다) ⑤ 를 먼저 띄워도 된다 — 팔을 움직이는 작업만 기다린다.

```bash
./scripts/functionbay/fb_wait_chart.py          # 차트가 끝나면 종료 코드 0
```

`fb_wait_chart` 는 활성 씬(`SolverConfig.json`)으로 차트 파일을 찾아 길이와 **끝 자세**를 읽고, 팔·그리퍼 보고가 3 s 동안 멈춰 있으면서
팔이 끝 자세에 있으면(또는 차트 길이만큼 지났으면) 끝난 것으로 본다. 종료 코드: 0 끝났다 · 1 시간 초과(기본 120 s) · 2 보고가 안 온다 ·
3 차트를 못 읽었다. 설정 DB 경로는 `fb_gains.py` 와 같다(인자 > `FB_MMR_DATABASE` > 기본값).

**차트가 끝난 뒤 팔을 움직이는 작업은 그리퍼를 열고 `ready` 로 가는 것으로 시작한다** — 벤더 차트면 t1 은 그리퍼가 peg 를 문 채
끝난다. 우리 차트는 이미 그 상태로 끝나지만 순서는 그대로 지킨다(차트가 바뀌어도 안전하게).
`scripts/functionbay/` 의 `fb_*` 스크립트는 이것을 스스로 한다(`fb_ready.goto_ready()`). 따로 할 때는 `./scripts/functionbay/fb_recover.py`.

## 3. 시뮬레이션 시작 · 정지 — ROS 토픽으로

시뮬레이터를 띄운 채 시뮬레이션만 멈추고 다시 시작할 수 있다. **`ros_tcp_endpoint` 가 떠 있어야 한다**(§2 ③) —
명령이 endpoint 를 거쳐 시뮬레이터에 닿는다. 도메인·RMW 는 §2 ③ 과 같게 둔다.

```bash
# 시작
ros2 topic pub --once -w 1 /scene/start std_msgs/msg/String "{data: ''}"
# 정지
ros2 topic pub --once -w 1 /scene/stop std_msgs/msg/String "{data: ''}"
```

- `-w 1` 은 구독자(시뮬레이터) 하나가 붙을 때까지 기다렸다가 보낸다 — endpoint 가 없으면 보내지 않고 계속 기다린다.
- **인자(`-Scene` · `-Model`)로 띄워도 시작은 이 토픽으로 한다**(§2 ④). `/scene/stop` 뒤에 다시 시작할 때도 같다.
- 토픽 이름은 `<sim_folder>\MetaMotionRobot_Data\StreamingAssets\SimControlTopics.json` 이 정한다. 같은 파일에 상태 ·
  씬/모델 제어 토픽도 있다:

  | 키 | 토픽 | 비고 |
  |---|---|---|
  | `start` · `stop` | `/scene/start` · `/scene/stop` | 위 명령 (`std_msgs/String`, 내용은 비운다) |
  | `state` | `/scene/state` | 시뮬레이터가 상태를 5 Hz 로 낸다(`Player.log` 의 `[SimStatePublisher]`). 타입은 **`std_msgs/String`** 이다(endpoint 로그 `RegisterPublisher(/scene/state, …String)`) — 내용 형식은 아직 안 봤다 |
  | `loadScene` · `loadModel` · `removeModel` | `/scene/load_scene` · `/scene/load_model` · `/scene/remove_model` | 씬·모델을 실행 중에 바꾸는 토픽으로 보인다 — 아직 쓰지 않았다 |

- **정지했다 다시 시작하면 씬이 처음으로 돌아간다** (2026-10-21 실측, r2) — peg 는 처음 자리(`peg_tray`)로, 팔은 차트의 t=0 자세로
  돌아가고 **차트가 다시 재생된다**(씬 XML · 차트 파일도 이때 다시 읽는다). 정지 중에는 `/output/panda_joint` 가 거의 멈춘다(4 s 에 3건).
  로봇 스택은 다시 띄우지 않아도 됐다 — 재시작 뒤 트윈의 `ee_pose` 가 `quality OK` 로 계속 갱신됐다. sim 시계 자체는 재 보지 않았다.
  살아남은 노드가 `TF_OLD_DATA` 를 내면 그때 로봇 스택을 다시 띄운다(§4 6).
  - 시작 직후 첫 보고는 팔 일곱 관절이 전부 `0` 이다 — **시작 직후 보고로 판정하지 않는다.** (그리퍼 둘째 축이 `−99.89` 를 낸
    적이 있는데, 그것은 입력이 빠진 차트 탓이었다 — §2 ⑥ 「우리 차트」의 경고.)
- 이 토픽들은 우리 계약의 `/scene/objects` 와 같은 `/scene` 이름공간에 있지만 **시뮬레이터 쪽 토픽**이다. 펑션베이는 `/scene/reset` 을 제공하지 않는다.

## 4. 씬 바꾸기

1. **로봇 스택을 내린다** — launch 터미널에서 Ctrl-C. 남은 노드는 `./scripts/kill_stack.sh --ros` 로 정리한다(먼저 `--dry-run`).
2. **시뮬레이터와 솔버를 끈다.**
3. 새 씬의 **솔버** → **시뮬레이터**(`-Model <새 씬>_ms`) 순으로 띄운다 (§2 ①②).
4. **`ros_tcp_endpoint` 를 다시 띄운다** — endpoint 는 앞 씬에서 등록된 퍼블리셔를 들고 있어(예: t1 의 `/output/endeffector`) 토픽 목록이 섞인다.
5. **`/scene/start` 로 시작한다** (§2 ④).
6. **프로파일의 `sim_scene`** 을 새 씬으로 바꾸고 `robot_control` 재빌드 → `fb_gains.py` (§2 ⑤). 그다음 **로봇 스택을 다시 띄운다.** 시뮬레이터를 재시작하면 sim 시계가 0 으로 되감기므로, 살아남은 노드가 있으면 `TF_OLD_DATA` 를 낸다.
7. **차트가 끝날 때까지 기다린다** — `fb_wait_chart.py` (§2 ⑥).

## 5. 내리기

- **로봇 스택** — launch 터미널에서 Ctrl-C(`SIGINT`). `setsid` 래퍼나 프로세스 `kill` 로 끝내면 자식 노드가 남는다 — `./scripts/kill_stack.sh --ros`.
- **`ros_tcp_endpoint`** — Ctrl-C. 시뮬레이터만 재시작할 때는 둬도 된다(시뮬레이터가 다시 붙는다).
- **시뮬레이션만 멈출 때** — `/scene/stop` (§3). 창은 그대로 둔다.
- **시뮬레이터 · 솔버** — 창을 닫는다. 그 전에 필요하면 `Player.log` 를 복사한다.

## 6. 안 될 때

| 증상 | 먼저 볼 것 |
|---|---|
| `readiness_gate` 가 60 s 뒤 타임아웃, launch 전체 종료 | `ros_tcp_endpoint` 가 떠 있는가 (`ss -ltnp \| grep :10000`), 도메인·RMW 가 같은가 — [체크리스트 함정 11](펑션베이_인수_체크리스트.md) |
| 차트가 중간에 멈췄다 · 팔이 차트 도중 자세에 서 있다 | 차트 도중에 `/input/*` 명령이 갔다 — `Player.log` 의 `토픽 명령 감지 → 토픽 모드 전환`. 시뮬레이션을 다시 시작한다 (§2 ⑥) |
| 시뮬레이터는 떴는데 `/output/*` 토픽이 없다 | 시작을 안 했다 — `/scene/start` (§2 ④). endpoint 가 먼저 떠 있어야 한다 |
| 토픽은 50 Hz 로 오는데 값이 전부 `0.0000`, 팔·그리퍼가 안 움직인다 | 그 씬의 **솔버 프로세스** — 함정 14 |
| 그리퍼는 움직이는데 **팔만** 안 움직인다 | `Player.log` 의 `JointStateMsg` 예외 (빈 `velocity`) — 함정 10 |
| 로봇 스택이 `Scene mismatch` 로 멈춘다 · 그리퍼 명령이 거부된다 | 프로파일 `sim_scene` 이 시뮬레이터 씬과 맞는가 (보고 축 수: r2 2 · t1 6) — 함정 15 |
| 팔이 몇 mm 어긋난 곳에 선다 | `fb_gains.py` — 게인과 우리 `kp` 가 다르거나, 벤더 보상 씬에 우리 보상이 남아 이중 보정 |
| 시뮬레이터 재시작 뒤 `TF_OLD_DATA`, `/ee_pose` 가 멈춘다 | ROS 스택 재기동 (`kill_stack.sh --ros` 후 다시 띄운다) |
| `ros2 topic list` 에 `/rosout` 만 보인다 | CLI 데몬 — `--no-daemon` 으로 대조 (함정 2) |
