`readiness_gate` 가 조용히 타임아웃될 뿐 원인이 로그에 드러나지 않는다.

```bash
ros2_env humble          # ROS_DOMAIN_ID=31, RMW_IMPLEMENTATION=rmw_fastrtps_cpp
```

워크스페이스는 fastdds 로 통일돼 있으므로 맞춰야 할 쪽은 시뮬레이터다.
2차 측정 시점의 브리지는 `ROS_DOMAIN_ID=31` / `rmw_fastrtps_cpp` 로 떠 있었다.

확인:

```bash
ros2 topic info /output/panda_joint      # Publisher count 가 1 이어야 한다
```

### 9.2 스택 기동

**순서가 있다** — 솔버 → 시뮬레이터 → `ros_tcp_endpoint` → `/scene/start` → 우리 스택 → 차트 종료 대기 (명령은 [펑션베이_시뮬레이터_사용법.md](펑션베이_시뮬레이터_사용법.md) §2). **endpoint 는 우리
launch 가 띄우지 않는다** — 없으면 `readiness_gate` 가 60초 타임아웃으로 launch 전체를
끝내고, `Player.log` 에는 `127.0.0.1:10000` 연결 거부만 반복된다.

```bash
ss -ltnp | grep :10000        # 없으면 아래로 띄운다 (이미 떠 있으면 포트 충돌)
source ~/development/ros/tcp_ws/install/setup.bash
ros2 daemon start                                   # 먼저 데몬
ros2 run ros_tcp_endpoint default_server_endpoint   # 그다음 endpoint (기본 0.0.0.0:10000)
ros2 topic pub --once -w 1 /scene/start std_msgs/msg/String "{data: ''}"   # 다른 터미널 — 시뮬레이션 시작

colcon build --packages-select rdfp_msgs robot_control rdfp    # 설치본을 소스와 맞춘다
./scripts/run_panda_functionbay.sh
./scripts/functionbay/fb_wait_chart.py                        # 다른 터미널 — 자동 재생 차트가 끝날 때까지 (그 전에 팔·그리퍼 명령 금지)

# 수집 계층(세션·녹화)까지 필요하면
ros2 launch rdfp rdfp_collect.launch.py backend:=functionbay   # 2026-09-13 부터 묶음 launch 대신
```

기동 로그에서 **그리퍼 규약이 씬과 맞는지** 본다 — `convention: solver=RecurDyn scene=r2`.
안 맞으면 노드가 보고 축 수(r2 2 · t1 6)와 대조해 **명령을 거부한다.**

### 9.3 진단 — 반드시 이 순서로

```bash
# 0) 씬의 솔버 프로세스가 떠 있는가 (r2 -> SolverTCPServer.exe, t1 -> CrispSolver.exe)
#    없어도 /output/* 는 50 Hz 로 나오고 값만 0 에 고정된다 — 1) 이 0 % 로 나오는 원인 1위다
tasklist.exe | grep -iE "SolverTCP|Crisp"

# 1) 시뮬레이터가 명령에 반응하는가 (여기서 갈린다)
./scripts/functionbay/fb_raw.py named  0.30 4.0
./scripts/functionbay/fb_raw.py noname 0.30 4.0

# 2) 정착 오차 — 현재 자세를 그대로 명령해 중력 처짐을 잰다
./scripts/functionbay/fb_hold.py 15

# 3) 정규 경로 + 추종 성능 (측정기를 먼저 띄우고 명령을 낸다)
./scripts/functionbay/fb_probe.py 30 /tmp/probe.json &
./scripts/functionbay/fb_move.py named extended 50.0 /tmp/start.json

# 4) 자세 복구 (자기충돌이나 이상 자세에 빠졌을 때)
./scripts/functionbay/fb_recover.py 5.0
```

**0) 을 건너뛰면 1) 의 "0 % 무반응" 을 벤더 A-4(수신 경로 고착)로 오진한다** — 2026-09-29 에
실제로 그랬다. 그 상태의 지문은 **전 관절이 정확히 `0.0000` 이고 변하지 않는 것**이고,
`Player.log` 에는 `[PandaCommandTopicApplier] 토픽 명령 감지` 까지 찍힌다. ⚠️ **다른 씬의
솔버가 남아 있을 수 있으니 이름이 씬과 맞는지 본다.**

`fb_probe.py` 를 **별도 프로세스**로 돌리는 것이 중요하다. 같은 Node 를 두 곳에서
spin 하면 `MoveGroupClient` 의 동기 메서드와 충돌한다
([move_group_client_user_guide §14.2](../../control/move_group_client_user_guide.md)).

### 9.4 수집 계층 얹기

```bash
ros2 launch rdfp rdfp_collect.launch.py backend:=functionbay \
    enable_image_viewer:=false image_recorder_output_dir:=/tmp/recordings
```

**실제 시뮬레이터로 확인됐다 (2026-09-17 → 09-29 `t1` → 09-30 `r2`)** — 체크리스트 C-10.
`/target_joint_cmds` 가 `/joint_states` 와 **같은 벽시계 축**이고(stamp 만으로 잰 명령→응답
dead time 52.0 ms · τ 100.0 ms 가 수신 기준과 같은 대역), 세션 레코더가 정렬된 영상
(`/camera_image_aligned/compressed`)을 받아 드롭 0 · sidecar 역순 0 이다.

⚠️ **`image_recorder_output_dir` 을 주지 않으면 노드가 죽는다** — 기본 `/data/rdfp/recordings`
에 권한이 없다(§8 항목 16). ⚠️ **뷰어를 켜면 WSLg 창이 뜨므로** 헤드리스 확인에서는 끈다.

## 10. 작업 중 실제로 당한 함정

### 10.1 정지한 값을 "죽었다"로 읽지 않는다

§2.3. 위치 제어 팔은 목표를 유지하면 값이 고정된다. 정지한 장면을 그리는 카메라도
프레임 해시가 같다. **자극을 준 뒤 반응을 보는 것이 유일하게 신뢰할 수 있는 판정**이다.

### 10.2 처진 값을 다시 명령하면 누적된다

§3.1 · §4. 진단 스크립트가 "현재 자세를 읽어 그대로 명령"하는 패턴을 쓰면 호출할
때마다 팔이 더 처진다. 절대 목표를 주거나, 처짐을 감안해 보정한다.

> **2026-09-30 — `r2` 에서는 처짐이 없다** (벤더가 중력을 보상한다, 정착 오차 0.0000).
> 그래도 **패턴 자체는 그대로 금지한다** — `t1` 에는 처짐이 남아 있고(우리 보상으로 상쇄),
> 자세를 상대로 이어받는 것은 처짐과 무관하게 오차를 쌓는다(CLAUDE.md: 16회 이동에
> 접근축이 22.3° 기울었다).

### 10.2b 접촉을 "중력 처짐" 이나 "고착" 으로 읽지 않는다

**2026-09-01 에 실제로 두 번 오진했다.** 그리퍼가 닫힌 채 무언가에 눌린 상태에서
(1) 하강 명령이 먹지 않는 것을 "명령 무반응 고착"으로, (2) 그리퍼를 연 직후 EE 가
40 mm 내려간 것을 "명령을 멈추면 중력으로 처진다"로 읽었다. **둘 다 접촉 하나로
설명된다** — 접촉이 팔을 받치고 있다가 풀린 것이다.

실측하면 명확하다. 목표를 1초만 보내고 끊어도 **25~30초간 자세가 유지된다**
(정상상태 오차 0.19°, `ready` 에서는 0.00000 rad). setpoint 는 latch 된다.

판정 순서: (1) 접촉 여부 — 그리퍼 `effort` 가 1 N·m 을 넘는가, (2) 명령 경로 —
`joint1`/`joint7`(중력 토크가 없는 축)이 단독 명령에 응답하는가. 이 둘을 먼저
가른 뒤에야 고착을 의심한다.

### 10.2c Unity 를 재시작하면 ROS 스택도 재기동한다 — `/ee_pose` 가 굳는다

**2026-09-01 실측.** Unity 재시작으로 시뮬레이터 시계가 0 으로 되돌아가면 TF 버퍼가
굳어 `/ee_pose` 가 **같은 값을 계속 발행한다.**

```
150건 수신 / 3초, 전부 동일값, header.stamp 가 3632초에 정지
같은 구간에 관절은 0.15335 rad 움직였다
```

**발행은 계속되므로 토픽 목록·주기만 봐서는 정상으로 보인다.** `/ee_pose` 가
`/output/panda_joint` → TF 에서 파생된 값이라 생기는 문제다(backend_design §5.3).

판별: **관절은 움직이는데 EE 가 안 변하면** 이것을 의심한다. `header.stamp` 가
멈춰 있는지 보면 확정된다. ROS 스택 재기동으로 해소된다.

실제로 이 함정이 측정을 한 번 오염시켰다 — "6방향 전부 0 mm" 를 보고 servo 문제로
읽을 뻔했는데, 관절 이동값이 0 이 아닌 것을 보고 갈라냈다.

### 10.3 시뮬레이터가 "살아 있는데 명령만 안 먹는" 상태로 빠질 수 있다

> ### ⚠️ 2026-09-30 — **그 증상의 1위 원인은 고착이 아니라 "솔버 미기동" 이다**
>
> 씬의 솔버 프로세스(`r2` → `SolverTCPServer.exe`, `t1` → `CrispSolver.exe`)가 안 떠
> 있으면 **Unity 는 `/output/*` 를 50 Hz 로 계속 발행하고**(값이 전 관절 `0.0000` 에
> 고정된 채) `/clock` 도 진행하며, 명령을 보내면 `Player.log` 에
> `[PandaCommandTopicApplier] 토픽 명령 감지 → 토픽 모드 전환` 까지 찍힌다 —
> **팔·그리퍼만 0 % 다.** 2026-09-29 에 이것을 벤더 A-4 재현으로 오진했다.
>
> 지문 셋: ① **전 관절이 정확히 `0.0000` 이고 변하지 않는다**(정상 회차는 차트 종료
> 자세에 있다) ② `tasklist.exe | grep -iE "SolverTCP|Crisp"` 에 **그 씬의** 솔버가 없다
> — ⚠️ **다른 씬의 솔버가 남아 있어 "돌고 있다"로 착각하기 쉽다** ③ A-17 정지가
> **2.1 s 로 균일**해진다(정상은 편차가 있다). **§9.3 의 0) 을 먼저 돌린다.**

§2.2. **진짜 고착의 트리거는 아직 모른다.** 상태 보고는 계속 나오므로 프로세스·토픽·연결만
봐서는 정상으로 보이고, `fb_recover.py` 로도 빠져나오지 못해 **Unity 재시작이
필요하다.**

> **다만 과거 사례 일부는 오진이었다**(§10.4). 판정은 반드시 고친 `fb_raw.py`
> (7관절 · 양방향)로 한다.

진단 스크립트는 발행 주기를 `0.02 s`(50 Hz)로 **명시적으로 고정**한다. 고착 예방
목적은 아니고(고율 발행은 트리거가 아님이 확인됐다) 시뮬레이터 수신 주기에 맞춰
결정적으로 동작시키기 위해서다. `rclpy.spin_once(timeout_sec=...)` 를 발행 주기로
삼으면 루프가 훨씬 빨리 돌아 의도치 않게 수백 Hz 가 되므로 쓰지 않는다.

### 10.4 진단 도구가 관절 하나·방향 하나에 의존하면 오진한다

§2.2 · §4.1. 옛 `fb_raw.py` 는 **joint7 을 + 방향으로만** 밀어 "시뮬레이터가
반응하는가" 를 판정했다. 그런데 그 관절의 실효 상한이 URDF 보다 훨씬 안쪽이라,
거기 걸리면 **멀쩡한 시뮬레이터를 "전체 무반응" 으로 판정**했다.

**"반응 없음" 은 여러 축·양방향으로 확인하기 전까지 결론이 아니다.** 현재
`fb_raw.py` 는 7관절을 각각 여유 있는 방향으로 시험한다.

### 10.5 `pkill -f` 는 자기 자신을 죽인다

패턴 문자열이 그 명령을 실행하는 셸의 cmdline 에 그대로 들어가므로 자기 매칭된다.

```bash
pkill -f 'ros2 launch robot_control panda_functionbay'   # 이 명령을 실행한 셸도 죽는다
```

PID 로 지목하거나 프로세스 그룹(`kill -- -PGID`)을 쓴다.

### 10.6 launch 부모가 죽으면 자식 노드가 고아로 남는다

`ros2 launch` 프로세스만 죽으면 `move_group` · `rviz2` · `robot_state_publisher` 등이
그대로 살아남아 도메인에 계속 붙어 있다. 다음 기동 때 조용히 간섭한다.

정리 후에는 반드시 확인한다:

```bash
ros2 node list --no-daemon      # 시뮬레이터 브리지만 남아야 한다
```

### 10.7 `OnProcessExit` 는 실패 종료에도 발동한다

`readiness_gate` 가 타임아웃(exit 1)해도 그냥 엮으면 `move_group` 이 올라온다.
`_chain_or_shutdown` 으로 종료 코드를 보게 되어 있다 —
[panda_functionbay.launch.py](../../../src/robot_control/launch/panda_functionbay.launch.py)
의 `startup_handler`. 구조를 바꿀 때 이 부분을 유지한다.
