## 1. 목표

**한 백엔드에서 모은 데이터로 학습한 추론기를, 같은 로봇 구성의 실제 로봇에 배치한다.**

줄(line)이 둘이고 **서로 닫혀 있다.**

```
isaac (Panda + Panda Hand)     ─학습→ isaac 배치       ─…→ 실기 Panda + Panda Hand
functionbay (Panda + Robotiq)  ─학습→ functionbay 배치 ─…→ 실기 Panda + Robotiq 2F-85
```

| | isaac 줄 | functionbay 줄 |
|---|---|---|
| 시뮬레이터 로봇 | Panda + Panda Hand | **Panda + FT 센서 + Robotiq 2F-85** (`panda_ftsensor_robotiq` = **대상 로봇**의 description) |
| 실기 목표 | 같은 구성 | 같은 구성 |
| 두 줄의 데이터 | **섞지 않는다** | |

**섞지 않는 이유는 취향이 아니다 — 다른 로봇이다.** 손끝이 **149 mm** 떨어져 있고 그리퍼 기구가 다르다.

## 2. 무엇이 범위 밖인가

목표가 정해지면서 **고민하지 않아도 되는 것**이 생겼다. 적어 두지 않으면 계속 비용을 치른다.

| | 왜 범위 밖인가 |
|---|---|
| **백엔드 혼합 학습** | 두 줄이 다른 로봇이다. [ACT 문서](학습_샘플_사양.md) §6 의 "백엔드 혼합 ○"은 **경우 B 의 성질**이지 우리가 쓸 기능이 아니다 |
| **여러 시뮬레이터에 걸친 일반화** | 각 줄이 자기 실기만 겨냥한다 |
| ~~도메인 무작위화(렌더러 섞기)~~ | 위와 같은 이유 — **다만 한 줄 안에서의 무작위화(조명·배치)는 별개이고 §7 Q3 에 남긴다** |

⚠️ **"섞지 않는다"가 "섞여도 괜찮다"는 아니다.** 실수로 섞이면 조용히 망가지므로 **탐지는 여전히 필요하다**([Q13 문서](열린_결정.md) §4 의 균질성 확인). 다만 성격이 **전제**에서 **사고 방지 가드**로 내려간다.

## 3. 단계

| 단계 | 무엇 | 산출물 | 도메인 갭 |
|---|---|---|---|
| **1 — 시뮬레이터 안에서 닫는다** | 한 백엔드에서 학습하고 **같은 백엔드에 배치**한다 | 동작하는 추론기 **+ 경험 + 몰랐던 문제 목록** | **없다.** 학습과 배치의 관측이 **동일하다** |
| **2 — 실기 배치** | 같은 구성의 실기로 옮긴다 | 실기에서 작업 수행 | **여기서 시작된다** — 영상·동역학·센서 |

**1단계에 도메인 갭이 없다는 것이 이 계획의 가장 좋은 성질이다.** 1단계는 순수하게 *"파이프라인이 끝까지 도는가, ACT 가 과제를 배우는가"* 를 묻고, 그 답이 **실기 이야기에 오염되지 않는다.**

> **1단계의 산출물은 추론기만이 아니다.** 경험과 **예기치 못한 문제 목록**이 함께 나오고, **그것이 2단계의 요구사항을 바꾼다.** 그래서 **2단계에 필요한 것을 지금 확정하지 않는다** — 확정할 수 없다. 아래 §4 가 드는 이슈들도 **"지금 해결할 목록"이 아니라 "2단계 문턱에서 다시 볼 목록"** 이다.

**1단계는 isaac 줄로 먼저 하는 것을 권한다** — 로봇 정합이 이미 맞아(§4.1) 변수가 하나 적고, R1/R2 가 **실제로 돈 것은 isaac 경로뿐**이다(펑션베이 스트리밍 경로는 시뮬레이터가 없어 한 번도 실행되지 않았다).

## 3.1 1차 목표 — isaac 에서 쌓기 (2026-09-19 확정)

**과제 하나다.** 탁자 위에 실린더와 블럭이 있고, **블럭을 실린더 위에 쌓는다.**
`/scene/reset` 으로 매 회 무작위 배치하고 그 과정을 녹화해 학습 데이터를 만든다.

> **isaac 을 먼저 하는 것은 대안이자 순서다.** 실기가 **Panda + Robotiq 2F-85** 라
> 원래 순서는 펑션베이(같은 구성)지만, 그 시뮬레이터가 개발 중이고 **peg-in-hole 환경이
> 서기까지 벤더 작업이 필요해 기다려야 한다.** isaac 은 지금 학습·추론을 바로 돌릴 수
> 있어 **그동안 경험을 쌓는다.** 펑션베이 환경이 서면 같은 흐름으로 peg-in-hole 을 하고,
> 만족스러우면 **실기 Panda + Robotiq** 으로 간다.

## 4. 이 목표가 만드는 설계 이슈

### 4.1 EE 프레임 B안이 펑션베이 줄의 **전제 조건**이 된다

**지금 MoveIt 은 두 줄 모두 `moveit_resources_panda`(Panda Hand)로 계획한다.**

| 줄 | 계획하는 로봇 | 시뮬레이터 | 실기 목표 | 정합 |
|---|---|---|---|---|
| isaac | Panda Hand | Panda Hand | Panda Hand | **맞는다** |
| **functionbay** | **Panda Hand** | Panda + Robotiq | Panda + Robotiq | **깨져 있다** |

무엇이 어긋나는가:

- **관절 공간 연산**(named target · `move_to_joints`) — 7축이 같아 **옮겨진다.**
- **데카르트 연산**(`move_linear`) — 손끝이 149 mm 다르다. `grasp_center` 정적 TF 가 **트윈 진입점에서만** 메운다.
- ⚠️ **충돌 기하가 Panda Hand 로 남아 있다.** 시뮬레이터 안에서는 충돌 판정이 시뮬레이터 몫이라 티가 덜 나지만, **실기에서는 계획이 Robotiq 을 모르는 채 경로를 낸다 — 안전 문제다.**

> **1단계는 B안 없이 된다** — 계획기·시뮬레이터·배치가 전부 같은 (틀린) 전제를 공유해 **자기 일관적**이기 때문이다. **B안은 2단계의 문턱이다.**

지금 [grasp_center_frame.md](../backends/functionbay/grasp_center_frame.md) 는 B안을 *"`grasp_center` 의 근본 해결"* 로 적는다. 이 목표에서는 **"계획이 실기와 같은 로봇을 전제하게 만드는 일"** 이고 무게가 다르다.

**B안을 하려면 무엇을 건드리는지는 [grasp_center_frame.md §7.2](../backends/functionbay/grasp_center_frame.md) 에 적었다 (2026-09-19 확인)** — 벤더 요청은 필요 없다. `panda_ftsensor_robotiq` 에 URDF · **SRDF(`group_state` 4개 포함)** · `kinematics.yaml` · 메시가 다 있어 **moveit_config 조립이 우리 쪽 일**이다. 바꿀 곳은 넷(`joint_state_fusion` 의 주입 관절 이름 · `grasp_center` TF 제거 · 프로파일 `frames` · moveit_config)이고, 벤더 쪽은 「요청」이 아니라 **「대조」**(URDF 가 구동 중인 씬과 맞나 · 충돌 기하 · FT 센서)다.

> ⚠️ **B안의 시점이 펑션베이 줄 데이터의 수명을 정한다.** 레이블 `plan(τ)` 는 **MoveIt 이 만든 값**이라(§5) description 을 바꾸면 계획이 달라진다 — 관절 공간 목표는 거의 같지만 **데카르트 계획과 충돌 회피 경로가 달라지고, 기구학 지문도 바뀐다.** 즉 **B안 이전에 모은 펑션베이 데이터는 B안 이후의 계획기와 짝이 안 맞는다**(지문 검사가 배선되면 §4.2 가 그것을 올린다).
>
> **1단계에는 문제가 없다** — 수집·학습·배치가 모두 B안 이전이라 자기 일관적이다. **다만 그 데이터를 2단계로 가져가지는 못한다.** 펑션베이 줄에서 데이터를 많이 모으기 전에 B안 시점을 정해 두는 편이 낫다.

### 4.2 ⚠️ `assert_compatible` 의 `backend` 검사가 2단계에서 **방해가 된다**

```python
if self.backend and other.backend and self.backend != other.backend:
    bad.append(f'backend: train={self.backend!r} deploy={other.backend!r}')
```

이 검사는 **혼합을 막으려고** 넣은 것이다. 그런데 이 목표는 **일부러 다른 백엔드에 배치하는 것**이다 — 학습은 `isaac`, 배치는 실기. **같은 로봇 구성인데 검사가 걸린다.**

**비교해야 할 것은 백엔드 이름이 아니라 로봇 구성이다.** 그 값이 `kinematic_model_hash`(R3/I2)이고, **지금은 비교조차 하지 않는다**(E7 §6.3 의 미검사 2개 중 하나).

| | 지금 | 이 목표에서 필요한 것 |
|---|---|---|
| `backend` | 다르면 올린다 | **2단계에서는 달라야 정상이다** — 경고로 내리거나, 같은 줄임을 아는 다른 수단이 필요 |
| `kinematic_model_hash` | **비교 안 한다** | **이것이 "같은 구성인가"의 판정이어야 한다** |

**그래서 R3/I2 의 우선순위가 오른다** — 지금은 "기구학 지문"이라는 이름으로 **섞임 탐지**용처럼 적혀 있지만, 이 목표에서는 **sim→real 이 정당한지를 말해 주는 유일한 값**이다.

### 4.3 실기 배선은 없다 — **그리고 지금 만들지 않는다**

`config/backends/` 에는 **`mock` · `mock_jgpc` · `isaac` · `functionbay` 넷뿐**이고, 저장소 어디에도 franka 하드웨어 인터페이스(`franka_ros2` · `libfranka`)가 없다.

**이것은 결함이 아니라 순서다.** 1단계를 마치기 전에는 만들지 않는다 — 이유가 둘이다.

| | |
|---|---|
| **요구사항을 아직 모른다** | 1단계의 산출물 중 하나가 **예기치 못한 문제 목록**이다(§3). 그것을 보기 전에 실기 배선을 설계하면 **틀린 것을 만들 위험**이 있다 |
| **1단계를 막지 않는다** | 시뮬레이터 안에서 닫는 데는 실기가 필요 없다 |

**진입 조건은 "1단계 완료"다.** 그때 이 절을 다시 읽고 항목을 세운다.

### 4.4 카메라 외부 파라미터 정합

영상 도메인 갭 중 **가장 구체적이고 조치 가능한 부분**이다. 시뮬레이터 카메라의 위치·자세는 `isaac_scene.json`(isaac) · 씬 XML(펑션베이)에 있고, **실기 카메라가 그 자리에 있어야** 관측 분포가 가까워진다. ⚠️ isaac_scene.json 의 주석이 *"orientation 은 눈대중으로 넣지 않는다 — 두 번 틀렸다"* 고 적어 둔 값이다.

### 4.5 그리퍼 폭의 의미가 줄마다 다르다

`qpos` 의 마지막 축은 **개구 폭(m)** 이다. **줄 안에서는 일관되지만 줄을 넘으면 다르다** — Panda Hand 와 Robotiq 2F-85 는 범위도 기구도 다르다. 섞지 않으므로 문제가 아니지만, **2단계에서 실기 그리퍼가 시뮬레이터와 같은 폭을 보고해야 한다.** 펑션베이는 `/joint_states` 에 고정값 `0.04` 를 주입하므로 **반드시 `/gripper_states` 를 쓴다**(워크스페이스 CLAUDE.md).

### 4.6 중력 보상은 배치 대상마다 다르다

- **펑션베이**: 시뮬레이터에 중력 보상이 없어 **우리가 얹는다**.
- **실기 Panda**: 로봇이 자체적으로 보상한다 → **얹으면 안 된다.**
- 레이블(관절-계획)에는 어느 쪽이든 오프셋이 없으므로(D13) **배치 어댑터(P2)가 대상에 따라 켜고 끄면 된다.** 지금도 백엔드 프로파일의 `motion.gravity_compensation` 키 유무로 정해진다 — **실기 프로파일에는 그 키를 넣지 않는다.**

## 5. 기존 결정이 이 목표에 맞는가

**맞는다. 그리고 그중 하나는 정확히 이 목표 때문에 옳다.**

| 결정 | 이 목표에서 |
|---|---|
| **관절-계획(경우 B)을 1차 학습으로** (결정 7 · 20) | ✅ **가장 중요한 정합**이다. `plan(τ)` 는 **MoveIt 이 우리 URDF 로 만든 값**이라 시뮬레이터가 만든 것이 아니다 — 실기에서도 같은 계획이 나온다. **관절-명령(경우 A)을 골랐다면 2단계에서 막혔다**(시뮬레이터 컨트롤러의 출력이고 펑션베이는 보상 오프셋까지 섞인다) |
| frame clock = 카메라 stamp (결정 21) | ✅ 실기 카메라도 간격이 흔들린다 — 고정 격자를 가정하지 않은 것이 맞다 |
| 저장 형식 (c) + `ACTPolicy` (E7 §5) | ✅ 배치 대상과 무관하다 |
| E5(관절-명령 비교 기준) | ○ **비교 기준으로서의 값은 남는다** — 다만 2단계로 옮겨 갈 대상은 아니다 |
| Q13′(오프셋 기록) | ○ 우선순위가 내려간다(§2) — 한 줄 안에서는 학습·배치가 같은 보상 상태다 |

|---|---|---|

| Q5 | **펑션베이 줄에서 B안을 언제 하나** | 데이터 수명이 걸린다(§4.1). **1단계용 데이터를 버릴 셈이면 나중에, 이어 쓸 셈이면 수집 전에** |
