### 1.2 실행 궤적 `rdfp_msgs/MotionTrajectory` (R1)

**연산 하나를 실행할 때 컨트롤러로 실제로 보낸 궤적(L2)** 을 연산마다 한 건 발행한다. 계획 궤적(`/display_planned_path`, L1)이
**아니다** — 데카르트 연산은 속도 배율 때문에 두 궤적의 시간이 다르다(vs 0.1 에서 L1 0.645 s / L2 6.451 s).

| 필드 | 뜻 |
|---|---|
| `header.stamp` | **t₀ — 궤적의 0초가 실제로 시작된 시각.** 발행 시각이 아니다. isaac 은 goal 전송 직전, 펑션베이는 첫 명령 발행 시각. 비면 적재가 에피소드 창 밖으로 버린다. `frame_id` 는 `''` |
| `operation_id` | 연산 UUID — R2 와 짝짓는 **유일한 끈** |
| `velocity_scaling` · `time_scaling` | 계획 속도 배율 · 스트리밍 재생 배율. `trajectory.time_from_start` 에는 **이미 반영돼 있다** (기록용) |
| `trajectory` | 경유점 — **보간 전 · 중력 보상 전** 관절 위치 · 속도 · 가속도, `time_from_start` 는 배율 적용 후 실제 실행 시간. `trajectory.header` 는 비운다 |

발행 지점 셋 — JTC 의 `execute_trajectory_async` · `follow_trajectory_async`, 스트리머의 `stream`(네 스트리밍 진입점이 모인다).
QoS RELIABLE · VOLATILE · 큐 10 (latched 로 두면 늦게 붙은 녹화기가 이전 연산을 중복 기록한다 — 녹화기를 먼저 띄운다).
발행 실패는 삼킨다(기록이 동작을 막지 않는다).

### 1.3 연산 이벤트 `rdfp_msgs/MotionEvent` (R2)

**연산이 어떻게 끝났나**를 연산마다 한 건 발행한다. 궤적만으로는 중간에 멈췄는지 알 수 없어 레이블이 "가지 않은 자리"를 가리키므로 있다.

| 필드 | 뜻 |
|---|---|
| `header.stamp` | 연산이 끝난 시각. ⚠️ **레이블의 구간 끝이 아니다** — goal tolerance 확인과 물리 지연(isaac 120 ms)이 들어 있다. 구간 끝은 `t₀ + truncated_at` |
| `operation_id` | 짝 R1 과 같은 값 |
| `operation` | 이동 방식 셋 — `named_target` · `joints` · `cartesian` (트윈 REST 이름이 아니다) |
| `result` | `succeeded` / `aborted` / `failed`. **기준은 "궤적을 컨트롤러로 넘기려 했는가"** — goal 거부 · 시작 오차 위반은 `aborted`(R1 이 이미 나갔다). **`failed` 만 짝 궤적이 없다** — 적재 검증의 유일한 불변식 |
| `reason` | 사람이 읽는 값 (레이블 계산에 쓰지 않는다) |
| `truncated_at` | **궤적 기준** 중단 시각(경과 초). 정상 종료면 궤적 길이(clamp), `failed` 면 0 |
| `target_kind` · `target_joint_names` · `target_joint_values` · `target_pose` · `target_frame` | 클라이언트가 **실제로 겨냥한** 목표. pose 는 tip link 기준(펑션베이는 사용자 값과 149 mm 다르다). `failed` 여도 채운다 |

발행 지점 셋 — JTC 결과 콜백(isaac 두 경로 합류) · 스트리머 · JGPC 계획 콜백(펑션베이 계획 실패). 그리퍼 연산은 싣지 않는다.
mock(JTC) 실측으로 검증표 전수 통과, 불변식 `(R1 있음) ⇔ (result ≠ failed)` 성립. **펑션베이 실주행은 미검증.**

## 2. 명령 체인 L0~L4

명령 하나가 연산(의도)에서 관측(결과)까지 구체화되는 단계다. 번호가 클수록 하드웨어에 가깝고 백엔드에 종속된다.

| 단계 | 이름 | 내용 | 전달 수단 | 녹화 |
|---|---|---|---|:-:|
| L0 | 연산 | `move_to_named_target` · `move_to_joints` · `move_linear` 호출과 인자 | HTTP(트윈) / 메서드 | ✗ (R2 가 해석된 목표를 싣는다) |
| L1 | 계획 궤적 | MoveIt 출력 (`RobotTrajectory`, 100 ms 격자) | `/display_planned_path` (`stamp` 0) | ✗ (쓰지 않는다) |
| **L2** | **실행 궤적** | 컨트롤러로 전달된 궤적. 관절 공간 계획은 L1 과 같고, 데카르트는 클라이언트가 시각을 1/vs 배 | **R1 `motion/trajectory`** | ○ |
| L3 | 컨트롤러 출력 | 보간 · 보정된 설정값 — isaac JTC 100 Hz, 펑션베이 `TrajectoryStreamer` 50 Hz + 중력 보상 | `/isaac/arm_command` · `/input/panda_joint` → `/target_joint_cmds` | ○ (비교 기준) |
| L4 | 관측 | `/joint_states` · `/gripper_states` · 영상 | — | ○ |

**1차 학습의 행동은 L2(관절-계획)** 이고, 관절-명령(L3)은 비교 기준이다. M1 = L3, M2 = L2, M3 = L0 로 부르던 옛 이름은 보관본에만 있다.

### 연산별 계획 · 실행 경로

| 연산 | 계획 | 속도 배율 적용 | isaac (JTC) | functionbay (JGPC) |
|---|---|---|---|---|
| `move_to_named_target` · `move_to_joints` | `MoveGroup` 액션 (OMPL 기본) | MoveIt (`max_velocity_scaling_factor`) | `plan_only=True` 계획 → `ExecuteTrajectory` (2026-09-18 분리) | `plan_only=True` → `TrajectoryStreamer` (50 Hz 선형 보간 + 중력 보상) |
| `move_linear` | `GetCartesianPath` (Humble 요청에 배율 필드 없음) | **클라이언트** `scale_trajectory_velocity()` 가 시각을 1/vs 배 | `ExecuteTrajectory` | `TrajectoryStreamer` |
| `move_gripper_to_target` | 없음 | — | `/gripper_cmds` → `GripperActionNode` | `/gripper_cmds` → `Robotiq2FGripperNode` (`r2` 는 2 s 램프) |

- 트윈의 vs 는 연산 인자 → 트윈 설정 → 프로파일 `motion.velocity_scaling` → 코드 기본 1.0 순, `[0.01, 1.0]`. **기본이 isaac 1.0 · 펑션베이 0.4** 로 다르다. 실효 배율은 R1 이 연산마다 싣는다.
- `move_to_joints` 는 지정하지 않은 관절을 현재값으로 고정한 뒤 계획한다(R2 의 `target_joint_*` 는 채워진 일곱 개).
- `move_linear` 의 `frame` 을 생략하면 트윈 `ee_frame` 기준으로 해석해 tip link(`panda_link8`)로 옮긴 뒤 계획한다.
- **servo 가 켜져 있으면 servo 출력이 같은 L3 채널로 들어온다** — 데이터 생성 중에는 `teleop_keyboard` 를 띄우지 않는다.

## 3. 시간과 정렬

### 3.1 기준 시각

- 적재는 `header.stamp` 로 에피소드 창을 거른다 — **stamp 가 0 이면 rosbag 에는 남고 DB 에는 안 들어간다.**
- isaac 은 `use_sim_time:=true` — 우리 노드와 시뮬레이터 보고가 모두 sim time. `/target_joint_cmds` 는 수신 시각으로 다시 찍혀 전달 지연(수 ms)이 더해진다. `rdfp_collect backend:=isaac` 이 수집 계층도 맞춘다.
- 펑션베이는 우리 노드(`/target_joint_cmds` · R1 · `/session`)가 벽시계이고 시뮬레이터 stamp 는 회차마다 벽시계와 경과시간을 오가므로 **백엔드 경계에서 벽시계로 정렬한다** — `joint_state_fusion`(`stamp_source: aligned`)이 오프셋을 더해 `/joint_states` 를 내고 `fb_camera_restamp` 가 카메라를 같은 오프셋으로 재stamp 한다(`/camera_image_aligned/compressed`). `stamp_source:=now` 는 쓰지 않는다(관절 보고가 2~3건씩 묶여 도착). 수집 전 확인은 `/joint_states` stamp 가 벽시계인지(체크리스트 C-4).
- 영상 sidecar 의 `stamp` 는 이미지 메시지의 `header.stamp` 다. mp4 는 프레임 순서만 담으므로 **프레임 순번으로 시각을 계산하지 않는다.**

### 3.2 frame clock 과 재표본화

export 는 모든 채널을 **카메라 프레임 시각 t_i** 에 맞춘다(프레임 하나 = 샘플 하나). 카메라가 여럿이면 `topic=` 을 요구한다.

| 채널 | 성격 | t 에서의 값 |
|---|---|---|
| 팔 관측 `/joint_states` | 연속 · 조밀 | t 에서 선형 보간 |
| 팔 행동 (관절-계획) | 연산마다 한 건 | `plan(τ)` 를 τ_j = t + Δ + j × 스텝 에서 평가 (§4.2) |
| 팔 행동 (관절-명령, 비교용) | 연속 · 조밀 | t + δ 에서 선형 보간, 명령 공백은 직전 명령 유지 (§5) |
| 그리퍼 행동 | 이벤트 · 상태 유지 | τ 이전 마지막 명령 (0차 유지) |
| 그리퍼 관측 | 주기 | t 에 가장 가까운 샘플 |
| 영상 | 프레임 | 프레임 i 그 자체 (`frame_index`) |

움직이는 동안 성긴 명령을 조밀한 관측 주기에 0차 유지로 반복하는 방식은 쓰지 않는다 — 연산 사이처럼 계획이 없는 구간을
직전 값으로 유지하는 것과는 다르다(컨트롤러가 실제로 마지막 설정값을 붙든다).

## 4. 샘플 구조

### 4.1 한 샘플

```
sample(i)                          # 카메라 프레임 i, 시각 t_i
  observation
    image   : [3, H, W]            # 프레임 i (640×480)
    qpos    : [8]                  # 팔 7축: /joint_states 를 t_i 에서 선형 보간
                                   # 그리퍼 1: /gripper_states 의 width (m) 최근접, 없으면 NaN
  action    : [k, 10]              # j = 0 … k-1,  τ_j = t_i + Δ + j × T_a
    arm     : [k, 7]               # plan(τ_j)  — 관절-계획 (§4.2)
    gripper : [k, 3]               # τ_j 이전 마지막 /gripper_cmds 를 one-hot(open · close · grasp)
  is_pad    : [k]                  # τ_j 가 에피소드 끝을 넘으면 True
```

| 항목 | 값 | 비고 |
|---|---|---|
| 행동 스텝 T_a | **100 ms** | 계획이 가진 정보가 10 Hz 다 — 50 Hz 로 뽑으면 보간값만 는다 |
| 첫 스텝 오프셋 Δ | **100 ms** | 다음 스텝부터 레이블로 쓴다 |
| chunk 길이 k | **20 저장** (2 s) | 최댓값으로 저장하고 짧은 k 는 잘라 쓴다 — `τ_j` 가 k 와 무관하다 |
| 격자 | **시각** (경유점 번호가 아니다) | 경유점 간격은 계획 종류 · 배율에 따라 100 ms 가 아니고(데카르트 10 × vs Hz) 카메라와 위상도 다르다 |
| 관절 순서 | `metadata.json` 의 `spec.arm_joints` | 행동 채널(`motion_trajectories.joint_names`)에서 온다 — `/joint_states` 가 아니다 |
| 그리퍼 심볼 순서 | `open` · `close` · `grasp` | **배치의 argmax 계약**. 모르는 심볼은 전부 0. 첫 명령 이전은 `open` |
| 정규화 | 저장은 원값, 학습 때 `metadata.json` 통계(Welford)로 | `NaN` 은 그 차원만 건너뛰어 세고, 움직이지 않은 차원은 정규화하지 않는다 |
| 샘플 수 | 에피소드 안 카메라 프레임 수 | 경계 프레임은 버리지 않고 양 끝 값을 유지한다 — 버리면 `frame_index` 가 밀린다 |

### 4.2 관절-계획 레이블 함수 `plan(τ)`

"시각 τ 에 계획상 팔이 있어야 할 관절 자세" 를 돌려주는 함수다. R1 · R2 를 `operation_id` 로 짝지어 만든다
(`load_operations` 가 두 테이블을 OUTER JOIN — 어느 쪽이 없는 것이 정상이다).

| τ 의 위치 | plan(τ) |
|---|---|
| 첫 연산 이전 | 에피소드 시작 시점의 관절 관측 |
| 연산 s 실행 중 (t₀ₛ ≤ τ < t₀ₛ + truncated_atₛ) | R1 경유점을 τ − t₀ₛ 에서 보간 — 속도가 있으면 3차 Hermite, 없으면 선형 |
| 연산 s 가 끝난 뒤, 다음 연산 전 | **`L2(truncated_atₛ)`** — 정상 종료면 자연히 끝점, 중단이면 멈춘 자리 |

- **구간 끝은 `t₀ + truncated_at`** 이다. R2 의 `header.stamp` 를 쓰면 경유점 하나 넘게 밀린다.
- 이벤트(R2)가 없는 연산은 정상 종료로 **가정**한다 — `episodes.jsonl` 의 `assumed_full_duration` 이 그 수를 세고 그런 에피소드는 **기본 제외**한다(`.npz` 는 남긴다). `overlapping`(앞 연산이 끝나기 전에 시작) 은 경고, `skipped_failed`(궤적 없음 = `failed`) 는 정상이다. ⚠️ 카운트가 두 군데(`load_operations` · `PlanLabel.stats`)에서 나온다.
- chunk 가 다음 연산의 시작을 넘으면 **다음 연산의 계획이 그대로 들어간다** — 시연이 이어서 한 동작이다.
- 접촉 구간(peg 삽입처럼 궤적이 밀린 곳)에서 `plan(τ)` 는 "밀리지 않았다면 있었을 위치" 다 — 관측과의 차이가 그만큼 벌어진다.
- 펑션베이 레이블에는 중력 보상이 **없다**(R1 이 보상 전 경유점). 배치 경로에서 보상을 건다.

## 5. 관절-명령 비교 기준

`/target_joint_cmds` 를 같은 격자에서 선형 보간한 레이블(`CommandLabel`)이다. `PlanLabel` 과 같은 인터페이스라
`arm_action_chunks()` 에 바꿔 끼워 두 레이블을 같은 격자에서 견준다.

- **명령 공백에서는 보간하지 않고 직전 명령을 유지한다** — 명령은 팔이 움직이는 동안에만 나오므로 이으면 없던 움직임이 생긴다. 공백 임계는 **명령 간격의 중앙값 × 2** (평균은 긴 공백에 끌려간다). `gap_intervals()` 가 공백 분포를 보여 준다.
- ⚠️ **단일 백엔드로만 쓴다** — 백엔드마다 보간이 다르고(isaac JTC 스플라인 100 Hz / 펑션베이 선형 50 Hz) 펑션베이는 중력 보상 오프셋(`ready` 에서 joint4 +9.67 mrad)이 들어 있다. `metadata.json` 은 오프셋 포함 여부를 아직 말하지 못한다(열린 결정 Q13′).
- 펑션베이 JGPC 에서는 관절-명령과 관절-계획이 사실상 같은 신호다(그 사이에 판단하는 컨트롤러가 없다) — 의미 있는 비교는 isaac 이다.

## 6. 배치 규약

학습 레이블의 정의와 배치 인터페이스는 **같은 규약을 공유해야 한다.** 컨트롤러가 보간한다고 학습 때의 의미가 자동으로 보존되지는 않는다.

| 항목 | 규약 |
|---|---|
| 추론 주기 | 10 Hz — 새 영상마다. **추론이 100 ms 안에 끝나야 한다** |
| 한 번의 출력 | k 스텝 chunk (τ_j = t + Δ + j × 100 ms) |
| temporal ensembling | 각 100 ms 스텝을 덮는 chunk k 개를 exp(−m · i) 가중 평균 — 원래 ACT 와 같은 형태 |
| isaac 에 넣는 법 | JTC 단일점, `time_from_start = Δ`, **`open_loop_control: true`**(이미 설정) — 측정 상태에서 보간을 다시 시작하면 부하 처짐이 명령에 적분된다(servo 래칫) |
| 펑션베이에 넣는 법 | 직전 명령에서 50 Hz 로 보간해 스트리밍하고 **중력 보상을 건다** (레이블에는 없다) |
| 계단 금지 | 10 Hz 목표를 컨트롤러에 그대로 넣지 않는다 — 펑션베이에서 peg 삽입 실패(15 mm 밀림, 3회 재현) |
| 그리퍼 | one-hot 의 argmax 심볼을 `/gripper_cmds` 로. 같은 심볼이 이어지면 다시 보내지 않는다 |
| 조건 대조 | 배치 스택의 `ExportSpec` 을 만들어 `assert_compatible()` — `label` · `delta_sec` · `step_sec` · `chunk_len` · `arm_joints` · `gripper_symbols` 는 **엄격**, `camera_hz` 는 상대 20 %, `backend` 는 양쪽 값이 있을 때만, `camera_topic` · `kinematic_model_hash` 는 비교하지 않는다 |
| 정규화 되돌리기 | 정책 출력을 `Normalizer.invert()`(또는 lerobot 후처리기)로 원값으로 |
| 체크포인트 | 정책 + **전처리기**(정규화가 정책 밖이다) + `rdfp_spec.json` 세 파일이 한 묶음 |

추론 노드(P1) · 컨트롤러 어댑터(P2) · 조건 대조(P3)는 아직 없다 — 재생용 `target_joint_cmds_executor`(JTC 단일점) 가 어댑터의 출발점이다. 스택 구성과 구현 전에 풀어야 할 것은 [추론기_배치_스택_구성.md](추론기_배치_스택_구성.md) 에 있다 — ⚠️ lerobot 의 temporal ensembling 은 **호출 횟수**로 스텝을 세므로, 프레임이 빠지는 isaac 에서는 위 표의 "각 100 ms 스텝을 덮는 chunk" 를 **시각으로** 맞춰야 한다(그 문서 §5.2).
