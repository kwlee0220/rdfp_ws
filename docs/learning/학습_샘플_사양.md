# 학습 샘플 사양 — 채널 · 명령 체인 · 샘플 구조 · 배치 규약

> **상태: 현행 사양.** 이 문서는 현재 파이프라인이 생성하는 학습 샘플의 구조와 처리 규칙을 정의한다. 대안 비교와 권고는 [결정_기록.md](결정_기록.md)(왜) 에, 남은 일은 [미구현_목록.md](미구현_목록.md) 에, 정하지 않은 것은 [열린_결정.md](열린_결정.md) 에 있다. 저장 파일의 모양은 [저장_형식.md §4](저장_형식.md#4-저장-형식-스키마) 이 정본이다. 1차 학습(isaac · 관절-계획 · ACT) 기준이다.

**주요 용어**

| 용어 | 뜻 |
|---|---|
| 연산 | 팔을 한 번 움직이라는 요청 하나 — `move_to_named_target` · `move_to_joints` · `move_linear` 호출 한 번이다(L0). 그리퍼 동작과 servo 입력은 연산이 아니다 — §1.3 · §2 |
| R1 · R2 | 연산마다 한 건씩 기록하는 실행 궤적(`MotionTrajectory`)과 연산 이벤트(`MotionEvent`) — §1.2 · §1.3 |
| L0~L4 | 명령이 연산에서 관측까지 구체화되는 단계. L2 가 실행 궤적이다 — §2 |
| frame clock | 샘플 시각으로 쓰는 카메라 프레임 시각열 — §3.2 |
| chunk | 한 샘플이 담는 미래 행동 k 스텝 — §4.1 |
| 배치 | 학습한 정책을 실행 환경(로봇 스택)에 배포하는 것. 학습의 mini-batch 가 아니다 — §6 |

### 1.2 실행 궤적 `rdfp_msgs/MotionTrajectory` (R1)

**컨트롤러에 전달할 실행 궤적(L2)** 을 연산마다 한 건 기록한다. JTC 에서는 goal 전송 직전에 발행하므로 R1 이 있다는 것만으로 컨트롤러의 수락이나 실제 실행을 판단할 수 없다 — 실행 결과는 같은 `operation_id` 의 R2 에서 확인한다. 계획 궤적(`/display_planned_path`, L1)이 **아니다** — 데카르트 연산은 속도 배율 때문에 두 궤적의 시간이 다르다(vs 0.1 에서 L1 0.645 s / L2 6.451 s).

| 필드 | 뜻 |
|---|---|
| `header.stamp` | **t₀ — 실행 궤적의 시간축 기준 시각.** JTC(isaac)는 goal 전송 직전, JGPC(펑션베이)는 첫 명령 발행 시점의 노드 시각이다. 로봇이 실제로 움직이기 시작한 시각을 잰 값은 아니다(isaac 은 JTC 보간 시작보다 약 12 ms 이르다, §7). 비면 적재가 에피소드 창 밖으로 버린다. `frame_id` 는 `''` |
| `operation_id` | 연산 UUID — R1 과 R2 를 연결하는 **유일한 식별자** |
| `velocity_scaling` · `time_scaling` | 계획 속도 배율 · 스트리밍 재생 배율. `trajectory.time_from_start` 에는 **이미 반영돼 있다** (기록용) |
| `trajectory` | 경유점 — **보간 전 · 중력 보상 전** 관절 위치 · 속도 · 가속도, `time_from_start` 는 배율 적용 후 실제 실행 시간. `trajectory.header` 는 비운다 |

발행 구현(구현 상세는 [실행_궤적_채널_구현.md](실행_궤적_채널_구현.md)):

- **발행 지점 둘** — JTC 는 `MoveGroupJtcClient._begin_motion` 이 goal 전송 직전에 발행한다(`execute_trajectory_async` · `_execute_joint_goal_async`(named target · joints 비동기) · `follow_trajectory_async` 가 부르며, 동기 경로는 `execute_trajectory_async` 를 거친다). JGPC 는 `TrajectoryStreamer.stream` 이 첫 명령 직전에 발행한다(스트리밍 진입점이 모두 여기로 모인다). 실행 궤적은 둘 중 한쪽에서만 나가므로 한 연산이 두 번 발행되지 않는다.
- **QoS** — RELIABLE · VOLATILE · KEEP_LAST 10. 늦게 붙은 구독자는 지난 연산을 받지 못하므로 녹화기를 먼저 띄운다.
- **실패 처리** — 발행에 실패하면 경고를 기록하고 예외를 호출자에게 전파하지 않는다. 기록 실패가 로봇 동작을 막지 않는다.
- **배율 반영** — `time_scaling` 은 스트리머가 발행 일정에만 곱하므로 발행자(`apply_time_scaling`)가 `time_from_start` · 속도 · 가속도에 반영해 싣는다.

### 1.3 연산 이벤트 `rdfp_msgs/MotionEvent` (R2)

**연산이 어떻게 끝났나**를 연산마다 한 건 발행한다. R1 만으로는 실행이 중간에 멈췄는지 알 수 없으므로, R2 가 실행 결과와 중단 시점을 기록해 중단 이후의 궤적이 레이블에 반영되지 않게 한다.

| 필드 | 뜻 |
|---|---|
| `header.stamp` | 연산이 끝난 시각. ⚠️ **레이블의 구간 끝이 아니다** — goal tolerance 확인과 물리 지연(isaac 120 ms)이 들어 있다. 구간 끝은 `t₀ + truncated_at` |
| `operation_id` | 짝 R1 과 같은 값 |
| `operation` | 이동 방식 셋 — `named_target` · `joints` · `cartesian` (트윈 REST 이름이 아니다) |
| `result` | `succeeded` / `aborted` / `failed`. **기준은 "궤적을 컨트롤러로 넘기려 했는가"** — goal 거부 · 시작 오차 위반은 `aborted`(R1 이 이미 나갔다). **`failed` 만 짝 궤적이 없다** — 적재 검증의 유일한 불변식 |
| `reason` | 사람이 읽는 값 (레이블 계산에 쓰지 않는다) |
| `truncated_at` | **궤적 기준** 중단 시각(경과 초). `publish_context` 가 정한다 — `succeeded` 는 궤적 길이, 값이 주어진 `aborted` 는 `[0, 궤적 길이]` 로 자른 값(JTC 는 결과 수신 시각 − t₀, 스트리머는 마지막으로 발행한 샘플의 시각), goal 거부처럼 한 점도 안 간 `aborted` 와 `failed` 는 0 |
| `target_kind` · `target_joint_names` · `target_joint_values` · `target_pose` · `target_frame` | 클라이언트가 실행 요청에 **사용한 목표값**. `target_kind` 는 발행자가 정한다(pose 가 있으면 `pose`, 관절값이 있으면 `joints`). pose 는 tip link 기준이고 `target_frame` 은 그 tip 이름이다(펑션베이는 사용자 값과 149 mm 다르다). `failed` 여도 채운다 |

발행 구현:

- **발행 지점 셋** — JTC 클라이언트(`_finish_motion`: 실행 결과 콜백 · goal 거부 · 예외, `_publish_failed`: 계획 실패 · 궤적 검증 실패), 스트리머(`stream`: 끝까지 보냈으면 `succeeded`, 중단 · 예외면 `aborted`), JGPC 클라이언트(`_publish_failed`: 계획 실패).
- **`failed`** — R1 없이 새 `operation_id` 로 나간다.
- **QoS** — R1 과 같다. 그리퍼 연산은 싣지 않는다.
- **검증 범위** — isaac(JTC)에서 R1 · R2 를 실측했다(t₀ 편향 · 데카르트 L2/L1 · R2 시각, §7). 불변식 `(R1 있음) ⇔ (result ≠ failed)` 는 발행부 단위 시험이 확인한다. **펑션베이 실주행은 검증하지 않았다.**

## 2. 명령 체인 L0~L4

명령 하나가 연산(의도)에서 관측(결과)까지 구체화되는 단계다. 번호가 클수록 하드웨어에 가깝고 백엔드에 종속된다.

| 단계 | 이름 | 내용 | 전달 수단 | 녹화 |
|---|---|---|---|:-:|
| L0 | 연산 | `move_to_named_target` · `move_to_joints` · `move_linear` 호출과 인자 | HTTP(트윈) / 메서드 | ✗ (R2 가 해석된 목표를 싣는다) |
| L1 | 계획 궤적 | MoveIt 출력 (`RobotTrajectory`, 100 ms 격자) | `/display_planned_path` (`stamp` 0) | ✗ (쓰지 않는다) |
| **L2** | **실행 궤적** | 컨트롤러로 전달된 궤적. 관절 공간 계획은 L1 과 같고, 데카르트는 클라이언트가 시각을 1/vs 배 | **R1 `motion/trajectory`** | ○ |
| L3 | 컨트롤러 출력 | 보간 · 보정된 설정값 — isaac JTC 100 Hz, 펑션베이 `TrajectoryStreamer` 50 Hz (+ 프로파일에 설정된 중력 보상 — `sim_scene` 이 고른 씬의 `motion.gravity_compensation` 이 있을 때만: `t1` 은 있고 `r2` 는 `null`(벤더 솔버가 보상한다)) | `/isaac/arm_command` · `/input/panda_joint` → `/target_joint_cmds` | ○ (비교 기준) |
| L4 | 관측 | `/joint_states` · `/gripper_states` · 영상 | — | ○ |

**1차 학습의 행동은 L2(관절-계획)** 이고, 관절-명령(L3)은 비교 기준이다.

### 2.1 연산별 계획 · 실행 경로

| 연산 | 계획 | 속도 배율 적용 | isaac (JTC) | functionbay (JGPC) |
|---|---|---|---|---|
| `move_to_named_target` · `move_to_joints` | `MoveGroup` 액션 (OMPL 기본) | MoveIt (`max_velocity_scaling_factor`) | `plan_only=True` 계획 → `ExecuteTrajectory` | `plan_only=True` → `TrajectoryStreamer` (50 Hz 선형 보간, 켠 씬이면 + 중력 보상) |
| `move_linear` | `GetCartesianPath` (Humble 요청에 배율 필드 없음) | **클라이언트** `scale_trajectory_velocity()` 가 시각을 1/vs 배 | `ExecuteTrajectory` | `TrajectoryStreamer` |
| `move_gripper_to_target` | 없음 | — | `/gripper_cmds` → `GripperActionNode` | `/gripper_cmds` → `Robotiq2FGripperNode` (`r2` 는 2 s 램프) |

- 트윈의 vs 는 연산 인자 → 트윈 설정 `moveit.velocity_scaling` → 프로파일 `motion.velocity_scaling` → 코드 기본 1.0 순이다. 연산 인자의 허용 범위는 `[0.01, 1.0]` 이다 — 기본 입력 스키마 검증이 켜져 있으면(`jsonschema` 설치 시) 범위 밖의 값은 `400 INVALID_INPUT` 으로 거부되고, 백엔드도 방어적으로 같은 범위로 자른다. 출하 트윈 설정은 이 키를 두지 않고 isaac 프로파일에는 `motion` 블록이 없어 **기본이 isaac 1.0 · 펑션베이 0.4** 다. 실효 배율은 R1 이 연산마다 싣는다.
- `move_to_joints` 는 생략한 관절의 최종 목표값을 현재 관절값으로 채운 뒤 계획한다. 이동 중 그 관절이 움직이지 않는다는 보장은 없다. R2 의 `target_joint_*` 에는 채워진 일곱 관절의 목표값이 기록된다.
- `move_linear` 의 `frame` 을 생략하면 트윈 `ee_frame` 기준으로 해석해 tip link(`panda_link8`)로 옮긴 뒤 계획한다. `ee_frame` 이 없는 백엔드(isaac)는 입력이 곧 tip 기준이다. `frame` 에는 tip 또는 `ee_frame` 이름만 받는다.
- **servo 가 켜져 있으면 servo 출력이 같은 L3 채널로 들어온다** — `/target_joint_cmds` 에는 섞이고 R1 · R2 에는 남지 않는다(servo 는 MoveGroup 클라이언트를 거치지 않는다).

## 3. 시간과 정렬

### 3.1 기준 시각

- 적재는 `header.stamp` 로 에피소드 창을 거른다 — **stamp 가 0 이면 rosbag 에는 남고 DB 에는 안 들어간다.**
- isaac 은 `use_sim_time:=true` — 수집 · 제어 노드와 시뮬레이터 보고가 모두 sim time 이다. `/target_joint_cmds` 는 수신 시각으로 다시 찍혀 전달 지연(수 ms)이 더해진다. `rdfp_collect backend:=panda_isaac` 이 수집 계층도 맞춘다.
- 펑션베이는 수집 · 제어 노드(`/target_joint_cmds` · R1 · `/session`)가 벽시계이고 시뮬레이터 stamp 는 회차마다 벽시계와 경과시간을 오가므로 **백엔드 경계에서 벽시계로 정렬한다** — `joint_state_fusion`(`stamp_source: aligned`)이 오프셋을 더해 `/joint_states` 를 내고 `fb_camera_restamp` 가 카메라 이미지에 같은 오프셋을 적용해 타임스탬프를 보정한다(`/camera_image_aligned/compressed`). `stamp_source:=now` 는 쓰지 않는다(관절 보고가 2~3건씩 묶여 도착). 수집 전 확인은 `/joint_states` stamp 가 벽시계인지(체크리스트 C-4).
- 채널 정렬에는 sidecar 에 기록된 이미지 메시지의 `header.stamp` 를 쓴다. **mp4 의 재생 시각이나 프레임 번호를 ROS 수집 시각 대신 쓰지 않는다** — mp4 의 시간 정보는 재생용 고정 fps 이고 실제 프레임 간격(누락 포함)을 담지 않는다.

### 3.2 frame clock 과 재표본화

export 는 모든 채널을 **카메라 프레임 시각 t_i** 에 맞춘다(프레임 하나 = 샘플 하나). 카메라가 여럿이면 `load_frame_clock(topic=)`(CLI `--camera-topic`)을 요구한다.

| 채널 | 성격 | t 에서의 값 |
|---|---|---|
| 팔 관측 `/joint_states` | 연속 · 조밀 | t 에서 선형 보간 |
| 팔 행동 (관절-계획) | 연산마다 한 건 | `plan(τ)` 를 τ_j = t + Δ + j × 스텝 에서 평가 (§4.2) |
| 팔 행동 (관절-명령, 비교용) | 연속 · 조밀 | 같은 τ_j 에서 선형 보간, 명령 공백은 직전 명령 유지 (§5) |
| 그리퍼 행동 | 이벤트 · 상태 유지 | 같은 τ_j 이전 마지막 명령 (0차 유지) |
| 그리퍼 관측 | 주기 | t 에 가장 가까운 샘플 (샘플이 없으면 `NaN`) |
| 영상 | 프레임 | 프레임 i 그 자체 (`frame_index`) |

움직이는 동안 성긴 명령을 조밀한 관측 주기에 0차 유지로 반복하는 방식은 쓰지 않는다 — 연산 사이처럼 계획이 없는 구간을 직전 값으로 유지하는 것과는 다르다(컨트롤러가 실제로 마지막 설정값을 붙든다).

## 4. 샘플 구조

### 4.1 한 샘플

```
sample(i)                          # 카메라 프레임 i, 시각 t_i
  observation
    image   : [3, H, W]            # 프레임 i (640×480)
    qpos    : [8]                  # 팔 7축: /joint_states 를 t_i 에서 선형 보간
                                   # 그리퍼 1: /gripper_states 의 width (m) 최근접, 없으면 NaN
  action    : [k, 10]              # j = 0 … k-1,  τ_j = t_i + Δ + j × T_a
                                   # .npz 는 action_arm · action_gripper 로 따로 두고 rdfp-train 이 잇는다
    arm     : [k, 7]               # plan(τ_j)  — 관절-계획 (§4.2)
    gripper : [k, 3]               # τ_j 이전 마지막 /gripper_cmds 를 one-hot(open · close · grasp)
  is_pad    : [k]                  # τ_j 가 에피소드 끝을 넘으면 True
```

| 항목 | 값 | 비고 |
|---|---|---|
| 행동 스텝 T_a | **100 ms** (`--step-sec` 기본 0.1) | 실행 궤적의 경유점 간격은 계획 종류와 속도 배율에 따라 다르며(관절 공간 계획은 약 100 ms), 더 촘촘하게 재표본화해도 원본 경유점 정보가 늘지는 않는다 |
| 첫 스텝 오프셋 Δ | **100 ms** (`--delta-sec` 기본 0.1) | 다음 스텝부터 레이블로 쓴다 |
| chunk 길이 k | **20 저장** (2 s, `--chunk-len` 기본 20) | 최댓값으로 저장하고 짧은 k 는 잘라 쓴다 — `τ_j` 가 k 와 무관하다. rdfp-train 은 저장값보다 큰 k 를 거부한다 |
| 격자 | **시각** (경유점 번호가 아니다) | 경유점 간격은 계획 종류 · 배율에 따라 100 ms 가 아니고(데카르트 10 × vs Hz) 카메라와 위상도 다르다 |
| 관절 순서 | `metadata.json` 의 `spec.arm_joints` | `--arm-joints` 를 안 주면 `default_arm_joints()` 가 **첫 에피소드의 행동 채널**에서 가져온다 — 관절-계획은 첫 `motion_trajectories.joint_names`, 관절-명령은 `/target_joint_cmds` 의 이름. 고른 레이블의 행동 채널에서 관절 순서를 얻지 못하면 오류를 낸다 — 다른 행동 채널이나 `/joint_states` 로 대체하지 않으며, 필요하면 `--arm-joints` 로 직접 준다. `/joint_states` 에서 가져오지 않는다(손가락 관절이 함께 실려 그리퍼가 `qpos` 에 두 번 들어간다) |
| 그리퍼 심볼 순서 | `open` · `close` · `grasp` (`GRIPPER_SYMBOLS`) | `spec.gripper_symbols` 에 기록되고 rdfp-train 이 팔 7 축 뒤에 이 순서로 이어 붙인다. 모르는 심볼은 전부 0. 첫 명령 이전은 `open`(`GRIPPER_PRIOR`) |
| 정규화 | 저장은 원값, 통계만 `metadata.json` 의 `qpos`(8) · `arm_action`(7) | Welford 누적. 팔 행동은 chunk 의 첫 스텝(τ₀)만 센다(겹치는 chunk 를 k 번 세지 않게). 그리퍼 one-hot 은 통계가 없다. `NaN` 은 그 차원만 건너뛰어 센다. 표준편차가 `1e-6` 미만인 차원은 `degenerate` 로 표시하고 std 를 1.0 으로 둔다(평균은 뺀다) — `notes` 에 관절 이름이 남는다 |
| 샘플 수 | 에피소드 안 카메라 프레임 수 | 경계 프레임은 버리지 않고 양 끝 값을 유지한다 — 버리면 `frame_index` 가 밀린다 |

### 4.2 관절-계획 레이블 함수 `plan(τ)`

"시각 τ 에 계획상 팔이 있어야 할 관절 자세" 를 돌려주는 함수다(`PlanLabel.at`). R1 · R2 를 `operation_id` 로 짝지어 만든다 — `load_operations` 가 `motion_trajectories` 에서 `motion_events` 로 **LEFT JOIN** 한다. 궤적 없이 이벤트만 있는 연산(`failed`)은 읽지 않는다.

| τ 의 위치 | plan(τ) |
|---|---|
| 첫 연산 이전 | 에피소드 시작 시점의 관절 관측 |
| 연산 s 실행 중 (t₀ₛ ≤ τ < t₀ₛ + truncated_atₛ) | R1 경유점을 τ − t₀ₛ 에서 보간 — 경유점에 속도가 있으면 3차 Hermite, 없으면 선형 |
| 연산 s 가 끝난 뒤, 다음 연산 전 | **`L2(truncated_atₛ)`** — 정상 종료면 궤적 끝점, 중단이면 `truncated_at` 에서 평가한 계획 관절값을 유지한다. 실제 정지 위치를 잰 값이 아니다 |

- **구간 끝은 `t₀ + truncated_at`** 으로 계산한다. R2 의 `header.stamp` 는 결과 처리 시각이라 레이블 구간 끝과 다를 수 있으므로(isaac 실측에서는 약 120 ms 늦었다, §7), 그것으로 대신하면 시간 정렬 오차가 생긴다.
- 카운트 셋이 `episodes.jsonl` 에 남고 출처가 두 군데다. `load_operations` 가 `assumed_full_duration`(짝 이벤트가 없어 궤적 끝까지 간 것으로 **가정**한 궤적 수)을, `PlanLabel.stats` 가 `overlapping`(앞 연산의 끝 `t₀ + truncated_at` 전에 시작한 연산 수 — 시간 구간이 겹치면 더 늦게 시작한 연산의 궤적을 쓴다)과 `skipped_failed`(결과가 `failed` 이거나 경유점이 없어 시간축에서 뺀 궤적 수 — LEFT JOIN 이라 보통 0)를 센다.
- `assumed_full_duration > 0` 인 에피소드는 **기본 제외**한다(`--keep-untrustworthy` 를 주면 이 제외 규칙을 적용하지 않는다). 제외는 `metadata.json` 의 `episodes` · `samples` 와 `manifest.json` 의 `kept_episodes` 에서 빼고 `excluded` 에 사유를 적는 것이다 — `.npz` 와 `episodes.jsonl` 의 줄은 남는다. 정규화 통계도 포함한 에피소드로만 만든다 — 에피소드마다 따로 누적한 뒤 포함한 것만 `RunningStats.merge` 로 합친다. rdfp-train 의 `RdfpEpisodeDataset` 은 `episodes=` 를 주지 않으면 `metadata.json` 의 `episodes` 목록만 읽는다(그 키가 없는 트리는 `episodes.jsonl` 전부).
- chunk 가 다음 연산의 시작을 넘으면 **다음 연산의 계획이 그대로 들어간다** — 시연이 이어서 한 동작이다.
- 접촉이나 추종 지연이 생겨도 `plan(τ)` 는 실행 궤적상의 목표 관절값을 돌려준다 — peg 삽입처럼 팔이 밀린 구간에서는 그만큼 관측값과 차이가 난다.
- 펑션베이 레이블에는 중력 보상이 **없다**(R1 이 보상 전 경유점). 프로파일에 중력 보상이 설정된 씬(`t1`)에서 스트리머는 명령점마다 보상을 더해 내보낸다 — 레이블과 L3 명령이 그만큼 다르다.

|---|---|---|---|---|---|---|---|

## 5. 관절-명령 비교 기준

`/target_joint_cmds` 를 같은 격자에서 선형 보간한 레이블(`CommandLabel`)이다. `PlanLabel` 과 같은 인터페이스라 `arm_action_chunks()` 에 두 레이블 구현을 각각 넘겨 같은 시간 격자에서 결과를 비교한다.

- **명령 공백에서는 보간하지 않고 직전 명령을 유지한다** — 명령은 팔이 움직이는 동안에만 나오므로 이으면 없던 움직임이 생긴다. 공백 임계는 **명령 간격의 중앙값 × 2** (평균은 긴 공백에 끌려간다). `gap_intervals()` 가 공백 분포를 보여 준다.
- ⚠️ **단일 백엔드로만 쓴다** — 백엔드마다 보간이 다르고(isaac JTC 스플라인 100 Hz / 펑션베이 선형 50 Hz) 펑션베이는 프로파일에 중력 보상이 설정된 씬(`t1`)이면 그 오프셋이 들어 있다(크기는 §7; `r2` 는 벤더 솔버가 보상해 오프셋이 없다). `spec` 은 오프셋 포함 여부를 기록하지 않고(열린 결정 Q13′), 관절-명령으로 export 하면 그 경고와 공백 임계가 `metadata.json` 의 `notes` 에 붙는다.
- 펑션베이(JGPC)의 관절-명령과 관절-계획은 같은 실행 궤적에서 만들어지지만 값이 같지는 않다 — 레이블은 속도가 있으면 3차 Hermite 로, 스트리머는 선형으로 보간하고, 명령은 발행 시각에 찍히며, `t1` 에서는 중력 보상이 더해진다. 둘 사이에 판단하는 컨트롤러가 없으므로 컨트롤러 동작을 보는 비교는 isaac(JTC 보간 결과 대 실행 궤적)에서 한다.

## 6. 배치 규약

이 장의 배치는 학습한 정책을 실행 환경에 배포하는 것을 뜻한다. 학습과 배치가 공유해야 하는 규약 가운데 **코드로 있는 것**은 넷이다 — 규약 기록과 대조(`ExportSpec`), 정규화 되돌리기(`Normalizer.invert`), rdfp-train 의 체크포인트, 관절 명령을 JTC 로 흘리는 `target_joint_cmds_executor`. 추론 노드(P1) · 컨트롤러 어댑터(P2) · 조건 대조를 돌리는 배치 쪽 코드(P3)는 없다.

### 6.1 규약 기록과 대조 — `ExportSpec.assert_compatible`

export 가 `metadata.json` 의 `spec` 으로 남기는 값이다. `label` · `delta_sec` · `step_sec` · `chunk_len` · `arm_joints` · `gripper_symbols`(`GRIPPER_SYMBOLS`) · `camera_topic`(`--camera-topic` 또는 첫 에피소드의 시계 토픽) · `camera_hz`(첫 에피소드 프레임 간격 평균의 역수 — 실측값) · `backend`(첫 에피소드 `sessions.metadata.backend`) · `kinematic_model_hash` 다. 이 워크스페이스에는 에피소드 metadata 에 `backend` 를 쓰는 코드가 없어 `backend` 는 대개 `None` 이고, `kinematic_model_hash` 를 채우는 코드도 없어 늘 `None` 이다 — 둘 다 `notes` 에 그렇게 적힌다.

학습 쪽 spec 에서 `assert_compatible(배치 쪽 spec, camera_hz_tol=0.2)` 를 부르면 아래 규칙으로 비교한다(아래 `train` 은 학습 쪽, `deploy` 는 배치 쪽 값). 어긋난 항목을 **전부 모아** `MetadataError` 하나로 올린다.

| 항목 | 규칙 |
|---|---|
| `label` · `delta_sec` · `step_sec` · `chunk_len` · `arm_joints` · `gripper_symbols` (`STRICT_KEYS`) | `!=` 로 엄격 비교한다 — 실수도 정확히 같아야 하고 튜플은 순서까지 같아야 한다 |
| `camera_hz` | 양쪽이 모두 0 보다 클 때만 본다. `abs(deploy − train) / train` 이 `camera_hz_tol`(기본 0.2)을 넘으면 위반이다 |
| `backend` | 양쪽 모두 값이 있고 다를 때만 위반이다 |
| `camera_topic` · `kinematic_model_hash` | 비교하지 않는다 |

`assert_compatible` 은 넘겨받은 `chunk_len` 을 그대로 비교한다. 저장된 chunk 를 잘라 학습한 체크포인트와 대조할 때는 학습 쪽 `ExportSpec.chunk_len` 을 체크포인트의 `chunk_len_used`(§6.3)로 바꿔 넣어야 한다 — `export_spec.chunk_len` 을 그대로 쓰면 정상적인 짧은 k 배치 설정이 불일치로 판정된다.

### 6.2 정규화 되돌리기 — `Normalizer.invert`

`Normalizer.invert(values)` 는 차원마다 `v × std + mean` 이다(`apply` 의 역). `degenerate` 차원은 std 가 1.0 이라 평균만 되돌린다. `metadata.json` 의 `arm_action` 이 팔 7 축의 통계이고(`Normalizer.from_dict` 로 읽는다), 그리퍼 3 차원은 통계가 없으므로 정책 출력의 그 3 칸은 그대로 argmax 해 `spec.gripper_symbols` 순서로 심볼을 읽는다.

### 6.3 rdfp-train 체크포인트

`train.py` 는 `--save-every` 스텝마다 `<out>/step_NNNNNN/`, 끝에 `<out>/final/` 을 만들고 세 가지를 넣는다.

- `policy.save_pretrained` — lerobot `ACTPolicy` 의 설정과 가중치. 설정은 `build_config` 가 데이터에서 만든다: `chunk_size` = `n_action_steps` = 쓴 k, 입력 `observation.state`(8) · `observation.images.<camera_name>`(3, H, W), 출력 `action`(10), 정규화 `STATE` · `ACTION` 은 `MEAN_STD`, `VISUAL` 은 `IDENTITY`.
- `preprocessor.save_pretrained` — `make_act_pre_post_processors` 가 만든 전처리기(정규화 · 디바이스 이동). 통계는 `RdfpEpisodeDataset.lerobot_stats()` 로, `qpos` 는 export 통계 그대로, `action` 은 팔 통계 뒤에 그리퍼 3 차원을 평균 0 · 표준편차 1 로 붙인다.
- `rdfp_spec.json` — `export_spec`(`metadata.json` 의 `spec` dict 그대로) · `step` · `camera_name` · `chunk_len_used`. `export_spec.chunk_len` 은 데이터셋에 저장된 길이이고, 저장된 chunk 를 잘라 학습했다면 실제 학습 길이는 `chunk_len_used` 다.

**후처리기(역정규화)는 저장하지 않는다** — 정책 출력을 원값으로 되돌리려면 `metadata.json` 의 `arm_action` 으로 `Normalizer.invert` 를 쓰거나 같은 통계로 후처리기를 다시 만들어야 한다. 학습 로그는 `<out>/train_log.jsonl` 이다.

### 6.4 지금 있는 관절 명령 실행기 — `target_joint_cmds_executor`

`target_joint_cmds`(`sensor_msgs/JointState`)를 받아 **점 하나짜리** `trajectory_msgs/JointTrajectory` 로 감싸 `joint_trajectory` 로 낸다 — 쓰는 쪽이 이 출력을 JTC 의 `/panda_arm_controller/joint_trajectory` 로 remap 한다. 점의 `time_from_start` 는 파라미터(기본 0.0 — 컨트롤러가 즉시 반영한다)이고, 관절 이름은 메시지 `name` 이 우선이며 비어 있으면 `joint_names` 파라미터를 쓴다. `velocity` · `effort` 는 길이가 `position` 과 같을 때만 싣는다. JTC 전용이고, 입력 메시지를 받을 때마다 변환해 발행할 뿐 보간이나 시각 정렬은 하지 않는다.

### 6.5 구현되지 않은 것

정책 출력을 isaac(JTC) · 펑션베이(스트리밍)에 넣는 방법, 10 Hz 목표를 컨트롤러에 계단으로 넣지 않는 규칙, chunk 를 시각 기준으로 겹쳐 쓰는 temporal ensembling, 같은 그리퍼 심볼을 다시 보내지 않는 규칙은 구현되어 있지 않다. 그 규칙과 구성은 [추론기_배치_스택_구성.md](추론기_배치_스택_구성.md) 가 다룬다.
