## R4 · Q5 — 에피소드 metadata 규약

> 원문: [../archive/learning/R4_에피소드_metadata_규약_고려사항.md](../archive/learning/R4_에피소드_metadata_규약_고려사항.md) (2026-09-19). 아래는 그 본문이다 — 결정되면 §1 의 표를 고치고 이 절은 요약으로 줄인다.



### R4.1 무엇을 정하는가

**에피소드마다 "이 데이터가 어떤 조건에서 만들어졌는가"를 남기는 규약**이다. 자리는 이미 있다 — `sessions.metadata`(jsonb)이고 `StopEpisode` 서비스가 JSON object 문자열로 받는다. **비어 있는 것은 자리가 아니라 규약이다.**

정할 것은 넷이고, 원래 질문(Q5 의 키 목록)은 그중 하나다.

| # | 정할 것 | 절 |
|---|---|---|
| 1 | **누가 채우나** — 호출자인가 시스템인가 | §2 · §7 |
| 2 | **언제 채우나** — 종료 시점뿐인 지금이 맞나 | §3 |
| 3 | **무엇을 담나** (Q5) — 그리고 **담지 말아야 할 것** | §4 |
| 4 | **검증을 어디까지** — 빠졌을 때 거부하나 | §5 |

### R4.2 지금 누가 채우나

**셋이고 규약이 없다.**

| 생산자 | 무엇을 넣나 |
|---|---|
| **트윈 클라이언트** (`mcp_server._end_task`) | 에이전트가 넘긴 metadata 에 **서버가 기억한 `scene` · `seed` · `objects` 를 `setdefault` 로 합친다** |
| **`teleop_keyboard`** | **아무것도 안 넣는다** — "키 하나로 끝내는 UI 라 성패를 줄 수단이 없다"(코드 주석). `outcome` 도 빈다 |
| 수동 `ros2 service call` | 사람이 적는 대로 |

**트윈의 방식이 옳은 선례다.** 주석이 이유를 적어 두었다:

> 재현의 근거는 seed 가 아니라 **실제 배치**다 — 추출 방식이 바뀌면 같은 seed 가 다른 배치를 만들기 때문이다. 에이전트가 넘긴 metadata 에 서버가 기억한 배치를 합쳐 둔다.

**즉 "시스템이 아는 것은 시스템이 채운다"** 이고, 호출자는 자기만 아는 것(작업 의도 등)을 더한다. R4 는 이 원칙을 넓히는 일이다.

⚠️ **그런데 트윈만 그렇게 한다.** `teleop_keyboard` 로 모은 에피소드는 metadata 가 **통째로 빈다** — `backend` 도 없다. teleop 출처를 수집 범위에 넣는 순간(수집 설계 D1 은 지금 범위 밖이라고 적는다) 그 에피소드들은 **어느 스택에서 나왔는지 알 수 없는 데이터**가 된다.

### R4.3 언제 채워지나 — 종료 시점뿐이다

`SessionCommand.metadata` 는 **에피소드 종료 전이에서만** 채워진다. 노드가 그렇게 정했고 이유도 적혀 있다:

> `outcome` / `metadata` 는 **에피소드 종료 전이에서만** 채운다. 다른 전이는 기본값('')을 그대로 쓴다 — 그래야 후처리기가 이 값을 종료되는 에피소드에만 귀속시킬 수 있다.

**귀속 규칙으로는 맞다. 그런데 기록 시점으로는 어긋난다.**

| | |
|---|---|
| **아는 시점과 기록 시점이 다르다** | `backend` · `publish_rate` · 계획 파이프라인은 **스택을 띄울 때 정해진다.** 에피소드가 끝날 때 적는 것은 그 사실을 끝까지 들고 있다가 옮겨 적는 일이다 |
| **끝나지 않으면 잃는다** | 스택이 죽거나 rosbag 이 SIGKILL 로 끊기면 `stop_episode` 가 안 불린다. **영상·관절·궤적은 남았는데 조건만 사라진다** |
| **호출자에게 의존한다** | 종료를 부르는 쪽이 metadata 를 함께 넘겨야 하므로, §2 의 teleop 처럼 **안 넘기면 그만**이다 |

**대안은 "시스템이 기본값을 들고 있다가 합친다"** 이다 — `session_control_node` 가 launch 파라미터로 받은 값을 종료 메시지에 merge 하면, 호출자가 무엇을 넘기든 채워진다. 귀속 규칙(종료 전이에만 싣는다)은 그대로 둔 채 **출처만 바꾸는 것**이다.

`rdfp_collect.launch.py` 는 이미 `backend:=mock` 을 인자로 받으므로 **그 값이 노드까지 내려가는 길이 이미 있다.**

### R4.4 무엇을 담을 것인가

미구현 목록 R4 가 세는 키는 여섯이다 — `backend` · 속도 배율 · 펑션베이 `publish_rate` · 씬 · 계획 파이프라인 · 생성 호스트. **대조해 보니 하나는 빼야 하고 하나는 더해야 한다.**

| 키 | 판정 |
|---|---|
| `backend` | **담는다.** 지금 `episode_backend()` 가 읽으려는 값이고 항상 `None` 이다 |
| ~~속도 배율~~ | ⚠️ **빼야 한다 — 이미 R1 이 연산마다 싣는다.** `motion_trajectories.velocity_scaling` · `time_scaling` 이 컬럼으로 있다. **입도도 그쪽이 맞다** — 배율은 연산마다 다를 수 있는데 에피소드에 하나로 적으면 거짓이 된다 |
| `publish_rate` (펑션베이) | **담는다.** R1 에 없고 설정 파일에만 있다. 나중에 바뀌면 그 에피소드가 어느 값이었는지 알 길이 없다 |
| 씬 | **담는다.** 트윈이 이미 `scene` · `seed` · `objects` 로 넣고 있다 — 규약에 편입만 하면 된다 |
| 계획 파이프라인 | **담는다** (OMPL · PILZ · CHOMP 중 무엇으로 풀었나) |
| 생성 호스트 | **담는다** — 재현과 추적용 |
| **중력 보상 설정** | ⚠️ **더해야 한다** — [Q13 문서](../archive/learning/Q13_중력_보상_기록_고려사항.md) §3 이 요구하는 값이다. 백엔드 프로파일의 `motion.gravity_compensation` 블록(`urdf` · `kp` · `scale`)을 그대로 싣는다 |

**담지 말아야 할 것의 기준이 있다.**

| 기준 | 예 |
|---|---|
| **더 고운 입도로 이미 기록되는 것** | 속도 배율(R1), 연산 결과(R2), 프레임 시각(sidecar) |
| **구조가 커서 따로 두는 것** | 기구학 모델 스냅샷 — **R3/I2 가 별도 채널·테이블로 간다.** metadata 에는 그 **지문(해시)만** 둘지가 열린 질문(§10 Q3) |
| **나중에 조회로 알 수 있는 것** | 토픽 목록 — bag 과 `topics` 테이블에 있다 |

**남는 기준은 하나다: "녹화 시점에만 알 수 있고, 다른 데 안 남는 것."**

### R4.5 검증을 어디까지 할 것인가

지금 검증은 **"JSON object 인가" 하나**다(`_is_json_object`). 키 이름을 틀려도, 필수 키가 없어도 통과한다.

| | 방법 | 대가 |
|---|---|---|
| (가) | 지금처럼 **형식만** | 오타가 조용하다. `backend` 를 `bakend` 로 적어도 통과하고, 읽는 쪽은 `None` 을 본다 |
| (나) | **필수 키가 없으면 `stop_episode` 를 거부** | ⚠️ **에피소드가 이미 녹화된 뒤에 거부하는 것**이라, 수집 한 회차를 망친다. 가장 나쁜 시점의 실패다 |
| (다) | **없으면 시스템 기본값으로 채우고, 모르면 경고** | §3 의 대안과 짝이 맞는다. 거부하지 않으므로 수집을 안 망친다 |
| (라) | 적재에서 검사 | 늦다 — 그때는 고칠 방법이 없다(bag 안의 값이 이미 그렇다) |

**(나) 는 피해야 한다.** `set_task_label` 이 `IN_EPISODE` 에서 거부되고 **빈 라벨로 시작한 에피소드는 재적재로도 못 고친다**는 것이 이미 알려진 함정이다(절차서 §4). 종료를 거부하면 같은 종류의 함정을 하나 더 만든다.

### R4.6 키가 늘어날 때

**옛 에피소드에는 새 키가 없다.** 읽는 쪽이 **없음을 기본값으로 바꾸면 안 된다** — 이미 그 원칙을 지키는 선례가 있다:

```
backend is unknown — episode metadata did not record it (R4)
```

`build_metadata` 가 `notes` 에 남기는 문장이다. **"모른다"와 "그 값이다"를 구분한다.** 규약에 버전을 붙일지(`metadata_version`)는 열린 질문(§10 Q4)이지만, **키 단위로 "없으면 모른다"** 가 성립하면 버전 없이도 자란다.

### R4.7 권고

**순서가 있다. 키 목록(Q5)을 정하기 전에 배선을 정한다.**

| 단계 | 무엇 | 왜 |
|---|---|---|
| **1** | **`session_control_node` 가 launch 파라미터로 받은 기본 metadata 를 종료 메시지에 merge 한다** | §2·§3 의 구멍을 한 번에 막는다 — 호출자가 무엇을 넘기든, teleop 이든, 채워진다. 귀속 규칙은 그대로다 |
| **2** | **`rdfp_collect` 가 백엔드 프로파일에서 값을 뽑아 그 파라미터로 넘긴다** | `backend` 는 이미 인자다. `publish_rate` · 중력 보상 블록도 같은 프로파일에 있다 |
| **3** | **키 목록을 확정한다 (Q5)** — §4 의 판정표 | 1·2 가 있으면 키를 더하는 일이 **launch 한 줄**이 된다 |
| **4** | 호출자가 더할 것(작업 의도, 성패 사유)은 그대로 `StopEpisode` 로 | 트윈의 `setdefault` 방식을 유지 — **호출자 값이 이긴다** |

**1 을 먼저 두는 이유**는 §2 다. 키를 아무리 잘 골라도 **teleop 처럼 안 넣는 생산자가 있으면 빈다.** 시스템이 채우면 생산자 수와 무관해진다.

**merge 규칙은 트윈을 따른다** — `setdefault`, 즉 **호출자가 준 값이 이긴다.** 사람이 일부러 덮어쓴 것을 시스템이 되돌리면 안 된다.

### R4.8 검증

| 확인할 것 | 합격 기준 |
|---|---|
| **teleop 에피소드에도 `backend` 가 있다** | `teleop_keyboard` 로 수집한 에피소드의 `sessions.metadata` 에 값이 있다. **지금은 `{}` 다** |
| 호출자 값이 이긴다 | 트윈이 `scene` 을 넘기면 시스템 기본값이 덮어쓰지 않는다 |
| 종료를 거부하지 않는다 | 필수 키가 없어도 `stop_episode` 가 성공한다 — 경고만 남는다 |
| `export` 가 읽는다 | `episode_backend()` 가 `None` 이 아니고, `build_metadata` 의 `backend is unknown` note 가 사라진다 |
| **입도가 겹치지 않는다** | 속도 배율이 metadata 에 **없다** — `motion_trajectories` 가 갖는다 |
| 옛 에피소드 | 키가 없는 에피소드를 읽어도 **죽지 않고 "모른다"로 다룬다** |

### R4.9 주의

- ⚠️ **`stop_episode` 를 거부하면 안 된다** — 에피소드가 이미 녹화된 뒤라 고칠 방법이 없다. `set_task_label` 이 `IN_EPISODE` 에서 거부되어 **빈 라벨로 시작한 에피소드를 재적재로도 못 고치는** 것과 같은 함정이다.
- ⚠️ **속도 배율을 metadata 에 넣지 않는다** — R1 이 연산마다 싣고 있어 **중복이면서 입도가 거칠다.** 두 값이 어긋나면 어느 쪽이 참인지 알 수 없다.
- ⚠️ **`seed` 는 재현의 근거가 아니다** — 트윈 주석이 적어 둔 것이다. 추출 방식이 바뀌면 같은 seed 가 다른 배치를 만든다. **실제 배치(`objects`)가 근거다.**
- **`sessions.metadata` 는 jsonb 라 스키마 변경 없이 키가 는다** — 그래서 싸지만, 그래서 **오타도 조용하다**(§5).

### R4.10 열린 질문

| # | 질문 | 정하는 방법 |
|---|---|---|
| Q1 | 키 이름과 중첩 — 평평하게(`backend`, `publish_rate`)인가 묶어서(`stack: {...}`)인가 | `metadata->>'backend'` 로 조회하는 코드가 이미 있다(`episode_backend`). **평평한 쪽이 조회가 싸다** |
| Q2 | 시작 시점에도 남길 것인가 | §3 의 귀속 규칙을 바꾸는 일이다. **1단계(시스템 merge)가 되면 필요가 줄어든다** — 다만 끝나지 않은 에피소드의 조건은 여전히 안 남는다 |
| Q3 | 기구학 지문(R3/I2)을 metadata 에도 둘 것인가 | 스냅샷 본체는 별도 채널이지만 **해시만 metadata 에 두면** export 가 조인 없이 읽는다. `ExportSpec.kinematic_model_hash` 가 그 값을 기다린다 |
| Q4 | `metadata_version` 을 둘 것인가 | §6 의 "키 단위로 없으면 모른다"가 성립하면 필요 없다. **키를 지우거나 뜻을 바꿀 때** 필요해진다 |
| Q5 | teleop 출처를 수집 범위에 넣을 때 무엇이 더 필요한가 | 수집 설계 D1 이 지금은 범위 밖이라고 적는다. 넣으면 **§2 의 빈 metadata** 와 **servo 경로 무보상**(R8 §9)이 함께 온다 |

## Q13′ — 중력 보상 오프셋 기록

> 원문: [../archive/learning/Q13_중력_보상_기록_고려사항.md](../archive/learning/Q13_중력_보상_기록_고려사항.md) (2026-09-19). 아래는 그 본문이다 — 결정되면 §1 의 표를 고치고 이 절은 요약으로 줄인다.



### Q13.1 무엇을 정하는가

**"이 학습 데이터의 행동값에 중력 보상 오프셋이 들어 있는가"를 데이터가 스스로 말하게 하는 방법**이다. 갈래는 다섯이고, 원래 질문(`ExportSpec` 에 필드를 넣을까)은 그중 하나일 뿐이다.

| # | 정할 것 | 절 |
|---|---|---|
| 1 | **값을 어디서 얻나** — 수집이 기록하나, export 가 유도하나, 데이터에서 검출하나 | §3 |
| 2 | **입도** — 데이터셋 하나에 한 값인가, 에피소드마다인가 | §4 |
| 3 | **무엇을 기록하나** — `bool` 인가, 보상을 되돌릴 수 있는 기술자인가 | §5 |
| 4 | **`STRICT_KEYS` 에 넣나** | §6 |
| 5 | 이름 | §10 |

### Q13.2 왜 필요한가 — 오늘은 말할 수 없다

**배치에서 틀리면 이중 보상이나 누락이 나고, 둘 다 오류 없이 일어난다**(수집 설계 §9). 규칙 자체는 간단하다.

| `label` | `backend` | 오프셋 |
|---|---|---|
| `joint_plan` | 아무거나 | **없다** — R1 이 보상 전 경유점을 싣는다(D13) |
| `joint_command` | `functionbay` | **있다** (MoveIt 경로 한정 — §4 의 ⚠️) |
| `joint_command` | 그 밖 | 없다 |

**문제는 이 규칙을 오늘 적용할 수 없다는 것이다.** 유도의 재료인 `backend` 가 `sessions.metadata` 에서 오는데 **R4 미구현이라 항상 `None`** 이다. `build_metadata` 가 그 사실을 `notes` 에 남기기는 한다:

```
backend is unknown — episode metadata did not record it (R4)
```

즉 **지금 만든 관절-명령 데이터셋은 오프셋 포함 여부를 어떤 방법으로도 말하지 못한다.**

> **1차 학습은 막히지 않는다** — 관절-계획에는 오프셋이 없고 배치 경로에서 보상을 건다(수집 설계 §0.4). 이 항목이 사는 곳은 **관절-명령을 비교 기준으로 쓸 때**(E5)와 **나중에 데이터를 섞을 때**다.

### Q13.3 값을 어디서 얻는가

넷이 있고 **성격이 다르다** — 하나는 사실을 남기고, 둘은 추론하며, 하나는 측정한다.

| | 방법 | 평가 |
|---|---|---|
| **(가)** | **수집이 기록한다** — 에피소드 metadata 에 보상 설정을 싣는다 | **사실을 남긴다.** 다만 **R4 의 키 목록에 보상 정보가 없다**(아래 ⚠️) |
| (나) | **export 가 유도한다** — `label` × `backend` 규칙(§2) | `backend` 가 R4 전까지 `None` 이다. 그리고 **R8 이 들어오면 규칙이 바뀐다** |
| (다) | **사람이 CLI 로 넘긴다** — `export --gravity-offset yes/no` | R4 없이도 오늘 된다. **사람이 틀리면 조용하다** |
| (라) | **데이터에서 검출한다** — 명령과 R1 보간의 잔차를 본다 | 펑션베이 JGPC 에서는 잔차가 **정확히 오프셋**이다(R8 §4). 다른 백엔드에서는 컨트롤러 보간이 섞여 판별이 안 된다 |

⚠️ **R4 의 키 목록을 넓혀야 한다** ([R4 고려사항](../archive/learning/R4_에피소드_metadata_규약_고려사항.md) §4 가 이 항목을 받아 판정표에 넣었다). 미구현 목록 R4 가 세는 키는 `backend` · 속도 배율 · 펑션베이 `publish_rate` · 씬 · 계획 파이프라인 · 생성 호스트다 — **보상 설정이 없다.** (가)로 가려면 R4 에 그 항목을 더해야 하고, 그러면 Q13′ 가 R4 에 **좋은 방향으로** 의존한다(유도 대신 기록).

`sessions.metadata` 는 자유 JSON object 라 **스키마 변경 없이** 들어간다 — 백엔드 프로파일의 `motion.gravity_compensation` 블록을 그대로 실으면 된다.

### Q13.4 입도 — 데이터셋인가 에피소드인가

**⚠️ 지금 export 는 `backend` 를 첫 에피소드에서만 읽는다.**

```python
spec = ExportSpec(..., backend=episode_backend(conn, ids[0]))   # writer.py:319
```

그래서 **백엔드가 섞인 데이터셋을 만들어도 드러나지 않는다** — `metadata.json` 에는 첫 에피소드의 값이 적히고, 나머지는 말없이 그 이름 아래 들어간다. `assert_compatible` 은 학습 ↔ 배치를 비교할 뿐 **데이터셋 안의 균질성은 아무도 안 본다.**

오프셋 플래그를 같은 자리에 넣으면 **같은 구멍을 물려받는다.**

그리고 섞임은 가정이 아니다:

| 언제 | 왜 |
|---|---|
| 백엔드를 섞을 때 | isaac(오프셋 없음) + 펑션베이(있음) |
| **같은 펑션베이 안에서 출처가 갈릴 때** | **MoveIt 경로는 보상하고 teleop(servo) 경로는 보상하지 않는다**(R8 §9) — 한 백엔드 안에서 값이 갈린다 |
| 벤더가 A-1 을 반영한 전후 | 보상을 끄면 그 뒤 에피소드만 오프셋이 없다 |

**그래서 값은 에피소드마다 정해지고, 데이터셋 값은 그것들이 모두 같을 때만 성립한다.**

### Q13.5 무엇을 기록할 것인가

| | 형태 | 평가 |
|---|---|---|
| **(A)** | `gravity_offset_included: bool` | 가장 싸다. **"있다"만 알고 얼마인지는 모른다** — 되돌릴 수 없다 |
| **(B)** | 보상 **기술자** — `{urdf, kp, scale}` (또는 그 해시) | 되돌릴 수 있다(역보상). 기구학 지문(R3/I2)과 성격이 같다 |
| (C) | `notes` 문자열만 | 사람은 읽지만 **기계가 못 건다.** 지금 상태다 |

**(B) 를 고르면 R8 의 절반이 필요 없어진다** — 오프셋이 `q` 의 결정적 함수이므로 기술자가 있으면 적재나 export 에서 역보상할 수 있다(수집 설계 §6 권고 5 의 (b)). 다만 **역보상에 벤더 URDF 와 `GravityCompensator` 가 필요하고**, 그것을 export 계층에 들이는 것은 지금 없는 의존이다.

**둘은 배타가 아니다** — `bool` 을 `ExportSpec` 에(검사용), 기술자를 `sessions.metadata` 에(복원용) 두는 조합이 자연스럽다. 검사는 싸야 하고 복원은 드물기 때문이다.

### Q13.6 검사에 넣을 것인가

`ExportSpec` 의 대조는 세 층이다(E7 §6.3).

| 층 | 키 | 동작 |
|---|---|---|
| 엄격 | `label` · `delta_sec` · `step_sec` · `chunk_len` · `arm_joints` · `gripper_symbols` | 다르면 올린다 |
| 관대 | `camera_hz` | 상대 20 % 까지 |
| 조건부 | `backend` | **양쪽 다 값이 있을 때만** 비교 |
| 미검사 | `camera_topic` · `kinematic_model_hash` | 비교하지 않는다 |

**오프셋은 엄격이어야 한다.** 어긋남의 대가가 `camera_hz` 와 다르다 — 주기는 조금 밀리지만 오프셋은 **팔이 두 배로 처지거나 보상 없이 움직인다.**

⚠️ **`backend` 식 "한쪽이 비면 넘어간다"를 따라하면 안 된다.** 그러면 값이 없는 옛 데이터가 조용히 통과한다. **모르면 모른다고 올리는 쪽**이 맞다 — 다만 그러면 R4 이전 데이터가 전부 막히므로, **`Optional[bool]` 로 두되 `None` 을 만나면 경고가 아니라 거부**할지는 정해야 한다(§10 Q2).

### Q13.7 권고

**단계로 나눈다. 오늘 할 수 있는 것과 R4 를 기다려야 하는 것이 다르다.**

| 단계 | 무엇 | 언제 |
|---|---|---|
| **1** | **`episodes.jsonl` 에 에피소드마다 값을 싣고, export 가 균질성을 확인한다.** 값의 출처는 당장은 (다) CLI 플래그 | **지금** — R4 를 안 기다린다 |
| **2** | `ExportSpec` 에 `gravity_offset_included: Optional[bool]` 을 더하고 **`STRICT_KEYS` 에 넣는다** | 1 과 함께 |
| **3** | **R4 의 키 목록에 보상 설정을 넣는다** — `sessions.metadata` 에 `motion.gravity_compensation` 블록을 그대로 | R4 할 때 |
| **4** | 3 이 되면 export 가 CLI 플래그 대신 **metadata 에서 읽는다.** 플래그는 덮어쓰기용으로 남긴다 | R4 뒤 |

**1 을 먼저 두는 이유**는 §4 다 — 필드를 `ExportSpec` 에만 넣으면 **첫 에피소드 문제를 물려받아** 섞임이 안 드러난다. **에피소드마다 싣고 확인하는 것이 필드보다 먼저다.**

**`backend` 도 같은 처지다.** 균질성 확인을 만들 때 오프셋만이 아니라 **`backend` 도 함께 본다** — 지금 `ids[0]` 에서만 읽는 그 값이다.

### Q13.8 검증

| 확인할 것 | 합격 기준 |
|---|---|
| **섞인 데이터셋이 거부된다** | 서로 다른 값의 에피소드를 한 번에 export 하면 **올린다**. 지금은 조용히 통과한다 |
| `backend` 도 같이 걸린다 | 백엔드가 섞여도 같은 검사가 잡는다 |
| 배치 대조가 실제로 걸린다 | 오프셋 값이 다른 `ExportSpec` 으로 `assert_compatible()` 이 올린다 |
| `joint_plan` 은 항상 `False` | 레이블이 관절-계획이면 백엔드와 무관하게 `False` 다(R1 이 보상 전이므로) |
| 옛 데이터 | 값이 `None` 인 에피소드를 만났을 때의 동작이 **정해진 대로**다(§10 Q2) |
| (라) 검출과 대조 | 펑션베이 JGPC 에서 `명령 − 보간(R1)` 이 `offset(q)` 와 맞는다 — `ready` joint4 **+9.67 mrad** |

### Q13.9 주의

- ⚠️ **부호**: `offset = −deficit`, `보상후 = 보상전 + offset`. `ready` joint4 에서 **`deficit = −9.67` · `offset = +9.67 mrad`** 다(2026-09-19 실측 계산). 플래그를 다루는 코드가 부호를 만질 일은 없지만, **검증(§8 마지막)에서 대조할 때 틀리기 쉽다** — R8 문서가 그 실수를 한 번 했다.
- ⚠️ **`joint_plan` 이 `False` 인 것은 "보상하지 않는다"는 뜻이 아니다.** 레이블에 오프셋이 없다는 뜻이고, **배치는 보상을 걸어야 한다**(수집 설계 §0.4 · §9). 이름이 그 오해를 부르면 이름을 바꾼다(§10 Q1).
- ⚠️ **R8 이 들어오면 (나) 의 유도 규칙이 바뀐다.** 보상 전 명령이 별도 채널로 남으면 `joint_command` + `functionbay` 도 오프셋이 없을 수 있다. **그래서 유도보다 기록이 낫다.**
- **벤더가 A-1 을 반영하면** `functionbay.yaml` 의 블록을 지워 보상을 끈다 — 그 전후 데이터가 갈리므로 §4 의 균질성 확인이 그때 값을 한다.

## R8 — 펑션베이 보상 전 명령 채널 (권고: 지금 만들지 않는다)

> 원문: [../archive/learning/R8_보상_전_명령_채널_설계.md](../archive/learning/R8_보상_전_명령_채널_설계.md) (2026-09-19). 아래는 그 본문이다 — 결정되면 §1 의 표를 고치고 이 절은 요약으로 줄인다.



### R8.1 무엇이 문제인가

**펑션베이의 관절-명령에는 중력 보상 오프셋이 섞여 있다.** 그 시뮬레이터의 관절 제어에는 중력 보상이 없어 우리가 지령에 `−τ_g(q)/Kp` 를 미리 더하기 때문이다([펑션베이_중력_보상.md](../backends/functionbay/펑션베이_중력_보상.md)).

크기는 작지 않다 — `ready` 자세에서 **joint4 +9.67 mrad**, 작업 영역 8지점 도달 오차가 보상으로 **12.37 → 0.00 mm** 바뀌었다.

그래서 세 가지가 걸린다.

| # | 무엇 |
|---|---|
| 1 | **백엔드를 섞을 수 없다** — isaac 의 명령에는 오프셋이 없다. 같은 레이블로 섞으면 펑션베이 쪽만 계통적으로 밀린 데이터가 된다 |
| 2 | **배치에서 이중 보상이나 누락이 난다** — 학습 데이터에 오프셋이 들어 있는지에 따라 배치 경로의 보상기를 끄거나 켜야 하는데, **어긋나도 오류가 안 난다**(수집 설계 §9) |
| 3 | **명령이 시뮬레이터에 묶인다** — 오프셋은 그 시뮬레이터의 `Kp`(2000)와 우리 URDF 에서 나온 값이다. 벤더가 A-1 을 반영하면 의미가 달라진다 |

### R8.2 지금 일어나는 일

보상은 **스트리밍 경로에만** 얹힌다.

```
MoveIt 계획 ─▶ TrajectoryStreamer
                 ├─ _build_samples()    경유점을 publish_rate 격자에 **선형 보간**
                 ├─ _apply_gravity()    ← 여기서 −τ_g(q)/Kp 를 더한다
                 └─ _build_command()  ─▶ /input/panda_joint   (보상 **후**)
                                             │
                          target_joint_cmds_publisher
                                             ▼
                                      /target_joint_cmds      (보상 후, 녹화된다)
```

- **모든 명령점에 적용한다** — 정착 오차만이 아니라 이동 중 처짐도 같은 식이라, 마지막 점에만 얹으면 과도 구간의 손끝 말림이 남는다(실측 −7.14 → −0.01 mm).
- **스트리밍(JGPC) 경로에만 얹히고, 프로파일에 `motion.gravity_compensation` 키가 있는 백엔드만 켠다 — 지금은 펑션베이뿐이다.** `mock_jgpc` 도 JGPC 지만 키가 없어 보상기가 `None` 이다. mock·isaac 은 컨트롤러가 중력을 잡는다.
- 값은 `config/backends/functionbay.yaml` 한 블록이다 — 벤더 URDF + `kp: 2000.0`.

### R8.3 비대칭 — R1 은 보상 전, 명령은 보상 후

**두 레이블의 원천이 서로 다른 시점의 값을 본다.**

| 레이블 | 원천 | 오프셋 |
|---|---|---|
| **관절-계획** (경우 B, 1차 학습) | 실행 궤적 `motion/trajectory` (R1) | **없다** — D13 이 "보간 전 · 중력 보상 전 경유점"으로 정했다 |
| **관절-명령** (경우 A, 비교 기준) | `/target_joint_cmds` | **있다** (펑션베이만) |

그래서 1차 학습은 영향이 없다 — **관절-계획에는 오프셋이 없고, 배치 경로에서 보상을 건다**(수집 설계 §0.4). 문제는 **관절-명령을 비교 기준으로 쓸 때**(E5)다.

### R8.4 ⚠️ 값어치를 다시 재야 한다

검토하다 드러난 것이다. **보상 전 명령은 새 채널 없이도 얻을 수 있다.**

스트리머가 명령을 만드는 식은 이렇다:

```
명령(t) = 선형보간(R1 경유점, t)  +  offset(q)        (= 보간값 − τ_g(q)/Kp)
          └──────── 이것이 "보상 전 명령" 이다 ────────┘
```

⚠️ **부호**: `offset = −deficit = −τ_g/Kp` 이고, `ready` 자세의 joint4 에서 `deficit = −9.67 mrad` · `offset = +9.67 mrad` 다(2026-09-19 실측 계산). 즉 **보상은 joint4 지령을 9.67 mrad 올린다.** §8 의 검증 기준이 이 부호다.

**앞항은 R1 에서 그대로 나온다.** R1 이 보상 전 경유점을 싣고(D13), `_build_samples` 가 **선형 보간**이고(⚠️ **`publish_rate` 가 주어질 때만이다** — 없으면 경유점을 그대로 쓴다. 펑션베이 프로파일은 `arm_command.publish_rate: 50.0` 이라 성립한다), `/target_joint_cmds` 가 각 명령을 기록한다. 그러므로 **R1 을 보간하면 보상 전 명령을 얻을 수 있다.**

⚠️ **다만 "기록된 stamp 에서" 보간하면 정확하지 않다.** `target_joint_cmds_publisher` 는 `header.stamp` 를 **수신 시각**으로 채우므로(DDS 전달 지연이 들어간다, 수집 설계 §8.1) 스트리머가 발행한 격자 시각과 다르다. 어긋나는 양은 `지연 × 관절 속도` 이고 **재 본 적이 없다** — 지연이 1 ms 수준이면 1 mrad 아래로 오프셋(~10 mrad)의 일부겠지만, 추정이다.

**정확히 하려면 명목 격자에서 복원한다.** R1 의 `header.stamp` 가 t₀ 이고 `publish_rate` 를 알므로 **`t₀ + k·dt` 에서 보간하고 기록된 명령과는 순번 k 로 짝짓는다** — 그러면 지연이 끼지 않는다. 스트리밍이 잘렸으면 R2 의 `truncated_at` 이 k 의 상한을 준다.

**그리고 이것이 더 큰 사실을 드러낸다.**

> **펑션베이 JGPC 에서는 관절-명령과 관절-계획이 사실상 같은 신호다.** 명령이 계획의 선형 보간이기 때문이다 — 그 사이에 자기 판단을 하는 컨트롤러가 없다.

E5(관절-명령 비교 기준)를 둔 까닭은 *"계획이 가리킨 것"* 과 *"컨트롤러가 실제로 내보낸 것"* 의 차이를 보려는 것인데, **JGPC 에는 그 차이를 만드는 주체가 없다.** 보상 오프셋을 걷어내면 남는 차이는 보간 방식(선형 대 3차 Hermite)과 격자 위상뿐이다.

**의미 있는 A·B 비교는 isaac 이다** — 거기서는 JTC 가 궤적을 받아 **자기 스플라인으로 100 Hz** 보간하므로 계획과 명령이 실제로 갈린다. 그리고 **isaac 에는 오프셋이 없다.**

그러니 R8 이 여는 것은 *"펑션베이에서도 A·B 를 비교한다"* 인데, **그 비교의 값어치 자체가 작다.**

### R8.5 선택지

| | 방법 | 평가 |
|---|---|---|
| **(a)** | **보상 전 명령을 별도 토픽으로 발행**한다 — 스트리머가 `_apply_gravity` 앞의 값을 함께 낸다 | 사실을 그대로 남긴다. 스트리머 몇 줄 + 녹화 목록 + 적재 |
| **(b)** | **적재에서 역보상**한다 — `cmd = q − τ_g(q)/Kp` 를 고정점 반복으로 푼다 | **적재에 벤더 URDF·`Kp`·`scale` 을 들여야 한다.** 녹화 당시의 값을 알아야 하는데 그것을 남기는 것이 R3/I2 다 — 의존이 거꾸로다 |
| **(c)** | **R1 에서 복원**한다 (§4) — 기록된 stamp 에서 경유점을 선형 보간 | **추가 녹화가 없다.** 다만 export 가 스트리머의 보간 방식을 **흉내 내야** 하므로, 스트리머가 바뀌면 조용히 어긋난다 |
| **(d)** | **벤더가 A-1 을 반영**하면 보상 자체가 사라진다 | 우리 손에 없다. 반영되면 `functionbay.yaml` 의 블록을 지워 끄고 이 문서는 무효가 된다 |

### R8.6 권고

**지금은 만들지 않는다. 대신 [E7](저장_형식.md) 의 Q13′ 를 먼저 한다.**

근거는 셋이다.

1. **위험한 절반은 Q13′ 가 막는다.** §1 의 문제 중 **1·2(백엔드 혼합 · 이중 보상)가 위험한 쪽**인데, 그것을 막는 데 필요한 것은 보상 전 명령이 아니라 **"이 데이터셋에 오프셋이 들어 있는가"를 metadata 가 말하는 것**이다. `ExportSpec` 에 `gravity_offset_included` 를 두는 일이고 **R8 보다 싸다.**

⚠️ **Q13′ 도 공짜는 아니다** — 필드를 넣는 것은 쉽지만 **값을 아는 것**이 걸린다. 유도의 재료인 `backend` 가 `sessions.metadata` 에서 오는데 **R4 미구현이라 지금은 항상 `None`** 이다(E7 §6.3). 그래서 R4 가 오기 전에는 **export CLI 로 명시해 넘겨야 한다.** 그래도 R8 보다 싸다.
2. **남는 절반의 값어치가 작다** (§4) — 펑션베이에서 A·B 비교가 거의 같은 신호를 견주는 일이 된다. 의미 있는 비교는 isaac 이고 거기엔 오프셋이 없다.
3. **1차 학습을 막지 않는다** — 관절-계획에는 오프셋이 없다(§3).

**만들게 된다면 (a) 다.** (b) 는 적재에 기구학 모델을 들이면서 결국 **재구성**일 뿐이고, (c) 는 추가 비용이 없지만 **export 가 스트리머 구현에 묶인다** — 녹화는 사실을 남기고 export 는 그것을 읽는다는 구분이 흐려진다.

**언제 다시 볼 것인가**

| 계기 | 판단 |
|---|---|
| **스트리머의 보간이 바뀔 때** (평활 추가 등) | **필요해진다** — (c) 는 export 가 스트리머 구현을 흉내 내는 것이라 그때 조용히 어긋난다. 녹화로 사실을 남기는 쪽이 답이 된다 |
| 복원 오차가 문제가 될 때 (§4) | 명목 격자 복원으로도 안 되면 — 예컨대 발행이 격자에서 벗어난 것이 확인되면 — (a) 로 간다 |
| 벤더가 A-1 을 반영 | **불필요해진다** — 보상을 끄면 오프셋이 사라진다 |
| isaac 만으로 A·B 비교를 마칠 때 | 그대로 둔다 |

⚠️ **펑션베이 teleop 은 계기가 아니다.** 한때 "teleop 은 R1 이 없어 복원이 안 되니 R8 이 필수"로 적었는데 **틀렸다** — teleop 명령은 servo → `servo_command_bridge` → `/input/panda_joint` 로 가고 **그 경로에는 보상이 없다**(보상기를 만지는 곳은 `gravity.py` · `move_group_factory` · `move_group_jgpc_client` · `trajectory_streamer` 넷뿐이다). 걷어낼 오프셋이 애초에 없다. **대신 다른 문제가 생긴다 — §9 의 마지막 항목이다.**

### R8.7 만든다면 — 채널 정의

**새 메시지 타입을 만들지 않는다.** `/target_joint_cmds` 와 **같은 `sensor_msgs/JointState`** 를 다른 토픽으로 낸다.

| | |
|---|---|
| 토픽 | `target_joint_cmds_raw` (상대 이름 — 규약은 [topic_naming_contract.md](../topic_naming_contract.md)) |
| 타입 | `sensor_msgs/JointState` |
| stamp | 스트리머의 발행 시각(`now()`). ⚠️ **보상 후 명령과 같은 값이 되지 않는다** — 그쪽은 `target_joint_cmds_publisher` 가 **수신 시각으로 재stamp** 하기 때문이다(§4) |
| 발행 지점 | `TrajectoryStreamer._build_command` 의 `_apply_gravity` **직전** |
| 적재 | **테이블을 만들지 않는다** — `joint_states` 에 `topic_id` 로 구분해 들어간다. 지금 `/joint_states` 와 `/target_joint_cmds` 가 같은 테이블을 쓰는 것과 같다 |

**이 설계가 싼 이유가 여기 있다** — 메시지 타입도 writer 도 테이블도 새로 만들지 않는다. 늘어나는 것은 **토픽 하나와 녹화 목록 한 줄**이다.

**짝짓기는 시각 일치가 아니라 순번으로 한다.** 두 메시지의 stamp 가 DDS 지연만큼 다르므로(위) export 가 시각으로 맞추면 어긋난다. 두 길이 있다 — ① 스트리머가 명령마다 **같은 순번을 두 메시지에 싣는다**(메시지 타입을 안 바꾸려면 별도 채널이 필요하므로 실질적으로 ②), ② export 가 **최근접 stamp** 로 맞춘다. **§4 의 명목 격자 복원이 되면 이 문제 자체가 사라진다** — 그쪽이 더 싼 이유이기도 하다.

⚠️ **이름은 정해진 것이 아니다.** `target_joint_cmds_raw` 는 제안이며, `motion/` 묶음에 넣지 않은 것은 그 묶음이 **연산마다 한 건**인 이벤트 채널이고 이쪽은 50 Hz 스트림이라서다(§10 의 Q2).

### R8.8 검증

| 확인할 것 | 합격 기준 |
|---|---|
| **두 채널의 차이가 `offset(q)` 와 같다** | `보상후 − 보상전` 을 `GravityCompensator.offset(q)` 와 대조한다. `ready` 에서 joint4 = **+9.67 mrad** (2026-09-19 실측 계산). ⚠️ **부호를 확인하고 적었다** — `deficit`(실제−지령)이 **−9.67**, `offset`(지령에 더할 값)이 **+9.67** 이다. 둘을 바꿔 적으면 **뒤집힌 구현이 합격한다** |
| stamp 가 짝을 이룬다 | 같은 명령점의 두 메시지가 **같은 `header.stamp`** 를 갖는다 |
| **R1 복원과 일치한다** (§4 의 (c)) | **명목 격자**(`t₀ + k/publish_rate`)에서 R1 을 선형 보간한 값이 k 번째 보상 전 명령과 같다. **다르면 스트리머 보간 가정이 틀린 것이다.** 기록된 stamp 로 하면 DDS 지연만큼 어긋나므로 그쪽으로 재지 않는다 |
| mock · isaac 에는 안 나온다 | 보상기가 `None` 인 백엔드에서는 이 토픽이 발행되지 않는다(또는 보상 후와 동일하다) |
| 적재 | `joint_states` 에 `topic_id` 로 구분돼 들어간다. 새 테이블이 생기지 않는다 |

### R8.9 주의

- ⚠️ **부호를 뒤집으면 오차가 두 배가 되고 증상은 "켰더니 더 나빠졌다" 뿐이다.** 실제로 그랬고, **구현과 시험을 같은 추론으로 써서 단위 시험이 못 잡았다.** 그래서 `gravity.py` 가 `deficit`(처짐)과 `offset`(= −deficit)을 나눠 두었다 — 실측 대조는 `deficit` 이 맡는다.
- ⚠️ **보상 전 명령은 "시뮬레이터에 보낸 값"이 아니다.** 실제로 나간 것은 보상 후다. 이 채널은 **레이블용 기록**이지 재현용 명령이 아니다.
- ⚠️ **`scale` 이 1.0 이 아니면 복원도 역보상도 그 값을 알아야 한다.** 지금은 프로파일에 없어 1.0 이지만, 넣게 되면 **에피소드 metadata 에 남겨야 한다**(R4).
- **벤더가 A-1 을 반영하면 `functionbay.yaml` 의 블록을 지운다** — 안 지우면 이중 보정이다. 그 시점에 이 채널도 의미가 없어진다.
- ⚠️ **펑션베이 teleop 은 보상 없이 움직인다 (2026-09-19 확인).** servo → `servo_command_bridge` → `/input/panda_joint` 경로에 보상이 없어 **팔이 처진 채로 조작되고 조작자가 눈으로 보정한다.** 그 데이터는 명령에 오프셋이 없는 대신 **관측이 처짐을 담는다**(명령 − 관측 = `deficit(q)`, 자세마다 다르다). **MoveIt 경로(보상됨)와 teleop 경로(보상 안 됨)를 같은 백엔드에서 섞으면 명령과 관측의 관계가 출처마다 달라진다.** 지금은 teleop 이 범위 밖이라(수집 설계 D1) 문제가 아니지만, 넣게 되면 **R8 이 아니라 "servo 경로에도 보상을 건다"가 먼저다.**

| # | 질문 | 정하는 방법 |
|---|---|---|
