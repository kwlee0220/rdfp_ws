## 0. 요약

**가장 중요한 것은 A-1 중력 보상 하나다.** 나머지는 없어도 데이터 수집을 시작할 수
있지만, A-1 이 없으면 **명령(action)과 실제(observation)가 자세에 따라 계통적으로
어긋난 채로** 데이터가 쌓인다 (open_work §3.5).

## A. 필수 요청

### A-1. 중력 보상 (피드포워드)

**무엇을** — 관절 명령 토크에 현재 자세의 중력 토크를 더해 달라.

```
토크 = K_p·(목표 − 실제) + K_d·(−속도) + τ_g(q)      ← τ_g 항 추가
```

**현재 증상** — 시뮬레이터는 중력 보상이 없는 유한 강성 위치 제어로 동작한다.
중력이 끌어내리는 힘과 제어기가 밀어 올리는 힘이 같아지는 지점에서 멈추므로
**정상상태 오차가 원리적으로 0 이 될 수 없다.**

```
K_p × 오차 = 중력 토크        →        오차 = 중력 토크 / K_p
```

발산이 아니라 정착이다 — 고정 목표를 15 초간 명령하면 **1.5 초 안에 수렴한 뒤
소수점 4 자리까지 미동도 없다** (open_work §3.2).

**이것이 버그가 아니라 중력 때문임을 보이는 실측 두 개** (open_work §3.3):

| 자세 | joint2 오차 | joint4 오차 | **joint1** | **joint7** |
|---|---|---|---|---|
| `ready` (접힘) | +0.0122 | **-0.0983** | **+0.0000** | **-0.0000** |
| 중간 | +0.0809 | -0.0968 | **-0.0000** | **-0.0000** |
| 펴짐 (수평쪽) | **+0.1428** | -0.0840 | **-0.0000** | **+0.0001** |

1. **joint2 오차가 팔을 펼수록 12 배로 커진다** (0.0122 → 0.1428). 모멘트 암이
   길어져 중력 토크가 커진 것이다 — `K_p` 는 그대로이고 분자만 커졌다.
2. **회전축이 수직이라 중력 토크가 0 인 joint1 · joint7 은 세 자세 모두 정확히
   0.0000 이다.** 분자가 0 이면 오차도 0 이다.

즉 **남은 오차는 전부 중력에서 온다.** `ready` 자세 최악은 joint4 의
**-0.0983 rad ≈ 5.6°** 다.

**왜 우리가 못 고치나** — 우리는 위치 명령만 보낼 수 있다. 오차가 `τ_g(q)/K_p` 이므로
명령 쪽에서 없애려면 예상 처짐을 미리 더해 보내야 하는데, 그러려면 `K_p` 값과
시뮬레이터의 질량 모델이 필요하다 (→ **A-2**). 시뮬레이터 안에서 하면 한 단계다.

**구현 힌트** (참고용, 판단은 벤더 몫)

| 방법 | 처짐 | 부작용 |
|---|---|---|
| **중력 토크 피드포워드** (권장) | **원리적으로 제거** | 없음 — 질량 모델만 있으면 된다 |
| 로봇 링크만 `useGravity = false` | 제거 | 접촉·파지 힘의 사실성 상실. **임시방편** |
| `K_p` 상향 | 감소할 뿐 0 은 안 된다 | 진동·발산 위험 (→ B-1 로 분리) |

- Unity `ArticulationBody` 기반이라면 `GetJointGravityForces()` 로 중력 토크를 받아
  매 `FixedUpdate` 에 `AddJointForce()` 로 상쇄하는 것이 정석이다. 중력은 scene 에 남고
  로봇만 보상된다.
- RecurDyn 계열 솔버라면 역동역학의 중력항을 그대로 쓰면 된다.

**수용 기준** — 우리가 `fb_hold.py 15` 로 검증한다 (§C).

| 항목 | 현재 | 요청 후 |
|---|---|---|
| joint4 정착 오차 (`ready`) | **-0.0983 rad (5.6°)** | **절대값 ≤ 0.005 rad** |
| joint2 오차의 자세 의존성 | 0.0122 → 0.1428 (**12 배**) | 자세 무관, 모두 ≤ 0.005 |
| joint1 · joint7 | 0.0000 (이미 정상) | 유지 |
| 수렴 시간 | 1.5 초 | 악화 없을 것 |

`0.005 rad ≈ 0.29°` 는 현재 joint1 · joint7 의 변동폭(0.0001 수준)에 비해 충분히
여유 있는 값이라, 모델 오차가 남아도 통과할 수 있는 선으로 잡았다.

### A-2. 제어기 사양 공개

**A-1 이 거절되더라도 이것만은 받아야 한다.** 알면 우리 쪽에서 명령을 보정할 수 있다.

- 제어 방식 — **PD 인가 PID 인가.** 특히 **적분항이 있는가** (있는데도 정상상태
  오차가 남는다면 원인이 중력이 아니라 다른 데 있다는 뜻이다)
- `K_p` / `K_d` 의 실제 값과 단위
- 물리 스텝 주기 · 명령 수신 주기 · **내부 보간 유무**
  (현재는 보간이 없다고 보고 우리가 50 Hz 로 선형 보간해 밀어 넣는다)
- 중력 모델의 링크 질량 · 무게중심 — **URDF 와 같은 값인가**

`K_p` 와 질량 모델만 있으면 `τ_g(q)/K_p` 를 우리가 계산해 명령에 미리 얹는 우회가
가능하다. 정확도는 시뮬레이터 내부 보상보다 떨어지지만 5.6° 를 방치하는 것보다 낫다.

### A-3. 카메라 `header.stamp` — **시간 기준을 맞춰 달라** (요청 변경)

**부분 해결됐다.** 미설정(0)이던 스탬프가 채워지기 시작했다. 다만 **관절 토픽과
시간 기준이 다르다.**

```
/camera_image        stamp: sec=63          ← 시뮬레이터 기동 후 경과 시간으로 보인다
/output/panda_joint  stamp: sec=1788146994  ← 벽시계 epoch
```

데이터셋은 에피소드 분할과 토픽 간 정렬을 전부 `header.stamp` 로 한다. **기준이
다르면 두 토픽을 짝지을 수 없어**, 스탬프가 채워졌어도 이미지를 시간축에 놓지
못하는 것은 그대로다.

**요청**: 카메라 스탬프를 `/output/panda_joint` 와 **같은 기준(벽시계 epoch)** 으로
발행해 달라. 값은 프레임을 렌더링한 시각이면 된다.

**수용 기준**

| 항목 | 현재 | 목표 |
|---|---|---|
| 시간 기준 | 기동 후 경과 (`sec=63`) | **관절 토픽과 동일한 벽시계 epoch** |
| 관절 스탬프와의 차 | 비교 불가 | **1 프레임 주기 이내** |

`camera_info` 에 해당하는 토픽도 없다. 카메라 내부 파라미터를 쓰는 경로가 생기면
필요해지므로, 발행 계획이 있는지 함께 확인한다.

### A-4. "명령 무반응 고착" 문의 — 알려진 현상인가

**요청이 아니라 질문이다.** 상태 보고는 정상인데(49.9 Hz) **명령만 전혀 먹지 않는**
상태로 빠지는 것을 두 차례 관측했다 (open_work §2.2).

- 상태 보고는 계속 나온다 → **살아 있는지 여부로는 판정할 수 없다**
- 50 Hz 램프(`fb_recover.py`)로도 빠져나오지 못한다 → **Unity 재시작이 필요하다**
- 보고 주기 지터가 커진다 (정상 13~23 ms → 고착 시 8.8~32.8 ms)

우리 쪽에서 트리거를 좁히려 다음을 시험했으나 **다섯 조건 모두 재현에 실패**했다 —
100/200/500 Hz × 5 초, 500 Hz × 15 초 + 목표 12 회 전환, 관절 한계 초과 명령
(joint4 → -3.36). 즉 **발행률도 한계 초과 명령도 트리거가 아니다.**

**묻고 싶은 것**

1. 알려진 현상인가. 재현 조건이 있는가
2. 고착 여부를 밖에서 판정할 수 있는 신호(로그·토픽·상태 플래그)가 있는가
3. Unity 재시작 없이 복구하는 방법이 있는가

장시간 수집 중 발생하면 세션 전체를 버려야 하므로, 최소한 **2 번(판정 신호)만이라도**
있으면 운영이 가능해진다.

## B. 후속 요청

### B-1. `K_p` 적정 상향

**A-1 과 뿌리가 같지만 별개의 요청이다.** 강성은 정상상태 오차와 응답 속도 양쪽의
분모에 들어간다.

```
정상상태:  오차 = τ_g / K_p          ← A-1 이 분자를 없앤다
과도응답:  시정수 τ ≈ B / K_p        ← 분자가 없어져도 이건 그대로다
```

**중력 보상은 τ 를 줄여 주지 않는다.** 실측 τ 는 **132.6 ms** 이고, 이것이 §5 의
servo 발산과 §6 의 느린 응답의 주범이다 (open_work §6.1).

`K_d` 도 함께 올려 감쇠비를 유지해야 한다. 너무 올리면 진동하고 접촉이 딱딱해지므로
**"진동하지 않는 선까지"** 가 요청의 전부다.

**수용 기준** — joint7(중력 중립축이라 처짐이 섞이지 않는다)에 계단 ±0.04 rad 을
방향을 번갈아 8 회, 50 Hz 발행으로 측정한다.

| 항목 | 현재 | 목표 |
|---|---|---|
| 시정수 τ | **132.6 ms** (중앙 126.0 / 범위 120.5~147.8) | **≤ 50 ms** |
| 오버슈트 | — | ≤ 5% |
| 정착 후 진동 | 없음 | 없음 (유지) |
| dead time | 33.7 ms (바닥 ~25 ms) | 악화 없을 것 |

### B-2. 게인·보상 스위치를 밖으로 노출

`K_p` · `K_d` · 중력보상 on/off 를 설정 파일이나 ROS 파라미터로 빼 달라.
B-1 은 본질적으로 튜닝이라, 값을 바꿀 때마다 벤더 빌드를 기다리면 수렴하지 않는다.
노출만 되면 **"적정값 찾기"를 우리가 대신할 수 있다.**

### B-3. 관절 한계 클램프

시뮬레이터가 관절 한계를 강제하지 않는다 — joint4 에 URDF 한계(-3.1416)를 넘는
**-3.36 을 명령했더니 그대로 갔다** (open_work §2.2).

처짐과 무관해 보이지만 **같은 사고 경로의 끝**이다. 처진 값을 다시 명령하면 누적되고
(open_work §3.1), 그 끝이 MoveIt 으로 복구 불가능한 자기충돌 자세다 (open_work §4).

```
/check_state_validity → valid = False
  contacts:  panda_hand ↔ panda_link5 / panda_leftfinger ↔ panda_link5 / panda_link5 ↔ panda_link7
```

**최소한 관절 한계에서 클램프**해 주면 이 경로 하나가 막힌다. 자기충돌 검사까지는
요구하지 않는다 (우리 쪽 `/check_state_validity` 로 사전 필터가 가능하다).

### B-4. `/output/endeffector` 복구

1차 측정에서는 **전부 0.0 으로 고정 발행**되었고, 2차에서는 **토픽 자체가 사라졌다**
(open_work §2.2). 현재는 TF (`world → … → panda_hand`) 로 대체하고 있어 급하지는
않지만, 시뮬레이터가 계산한 EE 값과의 교차검증 수단이 없다.

의도적으로 제거한 것인지, 발행할 계획이 있는지 확인이 필요하다.

### ~~B-5. 카메라 `rgb8` 발행~~ — **해결됨 (2026-08-31)**

`rgba8` → **`bgr8`** 로 전환된 것을 확인했다. 요청할 것이 없다.

| | 이전 (`rgba8`) | **현재 (`bgr8`)** |
|---|---|---|
| 640×480 한 프레임 | 1,228,800 B | **921,600 B** (−25%) |
| `step` | 2560 | **1920** |

`bgr8` 은 `cv_bridge` · OpenCV 의 기본 형식이라 **변환 단계도 함께 사라졌다.**
원래 요청은 `rgb8` 이었으나 `bgr8` 이 오히려 낫다.

### B-6. 그리퍼 출력 사양

`/output` 계열 그리퍼 값의 **단위와 성분의 의미를 확정할 수 없다** (open_work §7 ④).
1차와 2차 사이에 값의 구조가 바뀌었다.

| | 값 |
|---|---|
| 1차 | `[0.000143, ~0, **-14.34**, -0.000140, ~0, **13.97**]` |
| 2차 | `[**0.7198**, ~0, -0.0037, **-0.7198**, ~0, 0.0031]` |

큰 성분이 index 2·5 에서 index 0·3 으로 옮겨갔다. 3 개씩 두 묶음(손가락 2 개 ×
3 성분)으로 보이지만 확신할 수 없다. **각 성분의 의미와 단위(rad / deg / m)를 알려 달라.**
그리퍼 모델이 Robotiq 2F-85 인지도 함께 확인한다.

### B-7. 시뮬레이터 머신 시계 동기

시뮬레이터가 찍는 스탬프가 호스트 시각보다 **일정하게 2.22 초 뒤처져 있다**
(open_work §6.4).

| 토픽 | 스탬프 − 수신시각 | 변동폭 |
|---|---|---|
| `/output/panda_joint` | **-2.2207 s** | 0.0171 s |

드리프트가 아니라 고정 오프셋이고 변동폭이 작으므로 **두 머신의 시계 차이**로 본다
(스탬핑 버그가 아니다). **시뮬레이터 머신에 NTP/chrony 를 걸어 주면 해결된다.**

우리 쪽 우회(`stamp_source:=now` 로 재스탬프, 오프셋 -0.0009 s)가 있지만, 그러면
스탬프의 의미가 "그 자세였던 시각"에서 "우리가 받은 시각"으로 바뀌어 dead time
(약 34 ms)이 흡수된다. **NTP 가 가능하면 그쪽이 낫다.**

## C. 우리가 어떻게 검증하는가

수정본을 받으면 아래를 그대로 돌려 수용 기준과 대조한다. 절차 전문은
[functionbay_open_work.md §9](functionbay_open_work.md) 에 있다.

```bash
# 0) 도메인·RMW 를 시뮬레이터와 맞춘다 (ROS_DOMAIN_ID=31 / rmw_fastrtps_cpp)
ros2_env humble
./scripts/functionbay/run_panda_functionbay.sh

# 1) 명령에 반응하는가 — 가장 먼저 (A-4 판정도 겸한다)
./scripts/functionbay/fb_raw.py named 0.30 4.0

# 2) A-1 검증 — 현재 자세를 그대로 명령해 정착 오차를 잰다
./scripts/functionbay/fb_hold.py 15
#    → 자세를 ready / 중간 / 펴짐 세 가지로 바꿔 가며 반복한다

# 3) B-1 검증 — joint7 계단 응답으로 dead time · τ 를 분해한다
./scripts/functionbay/fb_probe.py 30 /tmp/probe.json &
./scripts/functionbay/fb_move.py named extended 50.0 /tmp/start.json

# 4) 이상 자세 복구
./scripts/functionbay/fb_recover.py 5.0
```

> `fb_hold.py` 는 **현재 자세를 읽어 그대로 목표로 준다.** 처짐이 있는 상태에서
> 반복 호출하면 값이 누적되므로(open_work §10.2), 자세를 바꿀 때는 `fb_raw.py` 나
> `fb_recover.py` 로 절대 목표를 먼저 준다.

## D. 요청하지 않는 것 — 이미 정상인 항목

혼선을 막기 위해 **문제 없음이 실측으로 확인된 것**을 함께 적는다.

| 항목 | 실측 |
|---|---|
| 명령 경로 | `/input/panda_joint` **50.43 Hz** 도달, 명령대로 이동 (joint7 +0.30000 → +0.29999) |
| 상태 보고 | `/output/panda_joint` **50.24 Hz**, `/joint_states` 49.8 Hz |
| 관절 이름 | 시뮬레이터가 `name` 을 **채워서 보낸다** (`panda_joint1~7`) |
| QoS | 양쪽 RELIABLE / VOLATILE / KEEP_LAST — 호환 |
| 실시간 배속 | **0.99993** — 사실상 정확히 실시간. `/clock` 발행은 **필요 없다** |
| 네트워크 | 왕복 0.303 ms — 전체 응답(약 180 ms)의 0.2%. **머신 배치는 무관하다** |
| 카메라 렌더링 | 실시간 렌더링 확인 (약 9.6 Hz, 움직이는 동안 프레임 해시가 전부 다름) |
| 고율 발행 내성 | 500 Hz × 15 초를 견딘다 |

특히 **`/clock` 발행(sim time)은 요청 대상이 아니다** — 이미 1.0 배속이라 도입해도
servo 안정성이 나아지지 않는다 (open_work §6.3). sim time 이 의미를 갖는 것은
시뮬레이터가 **lockstep(스텝 후 대기)** 을 지원할 때뿐이므로, 그 얘기를 꺼낼 때는
"`/clock` 발행"과 "lockstep 지원"을 반드시 구분해서 말해야 한다.
