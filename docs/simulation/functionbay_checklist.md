> **용도** 시뮬레이터가 갱신되어 새로 제공될 때마다 **무엇이 바뀌었는지 빠짐없이 가려내기 위한 절차서**다.
> 근거 수치는 전부 [functionbay_open_work.md](functionbay_open_work.md) 와 [functionbay_vendor_requests.md](functionbay_vendor_requests.md) 에 있고, 여기서는 절 번호로 가리킨다.

> **호출** "체크리스트 확인해줘" 라고 하면 이 문서의 A 단계를 돌리고 결과를 표로 낸다. B·C 단계는 팔이 실제로 움직이므로 **따로 승인을 받고** 진행한다.

## 0. 판정 규칙 — 먼저 읽는다

**이 체크리스트의 목적은 합격/불합격이 아니라 "무엇이 달라졌는가"를 놓치지 않는 것이다.** 기준선과 다른 값이 나오면 세 가지 중 하나이며, 셋을 구분하지 않으면 오진한다.

| 판정 | 뜻 | 다음 행동 |
|---|---|---|
| **개선** | 벤더가 요청 항목을 반영했다 | 해당 벤더 요청(A-n/B-n)을 닫고 기준선을 갱신 |
| **회귀** | 전에 되던 것이 안 된다 | 벤더에 회귀 보고. 예: A-9 stamp 가 벽시계에서 경과시간으로 되돌아가는 것 |
| **변경** | 의도적 사양 변경인데 통보가 없었다 | **가장 위험하다.** 우리 코드의 전제가 조용히 깨진다 |

### 측정 전 반드시 확인할 함정 아홉 가지

1. **토픽이 목록에 있는 것과 발행되는 것은 다르다.** `ros_tcp_endpoint` 는 Unity 가 끊겨도 등록된 퍼블리셔를 유지한다. `ros2 topic list` 에 보여도 한 건도 안 올 수 있다 — **반드시 실제 수신 건수로 판정한다.** (§7 ④-2 의 B-4 회귀가 정확히 이 모습이었다)
2. **`ros2` CLI 데몬이 눈이 멀 수 있다.** 데몬이 `ros_tcp_endpoint` 보다 늦게 뜨면 그래프를 하나도 못 보고, `ros2 topic list` 가 `/rosout` 만 낸다. 아무것도 안 보이면 **먼저 `ros2 topic list --no-daemon` 으로 대조**한다 (2026-09-03 실제 발생). **`ros2 daemon stop && start` 로도 안 낫는다** — 같은 날 재시작 후에도 계속 멀어 있었고 `--no-daemon` 만 통했다. "노드가 하나도 안 떠 있다"고 판정하기 전에 반드시 거친다. `rclpy` 로 직접 구독하는 스크립트(`fb_checkup`·`fb_stamp`)는 데몬을 안 타므로 무관하다.
3. **`ros2 topic hz` 는 창이 찰 때까지 기다려 읽는다.** 첫 줄을 읽으면 틀린다 — 한때 카메라를 4.4 Hz 로 오독했다 (§7 ⑤).
4. **관절 하나·방향 하나로 "무반응"을 판정하지 않는다.** joint7 실효 상한이 1.6387 rad 라 거기 걸린 것을 전체 고착으로 오진한 적이 있다 (§10.4).
5. **접촉을 고착이나 중력 처짐으로 읽지 않는다 — 단 `effort` 는 접촉력이 아니다.**
   그리퍼 `effort` 는 **`200 × 잔차`**(모델의 `Kp`)이므로 **정지 상태에서만** 접촉 판정에 쓸 수 있다.
   `> 1 N·m` = `잔차 > 0.005 rad` 이고, **이동 중에는 접촉이 없어도 잔차가 크다** — 램프 중에 이 조건을
   걸면 오검출한다. 실제 판정은 **어느 축에 잔차가 남는지**로 한다: 물체에 막히면 **구동축(1·4)은
   지령에 정확히 도달**하고 **접촉축(2·3·5·6)에만** 잔차가 남는다(실측: 구동축 0.00000 / 접촉축
   0.026~0.079 rad). 여섯 축이 함께 못 가면 그것은 구동 문제다 (§B-12 ① · §B-14 ②).
   무반응처럼 보이면 **중력 토크가 없는 `joint1`/`joint7` 단독 명령**으로 명령 경로부터 가른다 (§10.2b).
6. **`stamp` 오프셋의 산포를 '지터'로 읽지 않는다.** 시뮬레이터가 **34초마다 2초 멈추고 그 사이 6~7% 과속**해서, 오프셋은 진폭 약 2 s 의 **톱니**를 그린다 (A-17). 30초 창을 어디에 걸치느냐에 따라 평균이 −0.06 s 도 −0.65 s 도 나오는데 둘 다 같은 상태다. **창 하나로 오프셋을 비교하면 안 된다** — 180초 이상 관측해 톱니를 5회 이상 담는다.
7. **진행률(`stamp_rate`)을 끝점 두 샘플로 재지 않는다.** 톱니 진폭이 2 s 인데 30초 창의 끝점 추정은 오차가 ±2% 라 잡음이 재려는 값보다 크다. 같은 데이터가 끝점 기준 0.973× · 0.994× 를 냈지만 회귀로는 **1.00029 ± 0.00015** 였다. `fb_stamp.py` 를 쓴다.
8. **정지 중에는 우리 Python 프로세스도 멈춘다 — 정지를 실시간으로 감지할 수 없다.**
   실측 (2026-09-04): `rclpy.spin_once(timeout_sec=0.004)` 가 120초 중 3회
   **915·922·945 ms** 블록된다 — 정지 주기·길이와 일치한다. `timeout_sec` 을 지키지 않는다.
   **스핀을 별도 스레드로 분리해도 같다** — DDS 대기가 GIL 을 잡은 채 블록되어 메인 스레드의
   `time.sleep(0.002)` 판정 루프까지 굶는다(감지 지연이 스레드 유무와 무관하게 0.9~0.99 s,
   즉 침묵 길이와 같다). 결과적으로 **정지가 끝난 뒤에야 정지를 알게 된다.**

   두 가지 귀결이 있다. ① 정지 구간에 무언가를 **주입하는** 시험은 구독을 가진 Python
   프로세스로는 할 수 없다 — 발행 전용 프로세스(구독 0개)나 C++ 노드가 필요하다.
   ② `spin_once` 체류시간으로 정지를 재는 것은 **유효하다** (수신 공백과 같은 값을 준다).

   해제 직후에는 **캐치업 발행**이 보인다 — 침묵 0.97 s 뒤 0.36 s 동안 14~15건(≈40 Hz)이
   들어오고, 전체 1.43 s 에 걸쳐 `stamp` 는 +0.47 s 만 진행한다. 침묵 중 sim 시각은 0 이다.

9. **발행 주기는 시뮬레이터 XML 로 정하는 설정값이다** — 고정 상수가 아니다. `VariableModel/t1__panda_robotiq_ref_1_vm.xml` 의 `Hz`, `t1__RGBCamera_1_vm.xml` 의 `Publish_Frequency`·`Frequency`. 관측이 낮게 나왔다고 기준선을 고치지 말고 **설정을 먼저 확인**한다. `fb_checkup.py --joint-hz N --cam-hz N` 으로 알려준다.
   **XML 은 프로세스 기동이 아니라 시뮬레이션(Play) 시작 시점에 다시 읽힌다** — 실측(2026-09-08): 프로세스 기동 13:38:56 · XML 저장 13:48:22 인데 새 값이 적용됐다. 즉 **앱 내 재시작으로 충분하고 프로세스를 죽일 필요가 없다.** 파일은 **BOM + CRLF** 이므로 편집 시 보존한다.

## A. 수동 관측 — 팔을 움직이지 않는다 (자동 실행 가능)

**한 번에 확인:**

```bash
./scripts/functionbay/fb_checkup.py 180                      # 설정이 30 Hz / 10 Hz 일 때
./scripts/functionbay/fb_checkup.py 180 --joint-hz 15 --cam-hz 5   # 설정을 바꿨으면
```

**180초를 권한다.** 정지가 34초 주기라 그보다 짧으면 톱니가 창 안에서 상쇄되지 않아
진행률이 편향된다 (스크립트가 `창부족` 으로 판정을 보류한다).

**제어 게인과 중력 보상 설정도 함께 확인한다** (팔을 안 움직인다):

```bash
./scripts/functionbay/fb_gains.py            # 시뮬레이터 XML ↔ 우리 설정 대조 (A-19)
./scripts/functionbay/fb_gains.py /mnt/d/MMR-Build_260910/MMR_Database   # 새 빌드
```

활성 씬을 `SolverConfig.json` 에서 자동 판별해 그 씬의 `Kp` 를 우리 프로파일과 맞춰
본다. **불일치면 종료 코드 1** 이다. 우리 쪽 설정만 보려면:

```bash
python3 -c "from robot_control.gravity import describe; print(describe('functionbay'))"
```

실제 거동 확인은 B-17 이 한다.

`stamp` 를 더 봐야 하면 **`fb_stamp.py`** 를 쓴다 — 오프셋을 일정 지연 · 진행률 · 잔차로
분해하고, 잔차가 백색잡음인지 톱니인지 가르며, 토픽 간 정합을 낸다.

```bash
./scripts/functionbay/fb_stamp.py 180 misc/fb_stamp/<라벨>.json
```

### A-20 상세 — **접촉 정의가 그 씬으로 할 수 있는 일을 정한다** (2026-09-11 신규)

물리 접촉은 **명시적으로 선언된 쌍에서만** 일어난다. 선언되지 않은 조합은 서로를 통과한다
— 화면에는 보이는데 물리적으로는 없는 것이다.

```bash
ls "$DB/Database/VariableModel" | grep -i "<씬>__.*[Cc]ontact"
grep -o 'IGEOSURFNAME="[^"]*"\|JGEOSURFNAME="[^"]*"' "$DB/Database/VariableModel/<씬>__GGeomContact_*_vm.xml"
```

`RecurDyn-260907` 의 `r2`:

```
GGeomContact_1   peg_round_16_surf ↔ left_inner_finger_surf
GGeomContact_2   peg_round_16_surf ↔ right_inner_finger_surf
GGeomContact_3   peg_round_16_surf ↔ peg_hole_round_16_surf
GGeomContact_4   peg_round_16_surf ↔ peg_tray_round_16_surf
```

**`peg ↔ 탁자` 가 없다.** 그래서 **고정물 밖에 물체를 내려놓을 수 없다** — 손가락도
구멍도 트레이도 잡아 주지 않는 순간 peg 이 탁자를 통과해 무한히 떨어진다. 3회 재현했고
`/scene/reset` 이 없어 **복구가 시뮬레이터 재시작뿐**이다.

⚠️ **"튕겨 나간다"로 읽으면 원인을 못 찾는다.** 낙하 가속도를 재면 **−11.25 m/s²** 로
중력과 같다 — **자유낙하**다. 2026-09-11 에 이것을 이탈로 오해해 기울기 → 압축 → 개방
속도를 차례로 의심했고 **셋 다 아니었다**. 세 관측의 공통점은 *고정물 밖에서 놓았다*
하나였다. 물체가 사라지면 **먼저 낙하 가속도를 잰다.**

**표면 정의는 이미 있다** — `ConstantModel/geosurfs/ground_table_surf.xml`
(`PART="ground"`, 평면 `z=+720.2 mm`, `x [387, 1187]` · `y [-1353.5, 446.5]` mm).
접촉 쌍으로 **연결만 안 돼 있다.**

**씬마다 다르다** — `t1` 은 반대로 **손끝 접촉이 없어** 들면 미끄러진다(§B-16, 벤더 B-11).
그래서 **새 빌드·새 씬에서는 이 목록을 먼저 뽑아 본다**: 잡을 수 있는가(손끝), 꽂을 수
있는가(고정물), **내려놓을 수 있는가(탁자)**.

| 필요한 일 | 있어야 하는 접촉 | `r2` | `t1` |
|---|---|:-:|:-:|
| 물체를 쥐고 든다 | peg ↔ 좌·우 손끝 | ✅ | ❌ (B-11) |
| 구멍·트레이에 꽂는다 | peg ↔ 고정물 | ✅ | ✅ |
| **탁자에 내려놓는다** | peg ↔ `ground_table_surf` | ❌ (B-14) | ❌ |

### A-19 상세 — 제어 게인은 **우리 중력 보상의 입력**이다 (2026-09-11 신규)

우리는 처짐을 `Δq = −τ_g(q)/Kp` 로 상쇄하는데, 그 `Kp` 는 **시뮬레이터 씬 XML 에서 옮겨
적은 값**이다 (`<씬>__Manipulator_1_vm.xml` 의 `<Gain Kp=...>`). 새 빌드가 그 값을 바꾸면
**보상량이 그만큼 틀어지고 에러는 안 난다** — 증상은 "팔이 몇 mm 어긋난 곳에 선다" 뿐이다.

```bash
./scripts/functionbay/fb_gains.py [MMR_Database 경로]
```

**기록값 (`MMR-Build_260907`, 2026-09-11)**

| 씬 | 팔 Kp / Kd | 그리퍼 축 · Kp / Kd | |
|---|---|---|---|
| `t1` | 2000 / 200 | 6축 · 200 / 20 | Crisp |
| **`r2`** | **2000 / 200** | **1축\* · 200 / 20** | RecurDyn — **우리가 쓰는 씬** |
| `r1` | **200 / 20** | 6축 · 200 / 20 | ⚠ **팔이 1/10** |
| `indy7_01` | 20000 / 200 | 1축 · 10000 / 100 | 다른 로봇 |

\* `r2__Gripper_1` 의 `<Gain Kp="200" Kd="20">` 은 스칼라 하나이고 두 관절에 같이 걸린다.

> **같은 빌드 안에서도 씬마다 다르다.** `r1` 을 띄우면 실제 `Kp` 가 200 인데 우리 설정은
> 2000 이라 **보상이 1/10 만 걸린다.** 씬을 바꿀 때도 이 확인이 필요하다.

**활성 씬은 자동으로 판별된다** — `Database/SolverConfig/SolverConfig.json` 의 `MsFile`
(`r2_ms.xml` → `r2`). 이것으로 "어느 씬이 떠 있는지 우리 쪽에서 알 방법이 없다"는 제약이
풀렸다. 그리퍼 규약 판별(보고 축 수)과 함께 쓰면 확실하다.

**불일치일 때** — `config/backends/functionbay.yaml` 의
`motion.gravity_compensation.kp` 를 실제 값으로 고치고 재빌드한다. 스크립트가 그 문장과
비율(실제/설정)을 함께 낸다.

### A-9 상세 — stamp 시간 기준

판정은 세 가지다.

| 분류 | 조건 | 뜻 |
|---|---|---|
| `wall-clock` | \|stamp − 수신시각\| < 5 s | **정상. 2026-09-03 재측정에서 여기로 복귀했다** |
| `elapsed-since-start` | stamp − 수신시각 ≈ −(현재 epoch) | Unity 재시작마다 0 부터 다시 시작한다 |
| `skewed` | 그 사이 | 두 머신 시계 차이 (구 B-7 의 2.22 s) |

**2026-09-03 오전 관측에서 `elapsed-since-start` 였다가 같은 날 오후 `wall-clock` 으로
돌아왔다.** 아래는 `elapsed-since-start` 로 다시 떨어졌을 때 깨지는 것들이라, 회귀
감시 목적으로 남긴다.

- **TF·MoveIt** — 스탬프가 약 56.7년 과거라 `stamp_source=auto`(launch 기본값) 로는 TF 시각이 성립하지 않는다.
- **데이터셋** — [schema.sql:8-32](../../src/rdfp/rdfp/dataset/sql/schema.sql#L8-L32) 의
  `sessions.start_ts` 가 `to_timestamp(start_sec…)` STORED generated column 이라 1970년이 된다.
  더 나쁜 것은 `UNIQUE (start_sec, start_nanosec)` — 재시작마다 0 부터라 **에피소드 키가 세션 간에 충돌**하고,
  기본 정책 `on_existing_episode: skip` 이 **에러 없이 조용히 건너뛴다.**
- **우회는 반쪽짜리다** — `stamp_source:=now` 는 `/joint_states` 만 되돌리므로(실측 −0.0074 s)
  카메라와 다시 어긋난다. 근본 해결은 벤더가 `/output/*` 와 `/camera_image` 를 **모두 벽시계 epoch** 으로 찍는 것이다.

**주의: 오프셋 평균만으로 판정하지 않는다.** A-17 톱니 때문에 30초 창의 평균은
−0.06 s 도 −0.65 s 도 나온다. 분류(`wall-clock` / `elapsed`)는 5 s 허용오차라
톱니에 흔들리지 않지만, **오프셋 값 자체를 세션 간에 비교하려면 180초 이상 관측**해야 한다.

### A-16 상세 — Unity 가 물체 TF 를 발행한다 (벤더 B-12 반영, 2026-09-08)

A-16 의 기준선은 **`/tf` 발행자 0** 이고 "Unity 가 TF 를 쏘기 시작하면 우리
`robot_state_publisher` 와 충돌한다"는 경고였다. **발행자가 1 로 늘었지만 충돌하지 않는다** —
요청대로 **조작 대상 body 하나만** 내보내고 로봇 링크는 건드리지 않았다.

| 항목 | 실측 (60초) |
|---|---|
| 프레임쌍 | **`world → peg_round_16` 단 하나** |
| 발행률 | **28.75 Hz** (1725건) |
| `header.stamp` | **벽시계 epoch**. 역행 0회 · 중복 0건 · 진행률 0.99773× |
| 정지 동조 | A-17 에 함께 멈춘다 (최대 공백 1105 ms, 0.3 s 초과 2회) |
| 로봇 링크 | **발행하지 않는다** (`panda_link*` 없음) |
| 고정 물체 | `peg_hole_round_16` · `peg_tray_round_16` 는 `static="true"` → **제외됨** |

**단위·좌표계·회전 규약을 알려진 자세로 확정했다.** 재시작 직후 peg 가 XML 초기 자세로
돌아온 순간(`t1__floating_2_vm.xml`: `origin xyz="0.5 -0.1 0.028001" rpy="0 0 0"`)에 잡은 값:

```
위치  (+0.500000, -0.100000, +0.028001)   ← XML 과 소수 6자리 일치 (미터 · world 기준)
회전  (-0.000000, +0.000000, -0.000000, -1.000000)
      → xyzw 로 읽으면   0.000° (항등)  ✅
      → wxyz 로 읽으면 180.000°
```

**ROS 규약 `xyzw` 이므로 발행 노드에 변환 코드를 두지 않는다** — `SceneObject.msg` 가
경고하는 wxyz 함정에 걸리지 않는다.

> ⚠️ **`w` 가 음수로 온다** (`(0,0,0,-1)`). `q` 와 `−q` 는 같은 회전이라 tf2 는 정상
> 처리하지만, **`w ≥ 0` 을 가정하거나 성분을 그대로 비교해 항등을 판정하는 코드는 오판한다.**
> `lookup_transform` 결과를 그대로 싣는 한 안전하다.

> ⚠️ **XML 에 TF 설정 요소가 없다 — 벤더가 코드로 구현했다.** **우리가 대상 body 를 고를 수
> 없으므로**, 조작 대상이 여러 개가 되면 다시 문의해야 한다.

**우리 쪽 구현도 끝났다 (2026-09-08).** `config/functionbay_scene.json` +
`functionbay_scene_state_node` 를 붙이고 `panda_functionbay.launch.py` 에 배선했다
(`enable_scene` 로 끈다). 실측 확인:

```
/scene/objects  frame_id=panda_link0  stamp=1788845500.979 (벽시계)
  name='peg' type='cylinder' dims=[0.05, 0.008]
  pos =(+0.501799, -0.001168, +0.025658)
  quat=(-0.023821, +0.048293, +0.031183, +0.998062)
```

**`/scene/reset` 은 제공하지 않는다** — 런타임 배치 변경 수단이 없어 트윈의
`reset_scene` 이 서버 없음으로 실패한다. 매 에피소드 같은 배치로 수집하는 것이
전제다. 설계는 [scene_objects_guide.md §6.4](../scene/scene_objects_guide.md).

### A-15 상세 — `/clock` 이 생겼다. 그런데 **`use_sim_time` 을 켜면 안 된다** (2026-09-08)

새 빌드 `MMR-Build_260907` 이 **`/clock` 을 발행하기 시작했다** — A-15 행이 "생기면 sim time
도입 여부를 다시 판단한다"고 적어 둔 그 조건이 실제로 발생했다. **판단 결과는 "도입하지
않는다"** 이고, 이유는 성능이 아니라 **시간축이 하나로 정렬되지 않았다**는 것이다.

| 채널 | stamp 기준 | 실측값 예 |
|---|---|---|
| **`/clock`** | **기동 후 경과시간** | 2791.7 s (기동 46분 경과 시점) |
| `/output/panda_joint` · `gripper_joint` · `endeffector` | **벽시계 epoch** | 1788838268 s |
| `/camera_image/compressed` | **벽시계 epoch** | 동일 |

**같은 시스템 안에 두 시간축이 공존한다.** 차이는 약 **1.79 × 10⁹ 초 = 56.7년**이다.

`use_sim_time:=true` 를 켜면 우리 노드들(`robot_state_publisher` · `move_group` · TF 버퍼 ·
레코더)은 `/clock` 을 시각으로 쓰는데, 시뮬레이터가 보내는 메시지의 `header.stamp` 는 계속
벽시계다. **§A-9 가 이미 기록한 파손 양상이 그대로 재현된다** — TF 시각이 성립하지 않고,
데이터셋의 `sessions.start_ts` 가 1970년이 되며, `UNIQUE (start_sec, start_nanosec)` 가
재시작마다 충돌해 `on_existing_episode: skip` 이 **에러 없이 조용히 건너뛴다.**

**lockstep 도 아니다.** `/clock` 은 71.94 Hz 로 그냥 흘러가며 시뮬레이터가 우리를 기다리지
않는다. 즉 sim time 의 본래 이점(스텝 동기)은 얻을 수 없다.

#### 그럼 `/clock` 은 어디에 쓰나 — **A-17 계측기**로 쓴다

쓸모가 하나 생겼다. `/clock` 은 **sim 시각을 직접, 고해상도로 보여준다**(증분 13.89 ms =
시뮬레이터 내부 스텝 약 72 Hz — 이 값 자체가 새 정보다). 그래서 정지 구간을
**메시지 공백이라는 간접 지표 없이** 판정할 수 있다.

| 실측 (150 s) | 값 |
|---|---|
| 수신 공백 (팔 기준, 0.3 s 초과) | 4회, 길이 **0.72 ~ 0.75 s** |
| 그 사이 `/clock` 진행 | **+0.097 ~ +0.111 s** |
| 전체 진행률 | **0.99975×** |

**공백 0.74 s 동안 sim 시각이 0.10 s 만 흐른다** — 정지 중 시뮬레이션 자체가 멈춘다는
A-17 의 판단이 이제 `/clock` 으로 직접 확인된다(예전에는 `header.stamp` 가 한 프레임만
진행한다는 간접 근거였다). **§0 함정 8 은 그대로 유효하다** — 우리 프로세스도 그동안
멈추므로, 정지 구간에 무언가를 주입하는 시험은 여전히 불가능하다.

> **벤더 요청이 하나 생긴다.** 필요한 것은 `/clock` 발행이 아니라 **`/clock` 과
> `/output/*`·카메라가 같은 시간축을 쓰는 것**이다. 둘 중 어느 쪽으로 통일해도 좋다 —
> 전부 벽시계로 하거나, 전부 sim 시각으로 하거나. **섞인 상태가 가장 나쁘다**
> (벤더 요청 **B-13**).

### A-6 상세 — 카메라가 `CompressedImage` 로 바뀌었다 (2026-09-08)

`/camera_image` (`sensor_msgs/Image`, `bgr8`, 640×480, 921,600 B) 가 사라지고
**`/camera_image/compressed`** (`sensor_msgs/CompressedImage`, `format='jpeg'`,
약 **25.8 KB**, `frame_id='camera_link'`) 로 교체됐다. XML(`t1__RGBCamera_1_vm.xml`) 은
`Publish_Frequency="10"` · `Resolution="640 480"` 그대로이므로 **설정 변경이 아니라
발행 형식 변경**이다.

**대역폭은 약 36배 줄었다** — 초당 9.2 MB → 0.25 MB. 수집에는 유리하다.

**다만 우리 배선이 맞지 않는다.**

| 영향 | 내용 | 상태 |
|---|---|---|
| launch docstring | `panda_functionbay.launch.py` 가 "시뮬레이터가 `/camera_image` 로 발행한다"고 적고 있었다 | ✅ `/camera_image/compressed` 로 수정 (2026-09-08) |
| 레코더 | 뷰어·레코더가 `sensor_msgs/Image` 를 기대한다. `image_capture_node` 는 `CompressedImage` 를 **발행**하는 노드이지 구독 어댑터가 아니다 | ✅ 레코더는 압축 경로 구현 (아래) |
| 뷰어 | 같은 이유로 켜도 빈 창이었다 — **타입이 다르면 ROS 2 는 연결만 안 하고 오류를 내지 않는다** | ✅ `camera_republish`(`image_transport/republish`) 를 `enable_image_viewer` 와 짝으로 띄운다 (2026-09-08) |
| A-12 판정 | `encoding=bgr8` · `step=width×3` 기준이 무효다 — 압축 형식에는 그 필드가 없다 | ⬜ 재정의 필요 |
| A-18 | 카메라−관절 stamp 차를 다시 정의해야 한다 | ⬜ 재측정 필요 |

**결정: ② 소비자를 `CompressedImage` 로 받는다** (2026-09-08). ①처럼 우리가 풀어서
다시 인코딩하면 36배 대역폭 이점을 버리고 디코드-인코드를 두 번 하게 되고, ③은 벤더
왕복이 필요한데 대역폭이 오히려 나빠진다.

**레코더는 붙었다** — `FFMpegMp4Recorder(input_format='mjpeg')` 로 만들면 JPEG 바이트를
**우리가 풀지 않고** ffmpeg 에 그대로 넘기고, ffmpeg 이 디코드해 H.264 로 인코딩한다
(`-f mjpeg`; 출력은 그대로 H.264 라 데이터셋·replay 는 손대지 않는다). `write_compressed()`
가 그 입구이고, 방향이 어긋난 호출은 `InvalidFrameError` 로 거부한다 — 조용히 통과시키면
JPEG 이 raw 픽셀로 해석돼 깨진 영상이 나오고 원인을 못 찾는다.

**뷰어도 붙었다** — 압축을 푸는 것은 우리 노드가 아니라 `image_transport` 의
`republish` 다(C++). `enable_image_viewer` 하나로 뷰어와 함께 뜨며, 압축 토픽을
`camera_image_topic` 으로 되살린다. **파이썬 노드를 만들지 않은 이유는 성능이 아니다** —
실측으로 `cv2.imdecode` 는 640×480 / 26.8 KB 에서 0.75 ms/frame 이고 GIL 도 놓는다(파이썬
루프가 101% 유지). 직접 만들면 유지보수할 코드만 늘 뿐이었다. 대신 **raw 로 되살리는
순간 대역폭 이점이 사라지므로**(0.27 → 9.2 MB/s) 뷰어를 켤 때만 뜨게 묶었다.

**아직 안 된 것** — ⓐ `rdfp_image_recorder`(세션 자동 녹화) 에만 붙었고 서비스 구동
`image_recorder_node` 는 그대로다(첫 이미지에서 해상도를 정하는 구조라 손이 더 든다),
ⓑ `input_format` 을 넘기는 launch·YAML 배선이 없어 현재는 파라미터로 직접 줘야 한다.

### A-17 상세 — 시뮬레이터 주기적 정지 (2026-09-03 신규, 가장 큰 문제)

**시뮬레이터가 34초마다 약 2초간 완전히 멈춘다.** 그동안 네 토픽 모두 한 건도 오지 않는다.

| 항목 | 설정 30 Hz / 10 Hz | 설정 15 Hz / 5 Hz |
|---|---|---|
| 정지 주기 | 34.32 s (34.16~34.48) | 34.58 s (34.38~34.93) |
| 정지 시간 | 2.04 s (1.88~2.23) | 2.32 s (2.13~2.63) |
| 손실 비율 | 5.65 % | 6.44 % |
| 정지 사이 진행률 | 1.063× | 1.072× |
| sim 시각 기준 발행률 | 30.008 Hz | 14.999 Hz |

**발행 주기를 절반으로 낮춰도 정지 주기는 1% 미만 변한다** — 발행 부하가 원인이 아니고,
우리 쪽에서 주기를 낮춰 해결할 수 없다.

> ### ⚠ 정지 길이·주기는 세션마다 변한다 (2026-09-04)
>
> 같은 설정(30 Hz / 10 Hz)에서 하루 동안 다음 값들이 나왔다.
>
> | 관측 | 주기 | 정지 길이 | 손실 |
> |---|---|---|---|
> | 09-03 (기준선) | 34.32 s | **2.04 s** | 5.65 % |
> | 09-04 오후 `fb_checkup` 180 s | ~36 s (5회) | 평균 1.64 s, 최대 **1.69 s** | 4.5 % |
> | 09-04 저녁 연속 관측 | **33.245 s** | **0.889 ~ 0.99 s** (다수 회차, 산포 작음) | ~2.7 % |
>
> **한 회차의 값을 상수로 쓰면 안 된다.** 특히 정지 길이가 2.04 → 0.9 s 로 절반 이하가 된
> 것은 개선처럼 보이지만, **벤더는 아직 아무것도 반영하지 않았다**(A-5 는 회신 대기) —
> 즉 원인 변수가 우리가 모르는 곳에 있다. 수용 기준(§E 1번)은 길이가 아니라
> **"0.3 s 넘는 공백 0회"** 로 잡혀 있으므로 이 변동에 영향받지 않는다.
>
> **정지 중에는 우리 Python 프로세스도 멈춘다** — §0 함정 8 을 반드시 함께 읽는다.

**시뮬레이터 측 현상이라는 근거 넷:**

1. 정지 중 `header.stamp` 가 한 프레임(0.034 s)밖에 진행하지 않는다. 전송 지연이나
   버퍼링이면 stamp 는 계속 진행해야 한다 → **시뮬레이션 자체가 멈춘 것이다.**
2. 네 토픽이 **7~88 ms 안에 동시에** 멈춘다. 토픽별 전송 문제가 아니다.
3. 수신측(WSL2) 시계를 Windows 호스트와 대조했고 진행률 차이는 **0.4% 이내** —
   관측된 6.3% 과속을 설명하지 못한다.
4. 정지를 제외하면 sim 시각 기준 발행률이 **설정값과 정확히 일치**한다.

**과속은 캐치업이 아니다.** 정지 사이 구간을 4등분해 각각 진행률을 재면 처음부터 끝까지
일정하다 (`1.0587 1.0583 1.0584 1.0583`). 정지를 만회하는 단기 보상이 아니라 **상시 과속**이다.

**중요 — 데이터에는 결손이 없다.** sim 시각 기준으로 `header.stamp` 는 연속이다
(5419개 구간 중 간격 0.1 s 초과 **0건**, 최대 0.0499 s). 시각으로 정렬하면 관절·이미지
모두 끊김이 없다. 깨지는 것은 **실시간성**이다 — 원격 조작 중 2초 무반응, 접촉 동역학의
속도 불균일, 벽시계 기준 시간제한(데드맨 등)의 오발동.

> **`teleop_retarget` 의 `pedal_timeout` 을 켤 때 2.5 s 이상으로 잡는다.** 2 s 이하면
> 정지 때마다 하트비트가 끊겨 34초마다 클러치가 자동 해제된다. 기본값 0(비활성)이라
> 현재는 걸리지 않는다.

벤더 발송 문안: [functionbay_vendor_mail_20260903_stall.md](functionbay_vendor_mail_20260903_stall.md) — **발송 완료 · 회신 대기**.
원시 관측: `misc/fb_stamp/hz30_cam10_long.json` · `hz15_cam5.json`.

## B. 능동 확인 — 팔이 움직인다 (승인 후 진행)

**A 단계가 통과한 뒤에만 의미가 있다.** 순서를 지킨다 — 1번에서 갈리기 때문이다.

> ### 로봇이 실제로 움직이는 작업은 **① 그리퍼 개방 ② `ready` 이동** 으로 시작한다
>
> **B 단계 이후처럼 팔이 실제로 움직이는 모든 작업에 적용되는 규칙이다** (2026-09-03 `ready`
> 이동 도입, 2026-09-04 그리퍼 개방 추가). `fb_raw` · `fb_hold` · `fb_step` · `fb_limit` ·
> `fb_ee` · `fb_move` · `fb_curl` 은 실행 즉시 두 단계를 밟은 뒤 측정을 시작한다. 로직은
> [fb_ready.py](../../scripts/functionbay/fb_ready.py) 의 `goto_ready()` 한 곳에 있고
> `fb_recover.py` 도 같은 코드를 부르므로, **팔을 움직이는 새 스크립트는 그것만 부르면 된다.**
>
> #### ① 먼저 그리퍼를 연다
>
> **접촉을 남긴 채 팔을 옮기면 팔이 안 움직이는 것을 "명령 경로가 죽었다"로 오진한다**
> (§0 함정 5). 실제로 그렇게 오진했다 — 차트가 끝난 직후에는 그리퍼가 구멍에 꽂힌 peg 를
> 물고 있어(`|effort|` 6.8~7.2 N·m) 팔이 구멍에 걸린다. 물체를 끌고 가다 씬을 망가뜨리는
> 것도 막는다. 개방은 `fb_gripper.release_contact()` 가 맡고, 성공하면 `|effort|` 가
> **7 → 0.01 N·m** 로 떨어진다.
>
> **자세 판독보다 먼저 연다** — 접촉이 풀리면 부하가 바뀌어 팔이 실제로 움직인다(실측
> 0.0089 rad). 개방 전 자세를 시작점으로 잡으면 그만큼 틀어진다.
>
> **`--keep-grasp` 는 파지 상태에서 팔을 움직이는 것이 실험의 목적일 때만 쓴다**
> (예: §E 의 "파지가 팔 이동 중 유지되는가"). `fb_ready.py` / `fb_recover.py` 가 받는다.
>
> #### ② 그다음 `ready` 로 옮긴다
>
> 이유 셋:
>
> 1. **B 단계 측정값이 자세에 의존한다.** 처짐(B-3·B-4)은 모멘트 암에 비례하고
>    실효 가동범위(B-10)도 자세를 탄다. 시작 자세가 다르면 기준선 비교가 성립하지 않는다.
> 2. **`fb_hold` 는 현재 자세를 그대로 목표로 준다.** 되돌리지 않고 반복하면 처짐이
>    누적되어 자기충돌 자세까지 간다 (예전에는 B-15 로 수동 복귀해야 했다).
> 3. **작업면에 물체가 놓인 채로 시작하면 팔이 그것을 건드린다.** `ready` 는 팔을 접어
>    세운 자세라 작업면에서 떨어져 있다.
>
> **경로는 관절공간 직선이다** — 데카르트 직선이 아니라서 시작 자세에 따라 EE 가 휘어
> 지나갈 수 있다. 그래서 이동 전에 관절별 변화량을 먼저 출력한다. 물체 가까이에서
> 시작할 때는 `--ramp 10` 처럼 천천히 걸고, 출력에 `← 큰 이동` 이 보이면 `Ctrl-C` 로
> 멈춘다.
>
> **`--no-ready` 는 B-4(자세별 처짐)처럼 의도적으로 다른 자세에서 잴 때만 쓴다.** 이때는
> **그리퍼 개방까지 함께 건너뛴다** — 접촉 해제가 필요하면 `fb_gripper.py open` 을 직접
> 먼저 부른다. `fb_move restore` 는 저장한 자세로 되돌리는 것이 목적이라 자동으로 건너뛴다.

dx(mm)  0.00  -7.12  -6.95  -6.26  -5.19  -2.50  +0.32  +0.74
```

1.6초에 −7.1 mm 까지 말렸다가 풀린다. 이것이 **파지 정확도를 직접 망친다** — 집을 때
손끝이 물체 중심에서 벗어난 채 닫히고, 구멍에 넣을 때도 중심이 어긋난다.

**왜 기존 항목으로 안 잡히나.** B-3·B-4·B-5 는 **정지 상태**의 관절 오차를, B-8 은
lag 과 평균 오차를, B-9 는 상승·하강 비대칭을 본다. **이동 중 손끝이 옆으로 새는 양**을
보는 항목이 없었다.

**무엇을 가려내나.** 2026-09-11 부터 이 처짐을 우리가 상쇄한다
([functionbay_gravity_compensation.md](functionbay_gravity_compensation.md)). 그 보상은
**조용히 망가질 수 있다** — 아래 넷 중 어느 것이든 오류 없이 진행되고 증상은 "팔이 몇 mm
어긋난 곳에 선다" 뿐이다. B-17 이 그 창이다.

| 관측 | 원인 |
|---|---|
| 말림이 **수 mm 로 복귀** | 보상이 꺼졌다 — 프로파일 키 누락, URDF 경로 파손(로더가 `None` 을 준다) |
| 말림이 **커졌는데 부호가 반대** | **이중 보정** — 벤더가 A-1 을 반영했는데 우리 보상을 안 껐다 |
| 말림은 작은데 **도달 오차만 큼** | `Kp` 가 2000 이 아니다 — 씬 XML 의 `<Gain Kp=...>` 를 본다 |

> **B-3·B-4 로는 "꺼짐"을 못 가른다.** 보상이 꺼지면 정지 오차가 원래 값(joint4
> −0.0097)으로 돌아가는데, 그 값이 기준선에 **"정상"으로 적혀 있기 때문이다.**
> 이중 보정만 그쪽에서 부호 반전으로 잡힌다.

**팔을 안 움직이고 먼저 볼 것** — A 단계에 넣어 두었다(§A 표 아래 설정 확인 줄).

### B-18 상세 — peg-in-hole 왕복이 회피책 없이 된다 (2026-09-11 신규)

`./scripts/functionbay/fb_move_peg.py` 한 줄이다. 목적지를 안 주면 현재 위치에서

```

**왕복 실측** (반경 여유 0.5 mm):

| | `peg_hole` → `peg_tray` | `peg_tray` → `peg_hole` |
|---|---|---|
| 접근 오차 | 수평 0.00 · z +0.00 mm | 수평 0.00 · z +0.00 mm |
| 파지 오프셋 보정 | (+0.02, −0.36) mm | (−0.02, −0.36) mm |
| 하강 | **11.1초 · 1회** | **13.2초 · 1회** |
| tcp 도달 오차 | +0.05 mm | +0.05 mm |
| peg 밀림 | +0.01 mm | +0.01 mm |
| **삽입 오차** | **(+0.02, −0.33, −0.00)** | **(+0.06, +0.18, −0.00)** |

**분할 하강은 더 이상 필요 없다.** 여러 번 끊어 내리던 것은 중력 보상이 없던 시절의
회피책이다 — 그때는 하강이 목표보다 6.4 mm 덜 내려가 peg 이 구멍 턱에 눌렸고, 그 상태로
놓으면 물체가 씬을 이탈했다. 보상 후에는 tcp 도달 오차가 **+0.05 mm** 라 한 번에 내려도
밀림이 0.01 mm 다.

**대신 세 가지를 남긴다.**

**① 파지 오프셋 보정 — peg 을 정렬한다, tcp 가 아니다.** 그리퍼는 peg 을 정확히 중심에
물지 않는다. 실측 오프셋이 **y 로 −0.36 mm** 이고 **방향과 무관하게 일정**한데, 반경
여유가 0.5 mm 라 그 70% 를 먹는다. 무시하면 안 들어간다 — 실제로 오프셋 **+1.46 mm** 를
무시했다가 입구 턱에 걸렸다.

**② 기하 사전 확인 — 손끝이 고정물 상면 위에 남는가.** peg 이 그리퍼 안에서 밀려
올라가면 완전 삽입에 **손가락을 구멍(안지름 17 mm) 안에 넣어야** 해서 불가능하다. 정상
파지의 `peg − tcp` 간격은 약 **−54 mm** 이고, 한 번은 **−29 mm**(24.7 mm 밀려 올라감)로
줄어 그대로 밀어 넣다 peg 이 튕겨 나갔다. 스크립트가 시작 전에 막고 다시 잡으라고 알린다.

**③ 앉음 확인 — 놓기 전에 실제로 앉았는지 본다.** 안 앉은 채 놓으면 시뮬레이터가 물체를
씬 밖으로 튕겨낸다. 미착석이면 **쥔 채로 두고 종료**한다.

> **개방 시 물체 이탈은 시뮬레이터 쪽 결함이고 우리가 못 고친다.** 눌렸거나 떠 있는 채로
> 놓으면 x 로 188 mm 튀고 z 가 −3900 m 까지 가속한다. 그리퍼 `effort` 는 끝까지 정상
> 범위(2.2~2.5 N·m)라 **물체 TF 를 봐야만 보인다.** 펑션베이는 `/scene/reset` 이 없어
> 복구는 시뮬레이터 재시작뿐이다 — 그래서 앉음 확인을 남긴다.

### B-12 ~ B-14 (그리퍼) — 측정 불가는 **해제됐다** (2026-09-04)

**차단 사유가 우리 스크립트의 버그였다.** `fb_gripper.py` 와 `fb_cmdpath.py` 가
`/input/gripper_joint` 에 `sensor_msgs/JointState` 를 발행했는데 시뮬레이터는
`std_msgs/Float64MultiArray` 로 구독한다. 타입이 다르면 ROS 2 는 **연결하지 않고
오류도 내지 않으므로**, 증상이 "그리퍼가 ROS 명령을 무시한다"로 나타났다. 두 스크립트는
수정했다 ([백엔드 설계서](functionbay_backend_design.md) §2 경고).

앞서 원인으로 지목한 SignalChart 고정(`0.65 rad`)은 **현재 모델에서 재현되지 않는다** —
`s = 0.15` ~ `0.725` 를 지령대로 도달한다. 다만 당시 관측값이 `0.65002 rad` 로 차트
주석과 정확히 일치했으므로 그 시점에 차트가 잡고 있었을 가능성은 남는다. 무효가 된 것은
**"ROS 명령이 이기지 못한다"는 추론**이다 — 유효한 명령을 한 번도 보내지 못했다
([벤더 요청](functionbay_vendor_requests.md) §A-4 ④).

#### 새로 드러난 것 둘

**① 판정이 실물에서 계약대로 동작한다 (B-12·B-14).** 노드를 실제로 띄워 세 케이스를
확인했다 — `open` → `at_goal: true`(잔차 0.0001), 물체를 문 채 `close` →
`at_goal: false` · `stalled: true`("뭔가 끼었다"), 같은 상태에서 `grasp` →
`at_goal: true` · `stalled: true`(파지 성공).

> **⚠️ 한때 "개방 방향 저항"으로 기록했던 것은 오진이었다 (같은 날 정정).** `s = 0` 이
> 0.04 ~ 0.14 rad 에서 멈추는 현상을 시뮬레이터 특성으로 판단했는데, **그리퍼 안의
> 물체 때문**이었다. 장면 정리 후 4회 반복에서 `open` 은 매번 잔차 0.0001 이다. 멈춘
> 지점이 계속 올라간 것(0.04 → 0.14)이 물체가 밀려나던 흔적이다.
> **구별법: 물체에 막히면 구동축(1·4)은 정확히 도달하고 접촉축(2·3·5·6)에만 잔차가
> 남는다.** 여섯 축이 함께 못 가야 구동 문제다.

**② `effort` 는 측정된 토크가 아니다 (B-14).** 세 구간 18점 대조에서
**`effort = 200.0 × (지령 − 실제)`** 가 정지 시 오차 0.037 이하로 성립한다(과구동
20.8 rad → 4015.00, 예측 4015.00). 모델 설정이 이를 뒷받침한다 — `t1__Gripper6_1_vm.xml`
의 **`Kp=200`** 이 바로 그 계수다. 즉 드라이브의 비례 오차항이며 접촉 정보를 담지 않는다.

따라서 `stall_effort 1.0 N·m` 는 **`잔차 0.005 rad` 와 같은 조건**이고
(`1.0 ÷ 200`), 이는 `position_tolerance` 기본값과 수치까지 같다. 기준선의
*"파지 17.19 vs 빈손 0.004, 비 4300배"* 는 접촉력비가 아니라 잔차비다
(`0.0859 × 200 = 17.18`).

**물체를 물린 파지 측정은 2026-09-04 에 했다** — 차트가 만든 파지 상태에서 `close`(s=0.725)를 걸면
`|effort|` 가 **15.73 N·m**(15초 유지 후 15.58)이고 빈손은 **0.004** 다. 관절별로 보면
`effort = 200 × 잔차` 가 **6축 전부에서 소수 3자리까지** 성립하고, 잔차는 **접촉축에만** 남는다.
즉 **파지 여부는 판정할 수 있다** — 다만 재는 것은 접촉력이 아니라 **위치 오차**다. 접촉력 자체를
관측할 채널은 없고, 그것을 벤더에 문의한다(D 표 신규 항목).

### B-16 — 파지는 되는데 들면 떨어진다 (원인: 모델에 손끝 접촉이 없다)

**활성 씬 `t1` 에는 손끝 접촉 정의가 없다.** 등록된 접촉은 `Contact_1/2/3` 셋뿐이고
전부 물체 쪽이며(`peg_hole` · `peg` · `peg_tray`) 모두 `friction_coefficient="0.15"` 다.

**같은 빌드의 `r2` 씬에는 있다** — 손끝마다 전용 접촉을 걸고 마찰을 **1.0** 으로 잡는다
(`r2__GGeomContact_1/2_vm.xml`, `left/right_inner_finger_surf`, `K=1000000`).

| | `t1` (활성) | `r2` |
|---|---|---|
| 손끝 접촉 정의 | **없음** | 좌·우 각각 |
| 마찰 | `0.15` (물체 쪽만) | **`1.0`** (정지·동 모두) |

**실측** — P2 에서 파지 후 손끝 기준 수직 +88 mm 상승:

| 구간 | 접촉축 잔차 | 판정 |
|---|---|---|
| 상승 중 (0~8 s) | 0.0763 → 0.0690 (90.5%) | 유지 |
| **정지 후 (10 s)** | **0.0053 (6.9%)** | **상실** |

**정지한 뒤에 빠진다 — 정지마찰조차 부족하다.** 느리게 할수록 오히려 일찍 놓치고
(12 초 램프에서는 상승 중 70 mm 지점에서 상실), 단일 관절 이동에서도 재현된다.
**파지력을 올릴 수단은 없다** — `grasp` 가 이미 `finger_joint` 상한 `0.725 rad` 다.

**파지 판정 자체는 매번 정상이었다** (`at_goal`/`stalled` 계약대로). **쥐는 것과
유지하는 것은 다른 문제다.**

#### 2026-09-04 — §E 기준선(EE +2 cm)으로 재측정: 역시 상실

초기화 직후 P0(차트가 peg 를 구멍에 꽂아 물린 상태)에서 `close`(s=0.725)로 파지를 만들고
**tip(`panda_link8`) 기준 데카르트 +20 mm** 를 지령했다. `ready` 로 옮기지 않는다 — 옮기면
**§B 서문의 규칙**(팔 이동 전 그리퍼 개방)대로 그리퍼가 열려 파지를 잃는다.

| 구간 | 시각 | tip z | 최대 \|effort\| |
|---|---|---|---|
| 차트 파지 | t=1.0 s | 0.23156 | 6.78 |
| `close` 완료 | t=7.3 s | 0.23083 | **15.46** |
| 상승 완료 | t=8.9 s | **0.24062** (**+9.79 mm**) | 15.42 → 13.13 |
| 유지 | t=9~15.4 s | 0.24062 (고정) | **13.06 ~ 14.20** |
| **붕괴** | **t=15.43 s** | 0.24080 | **14.20 → 1.38 → 0.15** |
| 이후 | t=17~55 s | 0.24379 (**+3.2 mm** 더 올라감) | 0.15 ~ 0.19 |

**세 가지가 새로 확인됐다.**

1. **상승 중에는 버틴다.** effort 가 15.4 로 유지되고, 상승 도중 한 번 0.042 로 튀었다가
   즉시 12.75 로 복귀했다(순간 접촉 이탈).
2. **정지 후 6.5초를 버틴 뒤 떨어진다.** ±88 mm 측정의 "정지 후 즉시" 보다 오래 버티지만
   결국 같다. **정지마찰이 부족하다는 결론은 이동량과 무관하게 성립한다.**
3. **떨어지는 순간 팔이 +3.2 mm 올라간다** — 하중이 빠져 처짐이 줄어든 것이다. effort 붕괴와
   함께 보면 "물체가 빠졌다"의 독립 지표가 된다 (`/output/endeffector` 없이도 판정 가능).

**유지 구간 effort 는 13.06~14.20 으로 기준선 16~17 보다 낮다.** 같은 `close` 지령인데
파지력이 낮은 이유는 미확인이며, 접촉축 잔차가 그만큼 작다는 뜻이다(`effort = 200 × 잔차`).

**부수 관측 — 상승 달성률이 49% 다.** +20 mm 지령에 +9.79 mm. 같은 날 B-9 이 `ready` ·
빈손에서 76%(+15.13/+20)였으므로, **부하와 자세가 얹히면 방향 의존 오차가 더 커진다.**
벤더 A-1 의 실사용 영향이 B-9 단독 수치보다 크다는 근거다.

### `/ee_pose` 는 `grasp_center` 를 가리킨다 (2026-09-04)

description 이 Panda Hand 라 기본 프레임 `panda_hand` 는 실제 파지점에서 **149 mm + 90°**
어긋난다. launch 가 `panda_link7 → grasp_center` 정적 TF 를 띄우고 `ee_frame` 기본값을
그쪽으로 둔다. **`/ee_pose` 만 맞춰진 것이고 TF 형상·충돌은 여전히 Panda Hand 다** —
근본 해결(description 교체)에 필요한 정보는
[백엔드 설계서](functionbay_backend_design.md) §6.2 에 있다.

```bash
ros2 topic echo /ee_pose --once          # panda_link0 기준 파지 중심
ros2 run tf2_ros tf2_echo panda_link7 grasp_center
```

> ### ⚠ `/ee_pose` 로 데카르트 목표를 만들면 안 된다
>
> 데카르트 목표는 **MoveIt 그룹의 tip link** 기준으로 해석된다 — `panda_arm` 의 chain
> `tip_link` 은 **`panda_link8`** 이고, `/ee_pose` 의 프레임은 launch 의 `ee_frame` 이 정한다.
> 지금은 그 둘이 **z 로 149.2 mm 어긋나 있다** (실측: `panda_link0 → panda_link8` z=+0.5853,
> `→ grasp_center` z=+0.4361).
>
> **`fb_ee.py` 가 실제로 이것 때문에 깨졌다** (2026-09-04). `/ee_pose` 를 읽어 +20 mm 를
> 더한 값을 목표로 넘겨 **−129 mm 하강**을 지령했고, 상승·하강 시행이 둘 다 하강이 되어
> B-9 이 무의미해졌다. 지금은 `panda_link0 → panda_link8` 을 TF 로 직접 조회한다.
>
> **측정과 지령은 같은 링크여야 한다.** 파지점 기준으로 지령하고 싶으면 `/ee_pose` 를
> 읽는 것이 아니라 MoveIt 쪽 end-effector link 를 `grasp_center` 로 지정해야 한다 (미구현).

**B-14 의 값 차이도 결함이 아니다.** `effort = Kp × 잔차` 이고 Kp 는 양쪽 다 200 인데,
관절 수와 링키지가 달라 같은 peg 에 대한 잔차가 다르다 (0.0114 대 0.0862).

### G.3 B-9 재해석 — 비대칭이 아니라 **상수 오프셋**이다

| 빌드 | 상승 오프셋 | 하강 오프셋 | **비대칭** | 증분 이득 |
|---|---|---|---|---|
| 08-28 빌드 | −50.30 mm | −50.16 mm | **0.14 mm** | 99.65 % |
| **RecurDyn-260907** | −4.87 mm | −5.00 mm | **0.13 mm** | 100.33 % |
| 문서의 Crisp 기준선 (09-01) | −10.00 mm | −10.00 mm | 0.00 mm | 100.00 % |

`fb_ee.py` 는 `|+15.13|` 과 `|−25.00|` 을 비교해 "비대칭 9.87 mm" 라고 내지만, 그 차이는
오프셋 −4.94 mm 의 2배일 뿐이다. **세 데이터셋 모두 오프셋이 방향과 무관하고 증분
이득이 1.0** 이라, 이 자세에서는 정적 보정으로 흡수된다.

> **아직 A-1 문안을 고치지 말 것.** 전부 `ready` 한 자세에서 ±20 mm 두 점씩이다.
> 여러 자세·이동량으로 넓혀 확인한 뒤에 판단한다.

### G.4 이 회차에서 새로 드러난 것 셋

**① 그리퍼 명령 규약이 씬마다 다르다.** `r2` 는 **2축 · 도(degree) · 관절당
`(position, velocity, force)`** 다. 라디안을 보내면 `π/180 = 1.745%` 만 움직이는데
`effort` 도 안 올라 접촉으로도 안 잡힌다 — 요청서의 *"그리퍼 지령 미반영 1.6~4%"* 가
이것이었고 **철회**했다. 규약은 `config/functionbay_gripper_*.json` 이 갖는다
(backend_design §6.1a).

**② 손끝이 닿는 바닥은 탁자가 아닐 수 있다.** 구멍에 꽂힌 peg 은 자기 바닥이 구멍
속(z=+0.003)이지만 손끝이 실제로 닿는 면은 **구멍 상면(z=+0.028)** 이다. 물체 바닥으로
잡으면 칼라를 **15 mm 파고든다**. `FixtureSet.floor_at()` 이 그 면을 준다.
2026-09-09 의 "`grasp_center` ≠ 손끝" 과 **같은 종류의 실수가 다른 기준면에서** 난 것이다.

**③ ⚠️ 재삽입 후 개방하면 peg 이 씬을 이탈한다 — 재현율 3/3.**

| 순서 | 결과 |
|---|---|
| 파지 → **제자리** 개방 | 이탈 없음 |
| 파지 → +88 mm 상승 → 되내림 → 개방 | **이탈** |

되내림 중 손은 내려가는데 peg 은 오히려 올라가(peg−tcp 간격 51.7 → 22.6 mm) 눌린
상태가 되고, 놓는 순간 옆으로 튀며 발산한다(x +188 mm, z −50 m → −3814 m, 계속 가속).
**그리퍼 `effort` 는 끝까지 정상 범위(2.2~2.5 N·m)라 접촉으로 감지되지 않는다** —
물체 TF 를 봐야만 보인다. 팔·그리퍼는 멀쩡하고 물체 하나만 물리에서 빠진다.
**펑션베이는 `/scene/reset` 이 없어 복구는 시뮬레이터 재시작뿐이다.**

우리 쪽 몫도 있다 — 처짐으로 되내림이 목표보다 6.4 mm 덜 내려가 peg 이 구멍에
제대로 안 들어간 채 눌렸다. 다만 **눌렸다고 물체가 세계 밖으로 튀는 것은 시뮬레이터
쪽 문제**이며, peg-in-hole 과제 자체를 막으므로 벤더 요청 후보다.
