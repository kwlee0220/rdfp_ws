> 관측), 측정 도구는 `scripts/functionbay/fb_stamp.py`.

## 제목

시뮬레이터가 34초 주기로 2초간 정지하는 현상 — 원인 확인 및 제거 요청

## 본문

안녕하세요.

시뮬레이터 관측 데이터를 정밀 측정하던 중, **시뮬레이션이 일정 주기로 멈추는 현상**을
발견하여 측정 결과와 함께 문의드립니다. 재현성이 매우 높고 원인이 시뮬레이터 측에
있는 것으로 판단되어, 확인을 요청드립니다.

### 1. 현상

**시뮬레이터가 약 34초마다 약 2초간 완전히 멈춥니다.** 그동안 `/output/*` 와
`/camera_image` 를 포함한 모든 ROS 2 토픽이 한 건도 발행되지 않습니다.

2026-09-03, 180초 연속 관측 결과입니다. **발행 주기 설정을 절반으로 낮춰서도 동일하게
재현되어**, 두 설정을 나란히 싣습니다.

| 항목 | 설정 30 Hz / 10 Hz | 설정 15 Hz / 5 Hz |
|---|---|---|
| 정지 횟수 (180초) | 5 회 | 5 회 |
| **정지 주기** | **34.32 초** (34.16 ~ 34.48) | **34.58 초** (34.38 ~ 34.93) |
| **정지 지속 시간** | **2.04 초** (1.88 ~ 2.23) | **2.32 초** (2.13 ~ 2.63) |
| 실시간 대비 정지 비율 | 5.65 % | 6.44 % |
| 정지 사이 시뮬레이션 진행률 | 1.063 배 | 1.072 배 |
| 정지 사이 발행률 (벽시계) | 31.91 Hz | 16.08 Hz |
| 정지 사이 발행률 (sim 시각) | **30.008 Hz** (설정값과 일치) | **14.999 Hz** (설정값과 일치) |

정지 시각은 매우 규칙적입니다 (30 Hz 설정, 180초).

```
t =  17.21 s   정지 1.88 s
t =  51.37 s   정지 1.88 s      (직전으로부터 34.16 s)
t =  85.82 s   정지 2.23 s      (34.44 s)
t = 120.03 s   정지 1.96 s      (34.21 s)
t = 154.51 s   정지 2.22 s      (34.48 s)
```

**발행 주기를 절반으로 낮춰도 정지 주기는 34.32 → 34.58 초로 1 % 미만 변할 뿐이고,
지속 시간은 오히려 조금 늘었습니다.** 따라서 이 현상은 ROS 2 발행 부하 때문이 아니며,
저희가 발행 주기를 낮추는 것으로는 해결되지 않습니다.

### 2. 시뮬레이터 측 현상으로 판단한 근거

전송 지연이나 저희 측 수신 문제가 아님을 다음 네 가지로 확인했습니다.

1. **정지 중 `header.stamp` 가 한 프레임(0.034초)밖에 진행하지 않습니다.**
   네트워크 지연이나 버퍼링이라면 메시지가 밀려 있다가 한꺼번에 도착하므로 stamp 는
   그동안에도 계속 진행해야 합니다. 그렇지 않다는 것은 **그 시간 동안 시뮬레이션 자체가
   진행하지 않았다**는 뜻입니다.

2. **네 토픽이 동시에 멈춥니다.** `/output/panda_joint` 와 `/camera_image` 의 정지 시작
   시각 차이는 5회 모두 **7 ~ 88 ms** 이내입니다. 토픽별 전송 문제라면 이렇게 동기화될
   수 없습니다.

3. **수신 측 시계를 검증했습니다.** 수신 측은 WSL2 이고 시뮬레이터는 동일 머신의 Windows
   호스트입니다. 두 시계의 진행률 차이를 측정한 결과 **0.4 % 이내**로, 관측된 6.3 %
   과속을 설명하지 못합니다.

4. **정지 구간을 제외하면 발행 로직은 정상입니다.** sim 시각 기준 발행률이
   **30.008 Hz** 로 설정값 30 Hz 와 정확히 일치합니다.

### 3. 함께 확인된 현상 — 정지 사이의 과속

정지 사이 구간에서 **시뮬레이션 시각이 실시간보다 6 ~ 7 % 빠르게 진행**합니다
(30 Hz 설정 1.063배, 15 Hz 설정 1.072배). 그 결과 정지로 잃은 시간을 과속이 되메워,
**180초 창 전체로 보면 시뮬레이션 시각과 실시간이 거의 정확히 일치합니다**
(진행률 0.9996 ~ 1.0003, 표준오차 ±0.0003). 평균만 보면 정상으로 보이기 때문에 이
현상이 지금까지 드러나지 않았습니다.

다만 이 과속은 **정지 직후에 컸다가 줄어드는 형태가 아닙니다.** 정지와 정지 사이
구간을 4등분해 각각의 진행률을 재면 다음과 같이 처음부터 끝까지 일정합니다.

```
30 Hz 설정, 정지 사이 32초 구간을 4등분
   17.2~ 49.5 s :  1.0587  1.0583  1.0584  1.0583
   51.4~ 83.5 s :  1.0736  1.0740  1.0658  1.0619
   85.8~118.0 s :  1.0613  1.0681  1.0648  1.0518
```

즉 **정지를 만회하기 위한 단기 캐치업이 아니라, 시뮬레이션이 상시 6 ~ 7 % 빠르게
도는 상태**로 보입니다. 그러면서도 두 설정 모두 장기 평균이 1.000 에 수렴하므로,
훨씬 긴 시상수의 실시간 조절 기구가 따로 있는 것으로 짐작됩니다. 이 부분이 의도된
동작인지 확인 부탁드립니다.

### 4. 저희 쪽에 생기는 문제

먼저 명확히 해두면, **기록된 데이터 자체에는 결손이 없습니다.** 시뮬레이션 시각
기준으로 `header.stamp` 는 연속이며 (5419개 구간 중 간격 0.1초 초과 **0건**, 최대
0.0499초), 시각 기준으로 정렬하면 관절·이미지 모두 끊김이 없습니다.

문제는 **실시간성**입니다.

1. **원격 조작(teleoperation) 중 2초간 무반응.** 저희는 사람이 로봇을 조작하는 시연
   데이터를 수집합니다. 34초마다 2초씩 멈추면 조작자가 정상적으로 시연을 이어갈 수
   없고, 정지 중에 보낸 명령이 어떻게 처리되는지(버퍼링/유실/최종값만 반영)도
   확인이 필요합니다.

2. **접촉 동역학의 실시간성.** 현재 peg-in-hole 작업을 다루고 있어 접촉·마찰 구간의
   거동이 중요한데, 6.3 % 과속 구간과 정지 구간이 번갈아 나타나면 조작자가 느끼는
   물리 응답이 일정하지 않습니다.

3. **벽시계 기준 시간제한의 오작동.** 저희 스택에는 벽시계로 시간을 재는 대기·감시
   경로가 있습니다(액션 응답 대기, 데드맨 스위치 등). 2초 정지는 이런 경로를 오발동
   시킬 수 있습니다.

### 5. 요청 사항

1. **(우선) 34초 주기 2초 정지의 원인 확인 및 제거를 요청드립니다.**
   주기가 매우 규칙적이라 가비지 컬렉션, 주기적 체크포인트/저장, 로그 flush, 물리 엔진
   재구성 등이 후보로 보입니다. 어느 쪽인지 확인 가능하신지요.

2. **원인 제거가 어렵다면**, 다음 중 가능한 것을 알려주시면 저희가 대응하겠습니다.
   - 정지 주기·지속 시간을 설정으로 조절할 수 있는지
   - 정지 시작·종료를 알리는 신호(토픽/플래그)를 낼 수 있는지

3. **3항의 상시 과속(1.06 ~ 1.07배)이 의도된 동작인지 알려주십시오.** 만약 평균
   실시간 유지를 위한 보상이라면, 저희는 그 보상을 **끄는 편이 낫습니다.** 저희는
   시뮬레이션 시각을 기준으로 데이터를 정렬하므로, 실시간과의 평균 일치보다
   **속도의 일관성**이 중요합니다.

### 6. 수용 기준

다음을 만족하면 해결된 것으로 판단하겠습니다.

- 180초 연속 관측에서 **0.3초를 넘는 수신 공백 0회**
- 정지 제외 구간의 시뮬레이션 시각 진행률 **1.00 ± 0.01** (과속 없음)

측정은 저희 쪽 스크립트(`fb_stamp.py`)로 동일하게 수행하며, 필요하시면 원시 관측
데이터(180초, 5419 샘플)와 스크립트를 함께 전달드리겠습니다.

### 7. 참고로 여쭙습니다

- 발행 주기를 절반(15 Hz / 5 Hz)으로 낮춰 재측정한 결과는 1항에 실었습니다.
  **정지 주기는 거의 그대로였습니다.** 혹시 저희가 놓친 다른 설정 항목이 있는지요.
- 모델 규모(peg-in-hole 모델)나 접촉 개수에 따라 달라지는지요.

감사합니다.
