## 0. 한 줄 요약

**제어 계층은 명령 경로까지 전 구간 검증됐다.** 남은 과제는 **연동의 품질**이다.

- **중력 처짐** — 솔버 교체로 **10배 이상 줄었다**(최대 0.0097 rad ≈ 0.56°). 다만
  구조는 그대로라 자세에 따라 여전히 계통적으로 어긋난다 (§3)
- **응답이 느려졌다** — 시정수 **약 242 ms**(구 133 ms). 정확도와 맞바꾼 결과다 (§6)
- **보고 주기가 50 → 10 → 30 Hz 로 조정됐다** — 관측 양자화가 33 ms 로 좋아졌다.
  **처짐·τ 는 그대로**이므로 보고 주기는 관측 창일 뿐 물리를 바꾸지 않는다 (§6.1)
- **카메라는 9.6 Hz 로 일정하다** — 관절 보고 주기와 무관하다 (§7 ⑤)
- **servo(twist) 경로** — 발산은 사라졌으나 **추종하지 않는다**. 명령 방향과 무관하게
  EE 가 아래로 흐른다 (§5)
- **자기충돌** — 시뮬레이터가 막지 않아 MoveIt 으로 복구 불가능한 자세에 빠질 수 있다 (§4)
- **간헐적 고착** — 명령 입력 방향 전체가 죽는다. Unity 재시작만이 복구책 (§2.2).
  **다만 과거 판정 일부는 진단 도구 결함에 의한 오진이었다** (§10.4)
- **실효 가동범위가 URDF 보다 좁다** — joint7 상한 **1.6387 rad**. 관절 한계가 아니라
  **자기충돌**이다 (Robotiq 2F-85 가 팔에 닿는다) (§4.1)
- **대상 로봇 URDF 를 확보했다** — `src/panda_ftsensor_robotiq/` (전용 description 패키지). 순기구학이
  `/output/endeffector` 와 **완전 일치**해 EE 프레임·형식이 확정됐다 (§7 ⑥)
- **대상 과제는 Peg-in-Hole** (접촉 개입) 이고 솔버 정식 명칭은 **Crisp** 이다 —
  [`config/TCP_정의.txt`](../../config/TCP_정의.txt)
- **카메라 인코딩이 `bgr8` 로 바뀌었다** (기존 `rgba8`). `stamp` 도 채워지기
  시작했으나 **시간 기준이 관절 토픽과 다르다** (§6.5)

### 0.1 두 솔버 비교 — 펑션베이 vs 서울대

| 항목 | 펑션베이 솔버 (2026-08-28) | **서울대 솔버 (2026-08-31)** | 방향 |
|---|---|---|:-:|
| `/output/panda_joint` 주기 | 50 Hz | **30 Hz** (10 Hz 였다가 상향) | ▼ |
| 처짐 — `ready` 최대 오차 | 0.0983 rad (5.6°) | **0.0097 rad (0.56°)** | **▲ 10배** |
| 처짐 — joint2 (펴짐 자세) | +0.1428 rad | **+0.0109 rad** | **▲ 13배** |
| dead time | 25~34 ms | 약 43 ms | ▼ |
| **시정수 τ** | **133 ms** | **242 ms** | **▼ 1.8배** |
| 추종 최적 lag | 0.150 s | 0.255 s | ▼ |
| **정착 오차** (MoveIt 경로) | **0.0212 rad** | **0.0019 rad** | **▲ 11배** |
| 최대 오차 (지연 무보정) | 0.3549 rad | 0.6705 rad | ▼ |
| servo 단순 브리지 | 3 사이클 만에 **발산 → NaN** | **발산 없음 · 추종 실패** | 변화 |
| `/output/endeffector` | 토픽 없음 | **실제 값 발행** | ▲ |
| 카메라 `stamp` | 0 (미설정) | 0 (미설정) | — |
| 보간(`publish_rate=50`) 효과 | "필수" | 평균오차만 47% 차이 | 약화 |

**요약: 정확도는 10배 좋아지고 응답 속도는 1.8배 나빠졌다.** 강성을 올린 대가로
보이며, `오차 = 중력토크 / K_p` · `τ ≈ 감쇠 / 강성` 이라는 §3.3 의 모델과 방향이
일치한다 — 다만 τ 가 함께 줄지 않고 늘어난 점은 감쇠도 같이 올렸음을 시사한다.

### 0.2 수집용 권장 — 서울대 솔버

**학습 데이터 생성 관점에서는 서울대 솔버를 쓴다.**

#### 결정적 근거 — 편향이 정확히 데이터셋 계약을 때린다

[rdfp_framework_design.md](../rdfp_framework_design.md) §2.2 가 정의한 계약은 이렇다.

| 역할 | 토픽 | 의미 |
|---|---|---|
| **action** | `/target_joint_cmds` | 컨트롤러로 **나간 명령값** |
| **observation** | `/joint_states` | 실제 **도달값** |

**중력 처짐은 정확히 이 두 채널 사이의 오차다.**

| | 펑션베이 | **서울대** |
|---|---|---|
| action↔observation 오차 (joint4, `ready`) | 0.0983 rad (**5.6°**) | **0.0097 rad (0.56°)** |
| MoveIt 경로 정착 오차 | 0.0212 rad | **0.0019 rad** |

EE 환산으로 대략 **4 cm → 4 mm** 다 (팔꿈치~EE 약 0.4 m 기준의 추정치).

**모델은 이 편향을 로봇 동특성으로 학습한다.** 무작위 잡음이면 평균으로 씻기지만
**자세의 함수**라서 씻기지 않는다(§3.3). 학습된 정책을 실물이나 다른 백엔드로
옮기면 그대로 어긋난다.

#### 느린 응답은 왜 이를 뒤집지 못하는가

서울대가 τ 133 → 약 255 ms 로 1.8배 느리다(§6.1). 그러나 **지연은 상수이고 편향은
자세의 함수다.**

- 상수 지연은 데이터셋 구축 시 **시간축 이동으로 보정할 수 있다.** `fb_probe` 가
  최적 lag 을 하나로 찾아낸다는 것 자체가 그 값이 일정하다는 증거다(§3.4).
- 자세 의존 편향을 보정하려면 **역동역학 모델이 필요**하다 — 우리에게 없고, 벤더가
  제어기 사양을 공개해야 가능하다(요청서 A-2).

#### robot_twin 관점의 추가 이유

1. **조작 성공률.** `move_to_named_target` 은 스트리밍 완료 시점에 성공을 반환하는
   **개루프**다(§5.1). 펑션베이에서 "도달했다"는 1.2° 거짓말이고 서울대는 0.1° 다.
   "A 로 이동 → 파지" 같은 에피소드를 스크립트로 대량 생성할 때 5.6° 오차는 파지
   실패와 에피소드 품질 편차로 직결된다.
2. **장시간 수집 안정성.** 펑션베이에서는 servo 브리지가 3 사이클 만에 NaN 으로
   발산했고, 그 NaN 이 `/joint_states` → TF 트리로 번져 `move_group` 까지
   마비시켰다(§5.2). 무인 수집 중이면 세션이 통째로 날아간다. 서울대는 발산하지
   않는다(추종은 여전히 안 되지만 파괴적이지 않다).
3. **독립 검증 수단.** 서울대는 `/output/endeffector` 를 실제 값으로 준다(§1.2).

   **EE 자세 자체는 두 솔버 모두에서 얻을 수 있다** — `/ee_pose` 가 이미 50 Hz 로
   나온다. 다만 그것은 `/joint_states` 의 **순기구학 계산값**이라 관절값에서 파생된
   것이고, 관절값이 틀리면 EE 도 똑같이 틀린다. **독립적인 확인이 되지 않는다.**

   | | `/ee_pose` (TF 유래) | `/output/endeffector` |
   |---|---|---|
   | 출처 | `/joint_states` 의 순기구학 | 시뮬레이터 내부 값 |
   | 기준 모델 | **우리 URDF** (Panda + Panda Hand) | 시뮬레이터 로봇 (Robotiq 2F-85) |
   | 독립성 | **없음** | 있음 |

   `/tf` 는 시뮬레이터가 **발행하지 않는다**(구독만 한다 — `Publisher count: 0`).
   TF 를 채우는 것은 우리 `robot_state_publisher` 다.

   **그리고 두 값의 기준 프레임이 다르다**(§7 ⑥) — 파지 지점 라벨링처럼 실제
   손끝 위치가 필요한 용도에는 `/ee_pose` 를 그대로 쓰면 안 된다.

#### 카메라 5 Hz 를 쓸 때의 전제

**레코더는 CFR 기반이고 프레임을 솎아내지 않는다.**

```
image_recorder_node.py:50   # (CFR 기반이므로 불일치 시 재생 속도가 어긋나거나 프레임이 drop)
ffmpeg_command.py:123       "-framerate", str(fps)      ← mp4 시간축은 선언한 fps 로 결정
```

파이프라인에 데시메이션 로직이 없으므로 **소스가 5 Hz 여야 한다.** 현재 시뮬레이터
카메라는 **9.606 Hz** 이고 관절 보고 주기와 무관하다 — 여기에 `fps: 5` 를 선언하면
영상이 약 2배 빠르게 재생되어 **시간축이 통째로 어긋난다.**

선택지는 둘이다.

1. **시뮬레이터 카메라를 5 Hz 로 설정** (벤더 요청 — 설정 가능 여부 확인 필요)
2. `/camera_image` → 5 Hz 로 솎는 **데시메이션 노드**를 넣고 레코더에 `fps: 5`

**카메라가 관절 주기와 무관하므로, 관절 보고 주기는 카메라와 독립적으로 정할 수
있다.** 즉 5 Hz 영상을 쓰더라도 관절은 30 Hz 로 두는 편이 낫다 — 관측 해상도가
올라가고 처짐·τ 는 어차피 주기와 무관하다(§3.3 · §6.1).

> **3 Hz 로 더 내리는 것은 권하지 않는다.** 대상 과제가 **Peg-in-Hole**
> ([`config/TCP_정의.txt`](../../config/TCP_정의.txt) 에 peg/원기둥 SDF 정의가 있다)
> 로 **접촉이 개입한다.** 접촉 순간은 짧아서 프레임 사이에 묻히기 쉽다.
>
> 수치로도 경계에 걸린다 — 시뮬레이터 시정수가 **255 ms** 인데 3 Hz 는 프레임 간격이
> **333 ms** 라 과도 응답이 프레임 사이에서 끝난다. 5 Hz(200 ms)는 시정수보다 짧아
> 움직이는 중간 상태가 관측된다. 자세한 비교는 §6.1 과 아래 표를 본다.
>
> | 이미지 주기 | 동작 1회당 프레임 | 프레임 간격 | τ(255 ms) 대비 |
> |---|---|---|---|
> | 10 Hz | 18.2장 | 100 ms | 0.4배 |
> | **5 Hz** | **9.1장** | 200 ms | 0.8배 |
> | 3 Hz | 5.5장 | 333 ms | **1.3배** |
>
> (기준: `extended` 이동 = 91 command @ 50 Hz = 1.82초)

#### 권장 설정

| 항목 | 권장 | 근거 |
|---|---|---|
| 솔버 | **서울대** | 위 |
| `/output/*` 주기 | **30 Hz** | 관측 해상도 ↑, 물리 특성은 불변 |
| 카메라 | **5 Hz** — 소스를 5 Hz 로 맞춘 뒤 레코더 `fps: 5` | CFR 전제 |
| `publish_rate` | **50** 유지 | 평균오차 47% 이득(§5.2 비교) |
| 이미지 1장당 관절 샘플 | 6개 (30 / 5) | 관측이 action 보다 촘촘해야 한다 |

#### 솔버와 무관하게 남는 위험

- **간헐적 고착**(§2.2) — 두 솔버 모두에서 발생했다. Unity 재시작만이 복구책이라
  장시간 수집의 최대 위험이다.
- **카메라 `stamp = 0`**(§7 ⑤) — 이미지를 시간축에 놓을 수 없다.

**이 둘이 풀리기 전에는 어느 솔버든 무인 대량 수집은 이르다.** 감독하에 소규모로
시작하는 편이 안전하다.

## 1. 검증 완료 — 다시 확인할 필요 없는 것

`panda_functionbay.launch.py enable_camera_node:=false` 를 실제 시뮬레이터에 붙여
측정했다. 1차는 도메인 31 / `rmw_cyclonedds_cpp`, 2·3차는 도메인 31 /
`rmw_fastrtps_cpp` (워크스페이스 전체가 fastdds 로 통일된 뒤).

**아래 수치는 3차(서울대 솔버) 기준이다.**

### 1.1 기동 · 상태 경로

| 항목 | 실측 결과 |
|---|---|
| `readiness_gate` | **5 ~ 15 ms 만에 clean exit** — `got 7 joint position(s)` |
| 게이트 이후 체인 | `move_group` → `You can start planning now!`, servo · rviz2 · ee_pose 정상 기동 |
| `joint_state_fusion` | `input provides joint names; using them as-is` — 이름 수용 경로 동작 |
| `/joint_states` | **29.4 Hz**, 8관절 (`panda_joint1~7` + `panda_finger_joint1`=0.04) — 시뮬레이터 30 Hz 를 그대로 따른다 |
| `/ee_pose` | **50.0 Hz** — 자체 타이머라 시뮬레이터 주기와 무관하다. 보고 30 Hz 기준 **과표본 1.7배** (10 Hz 때는 5배) |
| TF | `world → panda_link0 → … → panda_hand` 성립 |
| launch 로그 | WARN/ERROR 전부 `panda_mock` 에서도 나오는 것. **펑션베이 고유 에러 없음** |

`panda_finger_joint2` 는 `/joint_states` 에 없지만 URDF 의 `<mimic>` 이라 MoveIt 이
채운다 — planning scene 조회로 `finger_joint1=0.04, finger_joint2=0.04` 확인했다.
**fusion 노드가 `finger_joint1` 하나만 덧붙이는 현재 구현으로 충분하다.**

## 2. 해소된 블로커 — "시뮬레이터가 명령에 반응하지 않는다"

1차 측정에서는 명령 41개가 `/input/panda_joint` 에 정확히 도달했는데도 관절이
**0.0 rad** 움직였다. 손으로 만든 `JointState` 를 4초간 356개 밀어도(이름 유무 양쪽)
동일했다. 2차 측정에서는 같은 절차가 **정상 동작**한다.

### 2.1 원인이 아니었던 것

원인을 좁히는 데 시간을 쓴 항목이라 기록해 둔다.

| 의심했던 것 | 판정 |
|---|---|
| RMW 불일치 | **아니다.** 1차 때도 양쪽 다 `rmw_cyclonedds_cpp` 였고 프로브가 명령 도달을 확인했다 |
| `name` 필드 유무 | **아니다.** 채운 쪽·비운 쪽 모두 무반응이었다 |
| QoS 비호환 | **아니다.** 양쪽 RELIABLE / VOLATILE 로 확인 |
| 우리 스택 | **아니다.** 클라이언트를 배제한 원시 발행도 무반응이었다 |

### 2.2 원인 — 미상 (유력 가설 2개를 실험으로 배제)

**2차 측정 중 같은 증상이 재현됐다.** 브리지는 멀쩡한데(상태 보고 49.9 Hz, TCP
`ESTAB`, 노드 8개 정상) 명령만 전혀 먹지 않는다.

고착은 **약 500 Hz 로 명령을 밀어 넣던 실행 중** 발생했다. 그래서 "수신 주기(50 Hz)
초과 발행"을 트리거로 의심했으나, 재시작 후 **의도적으로 재현을 시도해 배제했다.**

| 시험 조건 | 결과 |
|---|---|
| 100 Hz × 5초 | 정상 |
| 200 Hz × 5초 | 정상 |
| 500 Hz × 5초 | 정상 |
| **500 Hz × 15초 + 목표 12회 전환** (실패 당시와 같은 패턴) | **정상** |
| **관절 한계 초과 명령** (joint4 → -3.36, URDF 한계 -3.1416) | **정상** |

다섯 조건 모두 고착을 재현하지 못했다. **발행률도, 한계 초과 명령도 트리거가
아니다.** (위 "한계 초과" 시험은 펑션베이 솔버 때 것이다 — 서울대 솔버는 한계를
강제한다. §4.1 을 본다.)

#### ⚠️ 이 절의 "고착" 판정에는 도구 결함이 섞여 있다

**판정에 쓴 `fb_raw.py` 가 joint7 만, 그것도 + 방향으로만 밀었다.**

```python
target[6] = start[6] + delta     # 옛 판 — 관절 하나, 한 방향
```

그런데 시뮬레이터의 **joint7 실효 상한이 1.6387 rad** 로 URDF 한계(2.9671)보다
훨씬 안쪽이다(§4.1). joint7 이 그 근처에 있으면 `+0.10` 명령이 `0.00000` 으로
나오고, 그것을 **"시뮬레이터 전체 무반응"** 으로 오독했다. 실제로는 나머지 관절이
정상이었다.

**도구를 고쳤다** — 이제 7관절을 각각 여유 있는 방향으로 시험한다. 고친 도구로
재판정한 결과는 **7/7 반응, 시뮬레이터 정상** 이었다.

따라서 위에 기록된 고착 사례들은 **신뢰도를 낮춰 읽어야 한다.** 다만 전부가
설명되는 것은 아니다 — 1·2차와 3차 첫 사례에서는 joint7 이 상한에서 멀리
떨어져 있었고(0.0 ~ 0.83), `/input/endeffector` 와 전 관절 램프(`fb_recover`)도
함께 무반응이었다. **그 사례들은 여전히 미해명이다.**

실패 세션에서는 고착 직전까지 servo 브리지 실험으로 **NaN 이 여러 차례 발생**했고
(§5.2), 그때마다 복구했다. 누적된 상태가 원인일 가능성이 남지만 확인하지 못했다.

#### 3차 측정에서 다시 발생 — 범위가 크게 좁혀졌다

솔버 교체 후에도 고착이 재발했고, 그 진단으로 후보가 하나만 남았다.

| 관측 / 시험 | 결과 |
|---|---|
| `ros_tcp_endpoint` 가동 시간 | 1시간 47분 **연속** — 재시작된 적 없다 |
| TCP 상대 포트 | `10874` → `9828` 로 **변경** — Unity 만 끊겼다 재접속했다 |
| ROS 등록 상태 | 정상 — 노드 중복 없음, 구독자 count 1 |
| **엔드포인트만 재시작** | **복구 안 됨** — 명령 여전히 무반응 |
| **`/input/endeffector` (EE 명령)** | **무반응** — 입력 방향 **전체**가 죽는다 |
| Unity 재시작 | **복구됨** |

이로써 두 가지가 더 배제된다.

- **엔드포인트의 재접속 처리 문제가 아니다** — 새로 띄워도 그대로다.
- **"EE 제어 모드라 joint 명령을 무시한다"가 아니다**(1차 세션의 가설). EE 명령도
  똑같이 죽는다.

**남은 후보는 Unity 쪽 수신 경로 하나다.** Unity 가 TCP 는 정상 연결하고 상태도 계속
보내는데, **받은 메시지를 로봇에 적용하는 경로만 끊긴** 상태다. 고착이 Unity 재접속
직후 관측된 점은 정황이지만 인과로 확인하지는 못했다.

**복구는 Unity 재시작뿐이다.** 엔드포인트 재시작으로는 안 된다.

고착의 특징:

- 상태 보고는 계속 나온다 — **살아 있는지 여부로는 판정할 수 없다**
- 50 Hz 램프(`fb_recover.py`)로도 빠져나오지 못한다 → **Unity 재시작이 필요하다**
- 보고 주기 지터가 커진다 (정상 13~23 ms → 고착 시 8.8~32.8 ms) — 참고 지표

1차 측정 당시의 정황도 함께 남긴다. 그때는 아래가 관측됐다.

- `/output/endeffector` 가 전부 0.0 으로 고정 발행 (2차에서는 **토픽 자체가 없다**)
- `/UnityEndpoint` 노드가 **중복 이름으로 2개** (2차에서는 1개)

같은 증상이 재발하면 §9.3 의 `fb_raw.py` 를 가장 먼저 돌려 우리 쪽/시뮬레이터 쪽을
가른다.

### 2.3 "장면이 정지했다"는 오독이었다

1차 때 관측한 세 가지를 모두 시뮬레이터 고장의 근거로 삼았는데, 셋 다 정상이었다.

| 1차 관측 | 실제 |
|---|---|
| 관절값이 8초간 비트 단위 고정 | **위치 제어 팔이 목표를 유지하는 정상 동작.** 당시 자세는 `ready` 를 명령한 뒤 처진 자리였다 — 2차에서 `ready` 를 명령해 도달한 값과 소수점 3자리까지 같다 |
| `/camera_image` 3프레임 md5 동일 | **정지 화면이 아니라 정지한 장면.** 팔이 움직이는 동안 12샘플 중 6개가 전부 다른 해시였다 (§3.3) |
| `/output/endeffector` 가 0 | 이건 실제 이상이었다. 2차에서는 토픽이 사라졌다 |

**교훈: 정지한 값만으로 "죽었다"고 판정하지 않는다.** 자극을 준 뒤 반응을 본다.

## 3. 중력 처짐 — 명령과 실제가 계통적으로 어긋난다

시뮬레이터는 중력 보상이 없는 유한 강성 위치 제어로 동작한다. **솔버 교체로 오차가
10배 이상 줄었지만 구조는 그대로다** — 자세에 따라 계통적으로 어긋나는 성질은 남는다.

### 3.1 증상 — 현재 자세를 그대로 명령해도 더 흘러내린다

`fb_raw.py named 0.0 4.0`(현재 자세를 그대로 목표로 주기)을 반복하면 계속 흘러간다.

> 아래 두 표(§3.1 · §3.2)는 **펑션베이 솔버** 측정이다. 서울대 솔버에서는 같은 절차의 흐름이
> 회당 0.0025 rad 수준으로 줄어 누적이 훨씬 느리다 — 현상 자체는 남아 있다.

| | joint2 | joint4 | joint6 | joint1 · joint7 |
|---|---|---|---|---|
| 시작 | 0.0506 | 0.0337 | -0.0151 | 고정 |
| 1회 후 | 0.0858 | 0.0485 | -0.0225 | 고정 |
| 2회 후 | 0.1308 | 0.0605 | -0.0296 | 고정 |

**흘러가는 것은 중력 토크를 받는 관절(2~6)뿐이고, 중력 중립축인 joint1 · joint7 은
정확히 고정된다.** 처진 값을 다시 목표로 주기 때문에 누적된 것이다.

### 3.2 무한 표류가 아니라 정상상태 오차다

고정 목표를 15초간 계속 명령하며 추적했다 (`fb_hold.py`).

```
 t(s)        j2        j4        j6      j2 오차
  0.0    0.1308    0.0605   -0.0296     +0.0000
  1.5    0.1892    0.0681   -0.0364     +0.0584
  3.0    0.1890    0.0682   -0.0364     +0.0581
  ...      (13.5초 동안 소수점 4자리까지 완전히 평평)
 15.0    0.1890    0.0682   -0.0364     +0.0581
```

**1.5초 안에 수렴하고 그 뒤로는 미동도 없다.** 발산이 아니라 정상상태 오차다.

### 3.3 원인 — 제어기 강성이 낮다

**제어기 강성(stiffness)** 은 위치 오차 1 rad 당 관절이 내는 토크다. 스프링 상수와
같은 개념이며, 여기서는 `K_p` 로 쓴다.

```
토크 = K_p × (목표 − 실제)
```

중력이 팔을 끌어내리면 제어기가 밀어 올리고, **두 힘이 같아지는 지점에서 멈춘다.**

```
K_p × 오차 = 중력 토크        →        오차 = 중력 토크 / K_p
```

그래서 오차가 0 이 될 수 없다. **버그가 아니라 낮은 강성의 정상적인 귀결이다.**

#### 실측 — 오차가 중력 부하에 비례한다

자세를 바꿔 가며(= 중력 부하를 바꿔 가며) 정착 오차를 쟀다.

| 자세 | joint2 오차 | joint4 오차 | **joint1** | **joint7** | (펑션베이 솔버 joint2) |
|---|---|---|---|---|---|
| `ready` (접힘) | +0.0010 | -0.0099 | **+0.0000** | **-0.0000** | +0.0122 |
| 중간 | +0.0064 | -0.0092 | **-0.0000** | **+0.0000** | +0.0809 |
| 펴짐 (수평쪽) | **+0.0109** | -0.0071 | **-0.0000** | **+0.0000** | +0.1428 |

두 가지가 위 식을 그대로 보여준다.

1. **joint2 오차가 팔을 펼수록 11배로 커진다** (0.0010 → 0.0109). 팔이 펴지면
   어깨(joint2)의 모멘트 암이 길어져 중력 토크가 커진다. `K_p` 는 그대로인데
   분자만 커진 것이다.
2. **joint1 · joint7 은 세 자세 모두 정확히 0.0000 이다.** 회전축이 수직이라 중력
   토크가 애초에 0 이다. 분자가 0 이니 `K_p` 와 무관하게 오차도 0 이다.

`ready` 자세의 관절별 오차 전체는 다음과 같다.

| joint1 | joint2 | joint3 | joint4 | joint5 | joint6 | joint7 |
|---|---|---|---|---|---|---|
| **+0.0000** | +0.0009 | +0.0005 | **-0.0097** | -0.0007 | -0.0008 | **-0.0000** |

접힌 자세에서는 팔꿈치(joint4)가 **-0.0097 rad ≈ 0.56°** 로 최악이다
(펑션베이 솔버 -0.0983 rad ≈ 5.6°).

**구조는 보존됐다** — 오차가 부하에 비례하고 중력 중립축은 정확히 0 이다. 즉
처짐이 사라진 것이 아니라 `K_p` 가 약 10배 커진 것이다.

> **보고 주기와 무관하다.** 보고를 10 Hz → 30 Hz 로 올린 뒤 같은 절차를 반복했을 때
> 세 자세의 오차가 소수점 4자리까지 같았다(`ready` -0.0097 / 중간 -0.0092 / 펴짐
> +0.0109). 처짐은 제어기 특성이지 관측 주기의 산물이 아니다.

#### 지연과 같은 뿌리다

위치 제어 루프의 시정수는 대략 `τ ≈ 감쇠 / 강성` 이다. 강성이 낮으면 되돌리는 힘이
약해 느리게 접근한다.

**다만 서울대 솔버에서는 강성이 10배 올랐는데 τ 도 함께 늘었다** (133 → 242 ms, §6.1).
강성만 올렸다면 τ 는 줄어야 하므로, 감쇠도 함께 크게 올린 것으로 보인다 —
정확도를 얻고 응답 속도를 내준 셈이다.

**따라서 강성 하나가 세 증상의 공통 원인이다** — 이 절의 처짐, §6 의 느린 응답,
그리고 §5 의 servo 발산(정상상태 오차가 루프를 계속 밀어내는 것).

### 3.4 동작 중 추종 성능

`fb_probe.py` 로 명령/실제를 동시 기록해 지연을 스윕한 결과다.

| 항목 | 서울대 (보고 10 Hz) | **서울대 (보고 30 Hz)** | (펑션베이) |
|---|---|---|---|
| 추종 지연 (최적 정합 lag) | 0.255 s | **0.245 s** | 0.150 s |
| 최대 오차 (지연 보정 후) | 0.1313 rad | **0.0894 rad** | 0.0851 |
| 평균 오차 (지연 보정 후) | 0.0540 rad | **0.0414 rad** | 0.0549 |
| 최대 오차 (지연 보정 없이) | 0.6705 rad | **0.5797 rad** | 0.3549 |
| **정착 오차** | 0.0019 rad | **0.0019 rad** | 0.0212 |

성분 분해는 §6.1 을 본다.

> **오차 개선분을 전부 성능 향상으로 읽으면 안 된다.** 10 Hz 관측에서는 명령을
> 성기게 샘플링된 실제값과 비교하므로 오차가 부풀려진다. **lag(0.255 → 0.245)와
> 정착 오차(동일)가 거의 변하지 않은 것**이 그 증거다 — 물리는 그대로고 관측이
> 정확해진 몫이 크다.

### 3.5 학습 데이터에 주는 영향

**`/target_joint_cmds`(action)와 `/joint_states`(observation)가 자세에 따라 계통적으로
어긋난다.** 오차가 무작위가 아니라 중력 토크에 비례하므로, 학습 모델이 이 편향을
로봇 동특성으로 잘못 학습할 수 있다. 대응 후보:

1. 시뮬레이터 쪽에 **중력 보상**을 요청한다 (근본 해결 — §3.6).
2. action 을 명령값이 아니라 **다음 스텝의 실제 관절값**으로 기록한다 (설계 변경).
3. 현 상태로 수집하되 데이터셋에 이 편향을 명시한다 (임시).

**결정이 필요한 항목이다** — §8 우선순위 1번.

### 3.6 시뮬레이터 쪽 개선 — 강성 상향보다 중력 보상이 낫다

| 방법 | 처짐 | τ | 위험 |
|---|---|---|---|
| `K_p` 상향 | 감소 | 단축 | 너무 올리면 **진동·발산**, 접촉 시 딱딱해짐 |
| **중력 보상 (피드포워드)** | **원리적으로 제거** | 변화 없음 | 없음 — 모델만 있으면 된다 |

중력 보상은 오차가 생기기를 기다리지 않고 **중력 토크를 미리 계산해 더해 주는**
방식이다. 오차 없이도 팔이 제자리에 있으므로 처짐이 사라진다.

벤더 요청 순서 제안:

1. **중력 보상** — 처짐 제거. 부작용이 없다
2. **`K_p` 적정 상향** — τ 단축. 진동하지 않는 선까지

수용 기준까지 붙인 요청서는 [functionbay_vendor_requests.md](functionbay_vendor_requests.md) 에 있다 (중력 보상 = A-1, `K_p` 상향 = B-1).

## 4. 자기충돌 — MoveIt 으로 복구할 수 없는 자세

**시뮬레이터는 자기충돌을 막지 않는다.** §3.1 처럼 처진 값을 반복 명령하면 누적되어
Panda 모델에서 자기충돌인 자세에 도달한다. 실제로 그렇게 됐다.

```
/check_state_validity → valid = False
  contacts:  panda_hand ↔ panda_link5
             panda_leftfinger ↔ panda_link5
             panda_link5 ↔ panda_link7
```

그 상태에서 MoveIt 계획은 실패한다.

```
fix_start_state_bounds: Starting state is just outside bounds (joint 'panda_joint4')
fix_start_state_collision: Unable to find a valid state nearby the start state
OMPL: Skipping invalid start state (invalid state)
RRTConnect: Motion planning start tree could not be initialized!
→ RuntimeError: Planning to named target "ready" failed with code: -26
```

### 4.1 실효 가동범위 — 관절 한계와 자기충돌을 구분한다

**서울대 솔버는 관절 한계를 강제한다.** 그 값은 **대상 로봇 URDF**
([`src/panda_ftsensor_robotiq/urdf/panda_ftsensor_robotiq.urdf`](../../src/panda_ftsensor_robotiq/urdf/panda_ftsensor_robotiq.urdf))의
것이며, 우리가 MoveIt 에 물린 `moveit_resources_panda_description` 과 다르다.

URDF 한계를 0.6 rad 넘겨 명령하고 실제로 멈추는 지점을 쟀다.

| 관절 | 우리 URDF | **대상 URDF** | **실측** | 판정 |
|---|---|---|---|---|
| `joint4` 상한 | 0.0873 | **0.0698** | **0.0698** | **하드 관절 한계** — 대상 URDF 와 정확히 일치 |
| `joint4` 하한 | -3.1416 | -3.0718 | **-2.7599** | 0.31 rad 못 미침 → **자기충돌** |
| `joint7` 상한 | 2.9671 | 3.1500 | **1.6387** | 1.51 rad 못 미침 → **자기충돌** |
| `joint7` 하한 | -2.9671 | -3.1500 | -2.9988 | 0.15 rad 못 미침 |

**joint4 상한만 대상 URDF 의 한계와 소수점까지 일치한다.** 나머지는 한계에 한참
못 미쳐 멈추므로 **관절 한계가 아니라 자기충돌**로 보아야 한다 — Robotiq 2F-85 가
붙어 팔에 닿는 것이다. 우리 MoveIt 모델은 Panda Hand 라 이 충돌을 예측하지 못한다.

**`joint7` 실효 상한 1.6387 rad(94°) 이 가장 크게 어긋난다.** 대상 URDF 한계
(3.15)의 **52%** 이며, 이것이 §2.2 의 오진을 만든 원인이다.

> **측정 한계**: 다른 관절을 한 자세에 둔 채 쟀다. 자기충돌 범위는 **자세에 따라
> 달라지므로** 위 값은 그 자세에서의 값이다. 고정 상수로 쓰면 안 된다.

**실무적 함의**

- MoveIt 은 우리 URDF 한계로, 우리 충돌 모델(Panda Hand)로 계획한다. **계획은
  성공하는데 실행이 목표에 못 미치는 영역이 있다** — §3.4 의 정착 오차와 원인이
  다르므로 구분해야 한다.
- 근본 해결은 **대상 URDF 를 MoveIt 에 물리는 것**이다(§8-4). 그러면 관절 한계와
  충돌 기하가 동시에 맞는다.
- 펑션베이 솔버는 한계를 강제하지 않았다(joint4 를 -3.36 까지 밀 수 있었다).
  **솔버 간 차이이므로 교체할 때마다 다시 재야 한다.**

### 복구 방법 — MoveIt 을 우회한다

계획이 안 되므로 `MoveGroupClient` 로는 빠져나올 수 없다. **원시 `JointState` 를
직접 램프로 밀어** 정상 자세로 되돌린다. 시뮬레이터는 내부 보간을 하지 않으므로
큰 도약을 한 번에 주지 않고 50 Hz 로 선형 보간한다.

```bash
./scripts/functionbay/fb_recover.py 5.0      # 현재 → ready 로 5초 램프 후 정착
```

복구 후 `valid=True` 를 확인했고, 이어서 `extended` 로의 계획·스트리밍이 정상
동작했다.

## 5. servo(twist) 경로 — 무동작이며 단순 브리지로는 안 된다

`/servo_node/delta_twist_cmds` 에 트위스트를 넣어도 **로봇은 움직이지 않는다.**
그리고 **단순 중계 브리지로는 해결되지 않는다** — 실측으로 확인했다.

### 5.1 servo 는 정상이다 — 출력을 받을 주체가 없을 뿐

`start_servo` 호출 후 5초간 트위스트를 넣은 결과:

| 단계 | 결과 |
|---|---|
| `start_servo` | **성공** |
| 트위스트 발행 | 531개 |
| servo 출력 → `/panda_arm_controller/joint_trajectory` | **148개 정상 발행** |
| 시뮬레이터 입력 `/input/panda_joint` | **0개** |
| 관절 변화 | **0.00000 rad** |

```
/panda_arm_controller/joint_trajectory   Publisher 1 (servo_node)   Subscription 0
```

`panda_mock` 에서는 JTC 컨트롤러가 이 토픽을 받지만 이 스택에는 ros2_control 이 없다.

servo 출력의 내용은 시뮬레이터가 필요한 것과 **이미 같다.** 타입만 다르다.

```
joint_names : [panda_joint1 … panda_joint7]     ← 이름 일치
points      : 1                                  ← 절대 위치 1점
time_from_start : 0.034                          ← 약 29 Hz
```

### 5.2 단순 중계 브리지 — 발산은 사라졌으나 추종하지 않는다

`JointTrajectory.points[0]` → `JointState` 로 되싣는 20줄짜리 브리지로 시험했다.

**펑션베이 솔버 — 3 사이클 만에 발산했다.**

| 조건 | 브리지 전달 | 실제 이동 | 결말 | 실패까지 |
|---|---|---|---|---|
| 0.05 m/s, +Z | 41개 | — | **시뮬레이터 NaN** | ~1.4초 |
| 0.005 m/s, +Z | 37개 | 0.660 rad | servo NaN | ~1.3초 |
| 0.005 m/s, +X | 38개 | 0.680 rad | servo NaN | ~1.3초 |

트위스트를 1/10로 줄여도, 방향을 바꿔도 같았다.

**서울대 솔버 — 발산하지 않는다. 대신 추종하지 않는다.**

| 조건 | 브리지 전달 | 결말 | EE 변위 |
|---|---|---|---|
| 0.005 m/s, +X, 6초 | 180개 | **정상 완주** | 관절 0.144 rad |
| 0.05 m/s, +X, 6초 | 179개 | **정상 완주** | 관절 0.143 rad |
| 0.02 m/s, **+X**, 10초 | 297개 | 정상 완주 | dX **-0.021** / dZ **-0.130** m |
| 0.02 m/s, **+Z**, 10초 | 296개 | 정상 완주 | dX -0.031 / dZ **-0.131** m |
| **트위스트 0**, 10초 (대조) | 297개 | 정상 완주 | dX -0.000 / dZ **-0.005** m |

보고 주기를 30 Hz 로 올린 뒤 같은 시험을 반복해도 결과가 같다.

| 조건 (보고 30 Hz) | 전달 | 결말 | EE 변위 |
|---|---|---|---|
| 0.02 m/s, **+X**, 10초 | 297개 | 정상 완주 | dX -0.031 / dZ **-0.159** m |
| 0.02 m/s, **+Z**, 10초 | 297개 | 정상 완주 | dX -0.038 / dZ **-0.147** m |
| **트위스트 0**, 10초 (대조) | 297개 | 정상 완주 | dZ **-0.005** m |

NaN 도, 관절 한계 도달도, 가드 작동도 없다. 그러나:

1. **명령 방향과 무관하게 EE 가 아래로 약 0.13 m 흐른다.** +X 를 줘도 +Z 를 줘도
   결과가 거의 같다.
2. **이동량이 명령 크기와 무관하다.** 0.005 / 0.05 m/s 가 같은 0.14 rad 를 낸다.
3. **트위스트 0 에서는 5 mm 만 흐른다.** 즉 처짐 누적이 아니라 **트위스트 입력이
   있을 때만** 생기는 현상이다.

관절별로는 팔꿈치가 지배적이다 — +X 10초에서 joint4 **-0.243 rad**, joint2 +0.063,
나머지는 0.02 rad 이하. 중력 중립축(joint1 · joint7)은 0.0002 rad 로 사실상 정지.

**결론: 단순 중계 브리지는 여전히 쓸 수 없다.** 실패 양상이 "폭발적 발산"에서
"방향을 따르지 않는 느린 흐름"으로 바뀌었을 뿐이다. 기전은 규명하지 못했다.

### 5.3 루프를 닫으면 무엇이 달라지는가

브리지 유무로 servo 출력의 사이클별 증분을 비교했다.

**브리지 OFF (루프 열림)** — 118 사이클 내내 안정

```
  #   사이클 증분     명령-실제 j4
  1     0.00011        +0.00012
  5     0.00000        +0.00013
117     0.00000        +0.00013      ← 끝까지 일정
```

servo 는 누적하지 않는다. 정지한 피드백에서 일정한 작은 오프셋만 낸다.

**브리지 ON (루프 닫힘)**

펑션베이 솔버에서는 3 사이클 만에 발산했다.

```
  #   사이클 증분     명령-실제 j4
  1     0.00011        +0.00012
  2     0.00188        +0.00296     ← 17배
  3     0.02088        +0.02863     ← 11배 (누적 190배)
  4     0.02693        +0.01204     ← 진동 시작
  5     0.00952        +0.00252
 ...   nan
```

서울대 솔버에서는 같은 자리에서 증분이 커지지 않는다. 180 사이클을 완주하며 최대
증분이 0.0013 rad 에 머문다 — **발산이 사라졌다.**

```
  #   사이클 증분     명령-실제 j4
  1     0.00010        +0.00011
  3     0.00000        +0.00012
177     0.00112        +0.00175     ← 끝까지 이 수준
```

펑션베이 솔버의 발산은 구조상 그럴 만했다 — servo 는 34 ms 주기(29 Hz)로 도는데,
시뮬레이터는 dead time 약 30 ms + 시정수 133 ms 로 응답했고, 여기에 중력 처짐으로
목표에 영원히 도달하지 못하는 큰 정상상태 오차가 더해졌다.

서울대 솔버에서는 **정상상태 오차가 10배 줄어(§3) 루프를 밀어내는 힘이 사라졌다.**
지연은 오히려 늘었지만(τ 242 ms) 발산하지 않는 것으로 보아, 이 루프에서 지배적인
불안정 요인은 지연이 아니라 **정상상태 오차**였던 것으로 보인다.

다만 **추종이 되지 않는 문제는 남았다**(§5.2).

한때 **주기 불일치**를 의심했다 — 보고가 10 Hz 인데 servo 는 29 Hz 로 돌아 3 사이클 중
2 번은 갱신되지 않은 상태를 읽기 때문이다. **이 가설은 배제됐다.** 보고를 30 Hz 로
올려 servo 발행 주기(29 Hz)와 사실상 일치시켰는데도 결과가 같았고, 드리프트는 오히려
약간 커졌다(사이클이 늘어 누적이 많아진 것으로 보인다).

**추종 실패의 기전은 여전히 미상이다.**

`joint_limit_margin` 이 0.1 로 설정돼 있는데도 joint4 가 한계(-3.1416)에서 0.027
앞까지 갔다 — **발산 속도가 servo 의 한계 보호보다 빨랐다.**

### 5.4 브리지를 만든다면 필요한 것

- **증분 클램프 / 속도 제한** — 사이클당 관절 변화 상한
- **지연 보상** — 150 ms 를 감안한 예측, 또는 servo 주기 조정
- **NaN · 한계 가드 (필수)** — 가드 없는 첫 시도에서 NaN 이 `/joint_states` → TF
  트리 전체로 번져 `move_group` · `ee_pose_node` 가 마비됐고, `start_servo` 재호출도
  응답하지 않아 스택을 재시작해야 했다. 가드를 넣은 뒤로는 시뮬레이터가 NaN 에
  빠지지 않았다.

**결정이 필요하다** — 위 세 가지를 갖춘 브리지를 만들지, 아니면 이 백엔드에서는
twist 경로를 지원하지 않는다고 못 박을지. §8 우선순위 5번.

> **서울대 솔버 기준 갱신**: 발산 방지(클램프)의 시급성은 낮아졌다. 대신 **추종이
> 안 되는 원인**을 먼저 규명해야 한다 — 그것이 풀리지 않으면 클램프를 붙여도
> twist 경로는 쓸 수 없다.

> NaN 상태에서는 `fb_recover.py` 도 쓸 수 없다 (현재값을 읽어 보간하는데 그 값이
> NaN 이다). 현재값을 읽지 않고 절대 목표를 직접 반복 발행하면 탈출된다.

## 6. 시간 특성 — dead time · 시정수 · 시계

시뮬레이터가 명령에 **얼마나 늦게, 어떤 모양으로** 반응하는지다. §5 의 servo 발산과
§3 의 중력 처짐이 모두 여기서 나온다.

### 6.1 dead time 과 시정수 — 용어와 실측

두 가지를 구분해야 처방이 갈린다.

| 용어 | 뜻 |
|---|---|
| **dead time** (순수 지연·낭비 시간) | 명령을 준 순간부터 **어떤 반응이든 처음 나타나기까지**의 시간. 그동안 시스템은 완전히 무반응이다 |
| **시정수 τ** | 반응이 시작된 뒤 목표의 **63%** 에 이르기까지의 시간. 반응의 '굼뜬 정도' |

**제어에서 훨씬 나쁜 쪽은 dead time 이다.** 그 구간에는 정보가 아예 없어서 되먹임으로
보상할 방법이 없고, 제어 주기 대비 dead time 이 길수록 루프의 위상 여유가 줄어
발산한다. 반면 시정수는 느릴 뿐 예측 가능해서 설계로 흡수할 수 있다.

`panda_joint7`(중력 중립축이라 처짐이 섞이지 않는다)에 계단 명령을 주고 측정했다.

계단 ±0.05 rad 을 방향을 번갈아 **12회** 주고 잰 값이다.

**관측 양자화가 보고 주기와 같다.** 1회 측정으로는 분해되지 않으므로 반복해서
상쇄했다 — 샘플 위상이 매번 다르므로 **최소값이 참값에 접근**하고, 평균은 참값 +
약 (주기/2) 가 된다.

**보고 30 Hz (양자화 33 ms) — 현재 값**

| 성분 | 최소 | 평균 | 추정 | servo 주기(34 ms) 환산 |
|---|---|---|---|---|
| **dead time** | 42.7 ms | 74.1 | **≈ 43~58 ms** | 약 1.5 사이클 |
| **시정수 τ** | 251.6 ms | 275.4 | **≈ 252~259 ms** | 약 7.5 사이클 |

**보고 10 Hz (양자화 100 ms) — 참고**

| 성분 | 최소 | 평균 | 추정 |
|---|---|---|---|
| dead time | 35.8 ms | 92.7 | ≈ 43 ms |
| 시정수 τ | 244.7 ms | 291.5 | ≈ 242 ms |

두 조건의 추정치가 일치한다 — **보고 주기를 3배 올려도 dead time·τ 는 그대로다.**
관측 양자화만 100 → 33 ms 로 좋아져 신뢰도가 올라갔다. 각각 12회씩 모두 목표에
정확히 도달했다(±0.0500).

**펑션베이 솔버 대비 τ 가 1.8배 늘었다**(133 → 약 255 ms). §3 의 처짐이 10배
줄어든 것과 맞바꾼 결과로 보인다.

§3.4 에서 "추종 지연 0.15 s" 로 잰 값은 명령/실제 궤적을 가장 잘 겹치게 하는
lag 이라, **실제로는 이 두 성분이 섞인 결과**다. 지배적인 것은 시정수 쪽이다.

### 6.2 네트워크는 원인이 아니다 — 같은 머신으로 옮겨도 소용없다

시뮬레이터(Unity)와 로봇 스택은 서로 다른 머신에서 돈다. 다만 `ros_tcp_endpoint`
는 **이미 로봇 스택과 같은 머신**에 있어, 네트워크를 건너는 구간은 Unity ↔ 엔드포인트
하나뿐이다.

```
Unity (192.168.0.7)  --TCP-->  ros_tcp_endpoint (192.168.0.134, 스택과 동일 머신)  --DDS-->  스택
```

| 구간 | 실측 |
|---|---|
| 네트워크 왕복 (ping ×20) | **0.303 ms** (min 0.230 / max 0.399 / mdev 0.037, 손실 0%) |
| dead time 전체 | 약 43 ms |
| 네트워크가 차지하는 비율 | **0.7%** |

**같은 머신으로 옮겨 아낄 수 있는 것은 0.3 ms** — 전체 응답(약 180 ms)의 0.2% 다.
dead time 중 나머지 ~33 ms 는 Unity 의 프레임 파이프라인(수신 → 적용 → 물리 →
발행)으로 **추정**된다 — 뺄셈으로 얻은 값이고 `ros_tcp_endpoint` 자체의 기여분은
따로 재지 않았다. TCP 소켓의 커널 RTT 추정치가 12.7 ms 인 것도 Unity 가 프레임 단위로
소켓을 처리한다는 정황이다.

**지연을 줄이려면 손댈 곳은 시뮬레이터 쪽이다.** 그중에서도 **제어기 강성(τ 133 ms,
전체의 약 80%)이 우선**이며, 이쪽을 고치면 §3 의 중력 처짐도 함께 해소된다 —
구체적인 방법과 우선순위는 §3.6 을 본다. 프레임 파이프라인(~33 ms)은 그 다음이다.
머신 배치는 무관하다.

### 6.3 sim time 은 제공되지 않으며, servo 에는 도움이 안 된다

`/clock` 토픽이 없고 `use_sim_time` 은 기본값 `false` 다. 모든 타임스탬프가 호스트
벽시계 기준이다. 이 워크스페이스에서 sim time 을 쓰는 백엔드는 Gazebo 뿐이다.

배속은 문제가 없다 — 20초 1000샘플 측정:

```
벽시계 경과 20.001s   스탬프 경과 20.000s
진행 배속 = 0.99993        ← 사실상 정확히 실시간
(펑션베이 솔버 측정. 서울대 솔버에서는 재확인하지 않았다)
```

**따라서 sim time 을 도입해도 servo 안정성은 나아지지 않는다.**

- sim time 의 본래 목적은 시뮬레이터가 실시간이 **아닐 때** 벽시계와 분리하는 것인데,
  여기서는 이미 1.0 배속이다.
- 발산의 원인은 dead time 과 시정수(§6.1)이고, `/clock` 은 시간의 **단위**를 바꿀 뿐
  왕복 지연을 줄이지 않는다.
- servo 의 증분 계산은 메시지 스탬프가 아니라 `publish_period` 파라미터로 한다.

sim time 이 servo 에 의미를 갖는 경우는 시뮬레이터가 **lockstep(스텝 후 대기)** 을
지원할 때뿐이다. 그러면 dead time 이 결정적으로 고정되어 루프 설계가 가능해진다.
벤더에 요청한다면 "`/clock` 발행"과 "lockstep 지원"을 구분해서 말해야 한다.

### 6.4 시계 오프셋 2.22초 — 데이터셋 정합 문제

시뮬레이터가 찍는 스탬프가 호스트 시각보다 **일정하게 뒤처져 있다.**

| 토픽 | 스탬프 − 수신시각 | 변동폭 |
|---|---|---|
| `/output/panda_joint` | **-2.2207 s** | 0.0171 s |
| `/joint_states` (fusion 통과 후) | **-2.2283 s** | 0.0176 s |

드리프트가 아니라 고정 오프셋이고 변동폭이 작다 — **두 머신의 시계 차이**로 보인다
(스탬핑 버그가 아니다). fusion 은 기본값 `stamp_source=auto` 라 입력 스탬프를 그대로
통과시키므로, 이 오프셋이 MoveIt 까지 전달된다. `move_group` 의
`Failed to fetch current robot state` 경고와 무관하지 않아 보인다.

데이터셋에는 직접적인 문제다 — 에피소드 분할과 토픽 간 정렬이 `header.stamp` 기준인데,
시뮬레이터가 찍은 스탬프와 우리 ROS 노드가 찍은 스탬프가 2.2초 어긋난 채로 섞인다.

**대응 두 가지.**

1. **양쪽 머신에 NTP/chrony** — 근본 해결. 스탬프의 의미(그 자세였던 시각)가 보존된다.
2. **`stamp_source:=now`** — fusion 에서 재스탬프. 실측 확인:

   | `stamp_source` | `/joint_states` 오프셋 |
   |---|---|
   | `auto` (기본) | -2.2283 s |
   | **`now`** | **-0.0009 s** |

   단, `now` 는 *시뮬레이터가 그 자세였던 시각*이 아니라 *우리가 받은 시각*을 찍으므로
   dead time(약 34 ms)이 스탬프에 흡수된다. 1번이 가능하면 1번이 낫다.

### 6.5 카메라 — 스탬프 기준이 다르다

시뮬레이터 수정으로 **두 가지가 개선됐다.**

| 항목 | 이전 | **현재** |
|---|---|---|
| `encoding` | `rgba8` | **`bgr8`** |
| `step` / `data` | 2560 / 1,228,800 | **1920 / 921,600** (대역폭 −25%) |
| `header.stamp` | `0` (미설정) | **값이 들어온다** |
| 주기 | 9.606 Hz | 9.59 Hz (동일) |

**`bgr8` 은 `cv_bridge` 와 OpenCV 의 기본 형식**이라 변환이 필요 없다. 예전에 적었던
"`rgb8` 로 바꿔 달라"는 요청은 이것으로 해소된다.

**다만 스탬프의 시간 기준이 관절 토픽과 다르다.**

```
/camera_image        stamp: sec=63          ← 시뮬레이터 기동 후 경과 시간으로 보인다
/output/panda_joint  stamp: sec=1788...     ← 벽시계 epoch
```

기준이 다르면 **두 토픽을 짝지을 수 없다.** `image_frames` 처럼 타임스탬프로 정렬하는
경로가 여전히 깨진다. 스탬프가 채워진 것은 진전이지만, **관절 토픽과 같은 기준
(벽시계 epoch)으로 맞춰야** 쓸 수 있다.

## 7. 설계 문서 정정 대기 항목

아래는 **실측으로 확인됐으나 [functionbay_backend_design.md](functionbay_backend_design.md)
에 아직 반영하지 않은** 내용이다.

> 이 절 안의 `§` 번호는 **설계 문서 쪽 절 번호**다 (이 문서의 절이 아니다).

### ① 설계 문서 §2.1 — 시뮬레이터는 `name` 을 채운다

현재 문서는 "`name` 이 비어 있다 — 순서가 계약이다"를 **이 백엔드의 가장 큰
위험**으로 서술한다. 실측은 반대다:

```
name: [panda_joint1, panda_joint2, ..., panda_joint7]
```

`joint_state_fusion` 이 `input provides joint names; using them as-is` 로그를 내며
그 경로를 탔다(1·2차 모두). 코드는 양쪽 다 처리하므로 동작에는 문제가 없지만,
**위험도 서술이 현실과 다르다.** 순서 계약은 "현재 위험"이 아니라 "이름이 빠질
경우의 대비책"으로 격하해서 다시 쓴다.

### ② servo 출력에 소비자가 없다 (신규 항목)

**`servo_node` 는 떠 있어도 무동작**이며, twist 기반 teleop 이나
`replay_arm_path:=ee_twist` 는 이 백엔드에서 팔을 움직이지 못한다. 나아가
**단순 중계 브리지로도 해결되지 않는다**(루프가 발산한다).

실측과 근거는 §5 에 있다. 설계 문서 §5.2(미충족 — 의도적)에 추가한다.

### ③ 설계 문서 §4.2 — `mode='auto'` 오탐의 조건을 정확히

현재 문서는 "auto 는 `/panda_arm_controller/commands` 를 보므로 오판한다"까지만
적혀 있다. 실제 판별 로직은 **대상 토픽의 publisher 또는 subscriber 존재**를 본다
([move_group_factory.py](../../src/robot_control/robot_control/moveit/move_group_factory.py)
의 `detect_controller_mode`). 따라서:

| 호출 | 판별 | 결과 |
|---|---|---|
| `create_move_group_client(node)` | `/panda_arm_controller/commands` 없음 → **JTC** | 실행 액션 서버 0개 → 조용히 멈춤 |
| `create_move_group_client(node, arm_command_topic='/input/panda_joint')` | Unity 가 구독 중 → **JGPC** | 정상 |

즉 `arm_command_topic` 을 함께 넘기면 auto 도 맞게 판별한다. 다만 **시뮬레이터가
꺼져 있으면 구독자가 사라져 다시 JTC 로 떨어지므로**, `mode='jgpc'` 명시 권고는
그대로 유지한다.

JTC 오탐 시의 실제 상태:

```
/panda_arm_controller/follow_joint_trajectory   Action servers: 0, clients: 1
```

`moveit_simple_controller_manager` 가 클라이언트로 붙어 있으나 서버가 없다.
RViz 의 "Plan & Execute" 버튼도 같은 이유로 동작하지 않는다.

### ④ 그리퍼 출력 — 확정됨 (2026-09-01 3차 실측)

1·2차에서는 단위도 성분의 의미도 확정하지 못했다. 3차에서 형식이 바뀌면서 전부
풀렸고, 과거 값도 소급해 해석된다. 사양은 `functionbay_backend_design.md` §6.1.

**1·2차 형식** — `Float64MultiArray`, **손가락 2개 × (각도, 속도, 토크)**:

| | raw | finger0 | finger1 |
|---|---|---|---|
| 1차 | `[0.000143, ~0, -14.34, -0.000140, ~0, 13.97]` | q=+0.000143, v=0, f=−14.34 | q=−0.000140, v=0, f=+13.97 |
| 2차 | `[0.7198, ~0, -0.0037, -0.7198, ~0, 0.0031]` | q=+0.7198, v=0, f=−0.0037 | q=−0.7198, v=0, f=+0.0031 |

**"큰 성분이 index 2·5 → 0·3 으로 옮겨갔다"는 구조 변경이 아니라 상태 차이였다** —
1차는 열린 채(q≈0) 토크만 걸린 상태, 2차는 닫힌 상태다. `finger_joint` 범위
`[0, 0.725]` 에 대면 **0.02% = 완전 개방 / 99.3% = 완전 폐쇄**로 들어맞고, 좌우 q·f 가
부호만 뒤집힌 대칭인 것도 맞는다. 단위는 **rad / rad·s⁻¹ / N·m** 다.

**3차 형식 (현재)** — `sensor_msgs/JointState` 30 Hz, **6관절** (`gripper_joint1~6`).
q/v/f 가 인터리브 대신 `position`/`velocity`/`effort` 세 배열로 분리됐다. 벤더 패킹
규약(`res[3*i+0/1/2] = q/v/f`)은 그대로이며 **관절 단위**로 적용된다.

**단, 시뮬레이터가 mimic 을 강제하지 않는다** — `data=[0.30]` 을 보내면 관절 0 만
움직이고 나머지 5축은 그대로다. 6축을 일관되게 채워 보내는 것이 브리지 책임이다.

### ④-2 `/output/endeffector` — 다시 발행되지 않는다 (2026-09-01)

3차에서 실제 값 발행을 확인해 B-4 를 닫았는데, peg-in-hole 모델에서는 **토픽이
등록되어 있으나 15 초간 한 건도 오지 않는다.** `TCP_정의.txt` 는 body 9
(`robotiq_85_base_link`) 를 출력한다고 적고 있어 서술과 실제가 어긋난다.

발행 여부가 모델(Assembly)마다 갈리는 것으로 보이므로, 벤더 질문을 **"고쳐 달라"가
아니라 "어떤 조건에서 발행되는가"** 로 바꿨다 (vendor_requests B-4). 당장은 URDF FK
로 대체 가능하다 — 대상 URDF 가 시뮬레이터와 0.00 mm 로 일치함을 확인해 두었다.

### ④-3 그리퍼 open/close/grasp — 구현 가능함을 실측으로 확인 (2026-09-01)

peg-in-hole 모델에서 실제로 집어 들었다. 상수와 판정 규칙은
`functionbay_backend_design.md` §6.1 에 있고, 요약은 다음과 같다.

| 항목 | 결과 |
|---|---|
| open/close | `s·[+1,+1,−1,−1,−1,+1]`, `s ∈ [0, 0.725]` — 전 구간 오차 **0.0000** |
| 계단 응답 | dead time 88 ms, τ 283 ms, 99% 1051 ms |
| 파지 판정 | effort **17.19** vs 빈손 **0.004** N·m — **4300배** |
| pick 동작 | +2 cm 상승 중 effort 16~17 N·m 유지 — **성공** |
| 오분류 | 빈손·파지·유지·높이이탈 네 상황에서 **0건** |

`effort` 가 나오므로 `GripperCommand` 액션의 `stalled` 재구성이 설계서가 우려한 것보다
쉽다 — 위치 잔차와 토크 두 신호가 독립적으로 같은 답을 준다.

### ④-4 팔 제어에서 새로 드러난 것 두 가지

그리퍼 측정 중 팔을 움직이다 발견했다. **둘 다 브리지·트윈 구현에 직접 영향을 준다.**

**(a) 명령을 멈추면 처진다.** 무명령 구간에서 EE 가 **40 mm 내려앉았다.** 자세 유지
중에도 50 Hz 발행을 계속해야 한다. 증상이 **A-4 "명령 무반응 고착"과 구별되지
않으므로**, 무반응처럼 보이면 `joint1`/`joint7`(중력 토크가 없는 축)에 단독 명령을
넣어 먼저 갈라낸다 — 실제로 그렇게 오진했다가 joint1 정상 응답(+0.0526 / 지령 +0.05)
으로 구분했다.

**(b) 정상상태 오차의 부호가 이동 방향을 탄다.** 상승은 부족(+20 mm 지령 → +10.0 mm),
하강은 초과(−20 mm 지령 → −30 mm). 상승용 보정(잔차 2배 과지령)을 하강에 그대로 쓰면
발진한다(실제로 ±30 mm 왕복시켰다). 한 관절만 지령해도 나머지가 하중을 받아 밀리므로
(`joint2` 단독 이동 시 FK 예측 −14.02 mm vs 실측 −1.06 mm), **EE 위치는 반드시 측정값
기반 폐루프로 맞춘다.**

> (b)는 **A-1(중력 보상 피드포워드) 요청의 근거를 강화한다.** 지금까지 A-1 의 근거는
> "자세에 따라 편향이 다르다"였는데, 여기에 **"같은 자세에서도 이동 방향에 따라 부호가
> 바뀐다"**가 더해진다. 방향 의존 오차는 시간 이동(time-shift)으로 보정할 수 없다.

### ⑤ 카메라 — 실시간 렌더링 확인됨

`/camera_image` 는 `sensor_msgs/Image`, publisher 1, **9.606 Hz**.

> **관절 보고 주기와 무관하다.** 보고 10 Hz 일 때도 30 Hz 일 때도 카메라는 9.6 Hz
> 다 (20초 고정 구간 계수: 192건 / 19.88s = 9.606 Hz). 한때 "`/output/*` 상향과
> 카메라가 예산을 나눠 쓴다"고 적었으나 **측정 오류였다** — `ros2 topic hz` 의
> 수렴 전 첫 줄을 읽은 값(4.4 Hz)이었다. **`ros2 topic hz` 는 창이 찰 때까지
> 기다려 읽는다.**

- **정지 화면이 아니다.** 팔이 정지한 동안 6샘플은 같은 해시였지만, 움직이는 동안
  12샘플 중 6개가 전부 다른 해시였다.
- **`camera_info` 에 해당하는 토픽은 없다.** remap 하면 영상은 흐르지만
  `camera_info` 를 요구하는 경로는 비게 된다.

- **인코딩은 `bgr8`, `header.stamp` 는 채워지되 시간 기준이 다르다** — §6.5.

"미실측"에서 "**스트리밍 확인 · `bgr8` · `camera_info` 미제공 · `stamp` 기준 불일치**"
로 고친다.

### ⑥ `/output/endeffector` — 형식과 기준 프레임 (확정됨)

**자세는 쿼터니언이 아니라 RPY(rad) 이고, 기준 프레임은 `robotiq_85_base_link` 다.**

```
data: [0.5044, -0.00013, 0.2076,  3.1377, -0.00066, -1.5708]
       └── XYZ (m) ──┘  └──── RPY (rad) ────┘
```

배열이 **6개**이고(쿼터니언이면 7개), `3.1377` 은 단위 쿼터니언 성분이 될 수 없다.

#### 벤더 소스로 확정했다

[`config/TCP_정의.txt`](../../config/TCP_정의.txt) 에 솔버(**Crisp**, 서울대) 출력
코드가 그대로 들어 있다.

```
//  EE (robotiq_85_base_link, body 인덱스 9) pose:
//    res[3*N + 0..2] : EE position (x,y,z)
//    res[3*N + 3..5] : EE orientation (roll,pitch,yaw) [rad]
//                      d->body.quat[EE_BODY_ID] 를 ZYX intrinsic 로 변환
```

**ZYX intrinsic 은 tf2 의 고정축 XYZ 규약과 같다** — 우리가 쓰는 변환과 동일하다.
`body 인덱스 9` 도 URDF 와 정합한다 (MuJoCo 관례상 `world(0) → panda_link0(1) →
… → panda_link7(8) → robotiq_85_base_link(9)`).

#### 순기구학으로도 확인했다

대상 로봇 URDF([`src/panda_ftsensor_robotiq/urdf/panda_ftsensor_robotiq.urdf`](../../src/panda_ftsensor_robotiq/urdf/panda_ftsensor_robotiq.urdf))로
같은 관절값의 `robotiq_85_base_link` 자세를 계산해 비교했다.

```
FK(대상 URDF)        [0.50441, -0.00013, 0.20761,  3.13767, -0.00066, -1.57077]
/output/endeffector  [0.50441, -0.00013, 0.20761,  3.13767, -0.00066, -1.57077]
차이                  0.00 mm / 0.000°
```

**완전 일치한다.** 이로써 세 가지가 동시에 확정된다.

- 자세 표현은 **RPY(rad)**, tf2 규약(고정축 XYZ)과 같다
- 기준 프레임은 **`robotiq_85_base_link`**
- **시뮬레이터가 이 URDF 를 쓴다**

#### 우리 TF 와의 오프셋 — 원인까지 밝혀졌다

대상 URDF 의 고정 조인트가 그대로 답이다.

```xml
<joint name="robotiq2panda" type="fixed">      panda_link7 → robotiq_85_base_link
  <origin xyz="0 0 0.130" rpy="0 0 1.57079633"/>
```

우리 URDF 는 `panda_link7 → panda_link8` 이 `z = 0.107` 이다.

| | 계산 | 실측 |
|---|---|---|
| 위치 차 | 0.130 − 0.107 = **23 mm** | **23.4 mm** |
| 회전 차 (`panda_link8` 기준) | — | **Z축 +90.0°** |
| 회전 차 (`panda_hand` 기준) | — | **Z축 +135.0°** |

**고정 조인트이므로 joint7 과 무관한 상수 오프셋이다** — 이전에 "미확인"으로 남겨
두었던 항목이 해소됐다.

#### 변환식

```
robotiq_85_base_link  =  panda_link7 · Trans(0, 0, 0.130) · Rot_z(+90°)
```

`/ee_pose`(우리 TF, `panda_hand` 기준)를 시뮬레이터 EE 로 맞추려면 **Z축 +135° 회전 +
공구 방향 23 mm** 를 더한다. 근본 해결은 대상 URDF 를 MoveIt 에 물리는 것이다(§8-4).

### ⑦ 속도·힘을 계산하는데 발행하지 않는다 (신규 항목)

`/output/panda_joint` 는 `position` 만 채우고 `velocity` · `effort` 가 **빈 배열**이다.
그런데 [`config/TCP_정의.txt`](../../config/TCP_정의.txt) 의 솔버 출력 코드를 보면
**관절마다 세 값을 모두 계산한다.**

```c
res[3 * i + 0] = (float)q_full[qadr];   // position
res[3 * i + 1] = (float)v_full[vadr];   // velocity   ← 계산됨
res[3 * i + 2] = (float)f_full[vadr];   // force      ← 계산됨
```

**즉 발행만 하면 되는 상태다.** 얻을 수 있는 것:

| 값 | 쓰임 |
|---|---|
| `velocity` | 데이터셋 관측 채널 추가. servo 의 상태 추정 개선 |
| `effort` | **접촉 판정** — 과제가 Peg-in-Hole 이라(§0.2) 접촉 시점 라벨링에 직접 쓴다 |

벤더 요청 항목으로 추가한다 — **비용이 낮고 이득이 크다.**

## 9. 재현 절차

### 9.1 전제 — 도메인과 RMW 를 맞춘다

시뮬레이터 브리지(`ros_tcp_endpoint`)와 **반드시 같은 값**이어야 한다. 어긋나면
`readiness_gate` 가 조용히 타임아웃될 뿐 원인이 로그에 드러나지 않는다.

```bash
ros2_env humble          # ROS_DOMAIN_ID=31, RMW_IMPLEMENTATION=rmw_fastrtps_cpp
```

워크스페이스는 fastdds 로 통일돼 있으므로 맞춰야 할 쪽은 시뮬레이터다.
2차 측정 시점의 브리지는 `ROS_DOMAIN_ID=31` / `rmw_fastrtps_cpp` 로 떠 있었다.

확인:

```bash
ros2 topic info /output/panda_joint      # Publisher count 가 1 이어야 한다
```

### 9.2 스택 기동

```bash
./scripts/functionbay/run_panda_functionbay.sh
```

### 9.3 진단 — 반드시 이 순서로

```bash
# 1) 시뮬레이터가 명령에 반응하는가 (가장 먼저 — 여기서 갈린다)
./scripts/functionbay/fb_raw.py named  0.30 4.0
./scripts/functionbay/fb_raw.py noname 0.30 4.0

# 2) 정착 오차 — 현재 자세를 그대로 명령해 중력 처짐을 잰다
./scripts/functionbay/fb_hold.py 15

# 3) 정규 경로 + 추종 성능 (측정기를 먼저 띄우고 명령을 낸다)
./scripts/functionbay/fb_probe.py 30 /tmp/probe.json &
./scripts/functionbay/fb_move.py named extended 50.0 /tmp/start.json

# 4) 자세 복구 (자기충돌이나 이상 자세에 빠졌을 때)
./scripts/functionbay/fb_recover.py 5.0
```

`fb_probe.py` 를 **별도 프로세스**로 돌리는 것이 중요하다. 같은 Node 를 두 곳에서
spin 하면 `MoveGroupClient` 의 동기 메서드와 충돌한다
([MoveGroupClient_UserGuide §14.2](../moveit/MoveGroupClient_UserGuide.md)).

### 9.4 수집 계층 얹기

```bash
ros2 launch rdfp rdfp_collect.launch.py arm_cmd_source:=joint_state
```

`/target_joint_cmds` 로 49.9 Hz 통과가 **가짜 시뮬레이터로** 확인됐다
([functionbay_backend_design.md §7.1](functionbay_backend_design.md)).
실제 시뮬레이터로는 미확인 — §8 우선순위 8번.

## 10. 작업 중 실제로 당한 함정

### 10.1 정지한 값을 "죽었다"로 읽지 않는다

§2.3. 위치 제어 팔은 목표를 유지하면 값이 고정된다. 정지한 장면을 그리는 카메라도
프레임 해시가 같다. **자극을 준 뒤 반응을 보는 것이 유일하게 신뢰할 수 있는 판정**이다.

### 10.2 처진 값을 다시 명령하면 누적된다

§3.1 · §4. 진단 스크립트가 "현재 자세를 읽어 그대로 명령"하는 패턴을 쓰면 호출할
때마다 팔이 더 처진다. 절대 목표를 주거나, 처짐을 감안해 보정한다.

### 10.3 시뮬레이터가 "살아 있는데 명령만 안 먹는" 상태로 빠질 수 있다

§2.2. **트리거는 아직 모른다.** 상태 보고는 계속 나오므로 프로세스·토픽·연결만
봐서는 정상으로 보이고, `fb_recover.py` 로도 빠져나오지 못해 **Unity 재시작이
필요하다.**

> **다만 과거 사례 일부는 오진이었다**(§10.4). 판정은 반드시 고친 `fb_raw.py`
> (7관절 · 양방향)로 한다.

진단 스크립트는 발행 주기를 `0.02 s`(50 Hz)로 **명시적으로 고정**한다. 고착 예방
목적은 아니고(고율 발행은 트리거가 아님이 확인됐다) 시뮬레이터 수신 주기에 맞춰
결정적으로 동작시키기 위해서다. `rclpy.spin_once(timeout_sec=...)` 를 발행 주기로
삼으면 루프가 훨씬 빨리 돌아 의도치 않게 수백 Hz 가 되므로 쓰지 않는다.

### 10.4 진단 도구가 관절 하나·방향 하나에 의존하면 오진한다

§2.2 · §4.1. 옛 `fb_raw.py` 는 **joint7 을 + 방향으로만** 밀어 "시뮬레이터가
반응하는가" 를 판정했다. 그런데 그 관절의 실효 상한이 URDF 보다 훨씬 안쪽이라,
거기 걸리면 **멀쩡한 시뮬레이터를 "전체 무반응" 으로 판정**했다.

**"반응 없음" 은 여러 축·양방향으로 확인하기 전까지 결론이 아니다.** 현재
`fb_raw.py` 는 7관절을 각각 여유 있는 방향으로 시험한다.

### 10.5 `pkill -f` 는 자기 자신을 죽인다

패턴 문자열이 그 명령을 실행하는 셸의 cmdline 에 그대로 들어가므로 자기 매칭된다.

```bash
pkill -f 'ros2 launch robot_control panda_functionbay'   # 이 명령을 실행한 셸도 죽는다
```

PID 로 지목하거나 프로세스 그룹(`kill -- -PGID`)을 쓴다.

### 10.6 launch 부모가 죽으면 자식 노드가 고아로 남는다

`ros2 launch` 프로세스만 죽으면 `move_group` · `rviz2` · `robot_state_publisher` 등이
그대로 살아남아 도메인에 계속 붙어 있다. 다음 기동 때 조용히 간섭한다.

정리 후에는 반드시 확인한다:

```bash
ros2 node list --no-daemon      # 시뮬레이터 브리지만 남아야 한다
```

### 10.7 `OnProcessExit` 는 실패 종료에도 발동한다

`readiness_gate` 가 타임아웃(exit 1)해도 그냥 엮으면 `move_group` 이 올라온다.
`_chain_or_shutdown` 으로 종료 코드를 보게 되어 있다 —
[panda_functionbay.launch.py](../../src/robot_control/launch/panda_functionbay.launch.py)
의 `startup_handler`. 구조를 바꿀 때 이 부분을 유지한다.
