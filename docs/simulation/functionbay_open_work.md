# 펑션베이 백엔드 — 남은 작업 (인수인계)

> **측정** 2026-08-18 (1차) · **2026-08-28 (2차)** · **대상** [functionbay_backend_design.md](functionbay_backend_design.md)
>
> 실제 시뮬레이터(Unity + `ros_tcp_endpoint`)에 붙여 검증한 결과와, 거기서 새로
> 드러난 사실·미결 항목을 모아 둔 문서다. **설계 문서를 아직 고치지 않은 이유와
> 무엇을 어떻게 고쳐야 하는지**가 §7 에 있다.

## 0. 한 줄 요약

**제어 계층은 명령 경로까지 전 구간 검증됐다.** 1차 측정에서 최우선 블로커였던
"시뮬레이터가 명령에 반응하지 않는다"는 2차 측정에서 **해소됐다**(§2).

남은 실질 과제는 성격이 바뀌었다 — 이제는 **연동이 되느냐**가 아니라 **연동의 품질**이다.

- **중력 처짐** — 명령(action)과 실제(observation)가 자세에 따라 계통적으로 어긋난다 (§3).
  원인은 **제어기 강성이 낮은 것**이고, 아래 "응답이 느리다"와 뿌리가 같다 (§3.3)
- **자기충돌** — 시뮬레이터가 막지 않아 MoveIt 으로 복구 불가능한 자세에 빠질 수 있다 (§4)
- **servo(twist) 경로 무동작** — 출력에 소비자가 없고, 단순 중계 브리지는 발산한다 (§5)
- **시뮬레이터 응답이 느리다** — dead time 약 25~34 ms + 시정수 약 133 ms. 네트워크 탓이 아니다 (§6)

측정했다. 1차는 도메인 31 / `rmw_cyclonedds_cpp`, 2차는 도메인 31 /
`rmw_fastrtps_cpp` (워크스페이스 전체가 fastdds 로 통일된 뒤).

## 2. 해소된 블로커 — "시뮬레이터가 명령에 반응하지 않는다"

1차 측정에서는 명령 41개가 `/input/panda_joint` 에 정확히 도달했는데도 관절이
**0.0 rad** 움직였다. 손으로 만든 `JointState` 를 4초간 356개 밀어도(이름 유무 양쪽)
동일했다. 2차 측정에서는 같은 절차가 **정상 동작**한다.

### 2.1 원인이 아니었던 것

원인을 좁히는 데 시간을 쓴 항목이라 기록해 둔다.

| 의심했던 것 | 판정 |
|---|---|
| RMW 불일치 | **아니다.** 1차 때도 양쪽 다 `rmw_cyclonedds_cpp` 였고 프로브가 명령 도달을 확인했다 |
| `name` 필드 유무 | **아니다.** 채운 쪽·비운 쪽 모두 무반응이었다 |
| QoS 비호환 | **아니다.** 양쪽 RELIABLE / VOLATILE 로 확인 |
| 우리 스택 | **아니다.** 클라이언트를 배제한 원시 발행도 무반응이었다 |

### 2.2 원인 — 미상 (유력 가설 2개를 실험으로 배제)

**2차 측정 중 같은 증상이 재현됐다.** 브리지는 멀쩡한데(상태 보고 49.9 Hz, TCP
`ESTAB`, 노드 8개 정상) 명령만 전혀 먹지 않는다.

고착은 **약 500 Hz 로 명령을 밀어 넣던 실행 중** 발생했다. 그래서 "수신 주기(50 Hz)
초과 발행"을 트리거로 의심했으나, 재시작 후 **의도적으로 재현을 시도해 배제했다.**

| 시험 조건 | 결과 |
|---|---|
| 100 Hz × 5초 | 정상 |
| 200 Hz × 5초 | 정상 |
| 500 Hz × 5초 | 정상 |
| **500 Hz × 15초 + 목표 12회 전환** (실패 당시와 같은 패턴) | **정상** |
| **관절 한계 초과 명령** (joint4 → -3.36, URDF 한계 -3.1416) | **정상** |

다섯 조건 모두 고착을 재현하지 못했다. **발행률도, 한계 초과 명령도 트리거가
아니다.** 시뮬레이터는 관절 한계를 강제하지 않으며(한계를 넘겨도 그냥 간다) 고율
발행도 견딘다.

실패 세션에서는 고착 직전까지 servo 브리지 실험으로 **NaN 이 여러 차례 발생**했고
(§5.2), 그때마다 복구했다. 누적된 상태가 원인일 가능성이 남지만 확인하지 못했다.

**트리거는 미상이다.** 재현 조건을 모르므로 예방 규칙도 세울 수 없다 — 대신 아래
특징으로 빨리 알아채고 복구하는 것이 현재로서 최선이다.

고착의 특징:

- 상태 보고는 계속 나온다 — **살아 있는지 여부로는 판정할 수 없다**
- 50 Hz 램프(`fb_recover.py`)로도 빠져나오지 못한다 → **Unity 재시작이 필요하다**
- 보고 주기 지터가 커진다 (정상 13~23 ms → 고착 시 8.8~32.8 ms) — 참고 지표

1차 측정 당시의 정황도 함께 남긴다. 그때는 아래가 관측됐다.

- `/output/endeffector` 가 전부 0.0 으로 고정 발행 (2차에서는 **토픽 자체가 없다**)
- `/UnityEndpoint` 노드가 **중복 이름으로 2개** (2차에서는 1개)

같은 증상이 재발하면 §9.3 의 `fb_raw.py` 를 가장 먼저 돌려 우리 쪽/시뮬레이터 쪽을
가른다.

### 2.3 "장면이 정지했다"는 오독이었다

1차 때 관측한 세 가지를 모두 시뮬레이터 고장의 근거로 삼았는데, 셋 다 정상이었다.

| 1차 관측 | 실제 |
|---|---|
| 관절값이 8초간 비트 단위 고정 | **위치 제어 팔이 목표를 유지하는 정상 동작.** 당시 자세는 `ready` 를 명령한 뒤 처진 자리였다 — 2차에서 `ready` 를 명령해 도달한 값과 소수점 3자리까지 같다 |
| `/camera_image` 3프레임 md5 동일 | **정지 화면이 아니라 정지한 장면.** 팔이 움직이는 동안 12샘플 중 6개가 전부 다른 해시였다 (§3.3) |
| `/output/endeffector` 가 0 | 이건 실제 이상이었다. 2차에서는 토픽이 사라졌다 |

**교훈: 정지한 값만으로 "죽었다"고 판정하지 않는다.** 자극을 준 뒤 반응을 본다.

## 3. 중력 처짐 — 명령과 실제가 계통적으로 어긋난다

**이 백엔드에서 가장 중요한 특성이다.** 시뮬레이터는 중력 보상이 없는 유한 강성
위치 제어로 동작한다.

### 3.1 증상 — 현재 자세를 그대로 명령해도 더 흘러내린다

`fb_raw.py named 0.0 4.0`(현재 자세를 그대로 목표로 주기)을 반복하면 계속 흘러간다.

| | joint2 | joint4 | joint6 | joint1 · joint7 |
|---|---|---|---|---|
| 시작 | 0.0506 | 0.0337 | -0.0151 | 고정 |
| 1회 후 | 0.0858 | 0.0485 | -0.0225 | 고정 |
| 2회 후 | 0.1308 | 0.0605 | -0.0296 | 고정 |

**흘러가는 것은 중력 토크를 받는 관절(2~6)뿐이고, 중력 중립축인 joint1 · joint7 은
정확히 고정된다.** 처진 값을 다시 목표로 주기 때문에 누적된 것이다.

### 3.2 무한 표류가 아니라 정상상태 오차다

고정 목표를 15초간 계속 명령하며 추적했다 (`fb_hold.py`).

```
 t(s)        j2        j4        j6      j2 오차
  0.0    0.1308    0.0605   -0.0296     +0.0000
  1.5    0.1892    0.0681   -0.0364     +0.0584
  3.0    0.1890    0.0682   -0.0364     +0.0581
  ...      (13.5초 동안 소수점 4자리까지 완전히 평평)
 15.0    0.1890    0.0682   -0.0364     +0.0581
```

**1.5초 안에 수렴하고 그 뒤로는 미동도 없다.** 발산이 아니라 정상상태 오차다.

### 3.3 원인 — 제어기 강성이 낮다

**제어기 강성(stiffness)** 은 위치 오차 1 rad 당 관절이 내는 토크다. 스프링 상수와
같은 개념이며, 여기서는 `K_p` 로 쓴다.

```
토크 = K_p × (목표 − 실제)
```

중력이 팔을 끌어내리면 제어기가 밀어 올리고, **두 힘이 같아지는 지점에서 멈춘다.**

```
K_p × 오차 = 중력 토크        →        오차 = 중력 토크 / K_p
```

그래서 오차가 0 이 될 수 없다. **버그가 아니라 낮은 강성의 정상적인 귀결이다.**

#### 실측 — 오차가 중력 부하에 비례한다

자세를 바꿔 가며(= 중력 부하를 바꿔 가며) 정착 오차를 쟀다.

| 자세 | joint2 오차 | joint4 오차 | **joint1** | **joint7** |
|---|---|---|---|---|
| `ready` (접힘) | +0.0122 | -0.0983 | **+0.0000** | **-0.0000** |
| 중간 | +0.0809 | -0.0968 | **-0.0000** | **-0.0000** |
| 펴짐 (수평쪽) | **+0.1428** | -0.0840 | **-0.0000** | **+0.0001** |

두 가지가 위 식을 그대로 보여준다.

1. **joint2 오차가 팔을 펼수록 12배로 커진다** (0.0122 → 0.1428). 팔이 펴지면
   어깨(joint2)의 모멘트 암이 길어져 중력 토크가 커진다. `K_p` 는 그대로인데
   분자만 커진 것이다.
2. **joint1 · joint7 은 세 자세 모두 정확히 0.0000 이다.** 회전축이 수직이라 중력
   토크가 애초에 0 이다. 분자가 0 이니 `K_p` 와 무관하게 오차도 0 이다.

`ready` 자세의 관절별 오차 전체는 다음과 같다.

| joint1 | joint2 | joint3 | joint4 | joint5 | joint6 | joint7 |
|---|---|---|---|---|---|---|
| **-0.0000** | +0.0122 | +0.0052 | **-0.0983** | -0.0069 | -0.0074 | **-0.0000** |

접힌 자세에서는 팔꿈치(joint4)가 **-0.0983 rad ≈ 5.6°** 로 최악이다.

#### 지연과 같은 뿌리다

위치 제어 루프의 시정수는 대략 `τ ≈ 감쇠 / 강성` 이다. 강성이 낮으면 되돌리는 힘이
약해 느리게 접근한다 — §6.1 에서 잰 **τ = 133 ms** 가 그것이다.

**따라서 강성 하나가 세 증상의 공통 원인이다** — 이 절의 처짐, §6 의 느린 응답,
그리고 §5 의 servo 발산(정상상태 오차가 루프를 계속 밀어내는 것).

### 3.4 동작 중 추종 성능

`fb_probe.py` 로 명령/실제를 동시 기록해 지연을 스윕한 결과다.

| 항목 | 값 |
|---|---|
| 추종 지연 (최적 정합 lag) | **0.15 s** — 성분 분해는 §6.1 |
| 최대 오차 (지연 보정 후) | 0.0851 rad |
| 평균 오차 (지연 보정 후) | 0.0549 rad |
| 최대 오차 (지연 보정 없이) | **0.3549 rad** |
| 정착 오차 | 0.0212 rad |

### 3.5 학습 데이터에 주는 영향

**`/target_joint_cmds`(action)와 `/joint_states`(observation)가 자세에 따라 계통적으로
어긋난다.** 오차가 무작위가 아니라 중력 토크에 비례하므로, 학습 모델이 이 편향을
로봇 동특성으로 잘못 학습할 수 있다. 대응 후보:

1. 시뮬레이터 쪽에 **중력 보상**을 요청한다 (근본 해결 — §3.6).
2. action 을 명령값이 아니라 **다음 스텝의 실제 관절값**으로 기록한다 (설계 변경).
3. 현 상태로 수집하되 데이터셋에 이 편향을 명시한다 (임시).

**결정이 필요한 항목이다** — §8 우선순위 1번.

### 3.6 시뮬레이터 쪽 개선 — 강성 상향보다 중력 보상이 낫다

| 방법 | 처짐 | τ | 위험 |
|---|---|---|---|
| `K_p` 상향 | 감소 | 단축 | 너무 올리면 **진동·발산**, 접촉 시 딱딱해짐 |
| **중력 보상 (피드포워드)** | **원리적으로 제거** | 변화 없음 | 없음 — 모델만 있으면 된다 |

중력 보상은 오차가 생기기를 기다리지 않고 **중력 토크를 미리 계산해 더해 주는**
방식이다. 오차 없이도 팔이 제자리에 있으므로 처짐이 사라진다.

벤더 요청 순서 제안:

1. **중력 보상** — 처짐 제거. 부작용이 없다
2. **`K_p` 적정 상향** — τ 단축. 진동하지 않는 선까지

## 4. 자기충돌 — MoveIt 으로 복구할 수 없는 자세

**시뮬레이터는 자기충돌을 막지 않는다.** §3.1 처럼 처진 값을 반복 명령하면 누적되어
Panda 모델에서 자기충돌인 자세에 도달한다. 실제로 그렇게 됐다.

```
/check_state_validity → valid = False
  contacts:  panda_hand ↔ panda_link5
             panda_leftfinger ↔ panda_link5
             panda_link5 ↔ panda_link7
```

그 상태에서 MoveIt 계획은 실패한다.

```
fix_start_state_bounds: Starting state is just outside bounds (joint 'panda_joint4')
fix_start_state_collision: Unable to find a valid state nearby the start state
OMPL: Skipping invalid start state (invalid state)
RRTConnect: Motion planning start tree could not be initialized!
→ RuntimeError: Planning to named target "ready" failed with code: -26
```

### 복구 방법 — MoveIt 을 우회한다

계획이 안 되므로 `MoveGroupClient` 로는 빠져나올 수 없다. **원시 `JointState` 를
직접 램프로 밀어** 정상 자세로 되돌린다. 시뮬레이터는 내부 보간을 하지 않으므로
큰 도약을 한 번에 주지 않고 50 Hz 로 선형 보간한다.

```bash
./scripts/functionbay/fb_recover.py 5.0      # 현재 → ready 로 5초 램프 후 정착
```

복구 후 `valid=True` 를 확인했고, 이어서 `extended` 로의 계획·스트리밍이 정상
동작했다.

## 5. servo(twist) 경로 — 무동작이며 단순 브리지로는 안 된다

`/servo_node/delta_twist_cmds` 에 트위스트를 넣어도 **로봇은 움직이지 않는다.**
그리고 **단순 중계 브리지로는 해결되지 않는다** — 실측으로 확인했다.

### 5.1 servo 는 정상이다 — 출력을 받을 주체가 없을 뿐

`start_servo` 호출 후 5초간 트위스트를 넣은 결과:

| 단계 | 결과 |
|---|---|
| `start_servo` | **성공** |
| 트위스트 발행 | 531개 |
| servo 출력 → `/panda_arm_controller/joint_trajectory` | **148개 정상 발행** |
| 시뮬레이터 입력 `/input/panda_joint` | **0개** |
| 관절 변화 | **0.00000 rad** |

```
/panda_arm_controller/joint_trajectory   Publisher 1 (servo_node)   Subscription 0
```

`panda_mock` 에서는 JTC 컨트롤러가 이 토픽을 받지만 이 스택에는 ros2_control 이 없다.

servo 출력의 내용은 시뮬레이터가 필요한 것과 **이미 같다.** 타입만 다르다.

```
joint_names : [panda_joint1 … panda_joint7]     ← 이름 일치
points      : 1                                  ← 절대 위치 1점
time_from_start : 0.034                          ← 약 29 Hz
```

### 5.2 단순 중계 브리지 — 크기를 줄여도 실패한다

`JointTrajectory.points[0]` → `JointState` 로 되싣는 20줄짜리 브리지로 시험했다.

| 조건 | 브리지 전달 | 실제 이동 | 결말 | 실패까지 |
|---|---|---|---|---|
| 0.05 m/s, +Z | 41개 | — | **시뮬레이터 NaN** | ~1.4초 |
| 0.005 m/s, +Z | 37개 | 0.660 rad | servo NaN | ~1.3초 |
| 0.005 m/s, +X | 38개 | 0.680 rad | servo NaN | ~1.3초 |

**트위스트를 1/10로 줄여도 실패까지 걸린 시간이 거의 같고(1.4초 → 1.3초), 방향을
바꿔도 같다.** 크기 문제가 아니라는 강한 증거다.

얻은 것도 있다 — 작은 트위스트에서는 **팔이 실제로 움직였고**(0.66 rad), 명령과
실제의 괴리도 0.0285 rad 로 작게 유지됐다. 브리지 자체는 성립한다.

### 5.3 원인 — 루프를 닫는 순간 발산한다

브리지 유무로 servo 출력의 사이클별 증분을 비교했다.

**브리지 OFF (루프 열림)** — 118 사이클 내내 안정

```
  #   사이클 증분     명령-실제 j4
  1     0.00011        +0.00012
  5     0.00000        +0.00013
117     0.00000        +0.00013      ← 끝까지 일정
```

servo 는 누적하지 않는다. 정지한 피드백에서 일정한 작은 오프셋만 낸다.

**브리지 ON (루프 닫힘)** — 3 사이클 만에 발산

```
  #   사이클 증분     명령-실제 j4
  1     0.00011        +0.00012
  2     0.00188        +0.00296     ← 17배
  3     0.02088        +0.02863     ← 11배 (누적 190배)
  4     0.02693        +0.01204     ← 진동 시작
  5     0.00952        +0.00252
 ...   nan
```

**증분이 3 사이클 만에 약 190배로 폭증**한 뒤 진동하다 발산한다. 트위스트 입력이
아니라 루프 구조가 만드는 불안정이다.

구조상 그럴 만하다 — servo 는 34 ms 주기(29 Hz)로 도는데, 시뮬레이터는 **dead time
34 ms(약 1 사이클) + 시정수 133 ms(약 4 사이클)** 로 응답한다(§6.1). 순수 지연과
1차 지연이 겹쳐 위상이 크게 밀리는데 루프에 감쇠가 없다. 여기에 중력 처짐(§3)으로
목표에 영원히 도달하지 못하는 정상상태 오차까지 더해진다.

`joint_limit_margin` 이 0.1 로 설정돼 있는데도 joint4 가 한계(-3.1416)에서 0.027
앞까지 갔다 — **발산 속도가 servo 의 한계 보호보다 빨랐다.**

### 5.4 브리지를 만든다면 필요한 것

- **증분 클램프 / 속도 제한** — 사이클당 관절 변화 상한
- **지연 보상** — 150 ms 를 감안한 예측, 또는 servo 주기 조정
- **NaN · 한계 가드 (필수)** — 가드 없는 첫 시도에서 NaN 이 `/joint_states` → TF
  트리 전체로 번져 `move_group` · `ee_pose_node` 가 마비됐고, `start_servo` 재호출도
  응답하지 않아 스택을 재시작해야 했다. 가드를 넣은 뒤로는 시뮬레이터가 NaN 에
  빠지지 않았다.

**결정이 필요하다** — 위 세 가지를 갖춘 브리지를 만들지, 아니면 이 백엔드에서는
twist 경로를 지원하지 않는다고 못 박을지. §8 우선순위 5번.

> NaN 상태에서는 `fb_recover.py` 도 쓸 수 없다 (현재값을 읽어 보간하는데 그 값이
> NaN 이다). 현재값을 읽지 않고 절대 목표를 직접 반복 발행하면 탈출된다.

## 6. 시간 특성 — dead time · 시정수 · 시계

시뮬레이터가 명령에 **얼마나 늦게, 어떤 모양으로** 반응하는지다. §5 의 servo 발산과
§3 의 중력 처짐이 모두 여기서 나온다.

### 6.1 dead time 과 시정수 — 용어와 실측

두 가지를 구분해야 처방이 갈린다.

| 용어 | 뜻 |
|---|---|
| **dead time** (순수 지연·낭비 시간) | 명령을 준 순간부터 **어떤 반응이든 처음 나타나기까지**의 시간. 그동안 시스템은 완전히 무반응이다 |
| **시정수 τ** | 반응이 시작된 뒤 목표의 **63%** 에 이르기까지의 시간. 반응의 '굼뜬 정도' |

**제어에서 훨씬 나쁜 쪽은 dead time 이다.** 그 구간에는 정보가 아예 없어서 되먹임으로
보상할 방법이 없고, 제어 주기 대비 dead time 이 길수록 루프의 위상 여유가 줄어
발산한다. 반면 시정수는 느릴 뿐 예측 가능해서 설계로 흡수할 수 있다.

`panda_joint7`(중력 중립축이라 처짐이 섞이지 않는다)에 계단 명령을 주고 측정했다.

계단 ±0.04 rad 을 방향을 번갈아 **8회** 주고 잰 값이다 (발행률은 시뮬레이터 수신
주기와 같은 50 Hz — 그 이상으로 밀면 §2.2 의 고착이 생긴다).

| 성분 | 평균 | 중앙 | 최소 | 최대 | 범위폭 | servo 주기(34 ms) 환산 |
|---|---|---|---|---|---|---|
| **dead time** | **33.7 ms** | 27.9 | 25.1 | 49.1 | 24.0 | 약 1 사이클 |
| **시정수 τ** | **132.6 ms** | 126.0 | 120.5 | 147.8 | 27.3 | 약 4 사이클 |

**관측 주기가 20 ms 라 1회 측정에는 그만큼 양자화 오차가 실린다.** dead time 의
범위폭 24.0 ms 가 보고 주기와 거의 같은 것이 그 증거이며, 실제 바닥은 **약 25 ms** 로
보는 편이 맞다. 8회 모두 목표에 정확히 도달했다(오차 < 0.001 rad).

§3.4 에서 "추종 지연 0.15 s" 로 잰 값은 명령/실제 궤적을 가장 잘 겹치게 하는
lag 이라, **실제로는 이 두 성분이 섞인 결과**다. 지배적인 것은 시정수 쪽이다.

### 6.2 네트워크는 원인이 아니다 — 같은 머신으로 옮겨도 소용없다

시뮬레이터(Unity)와 로봇 스택은 서로 다른 머신에서 돈다. 다만 `ros_tcp_endpoint`
는 **이미 로봇 스택과 같은 머신**에 있어, 네트워크를 건너는 구간은 Unity ↔ 엔드포인트
하나뿐이다.

```
Unity (192.168.0.7)  --TCP-->  ros_tcp_endpoint (192.168.0.134, 스택과 동일 머신)  --DDS-->  스택
```

| 구간 | 실측 |
|---|---|
| 네트워크 왕복 (ping ×20) | **0.303 ms** (min 0.230 / max 0.399 / mdev 0.037, 손실 0%) |
| dead time 전체 | 33.7 ms (평균) |
| 네트워크가 차지하는 비율 | **0.9%** |

**같은 머신으로 옮겨 아낄 수 있는 것은 0.3 ms** — 전체 응답(약 180 ms)의 0.2% 다.
dead time 중 나머지 ~33 ms 는 Unity 의 프레임 파이프라인(수신 → 적용 → 물리 →
발행)으로 **추정**된다 — 뺄셈으로 얻은 값이고 `ros_tcp_endpoint` 자체의 기여분은
따로 재지 않았다. TCP 소켓의 커널 RTT 추정치가 12.7 ms 인 것도 Unity 가 프레임 단위로
소켓을 처리한다는 정황이다.

**지연을 줄이려면 손댈 곳은 시뮬레이터 쪽이다.** 그중에서도 **제어기 강성(τ 133 ms,
전체의 약 80%)이 우선**이며, 이쪽을 고치면 §3 의 중력 처짐도 함께 해소된다 —
구체적인 방법과 우선순위는 §3.6 을 본다. 프레임 파이프라인(~33 ms)은 그 다음이다.
머신 배치는 무관하다.

### 6.3 sim time 은 제공되지 않으며, servo 에는 도움이 안 된다

`/clock` 토픽이 없고 `use_sim_time` 은 기본값 `false` 다. 모든 타임스탬프가 호스트
벽시계 기준이다. 이 워크스페이스에서 sim time 을 쓰는 백엔드는 Gazebo 뿐이다.

배속은 문제가 없다 — 20초 1000샘플 측정:

```
벽시계 경과 20.001s   스탬프 경과 20.000s
진행 배속 = 0.99993        ← 사실상 정확히 실시간
```

**따라서 sim time 을 도입해도 servo 안정성은 나아지지 않는다.**

- sim time 의 본래 목적은 시뮬레이터가 실시간이 **아닐 때** 벽시계와 분리하는 것인데,
  여기서는 이미 1.0 배속이다.
- 발산의 원인은 dead time 과 시정수(§6.1)이고, `/clock` 은 시간의 **단위**를 바꿀 뿐
  왕복 지연을 줄이지 않는다.
- servo 의 증분 계산은 메시지 스탬프가 아니라 `publish_period` 파라미터로 한다.

sim time 이 servo 에 의미를 갖는 경우는 시뮬레이터가 **lockstep(스텝 후 대기)** 을
지원할 때뿐이다. 그러면 dead time 이 결정적으로 고정되어 루프 설계가 가능해진다.
벤더에 요청한다면 "`/clock` 발행"과 "lockstep 지원"을 구분해서 말해야 한다.

### 6.4 시계 오프셋 2.22초 — 데이터셋 정합 문제

시뮬레이터가 찍는 스탬프가 호스트 시각보다 **일정하게 뒤처져 있다.**

| 토픽 | 스탬프 − 수신시각 | 변동폭 |
|---|---|---|
| `/output/panda_joint` | **-2.2207 s** | 0.0171 s |
| `/joint_states` (fusion 통과 후) | **-2.2283 s** | 0.0176 s |

드리프트가 아니라 고정 오프셋이고 변동폭이 작다 — **두 머신의 시계 차이**로 보인다
(스탬핑 버그가 아니다). fusion 은 기본값 `stamp_source=auto` 라 입력 스탬프를 그대로
통과시키므로, 이 오프셋이 MoveIt 까지 전달된다. `move_group` 의
`Failed to fetch current robot state` 경고와 무관하지 않아 보인다.

데이터셋에는 직접적인 문제다 — 에피소드 분할과 토픽 간 정렬이 `header.stamp` 기준인데,
시뮬레이터가 찍은 스탬프와 우리 ROS 노드가 찍은 스탬프가 2.2초 어긋난 채로 섞인다.

**대응 두 가지.**

1. **양쪽 머신에 NTP/chrony** — 근본 해결. 스탬프의 의미(그 자세였던 시각)가 보존된다.
2. **`stamp_source:=now`** — fusion 에서 재스탬프. 실측 확인:

   | `stamp_source` | `/joint_states` 오프셋 |
   |---|---|
   | `auto` (기본) | -2.2283 s |
   | **`now`** | **-0.0009 s** |

   단, `now` 는 *시뮬레이터가 그 자세였던 시각*이 아니라 *우리가 받은 시각*을 찍으므로
   dead time(약 34 ms)이 스탬프에 흡수된다. 1번이 가능하면 1번이 낫다.

### 6.5 카메라 — 타임스탬프가 없다

```
header:
  stamp:  {sec: 0, nanosec: 0}      ← 미설정
  frame_id: camera_link
height: 480   width: 640   encoding: rgba8
```

20초간 192프레임을 받았는데 스탬프 경과가 **0.000초**였다. 이미지 프레임을 시간축에
놓을 수 없다는 뜻이라, `image_frames` 처럼 타임스탬프로 정렬하는 경로가 그대로 깨진다.
**시뮬레이터가 채워 줘야 한다.**

인코딩이 `rgba8` 인 것도 확인됐다 — 대부분의 파이프라인이 `rgb8`/`bgr8` 을 전제하므로
변환이 필요하다.

## 7. 설계 문서 정정 대기 항목

아래는 **실측으로 확인됐으나 [functionbay_backend_design.md](functionbay_backend_design.md)
에 아직 반영하지 않은** 내용이다.

> 이 절 안의 `§` 번호는 **설계 문서 쪽 절 번호**다 (이 문서의 절이 아니다).

### ① 설계 문서 §2.1 — 시뮬레이터는 `name` 을 채운다

현재 문서는 "`name` 이 비어 있다 — 순서가 계약이다"를 **이 백엔드의 가장 큰
위험**으로 서술한다. 실측은 반대다:

```
name: [panda_joint1, panda_joint2, ..., panda_joint7]
```

`joint_state_fusion` 이 `input provides joint names; using them as-is` 로그를 내며
그 경로를 탔다(1·2차 모두). 코드는 양쪽 다 처리하므로 동작에는 문제가 없지만,
**위험도 서술이 현실과 다르다.** 순서 계약은 "현재 위험"이 아니라 "이름이 빠질
경우의 대비책"으로 격하해서 다시 쓴다.

### ② servo 출력에 소비자가 없다 (신규 항목)

**`servo_node` 는 떠 있어도 무동작**이며, twist 기반 teleop 이나
`replay_arm_path:=ee_twist` 는 이 백엔드에서 팔을 움직이지 못한다. 나아가
**단순 중계 브리지로도 해결되지 않는다**(루프가 발산한다).

실측과 근거는 §5 에 있다. 설계 문서 §5.2(미충족 — 의도적)에 추가한다.

### ③ 설계 문서 §4.2 — `mode='auto'` 오탐의 조건을 정확히

현재 문서는 "auto 는 `/panda_arm_controller/commands` 를 보므로 오판한다"까지만
적혀 있다. 실제 판별 로직은 **대상 토픽의 publisher 또는 subscriber 존재**를 본다
([move_group_factory.py](../../src/robot_control/robot_control/moveit/move_group_factory.py)
의 `detect_controller_mode`). 따라서:

| 호출 | 판별 | 결과 |
|---|---|---|
| `create_move_group_client(node)` | `/panda_arm_controller/commands` 없음 → **JTC** | 실행 액션 서버 0개 → 조용히 멈춤 |
| `create_move_group_client(node, arm_command_topic='/input/panda_joint')` | Unity 가 구독 중 → **JGPC** | 정상 |

즉 `arm_command_topic` 을 함께 넘기면 auto 도 맞게 판별한다. 다만 **시뮬레이터가
꺼져 있으면 구독자가 사라져 다시 JTC 로 떨어지므로**, `mode='jgpc'` 명시 권고는
그대로 유지한다.

JTC 오탐 시의 실제 상태:

```
/panda_arm_controller/follow_joint_trajectory   Action servers: 0, clients: 1
```

`moveit_simple_controller_manager` 가 클라이언트로 붙어 있으나 서버가 없다.
RViz 의 "Plan & Execute" 버튼도 같은 이유로 동작하지 않는다.

### ④ 그리퍼 출력 — 단위 추정을 철회한다

1차 관측만 보고 "degree 로 보인다"고 적었으나, 2차에서 값의 구조가 달라졌다.

| | 값 |
|---|---|
| 1차 | `[0.000143, ~0, **-14.34**, -0.000140, ~0, **13.97**]` |
| 2차 | `[**0.7198**, ~0, -0.0037, **-0.7198**, ~0, 0.0031]` |

큰 성분이 **index 2·5 → index 0·3 으로 옮겨갔다.** 3개씩 두 묶음(손가락 2개 ×
3성분)인 것은 맞아 보이지만, **단위도 성분의 의미도 확정할 수 없다.** 벤더 확인이
필요하다. 설계 문서 §6(그리퍼 보류)에 "단위 미확정"으로 적는다.

### ⑤ 카메라 — 실시간 렌더링 확인됨

`/camera_image` 는 `sensor_msgs/Image`, publisher 1, **약 9.6 Hz**.

- **정지 화면이 아니다.** 팔이 정지한 동안 6샘플은 같은 해시였지만, 움직이는 동안
  12샘플 중 6개가 전부 다른 해시였다.
- **`camera_info` 에 해당하는 토픽은 없다.** remap 하면 영상은 흐르지만
  `camera_info` 를 요구하는 경로는 비게 된다.

- **`header.stamp` 이 0 이고 인코딩이 `rgba8`** — §6.5.

"미실측"에서 "**스트리밍 확인 · `camera_info` 미제공 · `stamp` 미설정 · `rgba8`**"
으로 고친다.

## 9. 재현 절차

### 9.1 전제 — 도메인과 RMW 를 맞춘다

시뮬레이터 브리지(`ros_tcp_endpoint`)와 **반드시 같은 값**이어야 한다. 어긋나면
`readiness_gate` 가 조용히 타임아웃될 뿐 원인이 로그에 드러나지 않는다.

```bash
ros2_env humble          # ROS_DOMAIN_ID=31, RMW_IMPLEMENTATION=rmw_fastrtps_cpp
```

워크스페이스는 fastdds 로 통일돼 있으므로 맞춰야 할 쪽은 시뮬레이터다.
2차 측정 시점의 브리지는 `ROS_DOMAIN_ID=31` / `rmw_fastrtps_cpp` 로 떠 있었다.

확인:

```bash
ros2 topic info /output/panda_joint      # Publisher count 가 1 이어야 한다
```

### 9.2 스택 기동

```bash
./scripts/functionbay/run_panda_functionbay.sh
```

### 9.3 진단 — 반드시 이 순서로

```bash
# 1) 시뮬레이터가 명령에 반응하는가 (가장 먼저 — 여기서 갈린다)
./scripts/functionbay/fb_raw.py named  0.30 4.0
./scripts/functionbay/fb_raw.py noname 0.30 4.0

# 2) 정착 오차 — 현재 자세를 그대로 명령해 중력 처짐을 잰다
./scripts/functionbay/fb_hold.py 15

# 3) 정규 경로 + 추종 성능 (측정기를 먼저 띄우고 명령을 낸다)
./scripts/functionbay/fb_probe.py 30 /tmp/probe.json &
./scripts/functionbay/fb_move.py named extended 50.0 /tmp/start.json

# 4) 자세 복구 (자기충돌이나 이상 자세에 빠졌을 때)
./scripts/functionbay/fb_recover.py 5.0
```

`fb_probe.py` 를 **별도 프로세스**로 돌리는 것이 중요하다. 같은 Node 를 두 곳에서
spin 하면 `MoveGroupClient` 의 동기 메서드와 충돌한다
([MoveGroupClient_UserGuide §14.2](../moveit/MoveGroupClient_UserGuide.md)).

### 9.4 수집 계층 얹기

```bash
ros2 launch rdfp rdfp_collect.launch.py arm_cmd_source:=joint_state
```

`/target_joint_cmds` 로 49.9 Hz 통과가 **가짜 시뮬레이터로** 확인됐다
([functionbay_backend_design.md §7.1](functionbay_backend_design.md)).
실제 시뮬레이터로는 미확인 — §8 우선순위 8번.

## 10. 작업 중 실제로 당한 함정

### 10.1 정지한 값을 "죽었다"로 읽지 않는다

§2.3. 위치 제어 팔은 목표를 유지하면 값이 고정된다. 정지한 장면을 그리는 카메라도
프레임 해시가 같다. **자극을 준 뒤 반응을 보는 것이 유일하게 신뢰할 수 있는 판정**이다.

### 10.2 처진 값을 다시 명령하면 누적된다

§3.1 · §4. 진단 스크립트가 "현재 자세를 읽어 그대로 명령"하는 패턴을 쓰면 호출할
때마다 팔이 더 처진다. 절대 목표를 주거나, 처짐을 감안해 보정한다.

### 10.3 시뮬레이터가 "살아 있는데 명령만 안 먹는" 상태로 빠질 수 있다

§2.2. **트리거는 아직 모른다.** 상태 보고는 계속 나오므로 프로세스·토픽·연결만
봐서는 정상으로 보이고, `fb_recover.py` 로도 빠져나오지 못해 **Unity 재시작이
필요하다.** 이상하면 `fb_raw.py` 로 반응을 확인하는 것이 유일하게 확실한 판정이다.

진단 스크립트는 발행 주기를 `0.02 s`(50 Hz)로 **명시적으로 고정**한다. 고착 예방
목적은 아니고(고율 발행은 트리거가 아님이 확인됐다) 시뮬레이터 수신 주기에 맞춰
결정적으로 동작시키기 위해서다. `rclpy.spin_once(timeout_sec=...)` 를 발행 주기로
삼으면 루프가 훨씬 빨리 돌아 의도치 않게 수백 Hz 가 되므로 쓰지 않는다.

### 10.4 `pkill -f` 는 자기 자신을 죽인다

패턴 문자열이 그 명령을 실행하는 셸의 cmdline 에 그대로 들어가므로 자기 매칭된다.

```bash
pkill -f 'ros2 launch robot_control panda_functionbay'   # 이 명령을 실행한 셸도 죽는다
```

PID 로 지목하거나 프로세스 그룹(`kill -- -PGID`)을 쓴다.

### 10.5 launch 부모가 죽으면 자식 노드가 고아로 남는다

`ros2 launch` 프로세스만 죽으면 `move_group` · `rviz2` · `robot_state_publisher` 등이
그대로 살아남아 도메인에 계속 붙어 있다. 다음 기동 때 조용히 간섭한다.

정리 후에는 반드시 확인한다:

```bash
ros2 node list --no-daemon      # 시뮬레이터 브리지만 남아야 한다
```

### 10.6 `OnProcessExit` 는 실패 종료에도 발동한다

`readiness_gate` 가 타임아웃(exit 1)해도 그냥 엮으면 `move_group` 이 올라온다.
`_chain_or_shutdown` 으로 종료 코드를 보게 되어 있다 —
[panda_functionbay.launch.py](../../src/robot_control/launch/panda_functionbay.launch.py)
의 `startup_handler`. 구조를 바꿀 때 이 부분을 유지한다.
