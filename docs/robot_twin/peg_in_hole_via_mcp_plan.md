## 1. 지금 있는 것

### 1.1 세 계층

```
자연어 프롬프트
      ↓
MCP 서버        /home/kwlee/development/mdtpy/robot-twin-client/src/robot_twin_client/mcp_server.py
      ↓ REST
로봇 트윈        src/robot_twin/          (rdfp_ws)
      ↓ ROS
제어 스택        robot_control            (rdfp_ws)
```

MCP 서버는 **별도 저장소**(`mdtpy/robot-twin-client`)에 있고 트윈의 `/variables` ·
`/operations` 카탈로그를 읽어 도구 목록을 자동 생성한다. 설계서:
[mcp_server_design.md](mcp_server_design.md) (구현 완료 v1).

### 1.2 트윈이 이미 주는 것

| 상태 변수 | 내용 |
|---|---|
| `scene_objects` | 물체별 `{position, orientation, dimensions}` — **peg 이 여기 있다** |
| `ee_pose` | 손끝 pose (펑션베이는 `grasp_center` 기준) |
| `gripper_state` | `at_goal` · `stalled` · `width` |
| `joint_states` · `session_state` · `named_targets` | |

| 연산 | 내용 |
|---|---|
| `move_linear` | pose 로 직선 이동 (**기본이 `grasp_center` 기준** — 2단계에서 `frame` 입력 추가) |
| `move_gripper_to_target` | `open` / `close` / `grasp` |
| `move_to_named_target` | `ready` 등 |
| `move_to_joints` · `reset_scene` · 세션 4종 | (`reset_scene` 은 펑션베이 미제공) |

### 1.3 MCP 서버가 이미 주는 것

- 트윈 연산을 도구로 자동 노출 + `read_state` / `read_states` / `list_state_variables`
- `move_linear_verified` · `move_to_named_target_verified` — **완료 ≠ 도달**을 보정
- `begin_task` / `end_task` — 세션·에피소드 묶기
- `pick_n_place.py` 에 `pick` · `place` · `above_of` · `grasp_pose_of` · `to_arm_command`

> **`to_arm_command()` 가 이미 프레임 변환을 한다.** ~~펑션베이의 149 mm 오프셋에 맞는지
> 2단계에서 확인해야 한다.~~ → **확인했다: 맞지 않는다.** 그 함수는 손끝(TCP)에서
> `panda_link8` 로 되돌리는 **mock 전용** 보정(10.3 cm + 45°)이다. 펑션베이 경로는
> 트윈의 `frame` 입력이 대신하며, 두 보정을 합치는 것은 **5단계**의 일이다.

### 1.4 중력 보상은 그냥 따라온다

트윈이 `create_move_group_client(backend='functionbay')` 로 클라이언트를 만들면 팩토리가
프로파일에서 보상기를 채운다. **트윈·MCP 쪽 코드 변경이 필요 없다.**

## 2. 메워야 할 틈 넷

### 2.1 펑션베이용 트윈 설정이 없다 → **1단계**

`src/robot_twin/config/` 에 `robot_twin_panda01.yaml`(mock)과
`robot_twin_panda_isaac.yaml` 뿐이다. 펑션베이용이 없다.

**주의할 것**

- `moveit.backend: functionbay` 한 줄이면 명령 채널 넷이 프로파일에서 채워진다
- **`check_action_server` 는 꺼야 한다** — 트윈은 컨트롤러보다 먼저 뜰 수 있다
- **`reset_scene` 을 넣으면 안 된다** — 펑션베이는 `/scene/reset` 을 제공하지 않아
  매번 실패한다 (CLAUDE.md 에 명시)
- 세션 연산은 `rdfp` 가 설치돼 있어야 동작한다

### 2.2 프레임이 어긋난다 → **2단계**

**`ee_pose` 는 `grasp_center`, `move_linear` 의 pose 는 `panda_link8` 기준이고 둘은
149 mm 떨어져 있다.** `ee_pose` 를 읽어 그대로 `move_linear` 에 넣으면 그만큼 어긋난다.

지금 `fb_move_peg.py` 는 `FG.Approach.tip_pose_for()` 가 변환한다. 트윈 경로에는 그
변환이 없다.

**선택지**

| 안 | 내용 | 평가 |
|---|---|---|
| **A** | `move_linear` 에 `frame: grasp_center \| panda_link8` 입력 추가 | 근본적. 트윈이 변환을 갖는다 |
| B | 클라이언트(`to_arm_command`)가 변환 | 이미 구조가 있다. 다만 **오프셋을 클라이언트가 알아야** 한다 |
| C | 그대로 두고 프롬프트로 경고 | ❌ — 조용히 149 mm 틀린다 |

**A 를 권한다.** 오프셋은 백엔드 성질이라 트윈이 아는 편이 맞고, MCP 도구 설명에도
그대로 실린다. → **A 로 구현했다** (2단계 참조). 이름의 정본은 백엔드 프로파일의
`frames` 블록이며 launch 와 트윈이 같은 값을 읽는다.

### 2.3 고정물 정보가 트윈에 없다 → **3단계**

`peg_hole` · `peg_tray` 의 입구·바닥 높이·안지름은 `/scene/objects` 가 아니라
`config/functionbay_fixtures.json` 에 있다. **`/scene/objects` 에 안 싣는 것은 의도**다 —
그 채널은 조작 대상 전용이고 `SceneObject` 에 고정물을 구분할 필드가 없다.

**선택지**

| 안 | 내용 | 평가 |
|---|---|---|
| **A** | 정적 상태 변수 `fixtures` 추가 (파일에서 읽어 카탈로그에 실음) | 에이전트가 목적지 이름을 알 수 있다 |
| B | 클라이언트가 파일을 직접 읽음 | 트윈이 원격일 때 깨진다 |

**A 를 권한다.** *"다른 hole 로"* 를 해석하려면 **에이전트가 고정물 목록을 볼 수 있어야**
한다. 지금은 `scene_objects` 에 `peg` 하나뿐이라 "다른 hole" 이 무엇인지 알 길이 없다.

### 2.4 peg-in-hole 고유 지식이 어디에도 없다 → **4·6단계**

`fb_move_peg.py` 가 들고 있는 것들이다. 연산 하나로 표현되지 않고 **절차와 판정**이다.

**작업 중 드러난 것 셋**

1. **`frame_id` 는 죽은 입력이었다.** 세 트윈 YAML 의 `move_linear` 이 전부 선언하고
   있는데 **읽는 코드가 없다.** 주면 조용히 무시된다 — 새 `frame` 옆에 두면 정확히
   이 단계에서 고치는 부류의 함정이라 지웠다.

2. **⚠️ mock·Isaac 에는 이 문제가 없다 — 그리고 켰다면 더 나빠졌다.**
   `panda_link8 → panda_hand` 는 **평행이동 0, z 축 −45° 회전**이다
   (`panda_links.urdf.xacro` 의 `panda_hand_joint`). 위치가 같으니 149 mm 류의 어긋남이
   없고, 그 45° 는 **MCP 클라이언트의 `to_arm_command()` 가 이미 곱한다.** 프로파일에
   `ee: panda_hand` 를 적었더니 트윈이 한 번 더 돌려 **90° 이중 회전**이 되는 구성이
   나와 되돌렸다 — mock 계열 프로파일의 `frames` 는 `tip` 만 갖는다.
   → **2.2 의 "`to_arm_command()` 가 펑션베이에서 맞는지 확인" 에 대한 답**: 그 함수는
   45° 와 10.3 cm 를 **손끝(TCP) 기준**으로 되돌리는 mock 전용 보정이라 펑션베이에는
   그대로 쓸 수 없다. 펑션베이 경로는 트윈의 `frame` 이 대신한다. **그 보정을
   클라이언트에서 트윈으로 옮기는 것은 5단계의 일이다** — 옮길 때 mock 계열 프로파일에
   `ee: panda_hand` 를 넣고 `to_arm_command()` 의 45° 를 뺀다.

**드러난 것 넷**

1. **⚠️ 고정 정착 대기는 틀린 도구다.** 3 초를 줬더니 하강 뒤 tcp 오차를 **7.55 mm** 로

   그 잘못 읽은 값으로 다음 목표를 만드니 정렬이 어긋났다. 고쳤다 —
   `ops.wait_until_still()` 이 `ee_pose` 가 **멈출 때까지** 기다리고, 못 멈추면
   `None` 을 준다(움직이는 중의 값을 도달로 넘기지 않는다). `settle_sec` 은 이제
   **상한**이다.

2. **도달하지 못한 이동을 그냥 넘기고 있었다.** `move_linear_verified` 의 `reached` 를
   `_go` 가 안 봤다. 이제 본다 — 다만 **접촉이 예상되는 하강 구간만 끈다**(거기서는 못
   간 것 자체가 정보이고 앉음 확인이 뒤에서 판정한다).

3. **기울기를 파지 직후와 정렬 후에도 본다.** 전에는 시작할 때 한 번뿐이었는데, 기운 것은
   **그리퍼 안에서** 생긴다. 내려가기 전에 막는다.

4. **⛔ 회복 시도가 상황을 악화시켰다 — 기록해 둔다.**
   peg 이 28° 기운 채 물려 있어 빈 탁자에 대고 눌러 세우려 했더니 **27° → 43° 로 더
   기울었다**(패드 안에서 계속 미끄러진다). 접촉을 푼 뒤 놓았더니 **z 가 −3615 m 까지
   날아갔다.** 그 전까지 이 사고는 *"구멍에 끼인 채 놓으면"* 으로 기록돼 있었는데,
   **빈 탁자 위에서도 기울어 있으면 같은 일이 난다** — 조건은 '구멍 안'이 아니라
   **'안정적으로 앉아 있지 않음'** 이다. 판정이 서지 않으면 **쥔 채로 두고 사람에게 묻는다.**

**2회차 (재시작 후) — 같은 실패를 재현하고 원인을 찾았다**

정착 수정은 효과가 없었다. 정렬은 오히려 좋았는데(peg 중심 오차 **0.18 mm**, 기울기
**0.74°**) 하강에서 똑같이 막혔고, tcp 는 목표에 **도달**했다(0.08194 vs 0.0820) —
**팔이 아니라 peg 이 못 들어간 것**이다.

**원인 ① 트레이에는 입구 모따기가 없다.** 메시 실측(peg 반경 8.0 mm):

| 입구 z | 구멍 최소 반경 | 트레이 최소 반경 |
|---|---|---|
| **+0.0250** | **9.473 mm** (여유 **1.47 mm**) | **8.498 mm** (여유 **0.50 mm**) |
| +0.0240 이하 | 8.498 mm | 8.498 mm |

구멍은 입구가 벌어져 있어 오차를 흡수하지만 트레이는 날카로운 모서리다. **그래서
구멍 방향은 되고 트레이 방향만 막힌다** — `fb_move_peg.py` 가 어느 방향에서 성공했는지
다시 볼 이유가 여기 있다.

**원인 ② 절차가 peg 의 *중심*을 겨냥했다.** 구멍에 들어가는 것은 **바닥 끝**이고,
50 mm peg 이 **0.74°** 만 기울어도 바닥은 중심에서 **0.32 mm** 벗어난다 — 트레이 여유
0.50 mm 의 **64 %** 다. 중심 오차 0.18 mm 와 합치면 한계에 정확히 닿는다.

**고친 것**
- `bottom_of()` / `axis_of()` — 정렬을 **바닥 끝** 기준으로 한다
- `entry_clearance()` — **모따기를 계산에 넣지 않는다**(트레이에 없으므로 보수적인 쪽)
- 하강 전에 **바닥 오차 ≥ 여유**면 거부한다 (기하 확인·앉음 확인에 이은 세 번째 방어선)

**회복 시도에서 또 배운 것** 기운 peg 은 **바로 세울 수 없다.** 빈 탁자에 눌러도
(27°→43°), 구멍 모따기를 깔때기로 써도(28°→35°) 더 기울기만 했다 — **접촉이 없어도**
이동마다 약 2° 씩 패드 안에서 미끄러진다. 기울면 그 시도는 포기하는 것이 맞다.

**3회차 — 진짜 원인은 스트리밍 주기였다. 구멍은 성공했다.**

동작하는 `fb_move_peg.py` 와 트윈 경로를 끝까지 대조해 남은 차이 하나를 찾았다:

| | `fb_move_peg.py` | 트윈 `move_linear` (수정 전) |
|---|---|---|
| 스트리밍 | `publish_rate=50.0` (**보간**) | 지정 안 함 → **10 Hz 계단** |

MoveIt 의 데카르트 궤적은 TOTG 로 **10 Hz 재샘플**되고 JGPC 경로에는 보간할 컨트롤러가
없다. 68 mm 하강이 **0.68 mm 짜리 계단 100개**로 나가는데, 여유 0.5 mm 짜리 입구에서는
그 계단 하나가 peg 을 튕겨낸다 — **매번 15 mm 밀려 올라간 것**이 그 증거다.

`arm_command.publish_rate: 50.0` 을 프로파일에 넣고 팩토리·JGPC 클라이언트·트윈
`client_kwargs()` 로 배선했다. 결과:

| 시행 | 하강 오차 | 밀림 | 삽입 오차 | 판정 |
|---|---|---|---|---|
| 구멍 → 구멍 (모따기 있음) | **+0.21 mm** | **−0.21 mm** | **(−0.15, +0.05, −0.00) mm** | ✅ |
| 구멍 → 트레이 (모따기 없음) | +8.02 mm | +14.90 mm | — | ❌ |

**두 시행의 정렬 품질은 같았다** (바닥 오차 0.31 vs 0.40 mm). 갈린 것은 **모따기**다 —
구멍은 1.47 mm 를 삼키고 트레이는 0.50 mm 뿐이다. 가설이 실측으로 확정됐다.

**덤으로 잡은 것 — 파지 판정이 동전던지기였다.** `move_gripper_to_target grasp` 가
성공한 파지를 `TIMEOUT` 으로 보고했다. 파지를 유지한 채 8초·365 표본을 받아 보니
`|velocity|` 가 **0.00017~0.00205 rad/s** 로 흔들려 임계 **0.001 을 46 % 확률로
넘나들었고**, 그동안 `|effort|` 는 2.29~2.47 N·m 로 안정이었다. 임계가 지터 대역
한가운데 있었던 것이다. `functionbay_gripper_recurdyn.json` 의 `stall_velocity` 를
**0.01** 로 올렸다 — 지터 최대의 5배 위, 실제 개폐 속도(≈0.36 rad/s)의 36배 아래다.
속도 조건을 끄지 않은 것은 그것이 토크와 서로 검증하는 두 번째 신호이기 때문이다.
⚠️ 이 값은 **그리퍼 노드가 기동 시점에만 읽는다** — 파일만 고치고 노드를 안 띄우면
안 바뀐다 (`param set` 도 안 먹는다).

**트레이를 위해 더한 것** 정렬을 **되먹임**으로 바꿨다. 옆으로 100 mm 옮기면 peg 이
그리퍼 안에서 조금 돌아앉아, 옮기기 전에 잰 오프셋으로 만든 목표가 0.4 mm 빗나간다.
이제 매 회 **peg 이 멎기를 기다린 뒤**(`wait_until_peg_still` — 팔이 섰다고 peg 이 선
것이 아니다) 바닥을 다시 재고 남은 오차만큼 목표를 옮긴다. **여유의 40 % 안**에
들어와야 내려간다(0.50 mm → 0.20 mm). 줄지 않으면 멈춘다 — 흔들수록 나빠진다.

**4회차 — 정렬을 0.18 mm 까지 좁혔는데도 트레이는 같은 자리에서 막힌다**

정렬 되먹임은 의도대로 동작했다(0.35 → **0.18 mm**, 여유 0.50 mm 의 36 %). 그런데
결과는 **바뀌지 않았다** — 하강 오차 +8.09 mm, 밀림 +14.79 mm, peg 중심 0.0510.
**네 번 모두 소수점 둘째 자리까지 같다.** 정렬 문제가 아니다.

| 가설 | 확인 방법 | 결과 |
|---|---|---|
| 정렬 오차 | 되먹임으로 0.18 mm 까지 | ❌ 그래도 실패 |

**중요한 발견 — 물리 접촉면은 OBJ 메시가 아니다.**
RecurDyn 이 쓰는 것은 `ConstantModel/geosurfs/*.xml` 이고 **훨씬 거칠다**:
peg 은 **12각 기둥**(꼭짓점 반경 8.000 mm), 구멍·트레이 보어는 z 층이 **5~6개**뿐인
다각 기둥이다. 그래서 **OBJ 로 잰 치수는 물리와 다를 수 있다** —
`functionbay_fixtures.json` 의 근거를 볼 때 기억해야 한다. (다만 이번 실패의 원인은
아니었다: 통과 여유가 트레이 쪽이 더 넓다.)

**5회차 — 사용자가 눈으로 잡아낸 것: 수정이 트윈 경로에는 안 걸려 있었다**

*"fb_move_peg 때는 부드러웠는데 지금은 뚝뚝 끊긴다"* 는 관찰에서 찾았다.
`publish_rate` 기본값을 **동기 경로(`stream_trajectory`)에만** 넣었는데, 스트리밍
진입점이 **넷이고 그중 셋이 비동기**였다. 트윈의 `move_linear` 는 `follow_trajectory_async`
→ `stream_async` 라 **기본값을 건너뛰었다.**

**`/health` 로는 알 수 없었다** — 거기 보이는 50.0 은 *설정값*이다. 실제 주기는
`/input/panda_joint` 를 세어야 안다. 실측:

| | 명령 간격 | 실효 주기 |
|---|---|---|
| 수정 전 | **1250 ms** | **1.0 Hz** (68 mm 하강이 8.5 mm 짜리 점프 8번) |
| 수정 후 | **20 ms** | **50 Hz** |

"10 Hz 계단"이라고 적었던 앞선 추정도 틀렸다 — 실제로는 **1 Hz** 였다. 속도 배율
0.08 이 궤적을 늘려 TOTG 점 간격이 1.25 초가 된 것이고, `publish_rate=None` 이면
그 점 시각을 그대로 따른다.

네 진입점을 `_rate()` 하나로 모으고 **소스를 검사하는 회귀 시험**을 붙였다
(`test_publish_rate_default.py`) — 새 진입점이 기본값을 건너뛰면 거기서 걸린다.
시험이 허수가 아닌 것은 한 곳을 일부러 되돌려 검출되는 것으로 확인했다.

⚠️ **교훈**: 이 결함은 시험도 `/health` 도 못 잡았다. **사람이 움직임을 보고 알려
줘서** 찾았다. 개루프 스트리밍에서는 "설정했다"와 "실제로 그렇게 나간다" 사이가
멀다 — 명령 토픽을 세는 계측을 도구로 남긴다.

**그리퍼도 같은 부류였다 — 계단으로 나가고 있었다.**
*"개폐를 조금 느리게 할 수 있나"* 라는 요청에서 드러났다. 시뮬레이터의 그리퍼 서보는
**계단 지령을 자기 최대 속도로** 쫓으므로, 천천히 물리려면 **지령 자체**를 나눠 보내야
한다. `fb_gripper.set_span` 은 `ramp_sec=2.0` 으로 그렇게 했는데 노드는 목표를 한 번에
던지고 있었다. 프로파일에 `command_ramp_sec: 2.0` 을 넣고 노드가
`command_ramp_rate`(50 Hz)로 보간하게 했다 — 실측 **지령 102건 / 2.0초**,
값이 41.54° → 0.00° 로 이어진다. 기본은 **0(계단)** 이라 다른 스택은 그대로다.
⚠️ 램프를 켜면 **`sync_timeout_sec` 도 늘려야 한다**(5 → 12초) — 안 늘리면 성공한
동작이 `TIMEOUT` 으로 보고된다.

**6회차 — 두 수정이 모두 실제로 걸린 뒤, 왕복 4/4 양방향 성공**

| 회차 | 방향 | 정렬(바닥 오차) | 하강 오차 | 밀림 | 삽입 오차 |
|:-:|---|---|---|---|---|
| 1 | 구멍 → 트레이 | 0.14 mm | +0.19 mm | −0.20 mm | **(+0.08, +0.07, −0.00)** |
| 2 | 트레이 → 구멍 | 0.11 mm | +0.15 mm | −0.17 mm | **(+0.09, −0.05, −0.00)** |
| 3 | 구멍 → 트레이 | 0.12 mm | +0.16 mm | −0.18 mm | **(+0.11, +0.33, −0.00)** |
| 4 | 트레이 → 구멍 | 0.11 mm | +0.15 mm | −0.17 mm | **(−0.14, −0.16, −0.00)** |

**정렬이 한 번에 0.11~0.14 mm 로 선다** — 전에는 되먹임을 두 번 돌려도 0.18 mm 였다.
지령이 20 ms 간격으로 이어지니 peg 이 그리퍼 안에서 덜 흔들린다. **밀림이 전부 음수**인
것도 같은 이유다: 튕겨 올라가는 대신 그대로 들어간다.

**결국 원인은 하나였다 — 지령이 계단으로 나갔다.** 팔은 1 Hz(1250 ms 간격), 그리퍼는
계단 한 번. 둘 다 기준 구현(`fb_move_peg.py` / `fb_gripper.set_span`)은 보간하고 있었고
트윈 경로만 안 하고 있었다. 앞서 의심했던 것들(정렬 오차, 모따기, 파지력, 팔의 횡방향
흐름)은 **전부 아니었다** — 모따기 차이는 실재하지만 그것은 *왜 구멍만 먼저 성공했는가*
를 설명할 뿐이고, 원인이 아니라 **증상의 차등**이었다.

⚠️ **두 결함 모두 시험으로도 `/health` 로도 안 잡혔다.** 사람이 움직임을 보고
*"예전엔 부드러웠는데 지금은 뚝뚝 끊긴다"*, *"개폐를 좀 느리게 할 수 있나"* 라고
말해 준 것이 단서였다. 개루프 스트리밍에서는 **"설정했다"와 "실제로 그렇게 나간다"
사이가 멀다** — 명령 토픽을 세는 계측을 습관으로 삼는다.

**함정 하나 더 — 시뮬레이터를 *프로세스째* 재시작하면 ROS 스택도 다시 띄워야 한다.**
앱 내 재시작(차트 재생)은 시계가 이어지지만 프로세스 재시작은 **0 으로 되감긴다.**
그러면 살아남은 노드의 TF 버퍼가 더 큰 타임스탬프를 들고 있어 새 데이터가
`TF_OLD_DATA` 로 버려지고, 증상은 **"팔이 명령을 받고도 안 움직인다"** 였다
(`move_linear` 이 37.78 mm 를 못 갔다). `./scripts/kill_stack.sh --ros` 뒤 재기동으로
복구된다.

| 도구 | 자연어 지시 | 비고 |

봐야 한다.** `fixtures` 변수를 직접 읽게 하면 peg 이 어느 자리에 있는지는 스스로
발자국 계산을 해야 하고, 그 산수는 틀려도 조용하다. 도구가 대신 풀어 `destinations` 로
준다.

**설명에 수치를 적지 않았다** — 44 mm(손끝) · 0.028(입구) · −54 mm(파지 간격) ·

조용하다. 설명이 말하는 것은 **언제 무엇을 부르고 실패를 어떻게 읽는가** 다.
시험이 그 경계를 지킨다 (`test_descriptions_carry_no_magic_numbers`).

**실패 문장을 갈랐다** — `PegInHoleError.holding` 이 **다음 판단을 가른다.** 쥔 채로
멈췄으면 *"재시도하지 말고, 열지도 말고, 사람에게 알려라"* 로, 움직이기 전에 멈췄으면
*"로봇 상태는 안전하다"* 로 말한다. 놓아도 되는 상황과 놓으면 물체를 잃는 상황이
겉보기로 같아서, 말해 주지 않으면 에이전트가 `move_gripper_to_target open` 을 부른다.

### 6단계 — MCP 프롬프트

**하는 일** — 2.4 의 지식 중 **에이전트가 판단에 써야 하는 것**을 프롬프트로 기술한다.

프롬프트에 들어갈 것:

| 내용 | 왜 |
|---|---|
| 작업 전 **`fixtures` 와 `scene_objects` 를 읽는다** | "다른 hole" 을 해석하려면 필요 |
| **완료 ≠ 도달** — 이동 뒤 `ee_pose` 로 확인 | 스트리밍이 open loop |
| **놓기 전 앉음 확인** — 안 앉았으면 놓지 말 것 | 놓으면 **물체가 씬을 이탈하고 복구 불가** |
| 물체를 쥘 때는 `grasp`, `close` 아님 | `close` 는 힘을 안 준다 |
| 실패 시 **재시도 대신 다시 잡기** | 밀려 올라간 파지는 반복해도 안 들어간다 |
| 펑션베이는 `reset_scene` 이 없다 | 물체를 잃으면 사람이 재시작해야 한다 |

**코드로 굳힐 것과 프롬프트로 알릴 것의 경계**

- **코드** — 수치(44 mm · 0.028 · −54 mm · 0.5 mm)와 절차. 에이전트가 틀릴 여지를 없앤다
- **프롬프트** — *언제 무엇을 읽고, 실패를 어떻게 읽고, 무엇을 하면 안 되는가*

> 수치를 프롬프트에 적으면 **에이전트가 산수를 하게 되고 조용히 틀린다.** 반대로 절차
> 판단을 코드에 숨기면 에이전트가 상황에 맞게 못 고른다.

**완료 기준** — 충족 (2026-09-11)

| 기준 | 결과 |
|---|---|
| 프롬프트가 클라이언트에 도달 | ✅ `prompts/list` · `prompts/get` 을 **메모리 트랜스포트 왕복**으로 확인 |
| 수치가 없다 | ✅ 시험이 강제 (`test_prompt_carries_no_magic_numbers`) |
| 물체를 잃는 두 경로를 막는다 | ✅ *직접 열지 말 것* + *재시도 말 것* 이 본문에 있고 시험이 지킨다 |
| 자연어 지시 수행 | 7단계에서 실증 |

**단위 시험으로는 부족했다** — `_PROMPTS` 를 채워도 `prompts/list` 핸들러를 등록하지
않으면 클라이언트에는 아무것도 안 보인다. 그것이 정확히 *"설정했는데 안 먹는다"* 이고,
이번 작업에서 `publish_rate` 로 두 번 겪은 부류다. 그래서 프롬프트 시험은 **프로토콜
위에서** 돈다.

**프롬프트에 넣지 않은 것** — 손끝 오프셋 · 입구 높이 · 정상 파지 간격 · 반경 여유.
전부 코드가 갖는다. 대신 넣은 것은 **판단**이다: 무엇을 먼저 읽는가, 어느 도구를
부르는가, 실패를 어떻게 읽는가, 무엇을 하면 안 되는가.

**가장 중요한 한 줄**은 *"`move_gripper_to_target open` 을 직접 부르지 않는다"* 이다.
그 도구는 목록에 그대로 보이고(다른 작업에는 필요하다) 부르면 성공하는데, 앉지 않은
peg 을 놓는 순간 물체를 잃는다 — **도구 이름을 대어 막는다.**
